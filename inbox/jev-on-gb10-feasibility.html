01 · 結論

三句話

Jev 本身放不進 GB10，它是閉源的雲端 API。但 Jev 的做法可以：讓已經部署好的 Gemma 4 26B 不生成文字、只回答「選項機率」，這在開源社群一週內就被複製了六次以上，效果最好的只落後 Jev 約一分。

能做的是「答案是固定選項」的題目：alarm 分級、工單分流、要不要派工、要不要升級。確定不行的是要寫字的題目：根因分析、報告、派工單內容，這些仍然要走 LLM 生成。

不用重新部署模型、不用新硬體。我們需要的是兩週和幾百筆真實資料，把「反應速度」和「信心分數可不可信」量出來。

02 · 名詞

Jev 是什麼，一句話

Jev 是 TypeSafe AI（前 OpenAI 研究員創立）在 2026 年 9 月 15 日發表的模型。它不生成文字：你給它一段狀態（一封信、一則 alarm、一張工單）和幾個「有固定選項的問題」，它一次回傳每個選項的機率。因為答案只能是你事先給的選項，所以它不可能輸出格式以外的東西；官方把這稱為「不會幻覺」。

題型問法回傳產線例子
Choice選擇這是哪一類？每個類別的機率這則 alarm 是機構／電控／物料／程式？
Score評分嚴重到哪一級？各等級的機率不急／盡快／停線
Noul是非是或不是？P(是)要不要派工給設備工程師？

它是一個「會讀懂上下文的 if 判斷式」，不是一個會講話的助理。

它賣的三件事：快（不生成文字，一次算完）、便宜（輸出免費）、校準（說 90% 的時候大約 90% 是對的）。前兩件是介面設計自然帶來的，任何開源模型只要照同樣方式讀機率就有；第三件是它未公開的訓練方法，也是唯一還沒被證明能複製的部分。

04 · 依據

為什麼「像 Jev」在 GB10 上可行

Jev 發表後，社群在兩天內做出了六個以上的開源版本。最成熟的一個叫 SemIf，做法就是拿一個凍結的開源模型，把問題和選項放進 prompt，然後不讓它生成文字，直接讀每個選項的機率。在獨立的 JevBench 上，它排名第二，得分 73.1，Jev 是 74.4。另一個叫 Nimble 的版本用 Qwen 9B 微調，在保留資料上和標準答案的一致率是 90.1%，Jev 是 93.2%。已經有人在 Gemma 4 上做同一件事：E4B 版本在一張 3090 上每題約 33 毫秒，26B 版本約 48 毫秒，而且同一個模型還能繼續當 LLM 用。

介面和速度一週內就被複製了。Jev 剩下的價值是校準品質，而校準可以用自己的資料補。

這對我們的意義是：Jev 的核心賣點不需要買。「不會輸出格式以外的東西」和「快」都是做法帶來的，我們現有的 Gemma 4 26B 照做就有。Jev 真正沒公開的是它怎麼訓練出可信的信心分數，但對工廠場景來說，用幾百筆真實 alarm 和工單做校準，很可能比它的通用校準更貼近我們的資料。

也要講清楚 Jev 沒有那麼神：在 TypeSafe 自己的 benchmark 上準確率約 68%，只接近中階 LLM；第三方實測它在某個情緒分類資料集上，有 16% 的樣本給了正確答案零機率。它是一個好工具，不是一個新物種。

05 · 實驗

這個實驗能回答什麼，不能回答什麼

實驗分三段：先盤點現有的 26B 服務能不能直接共用；再用合成的產線資料（alarm、SPC、工單，中文夾機台代碼，十種題目各 200 筆以上）量速度和準確率；最後用真實資料做校準，定出每一種題目的分流門檻。

能回答

Q1GB10 上 26B 做一次判斷要幾毫秒，跟「讓 LLM 輸出 JSON」比快幾倍。

Q2十種產線題目裡，哪些零樣本就夠、哪些改題目寫法就夠、哪些校準也救不回來。

Q3同一份狀態問多個問題的實際成本，決定 playbook 一次問幾題。

Q4有人在跑長篇生成時，判斷的延遲會被拖慢多少，決定要不要獨立一個小模型專做判斷。

Q5中文與英文 alarm 的表現落差。

Q6每一種題目的信心門檻應該設多少，以及設了之後有多少比例會交給人。

不能回答

真實產線資料的表現。合成資料能量出速度和方法是否成立，但最終準確率要用真實資料重跑一次。

長期漂移。機台換型、新 alarm code 出現後會不會退化，需要上線後持續監控。

Jev 本身的校準有多好。我們沒有 API 存取，所有 Jev 數字都是第三方公開的。

要不要微調。實驗會告訴我們哪些題目需要，但微調本身是下一階段。

一個必須先盤點的前提

「不重新部署」的前提是現有推論服務能回傳每個 token 的機率（logprobs）。llama.cpp 和 vLLM 都可以；某些包裝過的服務不行。實驗第一天就會確認，若不行，備案是另起一個共用同一份模型檔的服務，或放一個 5 GB 的小模型專做判斷。GB10 有 128 GB 記憶體，兩者都放得下。

06 · 對照

跟規則、統計、傳統 ML、LLM 差在哪

產線上這類「看到一筆資料、決定一件事」的題目，我們已經用四種方式做過。Jev 式方法不是第五種新物種，而是把 LLM 的理解力裝回分類器的殼裡。差別看這張表。

那 machine learning 的題目，不用 learning 了嗎

還是要，只是 learning 搬了位置。傳統 ML 的 learning 發生在每一個題目：每換一種分類，就要收幾千筆標註、重訓一個模型。Jev 式方法把 learning 拆成三段：語言理解在預訓練時就學完了（Gemma 4 已經會讀中文 alarm）；校準用幾百筆真實標註學門檻，這是輕量但不可省的 learning；真的不夠時才做微調，那又回到傳統 ML 的成本。

標註需求從「每題幾千筆」降到「每題幾百筆」，是下降一到兩個數量級，不是歸零。

另一件要講清楚的：傳統 ML 在數值資料上沒有被取代。感測器時序的異常偵測、CT 分布的漂移、SPC 管制圖，這些是數字進、數字出，用 Jev 式方法去讀一串數字是用錯工具。Jev 式方法接手的是原本要「把文字轉成特徵再訓練分類器」的那一段：alarm 原文、工單描述、操作員的備註。

在產線上各自做什麼

規則與統計 · 留著

CT、UPH、SPC 本來就是公式，門檻本來就該寫在程式裡。Jev 式方法不取代 SPC，它讀的是「SPC 已經判定連續七點下降」這句話，然後決定要抽檢還是停線。

傳統 ML · 留著

數值型的異常偵測與預測維護。這些有穩定的訓練資料，也不需要讀懂文字。

Jev 式 · 新接手

文字進、選項出的判斷：alarm 分類與分級、工單分流、要不要派工、要不要升級、自動流程每一步的閘門。一天幾百到幾千次，每次幾十毫秒，帶信心分數。

LLM 生成 · 留著，但少用

寫 RCA、寫報告、規劃查線步驟、處理意外。由 Jev 式判斷「信心不足」時觸發，而不是每筆資料都問一次。

所以真正的變化不是「不用學了」，而是分工變了：數字歸統計與傳統 ML，文字判斷歸 Jev 式方法，寫字與推理歸 LLM，門檻與流程歸程式碼。這個實驗要量的，就是中間那一格在 GB10 上能不能站得住。
