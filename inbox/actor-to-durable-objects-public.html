1973 → 2026 · 一部分散式系統史

演員登台:
從 Actor 模型到
Durable Objects 的五十年

一個 1973 年的學術構想,如何在電話交換機裡熬過三十年,最後變成你 wrangler.jsonc 裡的三行設定。

幕數 · 五幕一謝幕 閱讀時間 · 約 20 分鐘
序幕 · PROLOGUE

兩個請求,同一個計數器

先從一個你八成寫過的 bug 開始。

你做了一個服務,每個使用者每天有 600 秒的免費額度。程式很直覺:讀出今日用量,加上這次的秒數,寫回去。

// 看起來人畜無害
const used = await db.get(`usage:${user}`);
if (used + seconds > QUOTA) return reject();
await db.put(`usage:${user}`, used + seconds);

然後某天,同一個使用者在手機和平板上同時開了兩個 session。兩個請求同時讀到 used = 590,各自判斷「還有 10 秒,放行」,各自寫回。你的 600 秒上限,就這樣被兩個誠實的請求聯手繞過了。

這叫 race condition。五十年來,工程師發明了鎖、交易、樂觀併發、CAS 指令來對付它——每一種都有效,每一種都讓程式碼更難寫、更難讀、更難證明是對的。

但在 1973 年,有一個人提出了完全不同的解法:與其學會安全地共享,不如從一開始就不要共享。

第一幕 · 1973

Hewitt 的三條公理

MIT 的 Carl Hewitt 當時在做人工智慧研究。他問的不是「怎麼寫並行程式」,而是一個更根本的問題:運算的最小單位,到底應該是什麼?

當時檯面上有兩個答案:函式(λ 演算)和物件(Simula)。Hewitt 給了第三個:actor——一個只會「收到訊息、做出反應」的東西。名字取得很白話:它就像舞台上的演員,收到台詞(cue),然後演出。

一個 actor 收到一則訊息時,只被允許做三件事:

公理 一 送訊息 送出有限則訊息,給它「認識位址」的其他 actor。不認識就送不到。
公理 二 生小孩 建立有限個新的 actor。系統的規模是長出來的,不是配置出來的。
公理 三 決定下一步 指定「下一則訊息要用什麼行為處理」。這就是它改變狀態的唯一方式。

第三條是整個模型的靈魂,也最容易被略過。Actor 沒有「變數」——所謂改變狀態,是換一個行為去面對下一則訊息。狀態被定義成「未來的行為」,而不是「現在記憶體裡的值」。

三條紀律

  • 不共享記憶體。要溝通,只能送訊息。沒有東西被共享,就沒有東西需要上鎖。
  • 一個 mailbox,一次一則。訊息排隊進來,逐則處理。actor 內部永遠是循序的——你在裡面寫程式,可以完全當作單執行緒在寫。
  • 位置透明。對方在同一顆 CPU 或地球另一端,寫法一樣。這讓「分散」變成部署細節,而不是程式碼的形狀。
白話翻譯

傳統併發的所有痛苦——死結、race condition、heisenbug——都來自同一個前提:「兩個人可以同時碰同一塊記憶體」。Actor 模型不是更聰明地管理這個前提,而是把前提整個砍掉。併發存在於 actor 之間,不存在於 actor 裡面。序幕那個配額 bug,在這個世界裡寫不出來:同一個使用者的兩個請求,會排進同一個 mailbox,一個接一個。

代價當然有:所有跨 actor 的操作都變成非同步訊息。你再也不能假設「呼叫完就做完了」。1973 年的硬體跑不動這個模型,學界看完點點頭,然後它沉寂了十三年。

第二幕 · 1986 – 2011

電話交換機裡的三十年

讓 actor 復活的不是學術界,是電話公司。

1986 · 瑞典 Erlang——為了不能斷線的東西而生 Ericsson 要造電話交換機:幾十萬通電話同時進行、彼此完全獨立、一通掛掉不能影響其他任何一通、而且系統永遠不能停機維護。這根本就是 actor 模型的規格書。Joe Armstrong 團隊造出 Erlang,每通電話一個 process(就是 actor),輕量到可以同時跑百萬個。
1998 · AXD301 九個 9 的傳說 Erlang 寫的 AXD301 交換機,締造了廣為流傳的 99.9999999% 可用度——一年停機時間以毫秒計。Erlang 還加了原始論文沒有的兩樣東西:「let it crash」(不寫防禦性錯誤處理,出事就讓 process 死)和 supervision tree(上層監看下層,死了就重啟)。錯誤處理從行內的 try-catch,升格成架構的一層。
2009 · JVM Akka——主流世界的第一次接觸 Akka 把 actor 帶進 Java/Scala 生態,也暴露了主流開發者的不適應:mailbox 預設無界(沒有 back-pressure,塞爆就 OOM)、訊息沒有型別安全、除錯要追分散式因果而不是看 stack trace。更根本的:原始 actor 模型沒有「持久化」這個概念——actor 死了,狀態就沒了。Akka 後來得補一整套 Persistence(event sourcing)來救。
2011 · Microsoft Research Orleans 與 virtual actor——關鍵的一步 Orleans(後來撐起 Halo 的後端)提出 virtual actor:actor「永遠存在」(概念上),你不必建立它、不必銷毀它。拿名字去呼叫,runtime 負責在某台機器上把它啟動;閒置就自動休眠,狀態寫回儲存。古典 actor 最麻煩的營運問題——誰建立、放哪台、死了誰重建、位址怎麼發現——全部變成 runtime 的事。

記住 virtual actor 這個概念。九年後,它會換一個名字重新登場。

幕間:這個模型的天生代價

在進入下半場之前,先把醜話說完。以下四條不是任何實作的瑕疵,是 actor 模型本身的稅,用 Erlang、Akka、Orleans 的人都在繳:

  • 跨 actor 的交易做不到。兩顆 actor 之間沒有 ACID。要轉帳?只能 saga,自己補償。
  • 跨 actor 的查詢做不到。「所有使用者裡誰超額了?」——你得一顆一顆問(fan-out),或另外維護一份索引。
  • 單顆是瓶頸。一次一則訊息的另一面,就是單顆有吞吐上限。熱點只能靠切分成更多顆。
  • 除錯變成因果追蹤。沒有跨 actor 的 stack trace,只有訊息的先後。

第三幕 · 2017 – 2020

邊緣運算的狀態難題

2017 年,Cloudflare 推出 Workers,主導設計的是 Kenton Varda——寫過 Google 的 Protocol Buffers v2、做過 Cap'n Proto、還做過 Sandstorm.io(一個「每個使用者的每個 app 都是獨立沙箱實例」的個人伺服器平台,現在回頭看,根本是 DO 的世界觀預告)。

Workers 的口號是「你的程式碼不跑在 us-west-4,它跑在每個地方」。V8 isolate 比容器輕三個數量級,冷啟動以毫秒計,程式碼被推到全球三百多個節點。

然後所有人撞上同一面牆:運算去了邊緣,狀態沒有。

你的 Worker 在東京執行,資料庫在維吉尼亞。每次讀寫都是一趟 150ms 的太平洋來回——邊緣運算省下的延遲,全數還給了資料庫。更糟的是,三百個節點上的無狀態 isolate 同時讀寫同一個資料庫,序幕那個 race condition 被放大了三百倍。

傳統解法是把資料複製到程式旁邊(快取、read replica),然後你就得面對快取失效與一致性——電腦科學公認的兩大難題之一。Kenton 的答案反過來:

傳統雲端儲存天生就慢:它得跨網路存取,還得同步許多客戶端。那如果反過來,把你的程式碼放進儲存層的深處呢? — Kenton Varda,改寫自〈Zero-latency SQLite storage〉開場

不是把資料搬到程式旁邊,是把程式搬到資料旁邊。資料不複製、只有一份,由一個「有名字的東西」獨佔;所有想動這份資料的人,把請求送去給它。

聽起來很熟?這就是 actor。更精確地說——這就是 Orleans 的 virtual actor,只是這次它跑在全球網路上,而且有了新名字。

2020-09 · BETA Durable Objects 登場 發表文的副標把主張講完了:一致、低延遲、分散式,卻又免維護——而且讓 client 之間能夠「協調」。示範程式是一個幾十行的聊天室:一個房間一顆 DO,WebSocket 全部掛上去,廣播就是一個 for 迴圈。在無狀態 serverless 的世界,這件事之前根本做不到。

名字取壞了

多年後 Kenton 自己承認,「Durable Objects」這名字讓它聽起來比實際複雜。他的說法大意是:改名叫 Stateful Worker 大概能解決九成的誤解——它就是一個有狀態的 Worker;因為有狀態,所以必須有名字,這樣你才能路由到握著那份狀態的那一顆。

一句話版本:DO = virtual actor + 內建資料庫 + 全球路由,包裝成一個 JavaScript class。

第四幕 · 2021 – 2026

補完 actor 模型的六年

接下來的每一次演進,幾乎都在回應第二幕結尾列的那些「天生代價」,或是前人(Erlang、Akka、Orleans)踩過的坑。

2021-08 Input/Output Gates——〈Easy, Fast, Correct — Choose three〉 整個系列技術含量最高的一篇。問題:就算單執行緒,await 儲存操作的空檔,別的事件還是可能插進來,race condition 借屍還魂。解法:儲存操作進行中,其他事件一律擋在門外(input gate);寫入尚未確認落盤前,對外回應先不放行(output gate)。結果是你可以放心寫「讀、改、寫」,不加任何鎖——而且因為寫入可以背景進行,程式反而更快。「更安全」與「更快」通常互斥,這篇解釋為什麼在這裡不是。
2022-09 workerd 開源 跑 Workers 與 DO 的 runtime 以 Apache 2.0 釋出。平台鎖定的疑慮至少有了退路:同一套程式,理論上可以搬回自己的機器跑。
2024-04 JavaScript-native RPC——刻意背離古典 actor 古典 actor 堅持單向非同步訊息;Kenton 選了 RPC,而且是帶著他 Cap'n Proto 的看家本領 promise pipelining 來的:對尚未回來的結果繼續鏈式呼叫,多次往返合併成一趟。他的判斷很務實——非同步訊息在理論上乾淨,在工程上讓人寫不出東西。保留 actor 的隔離性,丟掉它的訊息語意。
2024-09 每顆 DO 一個 SQLite——「程式碼住進儲存層」兌現 SQL 查詢是同步 API——因為資料庫就在同一台機器的記憶體裡,沒有網路可等。持久化機制受 Litestream 啟發:WAL 持續串流到物件儲存(每 16MB 或每 10 秒一批),因此有 30 天的 point-in-time recovery;為了保住那 10 秒空窗,每次提交同時送往鄰近五個資料中心,三個確認才算數。Akka 當年要另外補一套 Persistence 才有的東西,這裡是內建的。他舉的例子:訂位系統,一個航班一顆 DO 配一個 SQLite——每家航空公司每天開出幾千個全新的資料庫,而你不覺得有什麼。
2025 WebSocket Hibernation 與計費現實 DO 的計費比 Workers 多一個維度:duration——物件醒著的每一秒都在計時,而且一律按 128MB 記憶體計價。長連線若直接 accept() 掛著,連線多久就付多久;Hibernation API 讓連線保持、物件休眠,事件來了再醒。官方定價頁的對照範例:同樣一百顆 DO,不休眠的寫法月費約 $419,休眠的寫法約 $21。這是 virtual actor「去啟動」機制第一次直接反映在帳單上。
2026 Dynamic Workers + Facets:AI 時代的一人一 app 三月:Dynamic Workers,讓 AI 生成的程式碼跑在毫秒級啟動的 isolate 裡,比容器沙箱快百倍。四月:DO Facets,讓每個動態生成的 app 各自帶獨立的 SQLite。八月,Kenton 的 Gadgets 演講把論點說白:個人 AI codegen 會打爆傳統雲端架構——當每個使用者的 app 都不一樣,你不可能 per-tenant 佈建容器和資料庫;但一台機器可以跑幾千個 isolate + 幾千顆 DO。1973 年「運算的最小單位是什麼」這個問題,在 AI 生成程式碼的時代,又被問了一次。
第五幕 · 實戰

回到那個配額計數器

序幕的 bug,在 DO 的世界長這樣:

// Worker:用名字路由——同一個 email 永遠到同一顆
const stub = env.QUOTA.getByName(`user:${email}`);
const ok = await stub.tryConsume(seconds);

// DO 內部:單執行緒 + input gate,插隊在物理上不存在
async tryConsume(seconds) {
  const used = this.sql.exec(
    "SELECT used FROM quota WHERE day = ?", today()
  ).one()?.used ?? 0;
  if (used + seconds > QUOTA) return false;
  this.sql.exec("UPDATE quota SET used = used + ?", seconds);
  return true;
}

手機和平板同時打進來?兩個請求排進同一顆物件的隊伍,一個接一個。第一個把 590 變成 600,第二個讀到 600,被拒絕。沒有鎖、沒有交易、沒有 retry loop——不是因為你處理得好,是因為問題不存在。

什麼題目適合它

判斷句只有一條:需要有人在中間主持秩序,才用 DO。展開來:

題目為什麼是 DO
即時房間聊天室、協作編輯、直播字幕。一個房間一顆,WebSocket 全掛上去,廣播是 for 迴圈。記得用 Hibernation。
計數與配額rate limit、庫存、抽號、每日額度。read-modify-write 的天堂。
每人一份的狀態使用者的同步端點、購物車、AI agent 的工作階段。Cloudflare 的 Agents SDK 整個蓋在 DO 上。
每個實體的排程Alarm API:每顆物件自己排未來的工作,等於「一人一個 cron」,不需要中央排程器。

什麼題目不適合它

第二幕結尾那些「天生代價」,一條都沒有消失:

  • 純儲存 → R2 / KV。倉庫不需要腦。
  • 跨使用者查詢、報表 → 傳統資料庫。「這個月誰超額了?」在一萬顆 DO 上是災難:要嘛 fan-out 叫醒一萬顆(付一萬次錢),要嘛自己維護一份索引。順帶一提,D1 本質上就是「Cloudflare 幫你做好的一顆 DO」——所以它有單庫 10GB 的上限。
  • 一次性 batch 工作 → Worker + Queues。沒有狀態要顧,就不要租一個會醒著的行程。
  • 全域單例當總管 → 反模式。所有流量塞進一顆單執行緒物件排隊,而且那顆物件固定在某一個地區。設計原則是圍繞你的「協調原子」切分:一個房間、一個使用者、一個航班——而不是一個系統。
帳單的形狀

最後一個心態校正:Workers 和 R2 是「用多少算多少、閒置零成本」;DO 是「你租的是一個會醒著的行程」,成本模型比較接近 VPS。它便宜的前提是物件大部分時間在睡覺——這正是 virtual actor 的原始設計意圖。讓它睡,是工程,也是財務。
