像不像，
不是是不是

EmbeddingGemma 2 拿來做決策，到底是哪一種 Jev？拿 1,690 組受控擾動去量，答案是：它是一把相似度尺。尺能回答「這段話像哪一類」，回答不了「這句話是不是真的」。這份檢定書寫下那條線畫在哪裡，以及尺、NLI、Gemma 4 三個引擎該怎麼分工。

項目 01 · 為什麼要量這一把

jevlike 問「讀機率能判什麼」，這份問「比向量能判什麼」

jevlike 已經走了十九輪：讀 Gemma 4 選項字母的第一個 token 機率當決策 API，十類產線判斷題七類零標註 ≥ 98%。Google 的 MediaPipe Decision Maker 把同一種「typed decision」包成 API，底下列了三種引擎：bi-encoder（EmbeddingGemma）、cross-encoder（Laya、GLiNER）、生成模型單次 prefill 讀 logit（Gemma 4）。jevlike 做的是第三種。

第一種便宜到不像話：選項向量算好存著，之後每次決策只算一個查詢向量，幾毫秒。jevlike v13 試過它當十類選擇器，平均 0.637，被判定只能當粗篩。但那是十個細類。這份檢定換一題問：如果題目只有四個粗類、而且問的是「狀態有沒有變」，這把尺到底能量到什麼？

一個 bi-encoder 能回答的唯一一種問題是：這段輸入跟那段描述有多接近。所有 Choice、Boolean、Score，最後都是這一件事。

項目 02 · 第一次量：當 diff 用

翻轉一個詞移動的距離，比改一個錯字還小

最直覺的用法是 vector diff：舊版段落算一個向量、新版算一個，比距離。距離大就是改了很多。第一輪 770 組資料跑完，各類擾動的平均距離如下。

擾動狀態變了？cosine 距離
改 2–3 個錯字、調標點否0.029
整段同義改述否0.029
句子重排否0.019
「沒有阻礙」→「有阻礙」（改一個詞）是0.005
「領先」→「落後」（改一個詞）是0.012
交付日改到超過截止日是0.009

狀態真的變了的三種擾動，距離全部落在「改錯字」之下。 第二輪用更嚴的配對對照重量，狀態翻轉一個詞的距離只有 22–24% 超過良性改動的 p95；錯字和改述反而 100% 超過。這把尺量的是「改了多少字」，不是「意思變了沒」。

不合格 EG2 當 vector diff，在這題上收掉；不調維度、不調前綴、不調 pooling。

項目 03 · 第二次量：投影到標籤

把距離換成方向，翻轉就看得見了

同一把尺，換個用法：不比新舊兩版的距離，而是各自投影到四個狀態描述（如期、延後、卡關、取消）上，看投影的分布有沒有移動。這才是 Decision Maker 實際做的事。第二輪 1,690 組的結果，翻轉一個詞的 AUROC 從 0.58 跳到 0.99。

但這個分數有一個現成的質疑：標籤描述寫了「阻礙」「落後」，擾動也改成「阻礙」「落後」，量到的會不會只是同一個詞出現在兩邊？所以第二輪準備了三組標籤：刻意與擾動詞重疊的、刻意不重疊的、以及語言對調的——中文段落配英文標籤、英文段落配中文標籤。如果投影量的是詞彙，跨語言那組應該垮掉。

配對（同底稿、同樣改一個詞）標籤同語同詞標籤同語異詞標籤跨語言
否定翻轉 vs 良性改一詞0.9940.9970.999
反義替換 vs 良性改一詞0.9990.9991.000

沒垮。三組差不到 0.01，中英分開看也一樣。投影量到的是語意，不是詞彙重疊。這是整份檢定裡最重要的一個正面結果：它救回了 EG2 在這題上的位置。

合格 EG2 當標籤投影，在四個粗類、狀態翻轉這題上成立；標籤可以只寫一套英文。

項目 04 · 同一張表，三個引擎

它贏在哪裡、輸在哪裡、慢多少

第二輪加了 jevlike 的 E2B 與 E4B 進來，用它既有的四選一題型，只看新版段落、不給舊版。下表是同底稿專屬負例的配對 AUROC；「單邊」表示不需要舊版。

三件事從表裡看出來。

類別題，尺和大模型打平。否定、反義、新增這三種，EG2 投影和 E4B 的差都在平手線 0.05 之內。四個粗類、互斥、題目是「這段話像哪一類」，bi-encoder 的舒適區就是這裡。

值的題，只有規則和 E4B 能做。「預計交付 2027-01-30，截止 2026-11-28」要算日期才知道超期。EG2 投影 0.32（比亂猜還低，因為它把日期數字的距離當訊號）、NLI 0.51、E2B 0.69。E4B 0.94，regex 1.0。這格把 jevlike 的階梯又切開一級：類別題 E2B 就夠，讀值推理要 E4B。

瀰散型，尺反而比 NLI 強。三段各改一點、沒有任何一句單獨構成狀態改變，EG2 投影每段單獨觸發率是 0%，三段加總後 AUROC 0.93–0.97；NLI 單邊只有 0.55。這格是探索性的（政策寫死、沒獨立判讀），但方向值得記：向量可以加，矛盾判斷不能加。

項目 05 · 三種呼叫長什麼樣

差別不在模型大小，在 text 和選項有沒有見過面

同一個題目——「這段文字的專案狀態是 A 如期／B 延後／C 卡關／D 取消」——100 筆資料，三種引擎各自怎麼呼叫。先看圖，再看 pseudo code。

1 · LLM call：生成文字

# 每筆一個 prompt，text 與題目同框，然後把答案「寫」出來
for text in texts_100:
    prompt = f"{text}\n請判斷專案狀態，回答 JSON：{{\"status\": \"A|B|C|D\"}}"
    out    = llm.generate(prompt)      # prefill + 逐 token decode
    status = parse_json(out)           # 可能多話、可能不照格式、沒有信心值

2 · jevlike call：讀第一個 token 的機率，不生成

# 每筆一個 prompt，text 與選項同框，但只做一次 forward、讀四格 logit
for text in texts_100:
    prompt = f"{text}\n請判斷專案狀態：\nA. 如期  B. 延後  C. 卡關  D. 取消\n答案："
    logits = llm.prefill(prompt)                       # 不 decode
    p      = softmax([logits[tok("A")], logits[tok("B")],
                      logits[tok("C")], logits[tok("D")]])
    status, conf = argmax(p), calibrate(p)             # 有信心值
# 多一題 = 再 100 次 prefill；prefix cache 只省題目模板那段

3 · EG2 call：沒有 prompt，比對在模型外面

# ── prewarm：標籤各自 encode 一次，永久留用 ──
labels = ["專案如期進行…", "專案延後…", "專案卡關…", "專案已取消…"]
L = eg2.encode(labels, prefix="task: classification | query: ")   # 4 × 768
L = whiten_and_normalize(L)

# ── 每批：text 各自 encode，不知道標籤存在、不知道其他 99 筆存在 ──
X = eg2.encode(texts_100, prefix="title: none | text: ")           # 100 × 768

S = X @ L.T                        # 100 × 4 的 cosine，一次矩陣乘法，模型不參與
P = softmax(S / 0.045)             # 溫度校準
status = argmax(P, axis=1)
# 多一題 = L 多一列；encode 不重跑
text 與選項同一個 context？輸出多一題的代價
LLM是，attention 互看文字，要 parse100 × (prefill + decode)
jevlike是，attention 互看4 個機率100 × prefill
EG2否，各自變向量，只剩 cosine4 個機率0（L 多一列）

jevlike 和 LLM 的差別在輸出端：不 decode、直接讀 logit，所以快、穩、有信心值，但模型看到的東西一樣，能推理的程度一樣。EG2 和前兩者的差別在輸入端：text 和標籤從來沒見過面。這是它快 30 到 67 倍、多一題零成本的原因，也是它只能答「像不像」的原因。「日期超期了但文字還寫領先」這種題，jevlike 的 attention 可以把「2027-01-30」和「截止 2026-11-28」對起來看；EG2 的 x 裡那兩個日期已經被壓成 768 個數字的一部分，L 裡的「延後」描述根本沒有日期可以對。

Google 的 Decision Maker 就是把第二張圖和第三張圖包在同一個 evaluate() 後面：prewarm() 對 EG2 後端是算 L，對 Gemma 4 後端是算 KV cache 前綴；evaluate() 對 EG2 是 X @ Lᵀ，對 Gemma 4 是一次 prefill 讀 logit。API 一樣，底下看不看得到選項不一樣——這也是它的 pitfalls 要分後端寫的原因。

項目 06 · 裁決

所以它是 Jev，又不是

是 Jev。TypeSafe 的 Jev API 本來就有兩種引擎，Jev-Gemma 讀生成模型的 logit、Jev-Embed 算 bi-encoder 內積；Google 自己的 Decision Maker 把 EmbeddingGemma 列為後端一號。EG2 投影回答的題型（Choice、Boolean、Score）、輸出的形狀（校準過的機率分布）、用法（選項 prewarm 之後每次一個 forward），跟 jevlike 完全是同一件事。這份檢定證明了：在四個粗類、狀態翻轉這種題上，它的準確度跟 Gemma 4 讀 logit 打平，速度快 30 到 67 倍。

又不是。jevlike 讀 logit 的時候，模型已經把題目和選項一起讀過，可以推理；EG2 的段落和標籤是分開編碼的，決策只剩下 cosine 距離。所以它只能回答「像不像」，回答不了「是不是」。三條邊界，三個實驗各自量到一條：

  • 否定要靠標籤軸救。純距離看不見「沒有阻礙→有阻礙」（本檢定項目 02）；投影到「卡關」這個方向才看得見（項目 03）。jevlike v19 量到的是同一件事的另一面：連 26B 零樣本遇到否定形問法都讀不準。否定在這整條線上都是硬傷，差別只在 EG2 有一個便宜的繞法。
  • 值完全看不見。日期、數量、料號，尺量不出大小關係。這類交給規則，規則做不到的交給 E4B（項目 04）。
  • 類別要粗、要互斥。四類狀態 0.99，jevlike v13 的十類產線判斷 0.637，v14 的 100 份 SOP 路由 top-1 0.527。類別一細、一近，相似度尺就分不開。這不矛盾，是同一把尺的兩端。

尺是用來量的，不是用來判的。量得準的地方，它比任何判斷器都便宜；要判的地方，它從來就不該站在那裡。

項目 07 · 階梯多一格

第 0 格，與分工規則

jevlike v3 定的階梯是 E2B → E4B → 26B，四類題 E2B 就夠、六類 26B 真的強。這份檢定在底下補一格，並且把「哪題給哪格」的規則從猜測變成量過的：

  1. 第 0 格
    EG2 投影 — 粗類、互斥、問「像哪一類」。狀態四類、意圖路由、主題分流。241 ms，可預算。也是瀰散型訊號的加總器。
  2. 第 1 格
    規則 — 日期、數量、閾值比較。regex 或欄位讀取，不用模型。這一格在項目 04 是 1.000，而且是零成本。
  3. 第 2 格
    E4B — 需要把值和文字一起推理的題（「日期超期了但文字還寫領先」），以及第 0 格沒把握的段落。16 s（CPU）；E2B 在這題沒有位置，類別題尺就夠、推理題它又不夠。
  4. 第 3 格
    26B — jevlike 已量過的六類強題：alarm 分類、根因、SPC。本檢定沒碰。

在這批資料上的管線長這樣：第 0 格篩，第 1 格抽值，第 2 格只讀篩出來的。Google 文件說 bi-encoder 遇到「除非」「例外」要把題拆成原子布林題、邏輯放回程式碼——那正是第 0 格加第 1 格的分工，這份檢定只是把它量出數字。

項目 08 · 本檢定不保證的事

合成骨架內成立，骨架外待驗

這張證書上的每一個數字前面都該加「在合成骨架內」。實作者自己的資料覆核列了這些：

  • 五個骨架、六個主題，狀態片語共用；30 個「不同底稿」實際上不是 30 個獨立的自然語言樣本。模板指紋沒排除，沒有第二個生成器可以對照。
  • 日期超期那格，改了日期但保留「進度領先」的文字，等於給模型互相矛盾的證據；E4B 的 0.94 不能單獨代表日期推理能力。
  • 所有正例都往「風險增加」走。沒有「本來就卡關、這版沒變」、也沒有「風險解除」的配對，所以「單邊不需要舊版」只在類別題上成立，不能推到一般的漂移偵測。
  • 瀰散型的 ground truth 是寫死的三信號政策，沒給模型、沒獨立判讀。
  • 日期只有 ISO 格式；T4 位移 1 天、T5 位移 10 天沒反平衡，EG2 在那格的分數可能受數字 token 距離影響。
  • CPU 成本表是下限，不是產品數字。

下一階段要的是真文件：真 git history、真的狀態變化點、人標的 ground truth，在那上面重調門檻、量精確率、數瀰散型佔多少。這份檢定能帶過去的，是「哪種題給哪個引擎」的分工，不是任何一個 AUROC。
