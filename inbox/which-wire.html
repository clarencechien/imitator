架構筆記 · 配線紀錄 · 2026-09-22

先問你連的
是什麼線

一篇「怎麼送一百萬則通知」的面試文，被連續追問六輪之後，露出三個問題：非同步架構到底在選什麼、那一百萬是不是假的，2026 年的架構師該站在迴圈的哪裡，以及你用 AI 的方式，其實也是在選一條線。

起點：一篇 Medium 面試文 · 六輪追問 · 一個結論

00 · 申請單

這份紀錄是怎麼來的

原文的設定很標準：Black Friday 午夜，行銷要同時推播一百萬則通知。作者是十幾年經驗的架構師，答案也是標準的：queue、獨立的 worker fleet、依 queue 深度自動擴縮、provider 限流、冪等、批次、重試加 DLQ、非同步的送達追蹤。每個名詞都對。

問題是，把這份答案逐項拆開，會發現名詞之間互相打架：一邊說瓶頸在 FCM 的配額，一邊說 queue 深了就開一千個 worker；冪等的寫法是先 INSERT 再送，結果把「可能重送」換成了「可能漏送」；批次 API 引用的是 2024 年就下架的介面。它答對了每一個名詞，卻沒有回答任何一個真正需要判斷的問題。

這篇不是要檢討那位作者，那是一篇為了流量寫的面試文，文類本來就如此。這篇要做的是把那六輪追問整理成三張表單：01 非同步架構在選什麼、02 一百萬則是不是假議題、03 當 LLM 可以自己跑完整個迴圈，架構師還剩什麼。

01 · 配線

「非同步」不是一種架構，是三條線

討論 async 架構時，最常見的錯誤是把它當成一種東西，然後問「要不要用 queue」。實際上大家口中的非同步，至少是三條性質完全不同的線。差別不在產品，在訊息沒有人接的時候，它去了哪裡。

A · 佇列線：訊息會停在中間、被記帳、被補送

這條線又分兩種。Work queue（RabbitMQ、SQS、Postgres 的 SKIP LOCKED）：一則給一個人，做完銷帳，之後就沒了。Log（Kafka、Redis Streams、RabbitMQ Streams）：訊息留著，被讀過也不刪，每個讀者自己記 offset，所以可以重讀、可以有多個讀者各走各的進度。兩者都是佇列線，但「讀過之後還在不在」是根本差異，多數人把 Kafka 當 SQS 用的時候，就是沒分清這一點。

B · 廣播線：送達即丟

MQTT 的 QoS 0、NATS core、Redis pub/sub、WebSocket 的 broadcast。broker 只負責把訊息路由給「現在在線」的訂閱者，沒人在線就沒了。它便宜、快、能養百萬條連線，代價是可靠性由連線層決定：MQTT 要做到 at-least-once，得把 QoS 1、持久 session、固定 client id、manual ack、payload 帶 UUID 全部補上，缺一項都會在某種故障下掉訊息。補上之後，它其實就變成了一條每個 client 各有一個小佇列的佇列線。

C · 回撥線：先掛號，對方做完再來敲門

Webhook、provider callback、long-poll。中間沒有 broker，可靠性完全靠雙方的重試協議：對方要重送幾次、你要能冪等地接。最常被忽略的一條是排程線：cron 加 batch，最陽春的非同步。很多「一百萬」的問題，其實是「排程分時跑」就解掉的問題，只是它太不性感，沒人在面試裡提。

選線的時候，先回答這七格

兩端是誰
裝置對服務（很多、很弱、網路很爛）選 MQTT 這類面向裝置的協定；服務對服務選佇列或 log。Kafka 不是設計給大量不穩定 client 直連的。
沒人接時
訊息要留 → 佇列線；不留也沒關係 → 廣播線。這是第一個、也是最重要的分岔。
讀過之後
還要重讀（新服務補讀上週資料、邏輯寫錯要重算）→ log；讀完就算數 → work queue。
讀者幾個
一個下游 → work queue 就夠；多個而且各自進度 → log；多個但只要當下 → 廣播。只有一個下游卻上 Kafka，通常是殺雞用牛刀。
誰負責重試
中間人負責 → 佇列線；發送端負責 → 回撥線。回撥線的接收端一定要冪等。
時間窗
秒 → 連線加廣播；分鐘 → 佇列加限速；小時 → 排程。時間窗拉寬一級，架構就便宜一級。
送還是握
如果難的是「同時握住一百萬條連線」，那是連線層的問題（gateway 分片、心跳、重連風暴），跟 queue 無關。這格答錯，後面全部白做。

回答完這七格，再去看產品。多數時候答案會比想像中陽春：一台跑 Mosquitto 的機器、一張 Postgres 表、一個 cron。每多加一層 broker，就多一個半夜會叫你起床的東西，而且那個東西的授權條款可能明年就變了。

先問訊息沒人接時去哪裡，再問要不要留、要不要重讀。產品名稱是最後一格。

02 · 核對

一百萬則，是不是假議題

把七格拿回去對照原題，第一個發現是：題目沒有給任何一格的答案。內容是一樣的還是逐人個人化？時間窗是一秒還是一小時？掉一則和重一則哪個比較糟？沒有這些，畫出來的每個方框都是猜的。

題目沒問的四件事

內容一樣還是逐人？如果一百萬則內容相同或只分幾種，用 FCM 的 topic 或 segment，一個 API call 解決，fan-out 交給 Google。整篇文章的 queue、worker、批次，只有在真正逐人個人化時才需要。這一格沒問，等於架構的一半是多餘的。

時間窗多寬？「午夜同時」是行銷的想像。Braze、OneSignal 這些平台的預設做法就是分時送：在 N 小時內平均送完、依使用者時區、依個人最常開 app 的時段。分散送出不只保護 provider，更保護你自己，因為一百萬人半夜同時收到通知，其中幾個百分比會點開，deep link 直接打到你的 API、登入、商品頁。真正會打掛平台的不是推播，是推播之後的回擊尖峰。而文章對這一點隻字未提。

瓶頸在哪？不在你的機器上。FCM 和 APNs 的配額花錢買不到更多，所以「用雲就是大力出奇蹟」不成立，雲省的是維運工作量，不是架構判斷。既然瓶頸在 provider，「queue 深了就開一千個 worker」就是自相矛盾：多開 worker 只會換來更多 429。正確的做法是一個全域的 token bucket 控制總速率，worker 數量剛好吃滿配額就好。

掉一則和重一則哪個糟？對外部 side effect 做不到 exactly-once，只能二選一。行銷推播其實適合 at-most-once：漏一則沒人在意，重複兩則會被客訴。原文的冪等寫法是先 INSERT 成功再送，INSERT 之後、送出之前 crash，重試時看到「已處理」就跳過，這則永遠不會送出。它把「可能重送」換成「可能漏送」，卻講得像解決了問題。這種錯誤不懂的人讀起來完全合理，只有做過的人才看得出來。

大多數的一百萬，都是把時間窗拉寬之後就消失的一百萬。

真的需要「同時」的場景是存在的，共通點是資訊價值隨秒數衰減，或先收到的人有優勢：限量搶購、開賣倒數、比賽比分、拍賣出價。但即使是這些，「同時」也是指一兩分鐘內，不是同一毫秒。而如果換成自建 WebSocket 或封閉網路裡的裝置，題目又會整個變質：難的不再是送一百萬則，而是握住一百萬條連線，還有部署重啟時一百萬個 client 同時重連的風暴。那是第七格的問題，文章完全沒碰到。

沒搞清楚題目之前，是假架構師嗎

這句話聽起來嚴厲，但如果把它當成定義而不是罵人，它其實很準確。架構師這個工作，在畫第一個方框之前就開始了。判準不是會不會畫 queue，是有沒有先問「這一百萬從哪裡來、要在多久內到、掉一則的代價是什麼」。拿著標準答案找題目，就是假架構師的操作型定義，不管年資幾年。

面試題的設計本身就是陷阱

系統設計面試的格式逼你在四十五分鐘內畫出方框，所以它獎勵的是「馬上端出標準架構」。真實工作恰好相反：前兩週都在把題目問清楚，方框往往是最後才畫、而且畫得比面試時少一半。一個在面試裡表現很好的答題框架，拿到真實專案裡，第一件事就是被拆掉。

一百萬則是假議題。真議題是時間窗、fan-out 由誰做、以及 at-most 還是 at-least。三題都答不出來的架構，是答對了沒人問的題。

03 · 迴圈

2026：從 in the loop 到 on the loop

回到這份紀錄的起點。一篇十幾年經驗架構師的文章，被一個要價一兩百美元的 LLM 追問六輪之後，拆得比原文完整得多。這是不是代表不需要架構師了？先看這六輪是怎麼發生的。

每一輪的方向都是人給的：「用雲是不是花錢就好？」「一百萬同時送是真需求嗎，為什麼不分時？」「MQTT 不能用最陽春的吧？」「RabbitMQ 會不會隨便被打爆？」這四個問句本身就是架構判斷：質疑前提、拉回真實場景、追問邊界。LLM 負責的是在每個問句下把廣度和細節展開。如果一開始只問「幫我設計一個送一百萬則通知的系統」，LLM 交出來的，大概就是那篇文章的整齊版。

LLM 也有明顯的錯過。EMQX 從 5.9 起改成 BSL 授權、免費叢集被拿掉，這件事如果沒有搜尋，它很可能照舊把 EMQX 當 OSS 首選推薦，而且講得很有信心。要知道哪裡該驗證，得先有底子。接回 02 那個冪等的漏送錯誤也一樣：LLM 看得出來，但只有懂的人才確認得了它真的錯。

兩個詞的定義

Human in the loop：每一步都要人簽字才能往下走。人是品質的來源，也是吞吐的瓶頸。對應到架構工作，就是人畫圖、AI 補細節、人逐行看。

Human on the loop：AI 在一組邊界之內把整個迴圈跑完，人不在每一步裡，而是在迴圈之上：設邊界、看指標、處理例外、事後審計、為結果負責。

2026 年的現況是，名詞層級的架構設計，從題目到方案到 PR 到壓測，coding agent 已經可以自己跑完一整段。這代表「在迴圈裡審每一行」的架構師會變成瓶頸，而不是價值。但 on the loop 不是「放手不管」。它的前提是你已經把判斷寫成了機器能檢查的邊界，否則你只是在迴圈外面，不是在迴圈上面。

三段路

一 · 在迴圈裡
先當審核者。把 LLM 的輸出當成一個聰明但可能胡說的資深同事的提案來審，目標是在一份看起來完整的答案裡找出那一個致命錯。這一段需要的底子比過去更厚，不是更薄，因為錯誤藏得更深、包裝得更好。
二 · 寫邊界
把審核時反覆抓到的東西，從「我的判斷」變成「可執行的規則」。不是寫設計圖，是寫不變量和禁止事項：行銷推播不得與 OTP 共用同一條 queue；任何持久 session 的 queue 必須有長度上限和 TTL；對外 side effect 必須在文件裡寫明選了 at-most 還是 at-least；引入任何 broker 之前，先用真實 payload 跑一輪 benchmark，並確認授權條款。這些是 AI 可以自己檢查、自己遵守的東西，像 ADR 加 lint。
三 · 站到迴圈上
讓 AI 從題目跑到方案、PR、壓測。人看的不再是每一行，而是三件事：題目有沒有被重新定義（那一百萬是不是假的）、邊界有沒有被觸碰、以及例外（授權變了、孵化專案停擺、客戶的資安政策不准連外）。抽查、不逐行；出事的時候，扛的人是你。

主要產出設計圖、技術選型文件題目的定義、邊界與判準、例外清單
時間花在畫方框、逐行審核問清楚題目、寫不變量、處理邊界外的事
被取代的方式LLM 秒答名詞層沒有底子，看不出答案哪裡錯
鑑別度來源知道多少名詞與套路能否質疑前提、挖出文件裡沒有的限制、為結果負責
面試怎麼考「設計一個通知系統」丟一份 LLM 產出的設計，請你找出哪裡會出事

真正的風險不在現在的架構師

判斷力來自踩坑：自己寫過會漏送的冪等邏輯、自己處理過一個週末堆滿的離線 queue。On the loop 的前提是曾經 in the loop。如果下一代一開始就把第一段整段跳過，就可能永遠停在「會問，但看不出答案哪裡錯」的階段，那時候站在迴圈上的人，其實什麼也看不見。

反過來說，像這六輪追問一樣把 LLM 當對手而不是神諭，學習速度可以比過去快得多。差別不在工具，在你站的位置。

架構師沒有消失，門檻搬了家：從「知道什麼」搬到「能不能把判斷寫成邊界、然後為邊界之外的事負責」。

終 · 留底

你連的是什麼線，你用的是什麼 AI

把 01 那七格拿回來，只換兩個詞：「訊息」換成「任務」，「接收端」換成「你」。三條線就變成三種用 AI 的方式，而且和前面一樣，差別不在產品，在輸出沒有人審的時候，它去了哪裡。

廣播線的用法：送達即丟

開一個聊天視窗，問，讀，關掉。這是最多人的用法，也是 QoS 0：你在線（真的在讀）才收得到，你不在線（掃過去、沒審）就沒了，下次同樣的問題從頭再來。它便宜、快，而且它是 human in the loop 最極端的形式，因為每一則都要你當場接，你就是那個吞吐瓶頸。接回 01 廣播線要變可靠，得補上持久 session 和 ack；聊天要變可靠，得補上留底和審核，補完之後它就不再是聊天了。

回撥線的用法：先掛號，它做完再來敲門

把任務丟給 agent，它跑完回來：一個 PR、一份報告、一個 cron 每天早上跑出來的日報。中間沒有 broker，可靠性完全靠你們之間的協議，而這個協議和 webhook 一模一樣：任務要冪等（重跑一次不會把事情弄壞），回來的東西要能審（你要看得出哪裡錯）。這是從 in the loop 走向 on the loop 的第一步，也是多數人卡住的地方，因為他們把發 email、動 production 這種 at-most-once 的任務，交給了一條會重試的線。

佇列線的用法：有記帳、有補送、有 log

任務進 queue，有人記帳（誰派的、邊界是什麼、做到哪），失敗會補送，而且留 log：ADR、git、逐字稿，半年後可以重放，回頭問「當時為什麼選這個」。這裡的 broker 就是 03 說的那組邊界，不變量和禁止事項。接回 03 沒有留底的 agent 用法只是 work queue，做完就沒了；有留底才是 log，才有「多個讀者各走各的進度」，也就是同一份判斷可以被下一個專案、下一個人、下一個 AI 重讀。這才是站在迴圈上。

02 那個假議題，換成 AI 也有一個一模一樣的版本：「讓 AI 一次把全部做完」。它和「午夜同時送一百萬則」是同一種幻覺，答案也一樣，真議題是時間窗多寬、fan-out 由誰做（哪些任務可以讓 AI 自己拆，哪些要你先切好）、以及掉一件和做錯一件哪個比較糟。寫程式是 at-least-once 加 review，可以重跑；發出去的信、動過的資料庫是 at-most-once，漏做比做錯便宜得多。分不清這兩種，就會把不准重試的任務丟進會重試的線裡。接回 02

對系統，問訊息沒人接時去哪裡；對 AI，問輸出沒人審時去哪裡；對自己，問你站在迴圈的哪裡。

三個問題是同一個問題。答案都不是產品名稱，不是模型名稱，也不是職稱，而是在畫第一個方框、下第一個 prompt 之前，你有沒有先把題目問清楚，然後才選線。

你用 AI 的方式，就是你替自己選的那條線。多數人在廣播線上，以為自己在佇列線上。

你搶的是什麼票

前面四張表單都在講「線」，這一篇拿一個大家都被折磨過的題目來實戰：搶票。演唱會、機票、高鐵、疫苗預約，表面上都是「很多人搶很少的東西」，但架構完全不同。差別在你搶的到底是什麼，而這件事要在畫任何方框之前先問清楚。接回 02

先問票是什麼：四個屬性

獨特性
對號座是一個一個不可替換的東西；自由入場的票是同質庫存，只有數量；疫苗預約搶的是「時段的容量」，也是同質的。獨特性決定分配層長什麼樣：一列一原子操作，還是一個計數器。
記名
要不要綁身份。記名代表分配前要先驗資格（一人限購、年齡、身分），資格檢查是可以提前做完、拿來分流的東西；不記名的票則只能靠等候室和 bot 防護。
時間窗
需求是壓縮在開賣後幾十秒，還是分散在幾個月。這一格決定要不要等候室，也是整個系統壓力的來源。機票的需求天生分散，演唱會把全部需求壓進同一分鐘。
能否超賣
有沒有商業規則可以吸收不一致。機票可以超賣、可以改搭下一班；演唱會的座位只有一個，也沒有下一場；疫苗的時段可以稍微超約，因為統計上有人爽約。能吸收的，強一致的範圍就可以放寬。
搶的是獨特性記名時間窗能否超賣強一致的那一列
演唱會對號座獨一無二常常不記名幾十秒不能一個座位一列的條件更新
演唱會自由入場同質不記名幾十秒不能一個計數器，要分桶
機票艙等內同質，座位可後選記名幾個月可以，且刻意某班某艙等的剩餘數
高鐵、台鐵座位 × 區間部分記名開賣日集中，其餘分散對號不能，站票可以座位在各區間的佔用圖
疫苗預約時段容量，同質強記名，有資格可由規則拉平可以少量時段的剩餘名額

漏斗：每一層是哪一條線

搶票系統的形狀是一個漏斗。每一層都對應 01 的一條線，而且只有一層需要強一致，範圍要縮到一列、一個原子操作。其他全部是非同步、最終一致，各有各的等待預算。

層做什麼是哪條線等待預算
分流等候室、分批、規則分流人的佇列線：排的是人，不是訊息幾分鐘到幾十分鐘，但要看得見
分配座位歸誰、名額歸誰不是線，是一個同步的原子操作一秒內
保留與付款hold 加 TTL，付款回來才 sold回撥線：金流 webhook十分鐘上下，逾時釋放
履約與通知開票、寄信、同步名單佇列線：outbox 加 relay幾分鐘，沒人在意
展示剩餘票數、座位圖廣播線：快取加推送幾秒的落後可接受

分流層是整個系統裡最重要的 queue，而且它在最前面。等候室把「一秒一百萬人」變成「一分鐘五千人」，後面每一層的壓力都跟著降一到兩個數量級。這正是 02 講的「把時間窗拉寬」，只是這次拉寬的是入場。分流的方式有三種：等候室（不記名時唯一的選項）、時間分批（分區、分場次開賣）、規則分流（記名時可以依身分證尾數、年齡、資格把人分到不同時段）。規則分流是最強的，因為它在開賣前就把尖峰削掉了。

分配層不能排隊，也不能最終一致。對號座用一列的條件更新：座位是 available 才改成 held，回傳一列就是搶到、零列就是被拿走，不需要分散式鎖，也不會超賣。同質庫存用計數器，但一個計數器就是一列熱點，所以要分桶：一萬張拆成二十桶，爭用被分成二十份。也可以把庫存先放進 Redis 當閘門，擋掉注定失敗的請求，但 DB 仍是真相，Redis 只是門口的人，要定期對帳。另一條路是單一 allocator：把一場活動的所有請求送進一條有序 queue，由一個寫者依序分配，沒有爭用、天然公平，代價是前端要接受「送出後等幾秒才知道」，也就是把分配層整個換成事件優先。

保留與付款層是最容易把系統拖垮的地方，原因很簡單：金流是整條鏈裡最慢、最不可靠的外部系統。它有自己的 TPS 上限，它是 provider 配額，和 02 的 FCM 一模一樣，花錢買不到瞬間。所以三件事：付款絕對不能在持鎖的交易裡發生，座位先 held、鎖放掉，再去付款；hold 的 TTL 決定了金流的尖峰形狀，TTL 越短，付款越集中；付款的結果是 webhook 回來的，是一條回撥線，要冪等地接。疫苗預約沒有金流，所以這一層簡化成「爽約釋放」，難度低一級，但公平的要求高一級。

履約與通知層才是 outbox 該在的地方。座位轉成 sold 的同一個交易裡寫進 outbox，relay 負責開票、寄確認信、同步名單到場館或政府系統。這些下游同樣有各自的配額，所以 relay 要限速，不是把一百萬則一口氣倒進去。

展示層永遠不要用真相來源來渲染。剩餘票數、座位圖是快取，用推送更新，落後幾秒完全可以接受。讓幾十萬人的重新整理直接打到分配層的那張表，是搶票系統當機最常見的原因之一。

使用者信任：在哪裡失敗，比失不失敗重要

搶票的信任不是「有沒有搶到」，是「在哪一層被告知沒搶到」。排隊時就知道沒希望，使用者可以接受；選好位、輸入完卡號、付款按下去才失敗，信任會一次歸零。所以失敗要盡量往前推：等候室要顯示號碼和預估時間，讓人可以決定要不要繼續等；hold 拿到才進付款頁，不要讓人填完資料才發現位子沒了；付款失敗要保留 hold 到 TTL 結束，讓人換張卡再試。

先到先得，還是抽籤

先到先得獎勵的是網路速度和 bot，公平性最差，但架構最簡單。抽籤是把「時間窗」換成「公平性」：開放幾天登記，再由系統分配，尖峰整個消失，代價是使用者要等結果，而且要接受抽不到。日本的演唱會普遍採抽選制，疫苗預約的意願登記加分批通知也是同一個思路。最好的搶票架構，往往是讓人不用搶。

各種票，各自的關鍵一格

演唱會對號座：等候室 → 座位圖（快取）→ 一列條件更新 → hold 十分鐘 → 付款 → sold 加 outbox。關鍵是分流和展示，分配層本身反而簡單。

演唱會自由入場：同上，但分配層換成分桶計數器或 Redis 閘門。關鍵是熱點，不是一致性。

機票：需求分散，同一班機的爭用本來就低，等候室通常不需要。難的地方在庫存模型：艙等是巢狀的，賣掉一張商務艙可能影響多個票價等級；價格會動，分配時要鎖定價格；核心庫存在航空公司的 PSS 裡，你的系統只是它的客戶，一樣是 provider 配額的問題。超賣是刻意的商業規則，把不一致吸收在商業層。強一致從 1960 年代的 SABRE 開始就存在，只是範圍只有「某班某艙等還剩幾個」。

高鐵、台鐵：對號座加上區間，同一個座位可以賣台北到台中和台中到左營，所以分配層檢查的不是一個布林值，而是這個座位在各區間的佔用圖，原子更新要驗證區間不重疊。開賣日的尖峰需要等候室，平日不需要。12306 早年的當機和後來的改造，方向和這裡一致：前面排隊控流量，中間用記憶體內的分配層，核心保持強一致。

疫苗預約：搶的其實不是時段，是資格加上時段。強記名讓規則分流變成可能：依身分證尾數、年齡、族群分批，尖峰在開放前就被削掉。分配層是每個時段一個容量計數器，可以少量超約，因為一定有人爽約。沒有金流，所以保留層只剩「爽約釋放」。最難的一格是公平與信任：這不是商業服務，搶不到的人不會覺得「下次再來」，而是覺得系統不公平。所以它的正確架構是意願登記加上分批通知，也就是抽籤那一型，把搶完全拿掉。

五種票走完，會發現同一件事重複出現：分配層都很小，而且都很像。真正把它們區分開的是前面的分流怎麼做、後面的金流和外部系統怎麼扛、以及使用者被拒絕的時候站在哪一層。這三件事，題目沒問清楚之前，一格都填不了。

搶票只有「歸誰」那一列要強一致。其餘全是選線：分流是人的佇列、付款是回撥、履約是 outbox、展示是廣播。而最好的分流，是讓人不用搶。
