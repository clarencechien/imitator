SHT 01 · 事故現場

Zeabur 的三年半，分三段讀

先把事實擺好。Zeabur 不是突然倒的，它在倒之前八個月就自己寫下了診斷書。

日期事件它說明了什麼
2026-02-23宣布共享叢集不再接新專案，定位改為「Your AI DevOps Engineer」自己承認：賣算力就是在跟 AWS、GCP、Hetzner 比價，而機器跑在它們之上，價格永遠不可能更低；共享叢集的按量計價低於成本，一直在補貼。
2026-08-27第一次資安事件部分帳號資訊與專案環境變數遭讀取，含第三方 API 金鑰與資料庫密碼。
2026-09-22關閉 AI Hub 並退款評估維運成本與資安風險後，決定不再恢復。
2026-10-14第二次入侵，範圍比第一次大攻擊者取得平台資料庫讀取權限；環境變數、帳號、API token、zSend 金鑰受影響，部分 GCP 專用伺服器也遭未授權存取。
2026-10-17創辦人發信宣布關閉12/1 起專用伺服器停止續費、共享叢集暫停；12/31 全面停止。帳戶退款與資安損失賠償分開受理。

三段的邏輯是連著的。第一段承認「轉賣層沒有結構優勢」，於是轉型。但「AI DevOps Engineer」這個定位的前提，是平台要持有客戶 production 的所有鑰匙：環境變數、資料庫密碼、雲端 token。第二和第三段外洩的，剛好就是這些鑰匙。

轉型不是失敗的原因，轉型把資安從功能變成了存在條件，而他們沒有那個底子。

同一年，同一種東西外洩了三次

Vercel 4 月的事件起點是員工用的第三方 AI 工具 Context.ai 被入侵，再進到 Google Workspace，最後拿到客戶的環境變數。Lovable 4 月的 BOLA 漏洞讓任何免費帳號讀到 2025 年 11 月前所有專案的原始碼、資料庫憑證和 AI 對話記錄，而 Lovable 建的 app 常嵌著 Supabase、Stripe、Google API 的金鑰。Zeabur 兩次都是環境變數和 token。三家平台、三種架構，外洩的永遠是「平台替你保管的鑰匙」。差別只在 Lovable 和 Vercel 撐得住，Zeabur 撐不住。

還有一個對照組要擺出來，免得把「薄 PaaS」整個判死。Railway 1 月募了 $100M Series B，ARR 超過 $10M 且已獲利，自建整套 stack；Render 2 月以 $1.5B 估值募 $100M；Fly.io 7 月募 $25M，產品重新定位成「給 agent 的電腦」。三家活得好，共同點是要嘛自有基礎設施，要嘛有明確的 agent 時代定位。Zeabur 兩者都沒有。

SHT 02 · 時間軸

2024 到 2026 下半，三條線各自在做什麼

把 AI SDLC 拆成三條線看：Build（寫 code）、Ship 與 Run（部署與維運）、Data（資料層）。三條線的斜率完全不同。

SHT 03 · 設計條件

市場不是二分，是五塊

「企業 vs 非企業」太粗。按「誰擁有資料和權限」切，是五塊，每塊的治理來源不同，而 Cloudflare 只在其中一塊。

市場誰在吃治理從哪來證據
個人、創作者、小生意Lovable、Base44（Wix）、Google AI Studio平台預設，而且預設常常是錯的Lovable 使用者調查：近八成想變現、三分之一已有營收；Base44 收購九個月後 ARR $100M、無業務團隊；但 RedAccess 的 38 萬個公開資產
新創與技術團隊Replit、Railway、Render、Fly.io、Cloudflare、Vercelruntime 隔離；code 自己管63 家 YC 公司有端點掛在 Replit；Supabase 調查：61% 新創過半程式碼由 AI 寫，Cloudflare 是成長最快的雲
企業內部工具Replit Enterprise、Retool、Power Apps、Mendix、OutSystemsSSO、VPC peering、自架Zillow 600 席、7,000 個 app，非技術員工做的功能進 production；Retool 調查 48% 非工程師已能直接建置
資料平台Databricks、SnowflakeUnity Catalog、PolarisReplit 建、Databricks Apps 跑、Unity Catalog 管；Snowflake 超過一半客戶在用 Cortex Code
System of recordSalesforce、ServiceNow、SAPtrust layer，資料不出平台Agentforce Vibes 推出時 4 萬月活、100 萬行 AI 生成 code 進 production

企業端最硬的一句話是 Salesforce 自己說的：所有動作都在 trust layer 裡跑，企業資料不離開平台邊界。這不是 Cloudflare 能吃的，因為這塊的護城河是資料所在地，不是 runtime。

五塊市場裡，目前唯一跑通的「一條龍」長這樣：Build 在外面，Ship 與 Run 在資料平台裡面。Replit 的 agent 建 app，部署進 Databricks Apps 後繼承 Databricks 認證、Unity Catalog 治理和既有網路限制，還自動配一個 Lakebase Postgres 給 app 的操作資料。消費者層的 vibe 工具不自己長治理，而是把 app 投進已有治理的平台。

SHT 04 · 背壓閥

每一層贏家做的都是同一件事

把這一年的贏家和事故並排，會看到一個共同原則。化工廠的 P&ID 上，每條會失控的管線都要有一個背壓閥：流量太快、壓力不對，閥門自己關。AI 時代的平台也是，agent 跑得比人快，所以每一層都要有一個能拒絕它的機制。

層誰在做閥門怎麼關
編譯器TypeScript、Pulumi TS、Encore、Void型別錯誤在編譯時被擋，不會燒到 apply 才發現
資料寫入Convex、Supabase RLSConvex 的論述：後端必須拒絕格式錯誤的寫入，而不是接受再祈禱
基礎設施Pulumi Neo、Neon／Lakebase branchNeo 產 PR 不直接改 prod；branch 讓 agent 在進 production 前預覽
維運Cleric、Traversal、Replit App Monitoring唯讀。Traversal 明說不裝 agent、不寫 prod；Cleric 要走審批流程
資料目錄Unity Catalog、Polaris、Dremio Open Catalog政策寫在 catalog 而不是個別引擎，一份設定涵蓋 Spark、Trino、DuckDB 和 AI agent
組織Salesforce trust layer、Databricks App Spaces資料不出平台邊界；一組 app 一次設好權限，不逐個設

這不只是比喻，有實證

你可能會問：IaC 和 infra-from-code 如果都由 AI 來寫，差在哪？差在回饋出現的時間和品質，而這有研究支持。

IaC-Eval（NeurIPS 2024）

19.36%

GPT-4 在 458 個 AWS Terraform 情境的 pass@1；同一模型在 Python 的 EvalPlus 是 86.6%

Generative Compilation（2026）

65.9 → 13.1%

編譯錯誤率：無回饋 → 生成後回饋 20.7% → 生成中即時回饋 13.1%

TerraFormer（ICSE 2026）

贏 50 倍大的模型

用 verifier 回饋微調的小模型在 IaC-Eval 排第三，超過 Sonnet 3.7、GPT-4.1

TerraFormer 還解釋了為什麼 Terraform 比 Kubernetes 難：HCL 在訓練資料裡遠少於 k8s、CloudFormation、Ansible 用的 YAML 和 JSON。所以語言的勝負公式有三個乘數：訓練流行度 × 回饋品質 × 平台整合度。TypeScript 在前兩項最高，Octoverse 2025 顯示它在 8 月成為 GitHub 第一語言，月活貢獻者年增 66%。這就是為什麼「用 TS 寫 infra」（Pulumi、CDK、Encore、Convex）占便宜，而一個新發明的小眾 DSL 得靠把文件塞進 context 來補訓練資料的不足。

a16z 2026 年說理想的 agent 是「先診斷、先實作、再來請你批准」。那是前半句。後半句是：每一層都要能說不。

三件事同時發生。第一，三大資料陣營一年內各買了一個開源資料底座：Databricks 買 Neon、Snowflake 買 Crunchy Data 並開源 pg_lake、AWS 買 DuckLabs。第二，目錄層開源化：Unity Catalog 2024 年開源，Polaris 2026 年 2 月成為 Apache 頂級專案；Iceberg 成為所有人的共同底層後，table format 不再差異化，競爭上移到 catalog。第三，商業模式反轉：Lovable 和 Bolt 透過 Supabase for Platforms 白牌 Supabase，名義上的競爭者變成支柱客戶。

把這些拼起來，「資料自主」有了一個全開源的具體技術棧：Postgres 當 catalog、Parquet 放 S3 相容儲存、DuckDB 或 DuckLake 當無狀態計算、Polaris 或 Unity Catalog 管政策、MCP 給 agent 接。全部 MIT 或 Apache，三大雲都在背後出力，而且不需要任何一家雲。DuckLake 的設計一句話說完：metadata 放 Postgres，資料以 Parquet 放 S3，計算是可拋棄的 DuckDB 實例。

企業與非企業的差別，在這一層縮小到一件事：技術棧相同，分歧只剩政策住在哪。非企業端是平台替你保管（Lovable Cloud、Supabase 託管），企業端是 catalog 或引擎強制執行（Unity、Polaris、EDB 把治理放進引擎）。EDB 的講法最直接：agent 以機器速度行動時，治理必須住在引擎裡，才不會被繞過。

一個要盯的風險

AWS 收 DuckLabs 的結構是專案留在基金會、人全部進 AWS。有評論說得直白：基金會還在，但桌上每個人都戴同一個 logo 的名牌。MIT 授權是永久的，社群的最終武器是 fork，但斜率會被誰控制，值得看。

SHT 06 · SoR

一定要 Salesforce 或 SAP 嗎

技術上不是。System of record 的核心是 record 和 data，而這一層的開源替代品已經夠用，而且比 Salesforce 更「agent 可讀」。

Twenty 的做法值得單獨講。它有 40.2k star、592 位貢獻者，定位是「designed for AI 的 Salesforce 開源替代品」。2.0 在 2026 年 4 月把它變成可建構的平台：用 defineObject 在 TypeScript 裡定義 object、field、view，然後 app:publish。有團隊把它反過來用：CRM 不是通訊錄，是 control plane，保存每個流程的正式狀態和任務佇列，agent 是清佇列的 worker。客戶頁上已有從 Salesforce 遷出的案例，用 agentic AI 壓縮遷移工作；另一家從死掉的廠商匯出檔搬過來，CRM 成本降 90% 以上。Odoo 19 新增獨立的 AI App，定位是基礎設施而非功能，所有資料放 Postgres、沒有專有格式。

Salesforce 的黏性在於流程語意鎖在它的 UI 設定裡；一旦語意變成 repo 裡的 TS 檔案，agent 就能重生、遷移、驗證它。這是對 SoR 護城河最直接的攻擊。

但要誠實講規模：開源 ERP 市場 2026 年約 $53 億，年增 9.66%，相對 SAP 是零頭；案例集中在中型企業，大企業案例仍薄；ERPNext 的 AI 目前是第三方工具集合，不是核心原生。大企業留在 Salesforce 的原因是流程語意、合規、生態、遷移成本，不是資料庫。所以「在自己平台上 vibe」是路徑依賴下的最佳解，不是技術最佳解。這兩句話同時成立。

SHT 07 · 施工說明

對內網 IDP 的意涵

接回 Void 與 Encore 那題 這篇的起點其實是另一個問題：Void 能不能架在內網當 Internal Developer Platform，Encore.ts 能不能吃 k8s。答案是 Void 的「自架」仍在 Cloudflare 上，Encore 的 k8s 自動化只限 GKE 和 EKS，內網要走 self-host 路線自己寫 manifest。走到這裡，那題的答案變得清楚：你要的不是某家的產品，是內網版的 control plane。

  1. 不要選轉賣層。它們的經濟模型（Zeabur 自己說的）和資安模型（事件證明的）都撐不住。
  2. 第二層自己擁有，runtime 可換。審批加稽核那層是你的：agent 產 PR 和 manifest，人審，Argo CD 同步。審批面板在你手上，不在 SaaS 手上。
  3. Secrets 不集中在一個 SaaS。Zeabur、Vercel、Lovable 三案外洩的都是平台保管的鑰匙。內網走 Vault 或 External Secrets。
  4. 資料層照開源三件套走。Postgres、S3 相容儲存、DuckDB 或 DuckLake，加一個 catalog。這條和 UNS data hub、serverless 數據 API 是同一個方向。
  5. Run 層先接唯讀的 AI 根因分析。Cleric、Traversal、Replit 都收斂在唯讀，這可能會變成行規。
  6. IaC 選「高流行度語言加強 verifier 鏈」。Pulumi TS 加 policy-as-code，或 k8s YAML 加 OPA、Kyverno、admission。小眾 infra-from-code DSL 的賭注是 verifier 強到可以補流行度，目前沒有公開數據證明。

SHT 08 · 結論與未決

八條結論，標了證據強度

  1. Zeabur 的死因是結構性的。 強薄轉賣層加 AI 口號這個組合在 2026 年沒有生存空間；Railway、Render、Fly.io 活著是因為自有基礎設施或明確的 agent 定位。
  2. 平台競爭不在 Build 層，在「誰擁有授權邊界與稽核」。 強Build 一年內被開源和三大雲商品化；Lovable $600M 賣的是 hosting 和部署，不是生成。
  3. 每一層贏家做的都是 backpressure。 強編譯器、寫入、branch、PR、唯讀、catalog、trust layer，同一條原則；IaC-Eval 與 TerraFormer 給了實證。
  4. 市場是五塊，Cloudflare 只在一塊。 強每塊的治理來源不同，SoR 和資料平台的護城河是資料所在地，不是 runtime。
  5. 資料層是重力所在，企業與非企業在這裡收斂。 強一年內的收購全是開源資料底座；agent 開資料庫的比例從 30% 走到 80% 到 90%；分歧只剩政策住在哪。
  6. 「一定要 Salesforce 或 SAP」是假的，「大公司跑不動」是真的。 中Twenty 已有從 Salesforce 遷出的案例，但開源 ERP 市場相對 SAP 是零頭。
  7. 目前唯一跑通的一條龍是「Build 在外、Ship 與 Run 在資料平台內」。 中Replit 加 Databricks、v0 加 Snowflake 同構；沒有單一廠商橫跨五個市場。
  8. 下一代平台的 UI 是審批面板，不是設定面板。 中a16z 的「先做再求批准」、Claude Code 的 task list、Cleric 的 approval flow、Void 把憑證留給管理員，形狀一樣。偏推論。

仍是假設，不能寫成結論的

  • 任何平台「agent 建的 app 進 production 的佔比」都沒有公開數字。有的是間接指標（Supabase 的建立比例、Zillow 案例、63 家 YC 公司的 DNS）和反指標（IDC：88% 的 agentic 試點從未到 production；只有約三分之一開發者對用 vibe 工具建業務關鍵 app 有信心）。正確寫法是：production 化集中在內部工具和新產品，核心系統仍未。
  • 交易型 SoR 的 agent 化證據薄。Lakebase 說數千家在跑 production，但沒說是什麼工作負載；Odoo 19 的 AI App 才剛出。
  • Neon 80%、Supabase 90%、EDB「95% 企業三年內自建」都是廠商數字。
  • Encore、Void、Convex 在中立 benchmark 下的表現：沒有。IaC-Eval 只測 Terraform。這一塊自己跑實驗是唯一辦法。
