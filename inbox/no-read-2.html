N-08 · 起點

一篇整理得不差的部落格

11 月 15 日，agile3uncles 發了一篇白話整理。它的主張是：AI 動手前會先翻現有的程式，好的壞的一起學，所以團隊不再靠文字叮嚀，而是把每一次糾正變成自動檢查的規則，再讓 AI 用影片、截圖和驗證報告證明自己做對了。文末給了兩個數字，一個月 11,000 個 PR，0.5% 需要退回。

它的出處只附了一支 YouTube 影片，說明是照自動字幕整理的，沒有時間碼，也幾乎沒有直接引語。我拿 AI Engineer 官網的逐字稿逐句對過，大方向沒有錯，例子和數字也都對得上。偏掉的有四處，對照表放在附錄 A：

  • 「2024 年一天審 3 個 PR，現在 300 個」。逐字稿兩份都沒有「一天」這個時間單位。
  • 「規矩是花架」。她用的比喻是水泥地基，新程式繞著地基長。
  • 「不再靠文字叮嚀」。她的金字塔還有文字這一層，只是放得很低。
  • 「寫三成、檢查七成」。70% 是她引的一則貼文裡，Cindy 自己每天花在驗證上的 token 比例，不是團隊的分配。

這些都不嚴重。真正要補的是第五個：部落格把她的金字塔寫成四層，少了最底下那一層。少掉的那一層是人工審查，而這一層正是 9 月和 11 月之間移動最大的地方之一。

N-09 · 原話

她 11 月講的，照順序

這場 17 分半。我照逐字稿的順序重講一次，引號裡的是原話，其餘是我的轉述。

開場。她問台下誰看過別人的程式、覺得那是 slop。她自己也看過，但這場要講怎麼把 slop 變成金子。她說上個月她一個人上線了 3,000 個 PR，花了六個月才走到這裡，很多是在她睡覺的時候合進去的。

題目。工程師的核心工作，是在產量暴增的時候守住、甚至提高品質。有人把這叫做軟體工廠，她說她叫它信任。信任不是盲目相信，是投資在 agent 的環境上。

花園。agent 的產出取決於輸入，程式庫是最大的輸入之一。2024 年她要審三個同事的 PR，現在大約是 300 個。限制和護欄是水泥地基，新寫的程式繞著它長。權宜寫法和反模式是害蟲，過時的技術也是。下一個 agent 會把它們當成慣例照抄，很快就爬滿整片。

三個例子。都來自 Grok Bot 用的 Electron 框架 Dune。

  1. React 的 useEffect 在產品程式碼裡禁用，只有框架內部能用。她的理由是「anything that requires nuance to use well often leads to slop」。這一類錯從此不會出現，審查的人也就不用再抓。
  2. 最上層分成 electron/main 和 electron/renderer 兩個目錄，用相依圖分析和 lint 擋住互相匯入。這是 Cursor 時期學到的：agent 常把主程序的程式拉進畫面那邊，造成卡頓。
  3. Cursor 時期，agent 很愛拿計時器修問題，每個計時器旁邊都寫一段註解說明為什麼，結果計時器到處都是。Grok Bot 乾脆禁掉約 99% 的註解，因為註解會過時，也沒辦法強制。改成 lint 規則，錯誤訊息直接叫 agent 去修根本原因。

驗證。每一次糾正都變成一條確定性的檢查，審查要看的東西就越來越少。她說程式審查已經縮成看驗證產出，例如影片和截圖，還有形式化驗證的結果。他們用 TLA+ 檢查跨裝置的通知流程，用 Lean 檢查自己寫的 virtualization 程式庫會不會閃爍或抖動，用 Bombadil 做 UI 的 property-based testing。她說在 X 上看到 Cindy 的貼文：Cindy 原本不信任 agent，六個月後說自己每天 70% 的 token 花在驗證上。她說自己也差不多。逐字稿只有名字，有一份整理說這位是 @copyconstruct。這些技術都不新，以前是寫起來和維護起來都太貴。接回上篇 N-02

成果。團隊上個月上線約 11,000 個 PR，大約每天出一個穩定版。10 月有約 227 人貢獻過至少一個 PR，包括偶爾來一次的人。退回率穩定在 0.5% 左右。啟動和打字都比上市時快，開對話和切對話也是。她也承認 Electron 有它的天花板。

收尾。每次糾正 agent，先從改程式庫下手。先加 lint 擋住新的反模式，再清掉舊的，再把驗證做紮實。內圈還在產 slop 的話，自動化外圈只會產出更多 slop，還燒掉很貴的 token。地基打好之後，Grok Bot 現在每次發版都會自動開一個專案，像真的使用者一樣把整個 app 跑一遍，找到 bug 就開修正 PR，然後自動合併。她說大部分產品程式碼現在不經過深度的人工審查就進去了。

N-12 · 站得住的

糾正變成檢查，連顧舊系統的人都同意

她最核心的一招是「每次糾正 agent，就把它變成一條機器會執行的檢查」。這不是她一個人的主張。

Addy Osmani 9 月寫的〈Brownfield Agentic Engineering〉談的是舊系統，結論在這一點上跟她一樣：同一句審查意見第二次出現，就該寫成機器會執行的東西，像 lint 或測試，不要再寫成模型可能會忘的指示。機器強制的東西不用記得。

Vaibhav Gupta 在 AI Engineer World's Fair 的〈Fighting Slop with Slop〉做的是程式語言。他也用相依圖加 CI 檢查守住架構邊界，跟 Dune 擋 main 和 renderer 互相匯入是同一個做法。

「程式庫教壞 AI」這個說法也有別人講。Larridin 7 月的文章說，不一致的寫法和歷史包袱會被 AI 學走、大量複製。要注意 Larridin 自己在賣偵測 slop 的工具，文中的統計也是轉引的。

上篇的 Uncle Bob 是從另一條路走到這一招的。他先寫了 5 到 10 頁的 prompt，發現模型只把它當參考，才把規矩搬進事後跑的工具。接回上篇 N-03

所以她金字塔上面兩層的道理，有獨立的人支持，舊系統也適用。問題出在她沒講的那幾件事。

N-13 · 前提一

這座花園才四個多月大

8 月 31 日她在 pstack 指南裡寫，她大約兩個月前開始做 Grok Bot，那時產品還很早期，程式庫是新的，剛開始長大。她還說自己在開發期間把整個程式庫重構了一遍，加上更穩的地基，沒有停機。Dune 是他們自己寫的框架。

照這個時間推算，11 月演講時，這座程式庫大約四五個月大（這是我的推算）。她說要清掉舊的技術債，可是舊債最舊也才幾個月，框架是自己人寫的，每一條慣例都找得到人問。

舊系統是另一回事。Addy Osmani 那篇一開頭就說，舊程式庫已經不是系統行為的完整描述，有些限制只存在於人的記憶和其他團隊的依賴裡。他的建議是先寫 characterization test 把現有行為鎖住，包括醜的部分，再把程式碼分成綠、黃、紅三區，紅區是授權和計費這類地方，每一步都要有人陪著。Nick Sawinyh 把程式庫分成三種，說人寫了好幾年的舊系統最難，要先花一大段準備期，把相依關係畫出來，文件和測試補起來，才輪得到 agent 寫新東西。

她的順序可以搬到舊系統，她的速度不行。在舊系統上，「先把程式庫整理乾淨」本身就是一個大專案，而且清之前要先知道哪些醜東西是承重牆。

N-14 · 前提二

0.5% 量的是什麼

11,000 個 PR、0.5% 的退回率，AI Engineer 官網的整理特別註明這是團隊自己報的數字，不是對照研究。除了這一點，還有兩件事要知道。

退回不等於出錯。退回是整個 PR 被撤回。她講的外圈是每次發版後自動找 bug，開修正 PR 再自動合併。一個用新 PR 往前修掉的 bug，不會變成一次退回。所以 0.5% 比較接近「需要整個撤回的變更」的比例，而不是「上線後出問題的變更」的比例（這是我的推論，她沒有給後者的數字）。Addy Osmani 建議追的指標裡有一項是漏到線上的缺陷，她公開的是 rollback 和效能，沒有這一項。

產量很集中。她一個人 3,000 個，是團隊 11,000 個的約 27%。另外 226 人平均每人大約 35 個。她在 8 月說過，自己一直在盯程式碼，隨時重構、補 lint。這座花園的品質，有很大一部分是她本人在當園丁。換一個沒有她的團隊，同一套規則能維持多少，這場演講沒有回答。

N-15 · 前提三

最底下那一層還在

她在演講裡說，糾正一條一條變成檢查之後，審查要看的東西越來越少，最後沒什麼好審的，agent 可以自己合併大部分 PR。這句很容易被轉述成「不用審了」。部落格的「不再靠文字叮嚀」是同一種省略，只是省掉的是另一層。

她自己的投影片沒有拿掉 human review。它在最底下，是最貴的一層。

別人的說法可以幫忙讀這一層。Addy Osmani 說，產生的程式碼越多，人工審查要越有選擇性，但擁有權不能變少，人的注意力先放在爆炸半徑最大、驗證最弱的地方。Gupta 對 slop 的定義更直接，slop 就是「any code you do not read」。他也提醒，程式庫現在含的 slop 是它這輩子最少的，流程得跟著程式碼一起長。

她自己也還在讀。Barnaby Robson 整理她和 Matt Pocock 的訪談，說她每天抽看合併進去的 PR，早上讀一遍 commit 歷史，該退的退，該補 lint 的補。

放在一起看，我的讀法是：人工審查從「每一個 PR 都看」改成「只看驗證蓋不到的地方」。這是我的整理，不是她的原話，但跟她那支 cost 箭頭是一致的。

兩個人沒有互相引用過，至少我沒找到。他們有四件事是一樣的：

  1. 逐行人審跟不上產量，所以審查要退後。
  2. 寫給 agent 看的文字靠不住，規矩要變成機器會擋的檢查。
  3. 架構留在人手上。
  4. 人沒有離開。他留著抽查和手動測試，她留著金字塔最底下那一層。

不一樣的是人看的東西。他主要看結構：分數和相依圖。她主要看行為：app 跑起來的影片和截圖。位置也差一點。他在 agent 動手前還會讀一小份規格，她這場演講沒有提規格。檢查的做法也不同。他的檢查多半是事後量出來的分數，她的檢查有一大半是事前就讓錯的寫法寫不出來。

兩張單子併在一起才是一條完整的線：上游有人審過的規格，中間有寫不出錯的環境，下游有跑起來的證據，最底下留一層人。

兩個人各做了大半條，都沒有做滿。他沒有上線以後的數字。她這場演講沒有講需求和規格從哪裡來。

同一個方向還有第三個人。兩個人都上過 Matt Pocock 的節目。9 月下旬他推薦 Lauren 的一支影片，列的第一點是把 agent 鎖緊：人喜歡鋒利、用錯會割手的抽象，agent 在鎖死的環境裡表現好得多。他後來在自己的 skills 裡加了一個 /retro：把機械性的規則變成確定性的檢查，讓 AGENTS.md 變短。

11 月 16 日他直播訪問 coding agent Pi 的兩位作者，Mario Zechner 和 Armin Ronacher。他說當天早上才看完 Lauren 這場演講，接著把 N-09 那句 nuance 推到設計上：程式庫和 API 要盡量少留需要拿捏的地方。直播後他貼了一則評估 API 的 prompt，其中一個評分項就是這件事，要拿捏的地方越多越扣分，理由是選擇少的時候 agent 表現比較好。

同一場直播的反方 · v0.4 補

兩位來賓沒有照單全收。Matt 在節目上轉述 Zechner 開播前講的一句話：驗證被高估了。Zechner 先聲明這不是針對 Lauren。他說的是另一種人，看到 agent 寫了一大堆 lint 規則和測試，就以為系統沒問題。Ronacher 替 Pi 的一部分寫過 Lean 證明，結果它只是 agent 多了一份可以讀的東西。這兩段的細節放在第三篇 N-23。

跟這張表有關的是另外兩件事。Zechner 說模型從 Opus 4.8 到 5.5，系統設計和 API 設計沒有跟著變好，這跟上面第 3 點同向。他也還在讀程式碼：碰到 Pi 核心的變更，他整份 diff 讀完，匯出 HTML 這類周邊只看結果對不對。Ronacher 說他們現在讀的比例已經低很多。Zechner 的分法是照風險決定讀多少，跟 N-15 的讀法一致。

還缺的一塊資料

部落格的標題「slop 是你的 codebase 教出來的」是一個因果句。我找到的受控實驗只有上篇 N-05 那一篇，它量到的是乾淨的程式庫讓 agent 省 token、少重讀，通過率沒有變。它沒有量 agent 會不會把舊的爛寫法抄進新程式。另一篇分析 PR 的研究看到的是另一種毛病：agent 常常不重用現成的程式，自己再寫一份。所以「agent 會照抄」目前是 Lauren 和其他從業者的觀察，還沒有實驗。她的做法不必等這個實驗，禁掉 useEffect 的理由是讓錯寫不出來。但標題那個因果要打折。

N-17 · 能搬的

外面能搬的是順序

驗收筆記下篇的主軸是：實驗室和外面的差距在 oracle，外面能複製的是順序，複製不了規模。接回驗收筆記 S-10

兩篇看下來，兩個人改來改去的都是 oracle 放在哪。Uncle Bob 把規矩從 prompt 搬進工具，把架構收回自己手上。Lauren 把驗證從梯子旁邊搬進梯子裡，把人工審查標成最貴。她 11 月的收尾本身就是一個順序：先改程式庫，加 lint 擋新的，清掉舊的，把驗證做紮實，最後才自動化外圈。

想照抄的團隊，可以搬走的是這四件事：

  1. 需求先變成人審過、能執行的規格，一次一個 story。這是 Uncle Bob 的第 1 站。他試過把規格一次寫滿，說每次都失敗。
  2. 每一次糾正 agent，先問這條能不能往上推一層。能改架構就不寫 lint，能寫 lint 就不寫進 AGENTS.md。
  3. 開平行之前，先有一套可以重現的驗證：一支每次都一樣的 CLI，加一張功能地圖。這是 Lauren 9 月和 11 月都講的。
  4. 人工審查留給驗證蓋不到、出事最痛的地方。在舊系統上，先把那些地方標出來。

不要搬的有兩樣。一樣是數字：11,000 和 0.5% 是一座四個多月大、由她親自照顧的花園量出來的，拿來當目標，就是把驗收筆記 S-17 左邊那一排再走一次。另一樣是「不讀」這兩個字。兩個人都還在讀，只是換了東西讀。

變更通知只說明改了什麼。新版次有沒有比較好，要等下一次量測。她下一次公開講的時候，我會看最底下那一層還在不在。
