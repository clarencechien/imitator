改裝手冊 · CLAUDE CODE MODS · 2026-10

Mod 是裝在
Claude Code
裡面的一層

CLAUDE.md 是寫給模型看的規則，shell hook 是擋在門口的外部腳本。Mod 則是一段 TypeScript 函式，直接接在 Claude Code 處理每個事件的路徑上：同一個函式裡就能擋、改、看結果、畫介面。下面用四組「原廠 vs 改裝後」把差別拆給你看。

依據 Claude Code v2.1.287 隨附的 Mods 說明與型別定義整理 · API 仍可能隨版本變動

00 · 一句話

一個函式，三個參數

每個 Mod 都是一個 register(on)，在裡面用 on(事件, 篩選, hook) 掛上函式。所有 hook 長得都一樣：

on('tool.call', { tool: 'Edit' }, ($, e, next) => { … })
參數是什麼你可以拿它做什麼
e事件本身，例如這次 tool call 的工具名稱與參數。資料是凍結的。要改就做一份新的：{ ...e, command: '…' }
next「交給下一層」。呼叫它，內層的 Mod 和引擎本身才會執行。不呼叫 → 自己回答（例如回 { deny }）；await next(e) → 拿到執行結果再處理
$引擎提供的介面：檔案、程序、模型、狀態、介面……$.ui.status() 改狀態列、$.state 存值、$.command.register() 加斜線指令

如果你寫過 Express 或 Koa 的 middleware，這就是同一個模式：事件從外層一路往內傳，結果再原路傳回來，每一層都可以攔截、改寫或旁觀。

01 · 結構圖

事件怎麼穿過每一層

這張圖說明兩件事。第一，原本的 shell hook 沒有被取代，它變成鏈上靠內的一層。第二，Mod 的順序有影響：如果遮個資的 Mod 排在記錄日誌的 Mod 外層，日誌記到的就是遮過的版本；反過來，原文就進了日誌。

02 · 四組對照

原廠 vs 改裝後

每一組的左邊是沒有 Mod 時最好的做法，右邊是改用 Mod 的寫法。程式碼盡量用官方範例的寫法，示意用的地方會註明。

02-A · 保護 .env

「不要改 .env」

最常見的需求：無論如何都不能讓 agent 修改 .env。

原廠 · CLAUDE.md + shell hook

  1. CLAUDE.md 寫一句規則。這是「拜託」：上下文一長、被 compaction 壓縮，就可能被忽略。
  2. 要強制執行，就在 settings.json 掛一支 PreToolUse 腳本。
  3. 每次 tool call 都啟動一次 bash，用 jq 解析 stdin 的 JSON，exit 2 代表擋下。
# .claude/settings.json
"PreToolUse": [{ "matcher": "Edit|Write",
  "hooks": [{ "type": "command",
              "command": ".claude/hooks/protect-env.sh" }] }]

# .claude/hooks/protect-env.sh
f=$(jq -r '.tool_input.file_path // empty')
if [[ "$f" =~ (^|/)\.env(\.|$) ]]; then
  echo "受保護：$f" >&2; exit 2
fi
exit 0

改裝後 · Mod

  1. 同一份 TypeScript，e.file_path 直接是型別化的欄位，不用 jq。
  2. 回傳 { deny }，理由直接回給模型。
  3. 不必每次開一個 shell process。
import type { Register } from 'claude-code'

const PROTECTED = /(^|\/)\.env(\.|$)/

export const register: Register = on => {
  on('tool.call', { tool: 'Edit' }, ($, e, next) =>
    PROTECTED.test(e.file_path)
      ? { deny: `${e.file_path} 受保護，不能改` }
      : next(e),
  )
  // Write 同理再掛一個
}

差別不大。只是「擋下」的話，shell hook 本來就做得到。Mod 在這裡只是比較順手，真正拉開差距的是後面三組。

02-B · REVIEW 模式

「先看就好，不要順手改」

STS 那類 Skill 想解決的問題：叫 agent 看問題，它看完順便重構三個檔案。

原廠 · Skill + hook + 狀態檔

  1. Skill 告訴模型「現在是 review，只能讀」，模型要一直記得。
  2. hook 是另一支腳本，不知道 Skill 說了什麼，只能去讀一個狀態檔判斷模式。
  3. 誰來改狀態檔？通常是模型自己：開關在被管的人手上。
# review-guard.sh（PreToolUse, matcher: Edit|Write）
mode=$(cat .claude/sts-mode 2>/dev/null || echo review)
if [ "$mode" = review ]; then
  echo "review 模式不能寫入" >&2; exit 2
fi
exit 0

# 切換：Skill 叫模型自己跑
#   echo change > .claude/sts-mode

改裝後 · Mod

  1. 模式存在 Mod 裡，用斜線指令切換。開關在人手上，模型碰不到。
  2. 模型不用記規則；真的要寫入時才被擋，並收到理由。
  3. 狀態列顯示目前模式，人也看得到。
// 示意：正式版的 mode 要放 $.state，重新載入才不會歸零
let mode: 'review' | 'change' = 'review'
const WRITES = new Set(['Edit', 'Write', 'NotebookEdit'])

export const register: Register = on => {
  on('session.start', async ($, e, next) => {
    await $.command.register({ name: 'change', description: '允許寫入' })
    await $.command.register({ name: 'review', description: '切回唯讀' })
    return next(e)
  })
  on('command.run', { command: 'change' }, async $ => {
    mode = 'change'; $.ui.status('CHANGE')
    return { text: '已切到 change 模式' }
  })
  on('command.run', { command: 'review' }, async $ => {
    mode = 'review'; $.ui.status('REVIEW · 唯讀')
    return { text: '已切回 review' }
  })
  on('tool.call', ($, e, next) =>
    mode === 'review' && WRITES.has(e.tool)
      ? { deny: '現在是 review（唯讀）。要改請使用者下 /change' }
      : next(e),
  )
  // Bash 要另外判斷是不是寫入，這裡省略
}

這組才是重點。原廠做法裡，規則在 Skill，判斷在 hook，狀態在檔案，三者靠模型串起來。改裝後三者都在同一個函式裡，模型只需要專心工作。

02-C · 授權範圍

「這次只能改 src/payment/」

進了 change 模式，也不代表整個 repo 都能動。

原廠 · 寫在提示詞裡

  1. 提示詞說「只改 src/payment/」。
  2. 模型發現 src/auth/ 也要改時，可能會停下來問，也可能直接改，然後在總結裡附一句「順便調整了」。
  3. 要強制，就得再寫一支 hook，再加一個存放範圍的檔案。

改裝後 · Mod

  1. 超出範圍的寫入直接被拒，理由寫明「請先問使用者」。
  2. 模型收到 deny 後，自然會停下來回報。
const SCOPE = /\/src\/payment\//

on('tool.call', { tool: 'Edit' }, ($, e, next) =>
  SCOPE.test(e.file_path)
    ? next(e)
    : { deny: `超出這次授權範圍（只限 src/payment/）：`
            + `${e.file_path}。請先問使用者。` },
)

「邊界內自己跑，跨線才停」就是這樣落地的：不是每一步都請示，而是只有越線的那一步被攔下。

02-D · 改寫 + 看結果

「先整理指令，跑完失敗就提醒我」

同一次 tool call，執行前要改輸入，執行後要看結果。

原廠 · 兩支腳本 + 一支狀態列

  1. PreToolUse 腳本回傳 JSON 來改輸入。
  2. PostToolUse 是另一支腳本、另一個 process，要自己用 tool_use_id 把兩次對起來。
  3. 要在狀態列顯示，又是第三支 statusline 腳本，彼此之間只能靠暫存檔溝通。

改裝後 · Mod（官方範例）

  1. next() 前改輸入，await 之後拿到結果，全在同一個函式裡。
  2. 局部變數就能把前後對起來，不需要 id。
on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
  const ran = await next({ ...e, command: e.command.trim() })
  const hasFailed = ran.deny === undefined && ran.isError === true

  $.ui.status(hasFailed ? `failed: ${e.command.slice(0, 40)}` : undefined)
  return ran
})

shell hook 做不到「包住」這件事。Mod 也可以失敗後重試、把結果改寫後再交給模型，或乾脆自己回答、不讓工具執行。

規則寫在提示詞裡，是請模型記得；寫在 Mod 裡，是讓越線的動作自己過不去。

03 · 零件表

Skill、MCP、Hook、Mod、Plugin 各管什麼

零件本質強制力適合拿來
SkillSKILL.md給模型看的工作說明無，靠模型遵守流程、做事方法、領域知識
CLAUDE.md常駐上下文無專案慣例、背景
MCP外部工具與資料—接 Jira、資料庫、內部 API
Shell hooksettings.json特定時點跑外部腳本有，但只能放行、擋下或補充上下文簡單的硬規則，例如禁改某些路徑
Modfunction hooks引擎內的 TypeScript 中介層有，可擋、改、重試、包住授權模式、遮個資、記錄、自訂面板與指令
Plugin打包與安裝的單位—把上面幾樣裝在一起發佈

選擇原則：用能解決問題的最小零件。Skill 就夠的不要寫 hook；shell hook 一行就能擋的，不必升級成 Mod。

04 · 警告

裝之前要知道的三件事

⚠ 1. 擋人的 Mod 壞掉時，預設是放行

hook 執行時丟出錯誤，Claude Code 會跳過它，鏈繼續往內走。所以負責阻擋的 Mod 如果在檢查途中出錯（讀檔失敗、正則寫錯），結果等於沒裝。解法是掛 .catch，讓它在失敗時拒絕：

on('tool.call', { tool: 'Edit' }, guard)
  .catch(($, e, next) => ({ deny: '安全檢查失敗，保守拒絕' }))

2. Mod 不是 sandbox

Mod 的程式本身跑在沒有 Node、沒有 DOM 的獨立環境，但透過 $.fs、$.process，它用的是你本人的權限。權限規則管的是 Claude 呼叫的工具，不一定管得到 Mod 自己透過 $ 做的事。安裝別人的 Mod，等於把你的帳號權限交給它：它可以自動核准權限、讀所有提示詞。所以要像審查瀏覽器擴充套件一樣，先讀過程式碼再裝。真正的安全底線，還是權限規則、sandbox 和伺服器端授權。

3. 狀態放哪裡，決定它活多久

放在壽命用途
模組變數 let x重新載入就歸零暫時的計算
$.state整個 session；改值會自動重畫介面目前模式、面板內容
$.store跨 session設定、長期紀錄

05 · 安裝步驟

第一顆 Mod 怎麼裝

my-mod/
├── .claude-plugin/plugin.json   { "name": "my-mod", "version": "0.1.0" }
├── hooks/hooks.json             { "modules": ["./register.ts"] }
├── hooks/register.ts            export const register = on => { … }
└── tests/guard.test.ts

claude plugin validate ./my-mod    # 檢查會掛哪些事件、哪些會被拒
claude plugin test ./my-mod        # 跑 *.test.ts
claude --plugin-dir ./my-mod       # 只在這次 session 載入

API 以你安裝版本產生的型別定義為準：Mod 載入後，.claude-plugin/types/ 會出現完整的 .d.ts，事件、$ 的每個方法和範例都在裡面。

上線順序建議先觀察，再阻擋：第一版只記錄「這個動作有沒有越線」，跑一陣子確認不會誤判，再把記錄改成 deny。這樣誤擋正常工作時，你知道是哪一條規則造成的。
