    <h3>Executive Summary</h3>
    <p>
      本報告系統性釐清科技 YouTuber Andres Vidoza 放棄 Framework 13 Linux 筆電轉向 MacBook 的底層主因，確立了<strong>「用戶端（Client）與運算端（Server/Container）責任分離」</strong>的核心架構原則。針對 macOS 運行容器的效能痛點，詳細評析了 Apple 原生 <strong>Virtualization.framework (`vz`)</strong> 與 <strong>VirtioFS</strong> 最佳化機制；並進一步橫向對比 2026 年主流容器管理工具（OrbStack、Colima、Podman Desktop、Docker Desktop）與面版方案（Dockge vs. Portainer BE）。針對 Dockge 缺乏細部 RBAC 的資安疑慮，本報告給予了<strong>基於開源特權存取管理（OSS PAM / 堡壘機）實施零信任審批與操作錄影</strong>的落地解法。
    </p>
  </div>

  <section>
    <h2 class="section-heading"><span class="sec-num">01.</span> 事件始末：Framework 13 的理想與 Linux 行動端的現實碰撞</h2>
    <p>
      在科技圈廣受討論的影片《<em>Why I Gave Up on Linux… Hello MacBook</em>》中，創作者深入體驗了主打高度模組化、極致可修復性（Repairability）的指標性硬體 <strong>Framework Laptop 13</strong>。然而，在歷經數月、測試多達 4～5 種 Linux 發行版（包含官方認證的 Ubuntu 與 Pop!_OS）後，作者最終選擇回歸 MacBook。
    </p>
    <p>
      <strong>核心結論：</strong>作者放棄的<strong>並非 Framework 的硬體工程品質</strong>，而是 <strong>Linux 桌面系統（Desktop GUI）在現代行動工作場景中無可避免的系統性摩擦力</strong>。
    </p>


    <div class="grid-duo">
      <div class="panel-card danger-card">
        <h4 style="color: var(--c-danger);">Linux 筆電行動場景的 4 大痛點</h4>
        <ul class="clean-list">
          <li><strong>待機休眠耗電（S2Idle 陷阱）：</strong>現代 x86 筆電普遍捨棄傳統 ACPI S3 睡眠，改採 Modern Standby（S2Idle）。Linux 核心常因周邊輪詢無法深度休眠，筆電放進背包持續發熱、耗電達每小時 3%～5%。</li>
          <li><strong>模組卡暗電流（Expansion Card Drain）：</strong>Framework 的特色擴充卡（如 HDMI、DisplayPort、2.5GbE）內建主動轉換晶片，插在特定槽位即便未外接螢幕，仍會持續吃電。</li>
          <li><strong>3:2 螢幕非整數縮放（Fractional Scaling）：</strong>2256×1504 解析度在 13 吋下必須啟用 125% 或 150% 縮放。Wayland / XWayland 渲染架構導致 Electron 軟體（Slack、VS Code 等）邊緣模糊或 GPU 負擔過大。</li>
          <li><strong>除錯稅（Debugging Tax）：</strong>觸控板防誤觸不佳、外接螢幕更新率跳脫、顯卡混合調度失誤，使工程師耗費大量時間「修電腦」而非「做產出」。</li>
        </ul>
      </div>


      <div class="panel-card success-card">
        <h4 style="color: var(--c-success);">架構重塑：責任分離最佳實踐</h4>
        <ul class="clean-list">
          <li><strong>行動端（Client Device）：</strong>MacBook (Apple Silicon) 具備 SoC 一體化架構，提供<strong>闔蓋零掉電</strong>、<strong>開蓋 0 秒點亮</strong>、視訊/顯示硬體解碼與 14～18 小時真實續航。</li>
          <li><strong>服務端（Server / Home Lab）：</strong>Linux 回歸 24 小時插電運行的伺服主機（如作者最終建置的 10GbE UniFi 機櫃、CasaOS、Home Assistant）。</li>
          <li><strong>本機運算（Headless Containers）：</strong>在 macOS 上以無頭（Headless）方式運行 Linux 容器，彻底避開 X11/Wayland 桌面驅動問題。</li>
        </ul>
      </div>

  <section>
    <h2 class="section-heading"><span class="sec-num">02.</span> macOS 無頭容器架構與 Apple vz 核心調校</h2>
    <p>
      容器（Container）的本質不是虛擬機，而是依賴 Linux 核心的 <code>cgroups</code>、<code>namespaces</code> 與 <code>overlayfs</code> 進行行程隔離。macOS 底層核心為 XNU（BSD/Mach），先天不具備原生執行 Linux 容器的能力。因此，在 macOS 上運行 Docker，底層<strong>必定存在一個微型 Linux 核心（VM）</strong>。
    </p>


    <div class="diagram-box">
[ macOS 應用層 (開發者工作區 / IDE / 終端機) ]
       │
       │ (透過 /var/run/docker.sock 或 TCP 溝通)
       ▼
[ Apple Virtualization.framework (`vz`) ]  <── 原生呼叫 Apple Silicon 硬體虛擬化指令
       │
       ├── VirtioFS  ──► [ 超低延遲目錄記憶體映射 (本機專案原始碼) ]
       ├── Rosetta 2 ──► [ linux/amd64 x86 指令硬體即時轉譯 ]
       │
       ▼
[ 極簡 Linux 微核心 (Headless VM, 無 GUI) ]
       └── [ Docker / Containerd Engine ] ──► [ 應用容器群 (DB / Redis / Kafka) ]
    </div>


    <h3 class="sub-heading">Apple vz 虛擬化與調校三要素</h3>
    <p>
      傳統跨平台工具（如早期 QEMU）在指令轉譯與 I/O 攔截上存在顯著損耗。透過開啟 Apple 原生虛擬化機制，可釋放晶片頂級能效：
    </p>


    <table class="data-table">
      <thead>
        <tr>
          <th>參數技術</th>
          <th>底層運作機制</th>
          <th>效能與體驗優勢</th>
        </tr>
      </thead>
      <tbody>
        <tr>
          <td class="cell-highlight">--vm-type vz</td>
          <td>直接調用 macOS 13+ 提供的原生 <code>Virtualization.framework</code>。</td>
          <td>取代 QEMU 繁複排程，虛擬機待機 CPU 佔用趨近於 0%，大幅節省本機電量。</td>
        </tr>
        <tr>
          <td class="cell-highlight">--mount-type virtiofs</td>
          <td>透過共享記憶體區段（Shared Memory Ring Buffer）處理檔案映射。</td>
          <td>消弭傳統 9p/SSHFS 的 I/O 阻塞，大量小檔案讀寫（如 <code>npm install</code>、原始碼熱重載）速度提升 3～5 倍。</td>
        </tr>
        <tr>
          <td class="cell-highlight">--vz-rosetta</td>
          <td>將 Apple 原生 Rosetta 2 轉譯層注入 Linux 虛擬機核心。</td>
          <td>在 ARM64 架構上高速運行舊型 <code>linux/amd64</code> 容器，效率遠優於 QEMU TCG 軟體模擬。</td>
        </tr>
      </tbody>
    </table>


    <div class="code-container">

        <span>Production Colima Optimization Command</span>
        <span>bash</span>
      </div>
      <pre class="code-content"><code><span class="code-token-cmd">colima start</span> <span class="code-token-flag">--cpu</span> 4 <span class="code-token-flag">--memory</span> 8 <span class="code-token-flag">--vm-type</span> <span class="code-token-val">vz</span> <span class="code-token-flag">--mount-type</span> <span class="code-token-val">virtiofs</span> <span class="code-token-flag">--vz-rosetta</span></code></pre>
    </div>


    <div class="note-box">
      <strong>開機體感對比（Chromebook vs. MacBook）：</strong><br>
      Chromebook 依賴 Coreboot 達成 6～8 秒極速冷開機，並透過 <code>crosvm</code> 動態拉起 Debian 容器（Crostini）。而現代 Apple Silicon MacBook 的工程哲學是<strong>「從不關機」</strong>——休眠採用深度省電（一晚掉電僅 1%），<strong>掀蓋解鎖耗時 0 秒</strong>，搭配調校過的 vz 核心，其容器終端就緒體感比 Chromebook 的冷啟動更為順暢。
    </div>

    <h2 class="section-heading"><span class="sec-num">03.</span> macOS 本地容器執行階段（Runtime）矩陣評估</h2>
    <p>
      針對 macOS 開發環境，工具選型必須在「資源開銷」、「系統整合度」與「企業授權合規」之間取得平衡：

  <section>
    <h2 class="section-heading"><span class="sec-num">05.</span> 企業安全治理：Dockge RBAC 缺失與開源 PAM 解決方案</h2>
    <p>
      許多架構師偏愛 Dockge 的「純粹檔案目錄結構」與「直觀 YAML 編輯」，但在推向團隊使用時會面臨資安痛點：<strong>Dockge 原生沒有多租戶權限模型</strong>。
    </p>


    <h3 class="sub-heading">1. 邊界防禦模式（Reverse Proxy + Authentik）的極限</h3>
    <p>
      常見作法是在 Dockge 前方放置反向代理（Nginx / Caddy / Traefik）並串接 <strong>Authentik</strong> 或 <strong>Authelia</strong>：
    </p>
    <ul>
      <li><strong>能做到：</strong>對接公司 Active Directory (AD) / LDAP / OAuth 進行集中身分認證，強制執行二次驗證（MFA / TOTP）。</li>
      <li><strong>無法解決：</strong>這是「門禁卡」機制。<strong>一旦使用者通過驗證進入 Dockge，便擁有整個系統的最高 Root 控制權</strong>，可任意檢視、編輯、刪除全站所有的 <code>compose.yaml</code> 及環境變數機密。</li>
    </ul>


    <h3 class="sub-heading">2. 特權存取管理（OSS PAM / 堡壘機）架構解法</h3>
    <p>
      若團隊堅持保留 Dockge 的輕巧，同時必須符合企業稽核要求，最佳工程解法是引入<strong>開源特權存取管理系統（如 JumpServer 或 Teleport）</strong>，將資安控制點從「面板內部授權」轉移至「存取流程與行為審計」：
    </p>


    <div class="grid-duo">
      <div class="panel-card">
        <h4>即時權限申請（JIT Access & Approval）</h4>
        <p style="font-size: 14.5px; color: var(--c-text-secondary);">
          工程師平時無權存取 Dockge Web 介面。遇維運或改版需求時，透過 JumpServer 建立工單申請「存取 Dockge 2 小時」，主管於 Slack/Teams/AD 核准後自動開通臨時通道，過期立即撤銷。
        </p>
      </div>


      <div class="panel-card">
        <h4>全程操作錄影與鍵盤審計（Full Session Audit）</h4>
        <p style="font-size: 14.5px; color: var(--c-text-secondary);">
          使用者透過 PAM 代登進入 Dockge，<strong>所有網頁滑鼠點擊、輸入之 YAML 代碼、終端機互動均被 PAM 全程螢幕錄影並提取指令文字</strong>。發生配置錯誤或安全事件時，稽核紀錄具備法律可追溯性。
        </p>
      </div>
    </div>
  </section>
