00 · HOW IT WORKS

三個東西怎麼配合：repo、主控台、Claude Code

主控台不是教材本體，它是遙控器。教材、參考資料、起手式程式碼、助教 skills 全部在 repo 裡； 主控台負責告訴你「現在做哪一步、按哪個按鈕、把什麼貼給 Claude Code」。這一頁可以放在任何靜態主機上，所有連結都指回 GitHub。

STEP 1 · CLONE

git clone https://github.com/clarencechien/dddguide.git && cd dddguide
git checkout -b workshop/你的名字
printf 'LANG=node\n' > workshop/.config

分支名與 workshop/.config 會讓助教知道你是誰、用哪個 runtime。

STEP 2 · RUN TESTS

cd starter/node && npm install && npm test
cd starter/python && python -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt && pytest

看到 一個紅燈（R1）其他綠或 skip，就是對的。那個紅燈是 Day 4 的起點，現在不用修。

STEP 3 · CLAUDE CODE

claude

在 repo 根目錄啟動，它會讀 CLAUDE.md 變成助教。第一句輸入：

/ta 我是新學員，今天 Day 1

之後的循環：主控台按「複製提示」→ 貼到 Claude Code → 做事 → 產出放 workshop/dayN/ → /checkout dayN。

助教的三條規矩（寫在 CLAUDE.md 與 skills 裡，你可以要求它遵守）

  1. 先問後答。它會用問題逼你自己推導。你說「我卡住超過 20 分鐘」它才會給參考解或指向 solutions/。
  2. 沒有紅燈不准寫產品碼。Day 4–6 它會拒絕直接生成實作，直到你貼上失敗的測試輸出。
  3. 通用語言優先。OCPP 的字不准進 domain；聚合裡不准有 I/O；事件先記錄再由 Outbox 發。

DAY 1 · ENTRY

進場：從一個沒做過的領域開始問問題

方法論：領域入門 · 利害關係人訪談 · BPR教材 day1.md領域入門五位角色

你不需要懂充電樁。你需要的是在一個陌生領域裡，用對的問題把「人在兩套系統之間當 API」的地方問出來。今天不畫任何系統圖。

今天結束你會拿到勾選會存在瀏覽器；真正的驗收是 /checkout day1
Block 1 · 環境與領域入門90'
  1. 完成上面 00 的三步。
  2. 讀 ev-charging-primer.md（30 分鐘）：樁 / 槍 / kWh / 費率 / 總部派工 / 「場站要能在總部斷線時活著」。
  3. 讀完後用下面的提示，讓助教用問題檢查你有沒有真的懂。
Block 2 · 訪談五位角色90'

Claude 會扮演一位角色，帶著隱藏事實。你要靠問題把事實挖出來——問「你們系統有什麼功能」挖不到；問「上次出事你人在哪、手上拿什麼」才挖得到。一位 10–15 分鐘，換人前它會告訴你問出了幾個關鍵事實。

把每位的紀錄寫進 workshop/day1/interviews.md（範本在 workshop/day1/TEMPLATE.md）。寫「他說了什麼」和「他其實在意什麼」兩欄。

Block 3 · BPR：先刪交接，再談系統90'

企業流程再造（BPR）問的不是「這步怎麼自動化」，是「這步該不該存在」。先看一個示範，再做你自己的版本。

示範 · 切換 As-Is / To-Be同一條顧客旅程，看哪些角色從鏈上消失

    再造原則（本專案只留四條）

    1. 以結果為單位，不以部門為單位。顧客要的是「車能走、帳能清」，不是「兩個系統都有紀錄」。
    2. 現場擁有完整的現場交易。進場、占位、充電、離場的進行中狀態，總部讀得到，但批不准卡住閘門。
    3. 故障是一等公民流程，不是客服例外。樁說自己壞了，工單就該存在；電話只是備份通道。
    4. 對帳是事後對齊，不是同步鎖。允許短暫的兩邊數字不一致，但每筆都要有因果事件可追溯。

    BPR 課後必做

    用紅筆在 As-Is 上圈出「這一步只因為兩個系統不說話才存在」的活動。圈得到的，不准直接做成 microservice。先決定它該消失，還是該變成一個事件。

      DAY 5 · EVENT-DRIVEN
      

      事件怎麼設計：場站能離線，總部能追因果
      

      方法論：Application Service · Outbox · Integration Event · 冪等 · Process Manager教材 day5.mdeda.mdcontracts/
      

      Event-Driven 在本專案不是「全部丟進 Kafka」。它解決 BPR 留下的那條原則：跨部門的事實用事件走，跨部門的鎖用原則禁止。今天所有東西都跑在記憶體 bus 上；Day 6 才換真的持久化。

      Block 1 · Application Service 與 Outbox90'
      
  
      兩種事件，不准混名：Domain Event 是上下文內部的事實，用領域語言；Integration Event 是跨上下文的契約，穩定、版本化、經過 Outbox、永遠非同步。聚合裡不得直接打 broker（R8）。

        Q&A
        

        常見問題：學員最常卡的 16 件事
        

        這些答案也在助教腦裡（docs/ 與 skills）。這裡先擋掉最常見的，讓你把和 Claude 的對話留給真正的問題。
        

        

        我完全不懂充電樁，會不會學不到 DDD？
        不會，這正是設計。DDD 最重要的技能是「在陌生領域用問題建立語言」；如果你已經懂領域，Day 1–2 就變成默寫。先讀 領域入門 30 分鐘就夠開始訪談。
        

        TDD、DDD、Event-Driven 是三選一嗎？
        不是，它們不在同一層。BPR 決定什麼不該被自動化；DDD 決定什麼值得被模型化；事件決定邊界怎麼呼吸；TDD 決定模型明天還能不能改。順序是因果不是口味：沒有再造過的流程寫進 DDD，只會得到一個很精緻的舊組織圖。
        

        為什麼 Day 1 不能先畫系統圖？
        因為你會把「值班長打電話給總部」畫成一個 API。BPR 的工作是先決定那通電話該消失還是該變成一個事件，畫圖只會把它保存下來。
        

        Claude 一直問我問題不給答案，怎麼辦？
        那是 CLAUDE.md 規定的。你可以說「我卡住超過 20 分鐘了，給我最小提示」，它會給提示或指向 solutions/。直接要完整答案在 Day 4–6 會被拒絕，因為那會跳過紅燈。
        

        Event Storming 一個人怎麼做？
        牆變成 Markdown 表格，便利貼變成表格列，Claude 當那個一直問「這真的是已經發生的事實嗎」的引導者。/storm 會產出 storm-board.md 與 Mermaid 時間線。少了團隊的碰撞，所以要用訪談紀錄補：每一張黃貼都要能對回某位角色說過的話。
        

        「充電已開始」和「StartTransaction」差在哪？
        前者是領域事實，值班長聽得懂；後者是 OCPP 訊息，是協定細節。防腐層（ACL）負責把後者翻成前者。如果你的整合事件裡出現 transactionId、meterStart 這種字，就是 ACL 漏了。
        

        Bounded Context 一定要五個嗎？
        不一定。參考解是五個，因為它們換語言、換生命週期、換一致性邊界。你切成四個或六個都可以，但每條邊界要能用「這個詞在兩邊意思不同 / 誰要離線活著 / 不變條件不同」之一說明。/context-map 會挑戰你，不會直接判錯。
        

        Aggregate 要多大？
        Vernon 的四條：一個交易只改一個聚合、用 ID 參照其他聚合、聚合小、其他聚合用最終一致。ChargingSession 只管一把槍的一次會話；它不知道帳單，也不知道工單。
        

        領域事件為什麼不能直接 publish？
        因為交易可能回滾，事件卻已經飛出去了。聚合只 record()，應用服務在同一交易把聚合與 outbox 一起寫，relay 事後發。這就是 R8。
        

        至少一次投遞會重複，誰負責？
        消費者。Billing 用 sessionId 去重、AssetOps 用 chargerId + faultCode。Day 5 的測試會用 redeliver() 把同一事件送兩次，證明不會開第二張草稿或工單。
        

        沒有 Docker 能走完嗎？
        能。Day 6 預設 SQLite，零安裝；Postgres 是選配。其他六天完全不需要 Docker。
        

        Node 和 Python 選哪個？
        選你公司在用的那個，因為目標是帶回去。兩邊的 starter、solutions、e2e 腳本同構。不要中途換。
        

        我落後一天了怎麼辦？
        每天教材末尾有「如果你落後了」的最低可行版本。優先順序：Day 2 的規則、Day 4 的聚合、Day 6 的 e2e。Day 3 的 C4 與 Day 7 的 CI 可以壓縮。
        

        solutions/ 可以看嗎？
        可以，但規則是卡住 20 分鐘再看，而且看完要關掉自己重寫。它是參考解不是標準解；你的聚合比它多一個值物件或少一個事件，只要測試名對得上規則，就是對的。
        

        這個主控台可以放到別的地方嗎？
        可以。它是單一 HTML，沒有建置、沒有後端、沒有第三方 JS。上傳到 imitator、GitHub Pages、任何靜態主機都行；所有連結指回 GitHub repo。你的勾選只存在自己瀏覽器。
        

        回公司後第一件事該做什麼？
        不是導入 DDD。是找一條你們自己的「人當 API」的流程，做一次一小時的 Event Storming，寫三條帶例子的規則。/takeaway 會幫你排出 30 天計畫。
