# style/ — 報告的底盤與風格指引

這裡的報告不是工業化的產出，是**要說服人的文章** —— 傳一個概念、一種技術、一個看法。
所以立場是：**每一篇本來就該長得像有人做過它**，不該是同一個模板換掉文字。

`report.css` 因此不是「統一樣式」，是一副**底盤**：只固定那些不論什麼聲音都必須做對
的事，其餘全部交給寫報告的模型自己決定。

| 固定 | 交出去 |
|---|---|
| 可讀性（內文 17px 起跳、行高 1.85、量到 34 個字的行長）| 紙色、墨色、重點色 |
| 結構與間距的節奏 | 三個字面分別派給誰 |
| RWD（不橫捲、圖表與表格各自捲、tap target）| 標題多大、哪個字上色 |
| 深淺兩套配色的**契約**（值由報告自己給）| 分節怎麼標、用哪些編輯手法 |
| 動態的衛生（只做進場、只動 transform／opacity、尊重 reduced-motion、列印時關掉）| 要不要動態 |
| 圖表的色序 | — |

## 改東西的流程

```bash
node style/build.mjs          # mockup
node style/voices/build.mjs   # 六份樣張
```

改完 `report.css` 兩個都要重跑，否則範例會漂。

然後在瀏覽器開 `style/mockup.html`，**375px、1440px、深色、列印各看一次**。

## 幾個不要憑感覺改的地方

**圖表配色不是品味問題。** `--c1` 到 `--c6` 是驗證過的預設 palette。手調的暖色版本
先試過，四個顏色彩度不足會讀成灰，而 `#7a4a63↔#4a5a86` 在紅色盲下 ΔE 5.9（門檻 8）、
正常視覺 9.5（硬性下限 15）—— 一般人都分不出來。現在這組對四個底色各驗過一次。
要換先跑 dataviz skill 的 `validate_palette.js`。淺色模式下有三個系列色低於 3:1 對比，
補償是每張圖都要附 `<details class="datatable">` 表格，那不是裝飾。

**圖表畫在 640 寬的 viewBox 上、文字 12px。** viewBox 會把文字一起縮放：720 寬的圖在
375px 螢幕上標籤只剩 6px。CSS 把渲染寬度夾在 34–44rem，比下限窄就在自己的框裡橫捲。
改 viewBox 寬度就要重算那兩個界線。

**`.wide` 只用實際存在的留白來加寬。** 它刻意不用 `width` ＋ `50%` margin 那種常見的
breakout —— 那個百分比會對到錯的框，在 1440px 下把頁面推出去 80px。而且 `.wide` 一定
要宣告在其他元件之後：任何用 `margin` 簡寫的元件都會把它依賴的 inline margin 歸零。

**動態不能藏內容。** `.reveal` 用 scroll-driven animation，未進場時是 `opacity: 0`。
所以列印時必須把它整個關掉，否則整篇印出來是空白 —— `@media print` 裡那條
`animation: none !important` 是這個原因，不要拿掉。`prefers-reduced-motion` 則是靠
把整段 `.reveal` 包在 `no-preference` 裡處理的。

**字型可以在 runtime 抓，script 不行。** 樣式表不會執行程式碼，sandbox 底下那一頁也
沒有東西給它讀。只有 `X-Sandbox: off` 的頁面要連字型一起內聯。

## 中文標題的一個技巧

Google Fonts 沒有壓縮體或展示用的中文字面。把**拉丁展示字放第一順位、中文字放後面**，
拉丁字取展示字面、中文落回思源黑 —— 這樣標題有質地，而不需要一個不存在的中文展示字型。

```css
--disp: "IBM Plex Sans Condensed", "Noto Sans TC", sans-serif;
```

`mockup.html` 用的是另一種：中文標題直接上思源宋，跟內文的思源黑拉開質地差。

拉丁半邊推薦 IBM Plex —— Sans、Serif、Sans Condensed、Mono 都在 Google Fonts 上，
共用同一套骨架所以混排不打架，而且拉丁子集只要 13–30 KB。**`IBM Plex Sans TC` 不在
Google Fonts 上**（實測回 400），所以中文那半只能配思源。`IBM Plex Sans JP` 倒是有，
但**不要拿來排正體中文**：實測 26 個字裡它供應了 25 個，看起來像可以用，但字形是日文
的（令 最明顯），而且缺的那一個會在句子中間掉回讀者系統上的任意字型。

## 實測：有推導機制的維度會分歧，沒有的會收斂

拿四份不相干的素材（CI 事故、鋰電池四十年、機票早鳥、養貓三十天）各餵一次同一份
`STYLE.md`，量出來的結論很一致，而且兩輪都成立：

**第一輪**（紙色只有「不要白、不要抄樣張」這種負面規則）：四份的紙色是
`#eef1f3` `#eef1f1` `#eef1f4` `#f1eff2` —— 距離 1 到 4，肉眼看不出差別。禁令沒有讓它們
各自推導，只是把它們一起趕進「沒有被禁的那塊安全地帶」。同時沒給指引的對照組選了暖
奶油配鏽紅，比四份都有辨識度。

**第二輪**（紙色改成「先說出材質，再用 `hsl()` 寫出色相」）：色相散開成 18°／62°／
76°／352°，飽和度從 6–14% 升到 22–30%。材質敘述真的在做事 —— 「歸檔四十年的專利影本」
推得出顏色，「暖灰」推不出來。

但同一輪裡，**沒有推導機制的兩個維度反而更收斂了**：

- 重點色（規則只有「選一個，用三個地方」）四份裡三份是藍：`hsl(218)` `hsl(220)` `hsl(250)`。
- 語域四份全部變成事務性表單（工單、交接紀錄、對帳、交接單）—— 這是「說出印在什麼紙上」
  這條新規則的副作用，它把想像力導向了「這是哪一種公文」。

**第三輪**（加上 REFERENCE 具名參照物，以及 RECENT 排斥場：離最近 8 份紙色 ≥30°）：
排斥場**讓事情變糟**。四份的紙色是 128°、132°、132°、154° —— 全部落在那 8 個色相留下
的最大空隙（76°–200°）正中央，而且四份的參照物全是綠色的帳簿紙（會計總帳、工程計算紙、
航空公司分類帳、母子健康手帳）：它們先找到空位，再反推一種材質來合理化。重點色同理，
避開 162°–250° 之後有兩份撞在 348°–350°。第二輪沒有排斥場，色相反而散得比較開。

一條「避開這些」的規則給所有人同一個最佳解。所以 RECENT 改成**最後一步、只做檢查**：
材質與紙色先從內容來，之後才對最近 3 份查 15°；撞到就換材質，不准挪色相。

REFERENCE 這一步本身是有效的：四份都給出了具體到年代與頁種的印刷品，而且參照物真的
決定了字面（Plex Serif、思源宋、Fraunces）與裝置。問題只在它被 RECENT 牽著走。

**第四輪**（RECENT 改成最後一步、只查最近 3 份、撞到換材質）：紙色 45°、46°、48°、38°
—— 四輪裡最集中的一次。排斥場拿掉之後，四份沒有回到第二輪的散開狀態，而是全部回到
「舊紙」：油印講義、1981 年專利說明書、1970 年代航空時刻表、1990 年代獸醫照護單。這次的
吸引子是 REFERENCE 本身 —— 「一個真實存在、有年代的印刷品」幾乎必然是奶油色的紙。第二輪
沒有 REFERENCE，色相反而散得最開。

四輪的紙色相：

| 輪 | 規則 | 四份的色相 | 最近兩份 | 平均兩兩 |
|---|---|---|---|---|
| 一 | 負面表列 | 200° 200° 200° 280° | 0° | 40° |
| 二 | 材質 ＋ `hsl()` | 352° 62° 76° 18° | 14° | **49°** |
| 三 | ＋ REFERENCE ＋ 排斥場 | 130° 132° 132° 154° | 0° | 12° |
| 四 | ＋ REFERENCE ＋ 事後檢查 | 45° 46° 48° 38° | 1° | 5° |

每一條新規則都製造了一個新的吸引子：負面表列→冷灰、排斥場→最大空隙、具名參照物→舊紙。
**程序沒有打敗平均值，程序只是把平均值搬到另一個地方。** 四輪裡最散的是規則最少的那一輪。

REFERENCE 在其他維度是有效的（字面、裝置、眉標系統都明顯跟著參照物走），它只在紙色上
帶來偏置。這個取捨留著，不再往 `STYLE.md` 加規則 —— 下一個能試的東西不是規則，是從模型
外面給進來的數字（例如 census 直接**指派**一個色相區間，而不是讓模型選），因為只有模型
沒有發言權的地方，平均值才進不來。

所以規則的形狀比規則的數量重要：**負面表列會製造新的預設值，推導程序才會製造分歧，
排斥場會製造共同的目的地，而具名參照物會把紙色拉回它的年代。**
反過來，每加一條推導也在把自由發揮換成照表操課，四份長得像四張表格可能就是第一個症狀。
這個取捨還沒有結論。

底線那十幾項在兩輪八份裡全過（19px／1.85、深淺兩套、零第三方 script、零 storage API、
375 與 1440 不橫捲、零 console error），沒給指引的對照組則掉了六項。

> 量測方法有個坑：紙色都在亮度 91–95%，色相差 100° 在 RGB 上也只有十幾個單位。用 RGB
> 距離判斷「有沒有分開」會得到錯的結論，要看 `hsl()` 的色相與飽和度。

## 指紋：知道套了沒、套的是哪一版、選了什麼

`STYLE.md` v3 要求報告最前面帶五個 `<meta name="imitator-*">`：版本、語域、參照物、
紙色、重點色。host 在 PUT 時抽出來，存進 R2 的 metadata，`/v1/a` 的每一列回精簡版
（版本、顏色、語域與參照物各截 24 字），`PUT` 的回應則是完整的。沒帶就是 `style: null`。
不擋、不警告 —— dumb host 不該因為一個 meta 拒收。

它服務三件事：

1. **下一份報告對照最近用過的顏色**（`STYLE.md` 的 RECENT 步驟，最後一步、只做檢查）。
   `node scripts/style-census.mjs --recent 3` 會印出可以直接貼進註解的那一行。
2. **看檔案就知道是哪一版指引產的**，之後改指引可以分批比較。
3. **累積個人偏好的材料** —— 每一份選了什麼語域、參照了什麼、用了什麼紙色，全部在列表裡。
   `node scripts/style-census.mjs` 印整張表。等累積夠了，「這個人喜歡什麼」就從這裡整理，
   不用再猜。

KV metadata 有 1024 bytes 的上限，title 最長會佔掉 600，所以列表裡的指紋是縮過的；
真的塞不下就只拿掉指紋、不動 title，完整版永遠在 R2 與 PUT 回應裡。

## 已知還沒做的

指紋只存、不驗。也就是說一份寫著 `v3` 但根本沒照指引做的報告，host 分不出來 ——

## 真實世界的第一批（2026-09-02）

Grok 與 GPT 各用 `STYLE.md` v3 產了一份，這是**第一批不是我測出來的資料**，結論跟四輪
合成實驗不同，而且更好：

| | Grok（`gas-permission-denied`） | GPT（`claude-apps-script-incident-report`）|
|---|---|---|
| 紙 | `hsl(174 22% 94%)` 淡青 | `hsl(92 18% 95%)` 淡綠 |
| 重點色 | `hsl(338 58% 38%)` | `hsl(24 72% 36%)` |
| 參照物 | 1990 年代台灣電信機房障礙申告單第二聯 | 1990 年代企業機房的連續報表紙 |
| 指紋 | 五個 meta 齊全、與 CSS 一致 | 同左 |

兩份的紙色相差 **75°**、重點色差 46°，比我四輪實驗裡任何一輪都散。同一題材、同一份
指引、不同模型，反而自然分歧 —— 合成實驗用的是我現寫的四份素材，題材本身太像，那才是
第四輪擠成一團的一部分原因。**跨模型 ＋ 真實題材的分歧，比任何一條規則都有效。**

參照物也真的做到了視覺推導：GPT 那份在背景畫了連續報表紙的橫線，Grok 那份用了申告單的
欄位框與拒辦戳。這是 REFERENCE 這一步最好的證據。

### 它們找出一個底盤的 bug

`gas-permission-denied` 在 320／375／414 都會橫向捲動，量到 375px 螢幕上頁面寬 534px。
原因不是模型寫錯，是**底盤沒有防住的一個 CSS 陷阱**：報告自己寫了
`grid-template-columns: 1fr`，而 grid track 的預設最小寬度是 min-content，格子裡一個
`<code>https://www.googleapis.com/auth/…</code>` 沒有斷行點，就把 track 撐到比視窗還寬。

底盤補了兩條（實測 320/375/1440 都乾淨）：

- `:not(pre) > code { overflow-wrap: anywhere }` —— 從源頭消滅那個 min-content。
- `.cols > *, .tiles > * { min-width: 0 }`，並在 `STYLE.md` 的底線寫明自己寫的 grid 要用
  `minmax(0, 1fr)`。

另外記一筆：GPT 那份 666 KB，其中 633 KB 是一張內聯的 base64 PNG 截圖。沒有違反任何規則
（上限 25 MB），但值得知道 —— 指引目前對圖片重量沒有任何說法。

### 三個懸而未決的決定（都是你的，不是我的）

1. **重點色與語域要不要也補推導。** 目前只有紙色有。第四輪的重點色散得不錯
   （268°／268°／214°／172°），語域則因為 REFERENCE 的關係全部偏向事務性文件。
   加規則的代價見上面那張表 —— 每一條都生一個新的吸引子。
2. **要不要改用「指派」而不是「選擇」。** 唯一還沒試、而且性質不同的做法：census
   直接給一個色相區間（例如上一份 ＋ 137.5° 的黃金角），模型只在區間內依材質微調。
   這會讓紙色不再從內容推導，改變了「依內容選聲音」的定義，所以我沒有動。
3. **`policy.js` 要不要檢查指紋。** 現在不檢查（決定過的：回 warning、不擋）。
   採用率因此還是量不到。
