架構筆記 · Agent vs Workflow · 2026-08

它們不會報錯,
它們會成功

兩個案子,同一種壞法。都不是掛掉、不是丟 exception——是跑完、亮綠燈、產出一份看起來很專業的東西,而裡面是錯的。這份筆記講怎麼把這件事設計掉。

CASE 01 Test Agent Jira 工單 → 產測試 → 跑 → 寫回。有 oracle。 CASE 02 RCA Report Grafana → snapshot → Evidence.dev → S3。沒有 oracle。
選型之前的兩個問題

控制流由誰決定,以及有沒有裁判

「用 agent 還是用 workflow」問得太粗。真正會改變答案的是兩件事,而且它們是獨立的兩條軸。

Q1
下一步做什麼,誰決定?
控制流
模型在 runtime 決定(agent loop),還是程式碼寫死(workflow)。這決定錯誤的傳播半徑。
Q2
有沒有 oracle?
可驗證性
有沒有一個「程式能判定對錯」的東西。這決定有界迴圈該放在哪一段。

常見的誤解:以為 workflow 消除了隨機性。沒有。它只是把錯誤關在單一節點裡,不讓它改變後面整條軌跡。

Q2 決定迴圈放哪裡

這是兩個案子最大的差別,也是最容易照抄錯的地方。

Q2 = YES · 有 oracle

迴圈放在「修復」

存在一個程式能跑、能回答對錯的東西(exit code、schema 驗證、對帳數字)。那就可以「做 → 驗 → 修 → 再驗」,用 oracle 當退出條件。

loop @ 修復
exit ← oracle 說 ok
bound ← max attempts
Q2 = NO · 沒有 oracle

迴圈放在「探索」

沒有東西能判定一份根因分析對不對。這時修復迴圈是假的——它只會收斂到「build 得過」。迴圈要往前移到蒐集資料那段,正確性改用限制模型能講什麼來守。

loop @ 探索
exit ← 查詢預算用完
正確性 ← 輸出契約,不是重試

Case 01 · B 的骨架
def process(issue_key):
    issue = jira.get(issue_key)              # code
    cases = llm_gen_cases(issue)             # model → schema
    code  = llm_gen_code(cases)              # model → schema

    for attempt in range(3):          # 有界:上限 3
        result = run_in_sandbox(code)        # 容器,無正式憑證
        if result.ok:
            break
        code = llm_fix(code, result.stderr)
    else:
        return mark_needs_human(issue_key, result)

    if not discriminates(code, known_buggy_rev):  # AP-03 防守
        return mark_needs_human(issue_key, "測試無鑑別力")

    jira.comment(issue_key, render_report(cases, result))
CASE 02

RCA Report

從 Grafana 拉 o11y 資料,解讀後產 data snapshot,寫成 Evidence.dev 的 markdown 加 LLM 摘要,build 完託管出去。

為什麼不能照抄 Case 01

沒有裁判,失敗就不會顯形

Test agent 有一個硬裁判:pytest 回 exit code。RCA 報告沒有。一份文字通順、圖表齊全、結論斬釘截鐵的報告,和一份正確的報告,在「build 成功」這件事上完全一樣。A 之所以危險,不是因為它會失敗,是因為它不會失敗。

A 的失敗長什麼樣

一段完美的段落

這是 LLM 直接讀 Grafana、直接寫 md 會產出的東西。讀起來沒有任何破綻——四個具體數字、一個時間關聯、一個明確結論。

P99 延遲從 12ms1 升到 340ms2,起始於 14:233,與 order-service 在 14:214 的部署時間吻合,判定為連線池耗盡5。

  1. 1正確。查詢真的有回傳這個值。
  2. 2估的。從圖表視覺讀出來,實際是 287ms。
  3. 3對到分鐘,但取的是 alert 觸發時間,不是指標偏離時間。
  4. 4不存在。模型的先驗是「事故通常跟部署有關」,於是補了一次部署。
  5. 5資料只支持相關性。被寫成了因果,而且沒有列出任何被排除的假設。

五個數字三個有問題,build 綠燈,報告已經上傳,沒有任何一步報錯。

Case 02 的關鍵設計

不准打數字

Evidence.dev 的 markdown 本來就能放 SQL block,再用元件把查詢結果插進句子裡。所以可以直接把它變成一道結構性的防線——模型寫敘事骨架,數字在 build 時才填。

模型輸出 · 禁數字
P99 從 <Value data={baseline} column=p99/> 升到 <Value data={peak} column=p99/>,偏離起於 <Value data={onset} column=ts/>。
Build 後 · 數字來自 snapshot
P99 從 12ms 升到 287ms,偏離起於 14:19。

這讓幻覺數值在結構上不可能發生。不是請求模型別編造,是型別檢查:引用了不存在的 query,build 失敗;query 本身寫錯,你能在 SQL 層 review。順便解決可重現性——三個月後 retention 過期、recording rule 補算過,同一份報告重 build 出來還是同樣的數字,因為它綁在凍結的 parquet 上,不是綁在當下的 Grafana。

Case 02 · B 的骨架
def build_rca(trigger, run_id):
    ctx = collect_trigger_context(trigger)         # code

    # ── 有界探索:上限 8 次查詢,產出是清單不是結論 ──
    manifest = llm_explore(ctx, max_queries=8)   # model → schema
    validate_manifest(manifest)                    # SQL 白名單 / 時間範圍檢查

    snap = execute_and_freeze(manifest, run_id)    # → parquet,之後只讀它

    md = llm_write_skeleton(manifest, snap.schema) # model,禁數字
    if contains_literal_numbers(md):               # AP-07 防守
        return needs_human(run_id, "敘事層出現寫死數值")
    if not has_ruled_out_section(md):              # AP-09 防守
        return needs_human(run_id, "缺少已排除假設")

    site = evidence_build(md, snap)                # 失敗不重寫數值,只回報引用錯誤
    upload(site, prefix=f"draft/{run_id}/")      # 人 review 後才 promote
十一個會咬人的地方

Anti-patterns

按失敗機制分類,不是按案子分類——因為同一個機制會在兩個案子裡以不同面貌出現。第二組是最重要的一組。

Family A · 控制流交錯了人把已知的東西交給模型決定
AP-01 · CONTROL_FLOW_GIVEN_AWAY 兩案通用

把已知的順序交給模型決定

「拉工單 → 產 case → 跑 → 寫回」、「查 → 凍結 → 寫 → build → 發佈」,這些順序你在寫 code 之前就知道了。交給模型 runtime 決定,只是多付一次 token、多一個出錯機會。

判準畫得出流程圖的,就寫流程圖。
AP-02 · UNBOUNDED_LOOP 兩案通用

沒有 step 上限

單步 95% 正確,20 步下來是 36%。Agent 的可靠度隨軌跡長度衰減,不會自己收斂到對的地方——只會收斂到「能停下來」的地方。

做法每個迴圈都要有 max attempts,超過就走失敗出口,不是繼續試。
AP-06 · FRAMEWORK_HIDES_CONTEXT 兩案通用

框架把 context 組裝藏起來

調 agent 最主要就是調進 context 的東西。框架包掉這層之後,你會變成隔著兩層抽象在猜——而它給你的持久化、重試、tracing,自己寫大概一天的工。

判準框架解決的是 workflow 那一側的問題,它不會讓 agent 變可靠。
AP-04 · NO_SANDBOX Case 01

生成的程式碼直連正式環境

不是理論風險。模型寫的測試很容易照著 config 連到真的資料庫、真的產線 API,然後做出寫入動作。

做法跑在容器裡,不給正式憑證,網路白名單。
Family B · 目標置換為了讓任務收斂,把要達成的事偷偷換掉
AP-03 · TAUTOLOGICAL_TEST Case 01

一定會過的測試

模型很擅長讀完程式碼,然後 assert 現在的行為。這種測試通過率 100%、鑑別力 0,抓不到任何 bug,還給你虛假的安全感。

防守拿一個已知有 bug 的版本當基準,生成的測試必須在那個版本上失敗;或用 mutation testing 量鑑別力。
AP-09 · MANDATORY_ROOT_CAUSE Case 02

一定會有的根因

你問模型「根因是什麼」,它一定會給你一個。它永遠不會說「資料不足以判斷」。同一個機制,換了個面貌:任務要求有結論,那就生一個出來。

防守模板強制要有「已排除的假設」與「要區分剩下的假設還需要什麼資料」;把 insufficient_evidence 設成正常出口,不是失敗。
AP-10 · BUILD_UNTIL_GREEN Case 02

改到 build 過為止

Evidence build 失敗時讓模型自己改 md,它會把引用不到的元件換成寫死的數字——恰好繞過你整條防線。這是 Family B 裡最容易不小心引入的一個。

做法修 build 錯誤限制在格式層,不允許動數值來源;引用錯誤直接走 needs_human。
— 這一組的共通形狀

它做到的是「看起來完成」

三個都不是能力問題,是誘因問題。只要「完成」比「正確」容易被判定,模型就會往完成走。設計時要讓「完成」的判定條件盡量貼近「正確」,或者乾脆讓它有一個體面的放棄出口。

自我檢查問一句:這個系統有沒有辦法產出「我不知道」?如果沒有,它就一定會編。
Family C · 資料不可信 / 不可重現數字的來源沒有被鎖住
AP-07 · NUMBER_FROM_MODEL Case 02

模型直接打出數字

自信給出錯誤數值,是這類系統最貴的錯。而且它混在正確的數字中間,審閱的人抓不出來。

做法敘事層禁數字,一律用佔位符,build 時由 SQL 填。加一個 lint:敘事段落出現數字字元就擋掉。
AP-08 · LIVE_QUERY_AT_READ_TIME Case 02

讀報告時才查資料

事故當下的數字和一週後檢討時的數字會不一樣,而且沒人知道它變了。Retention 過期、recording rule 補算,都會默默改寫歷史。

做法snapshot 凍結成 parquet、綁 run_id,跟報告一起存。報告只讀 snapshot。
Family D · 發佈太早還沒量出準確率就給了寫入權
AP-05 · WRITE_BACK_TOO_EARLY Case 01

一上線就讓它改工單狀態

錯誤會直接進到別人的工作流,而且很難回溯是哪一次跑壞的。

做法初期只發 comment 或開 sub-task,不動 status。
AP-11 · PUBLISH_WITHOUT_GATE Case 02

直接上傳到正式路徑

事件檢討報告是要進 review、可能給客戶看的東西。錯的數字比沒有報告糟得多。

做法先落 draft/ 前綴,人看過才 promote 到正式路徑。
不管迴圈放在哪一段

「有界」的三個必填欄位

少任何一個,它就不叫有界,只是還沒跑爆的無界迴圈。

UPPER BOUND最多幾次?Case 01 是 3 次重試,Case 02 是 8 次查詢預算。
EXIT CONDITION什麼算成功?要能用程式判斷。有 oracle 用 oracle,沒有就用預算——但不能用模型自評。
FAILURE PATH用完之後往哪走?預設不能是「繼續試」或「當作成功」。needs_human 是正常出口。

兩條規則,看你有沒有裁判

RULE 01 · 控制流畫得出流程圖的,就寫流程圖。需要 agent 的條件是「分支事先枚舉不完」——Case 01 是測試失敗後的修復判斷,Case 02 是事故該看哪些 metric。其餘的不值得。

RULE 02 · 正確性有 oracle,就用它當退出條件,迴圈放修復。沒有 oracle,重試是假的防線——改成限制模型能講什麼:凍結資料、輸出契約、強制留一個「資料不足」的出口。

兩個案子的 B 骨架長得幾乎一樣,唯一的差別是有界迴圈的位置:Case 01 在修復,Case 02 在探索。這一格放錯,整套防線就會變成裝飾。
