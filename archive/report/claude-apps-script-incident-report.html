00 · CASE FILE

DIAGNOSIS / NOT A GAS LIMIT

不是 Apps Script 不能改，
是 Claude 當時沒有路

你截圖裡那句「Google Drive API 只能讀、瀏覽器又 Permission denied，所以只能請你貼上」描述了當下的困境，但把「當下沒有可用工具」說得像「Google 本身不允許自動修改」。真正的始末，是兩條不同的存取路徑同時斷掉。

事件重建 · 依 Google Apps Script API / clasp 官方文件、Anthropic Chrome 權限文件與已回報 regression 整理 · 2026-09-02

01 · WHAT ACTUALLY HAPPENED

先把「Claude」拆成三個不同角色

這種問題最容易誤判，是因為畫面上看起來都叫 Claude，但背後其實可能是三種完全不同的執行面：

A · CONNECTOR

Google 連接器

能做什麼，取決於產品暴露了哪些 API action，不等於 Google API 全能力。

B · BROWSER AGENT

Claude in Chrome

靠讀頁、截圖、點擊與頁面操作；另外受到 Claude 自己的安全與站點權限層控制。

C · LOCAL AGENT

Claude Code + CLI

如果本機有 clasp / Git / OAuth，根本不需要碰 Apps Script editor 的網頁。

同一個「幫我改 Apps Script」要求，走 connector、走 Chrome、走 CLI，是三條完全不同的路；其中一條失敗，不能推論另外兩條也做不到。

02 · THE TWO BROKEN ROADS

截圖當下，兩條路剛好都斷了

第一條路的關鍵不是「Google Drive API 是唯讀」。Drive API 本身當然可以對一般 Drive 檔案做寫入；真正要說的是：Apps Script 專案的程式碼不是應該靠一般 Drive 檔案寫入介面去改的，Google 有獨立的 Apps Script API。更進一步，Claude 當時所拿到的 Google connector 也可能只暴露讀取類 action，因此對那個 Claude session 而言確實「沒有寫入工具」。

第二條路則是 browser agent。Anthropic 的 Claude in Chrome 有自己的 permission / safety layer；它不是只看 Chrome 擴充套件的「Site access」。2026 年已有公開 issue 回報：在 script.google.com 上，screenshot、read_page、javascript_tool 等操作全部回傳 Permission denied for this action on this domain，而且使用者把 Chrome extension 設成「All sites」也沒解掉。這正好和截圖症狀吻合。

這裡要保留一個重要限定

公開 issue 能證明「確實發生過這種 regression / domain block」，不能證明 script.google.com 在所有帳號、所有版本、現在此刻都永久被封。截圖最合理的解讀是：那個時間點、那個 Claude 執行環境，browser route 被擋。

03 · WHAT THE SCREENSHOT GOT WRONG

哪一句對，哪一句容易誤導

截圖中的說法判定更精確的版本
「我沒辦法直接連進去改」當下合理如果該 session 沒有 Apps Script API write action，而 Chrome route 又被擋，Claude 的確沒有可執行路徑。
「Google Drive API 只能讀取」表述不精確Drive API 不是整體唯讀。應說「目前這個 connector 對 Apps Script source 沒有寫入 action；而 Apps Script source 的正式寫入介面是 Apps Script API」。
「不能寫 Apps Script 程式碼內容」若指 Drive connector，合理Google 官方 Apps Script API 明確有 projects.updateContent，可以直接覆寫專案 source。
「瀏覽器互動持續 Permission denied」有公開佐證Anthropic GitHub issue #48960 回報過 script.google.com 的同樣錯誤；Anthropic 官方也說 Claude in Chrome 有獨立 permission mode、站點權限與組織 allow/blocklist。
「所以只能請你手動貼」只是 fallback若只允許 connector + browser，這是可行 fallback；但工程上還有 Apps Script API / clasp 兩條更好的路。

04 · THE API THAT WAS MISSING

Google 其實有正式的「直接改 GAS」介面

Apps Script API 的 v1.projects resource 包含 getContent 與 updateContent。其中 updateContent 使用：

PUT https://script.googleapis.com/v1/projects/{scriptId}/content
OAuth scope: https://www.googleapis.com/auth/script.projects

它不是「模擬按鍵貼進 editor」，而是直接更新 script project 的 source。Google 文件明確指出：這次更新會成為目前的 HEAD；request 裡帶的是整個 files[]，而且既有檔案會被清掉再以提交內容取代。因此它本質上更接近「整包 project sync」，不是細粒度的單檔 patch。

這也是為什麼 agent 直接呼叫 updateContent 要非常小心

如果你的 agent 只抓到一個 Code.gs 就送 updateContent，其他檔案可能被清掉。安全流程應該是：先 getContent → 在完整 project snapshot 上改 → diff / review → 再 updateContent。

05 · WHY CHROME "ALL SITES" WASN'T ENOUGH

Chrome 權限與 Claude 權限不是同一層

Anthropic 官方現在描述的是多層 permission model：Manual、Auto、Skip 三種模式之外，還有特定網站需要額外批准、某些 action 永遠要 explicit permission，以及 Team / Enterprise 的 allowlist、blocklist 與角色控制。也就是說：

所以「我已經把 Chrome extension 設成 All sites」只能證明瀏覽器擴充套件有 host permission，不能保證 Claude 的 browser tool 一定會執行該站操作。

06 · THE BETTER ENGINEERING PATH

如果目標是讓 Claude 長期維護 Apps Script，別把 browser editor 當主路

推薦順序：Git + clasp → Apps Script API connector/MCP → browser automation → 手動貼上。
越往右，越容易被 UI、權限層、DOM 改版與人工步驟影響。

A. Claude Code + clasp：最接近正常軟體開發

Google 的 clasp 就是為「在本機而不是 Apps Script editor 開發」設計。現行 clasp 可以 clone / pull / push、建立版本、建立與更新 deployment；而且 Google 官方文件直接把 Git workflow 與 CI/CD 當成使用方式。

# current clasp v3-style commands
npx @google/clasp login
npx @google/clasp clone-script <SCRIPT_ID>

# Claude Code edits .gs / .html / appsscript.json locally
npx @google/clasp show-file-status
npx @google/clasp push

git diff
git commit -am "fix: ..."

這條路的價值不是「比較酷」，而是 agent 看到的是正常檔案、Git diff 與測試結果，而不是網頁編輯器的畫面。它可以 review、rollback、PR、CI，也不再依賴 script.google.com 能不能被 browser agent 點。

B. 自建 Apps Script API tool：適合真的要 agent remote-edit

如果你不想讓 agent 有整個本機 shell，也可以把 Apps Script API 包成受控 tool：例如 get_project、propose_patch、update_head、create_version、redeploy。這時可以把「只允許特定 scriptId」「更新前必須驗證完整檔案清單」「production deploy 需要人類批准」寫進 tool 層，而不是靠 prompt 約束。

C. Claude in Chrome：適合 UI-only 工作，不適合當 source control

browser agent 適合處理「只有 UI 才有的設定」或一次性的操作；把它當長期程式碼同步管道，等於把 CI/CD 建在滑鼠點擊上。只要站點 policy、DOM、登入狀態或安全 classifier 改一下，整條流程就會斷。

07 · THE PRODUCTION TRAP

clasp push 成功，不代表正式 Web App 已更新

這是另一個很常踩的坑。Apps Script 有 HEAD 與 versioned deployment 的差別：HEAD 永遠跟目前保存的 code 同步，適合測試；正式對外 deployment 通常綁定某個 immutable version。也就是：

只 push 到 HEAD，測試環境可能已看到新 code，但既有的 versioned web app deployment 仍然留在舊版本。真正的 release pipeline 要把「同步 source」與「發布 version」分開看。

08 · RECOMMENDED CONTROL PLANE

一個比較不會「AI 改壞正式環境」的流程

  1. Repo 是唯一 source of truth。 一旦導入 clasp/Git，就盡量不要再讓人直接在 Apps Script editor 手改，避免 remote drift。
  2. Dev / staging / prod 分專案。 每個環境用不同 Script ID；不要讓「測一下」與「正式」共用同一 HEAD。
  3. Agent 只改 branch。 先 lint / unit test / static check，再產生 diff。
  4. Push 只到非正式環境。 PR merge 後才允許 production push。
  5. Release 明確建 version。 版本描述帶 commit SHA，讓 GAS version 能反查 Git commit。
  6. Production redeploy 要 approval。 把「改 code」與「讓使用者看到」切成兩個權限。
  7. 避免 blind --force。 clasp / Apps Script API 都是 project-level sync 思維；先確認 remote/local 差異，避免整包覆蓋錯專案。

09 · FINAL DIAGNOSIS

所以，這個 Facebook case 到底發生什麼？

最完整、也最公平的說法是：

Claude 沒有「能力上不會改 Apps Script」；它是「那次對話沒有拿到能寫 Apps Script source 的工具」。

Google connector 那條路沒有 Apps Script write action；Claude in Chrome 那條路又在 script.google.com 遇到 domain permission deny。兩條可見工具都失敗後，Claude 才退回要求人手貼 code。這個 fallback 在當下合理，但若因此推論「Apps Script 不能被 AI / API 直接改」就是錯的。

真正該修的不是「怎麼讓 Claude 更會點 Apps Script editor」，而是把 Apps Script 從一個網頁編輯器，升級成一個有 Git、版本、部署與審批邊界的軟體專案。
