00 · 前情

兩個問題、四個格子、一個棘輪

接回 VOL.1 兩條軸：Q1 控制流由程式碼決定（workflow）還是由模型在執行期決定（agent loop）；Q2 可驗證性有沒有 oracle——能客觀判定對錯的機制。有 oracle 用 oracle 當退出條件；沒有就限制模型的表達空間：凍結資料、綁契約、強制「資料不足」出口。

接回 VOL.2 兩軸交出四格：CELL A 可枚舉＋有 oracle（純流程引擎）、CELL B 可枚舉＋無 oracle（輸出契約守護）、CELL C 不可枚舉＋有 oracle（agent loop 主場）、CELL D 不可枚舉＋無 oracle（禁區，拆成兩段 B）。有界迴圈的四元組：上界、退出條件、失敗路徑、學習路徑——第四欄空著，系統永遠停在第一天。Harness 在那篇獨立成族：不決定對錯，只決定錯了多貴。

這一篇把 harness 這一族攤開來看：2026 年每家都在賣它，賣的是什麼、綁的是什麼、你手上那份自製的到底算什麼。

01 · 三個詞，三個問題

Harness 不是第三種控制流

Microsoft Agent Framework 把三個東西排成一列：Agent 是 intelligence，Harness Agent 是 intelligence 加上長任務的營運能力，Workflow 是 explicit orchestrationL4。排成一列很好記，但那是產品目錄的排法。照分類學，這三個詞回答的是兩個不同的問題：

詞回答的問題對回本系列誰決定
Workflow
predefined code paths		控制流誰決定？Q1 的一個答案程式碼
Agent
LLM directs its own process		控制流誰決定？Q1 的另一個答案模型
Harness
context · tools · state · constraints · permissions · tracing · recovery		錯了多貴？VOL.2 獨立成族的那一層殼——包在任一種 loop 外面

前兩行是 Anthropic 2024 年底的原始定義：「Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents … are systems where LLMs dynamically direct their own processes and tool usage.」L2 第三行的七個名詞來自 Harness-Bench：harness 是負責 context、tools、state、constraints、permissions、tracing、recovery 的系統層，論文的結論是 agent 能力應以「模型＋殼」的組合為單位報告，不能只歸給模型L3。Anthropic 自己給 Managed Agents 下的定義是同一件事的白話版：「決定何時呼叫工具、如何管理 context、如何從錯誤復原的內建協調層」L1。

Workflow 與 agent 是 Q1 的兩個答案；harness 不在 Q1 軸上。任何 loop 都有殼，差別只在殼是誰寫的、多厚。

還有一句值得記下：Anthropic 在 2026 年 3 月那篇長任務 harness 的文章裡寫，「harness 的每一個元件都編碼了一個『模型自己做不到』的假設，這些假設值得被壓力測試」——同一篇說 Opus 4.5 需要 context reset，Opus 4.6 已不需要L2。這直接接回 VOL.2 的歸因謬誤：模型變強會讓某些殼失效，但有一層不會——oracle 那一層。測試、schema、預算上限是對世界的假設，不是對模型的假設。這是本篇要守的線：殼可以買，別把 oracle 也外包給殼。

表裡真正分出高下的不是功能——大家都有 loop 上限、都有 HITL、都有 compaction——而是三條鎖定軸：

  1. 模型軸：Claude SDK 只跑 Claude；OpenAI SDK 能接別家但 structured output 與 tracing 都會掉功能；LangGraph、ADK、MAF 任意。
  2. 平台軸：追蹤（OpenAI Traces、LangSmith）、記憶（Vertex Memory Bank、Managed Agents memory store）、compaction 端點（OpenAI）——每一項都是一條回不去的路。
  3. 狀態軸：狀態在檔案／git（人讀得到）還是在 checkpointer DB（只有程式讀得到）。

第三條直接接 VOL.2 的第四欄位。如果 harness 的狀態只活在框架的 checkpointer 裡，人查明後要回寫的 template、規則、新查詢沒有地方可以落——棘輪轉不動。Anthropic 長任務 harness 的做法（progress 檔、feature list JSON、每 session 一個 git commitL2）之所以合理，是因為狀態同時給程式恢復用、也給人審與回寫用。

被低估的一格：恢復語意是「至少一次」

LangGraph 的 interrupt 文件寫明恢復時節點從頭重跑，interrupt 前的副作用必須冪等；ADK 的 resume 文件明言工具可能重複執行L1。所以 workflow 裡每個有副作用的節點——寫工單、發通知、上傳——要嘛冪等，要嘛放在 interrupt 之後。這對應 VOL.1 的 Family D「發佈過早」：框架的 durable 不會幫你擋，只會讓你重複發佈。

L4 的聲音——只能當「有人這麼說」

LangGraph：「框架本身成了我們必須理解的問題」，非線性執行難除錯、序列化與 checkpoint 藏了複雜度、多數企業流程其實是線性管線；「改一個 prompt 就得維護型別、節點簽章、圖拓樸」。OpenAI Agents SDK 0.13→0.17：19 個版本、三個破壞性變更，其中兩個是靜默行為改變（預設模型悄悄換、沙箱路徑限制）。ADK 2.0 升級：新欄位未先加，「容器健康、聊天全掛」。三條都是個人文章，日期與細節見來源區。

04 · 手刻那一份

你沒有手刻 harness，你手刻的是排程與記憶格式

把 cron + claude -p + md + git 對回 Harness-Bench 的七個要件：

  • contextCLAUDE.md、md 記憶檔、Auto memory
  • toolsClaude Code 內建：Read／Edit／Bash／Grep／WebFetch／subagent
  • statemd 檔——人讀得懂的那種
  • constraints--allowedTools、--max-turns、--json-schema
  • permissions--permission-mode，六種
  • tracing--output-format json 帶 total_cost_usd、num_turns
  • recoverygit——掉了就重跑

七項全齊

所以「我要不要手刻 harness」的答案是：你沒有手刻 harness。殼是 Claude Code 的，你手刻的只有排程（cron）與記憶格式（md＋git）。這正好是 Anthropic 官方長任務模式的極簡版：initializer 建進度檔與初始 commit，coding agent 每 session 推進並以描述性 commit 收尾，功能清單用 JSON 標 passing／failing，並明令「移除或編輯測試是不可接受的」L2。你少的是 initializer 那一步，多的是人在每次之間讀 md。

手刻那一份的價值在狀態是人讀得懂的（第三條鎖定軸），代價是綁 Claude（第一條）。第二點在雲端可用的專案上是零成本，在地端場景會變成硬牆——第 06 節。

  1. 先問 CELL（Q1 × Q2），不先問框架。

06 · 工廠版

三條鎖定軸在地端全部收緊

前提：地端、外網受限、正在評測地端模型能否局部取代雲端模型、可觀測性全地端、資安審批嚴，主要任務型態是事件檢討與根因分析。

  1. 模型軸：Claude Agent SDK 官方不支援非 Claude 模型。若地端模型是硬需求，Claude SDK 直接出局；OpenAI SDK 能接 OpenAI-compatible 端點，但 structured output 常不可用——而 CELL B 的契約正靠它——所以也只能算半個選項；剩 LangGraph、ADK、MAF 三家。
  2. 平台軸：OpenAI Traces 預設上雲且 ZDR 不可用；LangSmith 自架需 Enterprise；Vertex Memory Bank 綁 GCP。地端只剩 OpenTelemetry——三家都有，差在要不要自己接線。
  3. 狀態軸：事件檢討本來就要人審與回寫，狀態應在 md／git／物件儲存這類檔案，不在框架 DB。

事件檢討是 VOL.1 Case 02 的原型：CELL D 拆成 B 兩段。工廠版的特殊處是量測涵蓋率（VOL.2 RULE 03）：產線裝置的資料面（log、metrics、事件）遠大於儀表板面，Unknown-Known 帶的探索才有價值；預算解不了沒埋點的問題。

給工廠的殼規格，不指名框架：模型可換（地端／雲端雙跑）、OTel 追蹤、HITL 走既有審批（工單系統）、狀態落地端檔案、每次執行產出可 diff 的 manifest、副作用節點冪等。用這張規格去挑，不是用「哪家 GA 了」去挑。

出發前的雷區——社群回報，L4

  • MAF：OpenAI-compatible 供應商在 tool call 後續請求丟失 reasoning_content，reasoning 模型的 tool loop 直接失敗（issue #8382，2026-09-15，修正 PR 中）——地端 Qwen3 這類模型要先驗這條。RedisHistoryProvider 的 key 忽略 source_id，同 session 兩個 provider 會互相覆寫（#7471）。
  • LangGraph：Postgres checkpointer 無內建 TTL，社群回報 checkpoint_blobs 一週 56 MB，要自己排程清理或只在 supervisor graph 掛 checkpointer。vLLM＋Qwen2-VL＋ToolStrategy 回 400 的 issue（#35758）仍 open。本地模型的 tool arguments 有回巢狀 dict 而非 JSON 字串的案例，deepagents 內建 filesystem 工具對本地模型不穩。
  • ADK：升 2.0 順序必須是「先補 input_transcription／output_transcription 欄位 → 改 async URL → 部署」，反了就「health check 200、每回合 500」。adk migrate session 在 1.22.1 反而要同步驅動 URL（#4176）。FileArtifactService 2.8.0 有 user_id 含 / 的路徑穿越問題（#7067），地端要自己清洗 user_id。
  • 三家共用：vLLM 的 tool parser 要對模型；Llama 3 不支援平行 tool call；許多模型要自訂 chat template。這層不在任何框架裡，在你的推論伺服器。

比完之後，「MAF 文件沒寫狀態存哪」這句要收回：harness 概念頁沒寫，但 session、context-providers、planning-and-todos 三頁寫得很清楚——history 走 HistoryProvider、todo 走 TodoFileStore、file memory 走 FileSystemAgentFileStore，全部可以落本機檔案，唯一缺的是現成的 Postgres／SQLite history provider。

三家地端的手工量與可信度，分開排：

  • 殼的手工量：MAF 最少（一顆包完，補一個 history provider 約兩個方法）；ADK 次之（session 用 DB service，但記憶層整個自寫）；LangGraph 最多（checkpointer＋store＋summarization＋deepagents 四件自己組）。
  • 地端可信度：LangGraph 最高（core 承諾相容、Postgres 路徑最多人走過）；ADK 次之（可行，但三次 DB schema 變動是實打實的雷）；MAF 最低——不是不能，是 harness 兩個月大、周邊套件全在 pre-release，路上沒人走過 vLLM 這條。

修正後的暫定推薦：第 07 節的 scope 是 CELL B，workflow 自己寫、殼很薄，所以框架差異被壓到最小；W4 換殼的候選維持 MAF 與 LangGraph 兩條，ADK 排第三——記憶層自寫加上 DB 遷移史，在地端的性價比輸給前兩者。真正決定勝負的是上面那條「三家共用」：地端模型經 OpenAI-compatible 端點的 tool calling 與 JSON schema 品質，W2 用薄殼先量，量出來再談 W4 換誰。Claude SDK 留給雲端可用的專案。

07 · 開始實作

第一個 scope 選 CELL B，四週

不選 CELL C——那格買殼就好，沒東西可學。不選 CELL A——沒有 LLM 決策。CELL B 才會逼你把前兩篇的每一條規則變成程式碼：凍結、契約、needs_human、回寫。具體就拿 VOL.1 Case 02 的 RCA 或工廠的事件檢討。語言 Python。

  1. 只寫 workflow。純 Python，LLM 節點先用假函式；跑通 snapshot → 契約 → build → draft/。沒有任何 agent。這一週結束時，整條流程不接模型也能跑完、能 diff。
  2. 把探索段換成 bounded loop。用 claude -p --json-schema --max-turns 8 --output-format json 當最薄的殼；輸出受限 manifest；cost 與 turns 自 JSON 落檔。這就是「自製」那一欄的實體。
  3. 接 needs_human 回寫通道。人查明後的結論以 md／規則檔落地並 commit；開始記三帶比例（決定性／契約／未知）。四元組第四欄從這週起不是空的。
  4. 換殼，其他都不動。把 W2 的薄殼換成候選框架的 harness（MAF 或 LangGraph），workflow、契約、回寫全部原封不動，然後 diff 兩版：多了什麼、鎖了什麼、狀態還讀得到嗎、副作用有沒有重跑。這個 diff 是 VOL.3 的實測段，跑完補在這裡

量測從第一天記：每次執行的 turns／cost、needs_human 次數、回寫後轉出未知帶的案型數。沒有這三個數，第 100 次跟第 1 次的差算不出來，RULE 04 就只是一句話。

08 · 規則與反模式

RULE 05–06、AP-16–20

RULE 05 · 買殼、寫流程、借迴圈
Harness 買現成的；workflow 永遠自己寫——它是業務邏輯，也是各家最不穩定的 API 面；agent loop 從殼裡借，不自己寫。
RULE 06 · 鎖定看三軸
模型、平台、狀態存放。挑殼先答這三題，再看功能表。
AP-16 · DSL 稅
把一條 for-loop 改寫成框架的圖，只為了「有用框架」。
AP-17 · 尾巴搖狗
為了某家 harness 換模型或上雲。
AP-18 · 狀態只活在 checkpointer
人讀不到、回寫不進去，第四欄位形同空白。
AP-19 · 追 0.x
把生產流程綁在明示「Y 版可破壞相容」的框架版本上。
AP-20 · durable 當成 exactly-once
恢復重跑導致重複發佈。冪等，或放在 interrupt 之後。

四元組的四個欄位都在 workflow 層，不在殼裡——殼給你 max_turns 那個參數，值是你填的。
