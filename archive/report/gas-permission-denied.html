01 · 申告

他要的不是建議，是代理人動手

貼文原句很短：「我一直遇到一個問題 請 claude 自己去 chrome 改東西。都會出現下列訊息 但是能開的我都開。」

這句話裡有兩個假設，而且兩個都合理——如果只看 2025、2026 年代理產品的廣告口氣。第一個假設：Claude 既然能開瀏覽器，就能像人一樣進 script.google.com，點進專案、改 Code.gs、存檔。第二個假設：畫面上那個 Permission denied 是使用者權限沒開齊，把開關撥到允許就會通。

第一個假設碰的是產品能力的邊界。第二個假設碰的是權限系統真正擋人的位置。貼文把兩者疊在同一張截圖裡，所以看起來像「設定問題」，讀起來才會愈調愈氣。

02 · 原話

Claude 已經把兩條路都判死了

被截下來的那段回覆，不是客服套話，是一張寫得相當精確的拒辦單。原文如下：

我沒辦法直接連進去改你正式環境的 Apps Script 程式碼——Google Drive API 只能讀取，不能寫入 Apps Script 的程式碼內容；瀏覽器自動化這邊互動操作（點擊、截圖）也持續被系統擋下（Permission denied），只有「開啟網址」能用。所以我沒有一個真正能「直接改」的管道，還是得請你貼上去。

拆成四句，因果就清楚了。

  1. 目標被說死：要改的是正式環境裡那份 Apps Script，不是草稿、不是本機檔。
  2. API 這條：手上的 Google Drive 權限只夠讀，不夠寫進 Apps Script 原始碼。
  3. 瀏覽器這條：點擊與截圖持續被系統擋，錯誤字面是 Permission denied。
  4. 殘餘能力：只能開網址。因此沒有「直接改」的管道，程式碼仍須人貼上。

「只有開啟網址能用」不是安慰，是能力清單的最後一項。

開網址只證明瀏覽器還活著。它不代表代理能看見編輯器內容，更不代表它能把字打進去。申告人把能開的都開了，卻改變不了這份清單，因為清單上被劃掉的兩項，並不由他電腦上的某個核取方塊決定。

他以為自己在調權限。Claude 在告訴他：兩扇門都不歸你開。

03 · 兩扇門

同一件事，拆成 API 與滑鼠

要把程式寫進正式 GAS，實務上只有兩種動手方式。一種是對 Google 的專案 API 送寫入請求；一種是打開官方編輯器，像人一樣改。Claude 兩種都試了，兩種都被擋在不同的閘門後面。

門 A · API · 寫入失敗

Drive 讀得到，GAS 寫不進

Apps Script 專案確實住在 Google Drive 裡，但原始碼不是普通文件。官方現在寫入專案內容的正路，是 Apps Script API 的 projects.getContent 再 projects.updateContent，OAuth 範圍是 https://www.googleapis.com/auth/script.projects。

較舊的 Drive 匯入匯出路徑另要 drive.scripts，而且只適用獨立專案、整檔覆寫。綁在試算表或文件上的 bound script，更不是「對 Drive 檔案做一次 PUT」就能改。

Claude 常用的 Google 連線多半停在 Drive 讀取、Docs、Gmail 這一層。它說「Drive API 只能讀、不能寫 Apps Script 內容」，是在描述它被授與的那把鑰匙，不是在否定 Google 文件裡存在寫入方法。

門 B · 瀏覽器 · Permission denied

進得了網址，碰不得編輯器

Claude in Chrome、Cowork、Claude Code 的瀏覽器工具，理論上能導航、截圖、點擊、跑頁內腳本。對 script.google.com，這些互動從 2026 年春天起就有人整批回報失敗。

GitHub anthropics/claude-code#48960 寫得很白：擴充功能更新到 v1.0.68 之後，Apps Script 編輯器上的截圖、讀頁、JavaScript 工具一律回 Permission denied for this action on this domain。網站存取已設「所有網站」，重裝也不過，報告者判斷這是伺服器端的網域封鎖。

所以「開啟網址」還在，「點一下編輯器」不在。這正是截圖裡那句話。

04 · 權限層

「能開的都開了」開不到那一層

使用者能開的，通常是這幾層：Chrome 擴充功能的「所有網站」、Claude in Chrome 的自動核准、個別網站的「一律允許」、Google 帳號授權畫面裡那幾個 Drive／Docs 範圍。開完這些，心理上會覺得代理已經等於自己。

擋下來的位置更上面。Cowork 那條路徑會先向 Anthropic 查網域類別；被標成限制類別的網站，會在還沒跳出核准視窗之前就被拿掉，擴充功能內部甚至走 needsPrompt: false——意思是「直接拒絕，不要問人」。側邊欄有時還能用，桌面代理同一網域卻秒拒，原因就在這段分流，不是使用者漏按一次允許。

這也解釋了貼文最令人火大的一句。他不是沒開。他開的是會跳出視窗的那些權限。真正封死 script.google.com 互動的那層，視窗根本不出現。

同一句 Permission denied，至少三種來源

Google 自己的 Apps Script 也常吐「Authorization is required」或 DriveApp 被網域政策關掉。那是腳本執行時缺 scope。截圖裡這次不一樣：是代理的瀏覽器工具在碰編輯器網域時被自己的系統擋住。字面一樣，閘門不是同一扇。

05 · 為何是這裡

正式環境的編輯器，本來就不是給代理亂點的

就算明天 Anthropic 把 script.google.com 從封鎖名單拿掉，把「請 AI 開 Chrome 改正式環境」當部署流程，仍然是壞主意。理由跟權限開關無關，跟爆炸半徑有關。

Apps Script 編輯器連的是已登入的 Google 帳號。專案一旦授權，腳本可以讀信件、改試算表、動 Drive、對外發請求。代理若用截圖加點擊在這個畫面上操作，等於把「能動整個 Workspace 的開發者權限」交給一條會看錯按鈕的迴圈。金融、銀行那些類別會被預先擋，不是偶然；程式編輯器能造成的損害，不比轉帳介面小，只是比較不像轉帳。

技術上也脆。官方編輯器是複雜的單頁應用，帳號選擇器、多帳號登入、版本、部署、觸發器各是一層。截圖代理常在「選對帳號」之前就走丟。更關鍵的是：在編輯器裡存檔，改的是 HEAD；正式環境若綁的是某個已部署版本，沒做新版本、沒改部署，線上行為根本不變。代理若以為存檔即上線，會平靜地寫錯結論。

所以 Claude 回覆裡那個「正式環境」不是修辭。它在說：你要我碰的不是練習檔，是會跑觸發器的那一份。它沒有被設計成這件事的執行者。

06 · 正確管道

要改程式，走寫入 API，不要走滑鼠

能穩定改 GAS 原始碼的方法，從來不是「看著編輯器點」。官方把這件事寫在 REST 上：先 GET /v1/projects/{scriptId}/content 拿到檔案陣列，改完再 PUT /v1/projects/{scriptId}/content 整批寫回。請求裡必須帶一份名為 appsscript 的清單檔。沒寫進去的檔會被刪掉——這是整頁覆寫，不是補丁。

本機端對應的是 clasp：把專案拉成資料夾，用編輯器改 .gs 與 appsscript.json，再 clasp push。代理若要參與，正確位置是改這些檔、跑這些命令，而不是去駕馭 Chrome。

若一定要把 Google 接到 Claude，也該接的是包著 Apps Script API 的連線，授權範圍寫明 script.projects，而不是指望 Drive 讀取權限「順便」能改腳本。Drive 能看見專案這個檔案物件，與能改專案裡每一個 .gs，是兩種授權。

給這張貼文的可執行回覆

不要再追 Chrome 擴充功能的開關。請 Claude 產出完整的 .gs 與 appsscript.json，自己貼上，或用 clasp 推送。若要代理自動推，另外做一條有 script.projects 的連線，並接受它會整頁覆寫。正式部署仍應經過版本與審查，不要讓「截圖點擊」成為上線步驟。

07 · 裁決

誤診只有一句，卻會讓人空轉一個晚上

這張貼文的問題，不是 Claude 今天心情不好，也不是申告人少勾一個「允許」。問題是他把「代理會用瀏覽器」理解成「代理能以開發者身分改正式環境」，然後把系統拒辦讀成自己設定失敗。

Claude 那段話其實已經結案。Drive 那把鑰匙打不開 Apps Script 的寫入鎖。瀏覽器那隻手被自己的網域政策按住，只准開門、不准碰裡面的鍵盤。兩扇門之外沒有第三扇叫「直接改」的門。能開的都開了，門還是那兩扇。

下一張同類貼文若再出現，值得先問一句：你要的是建議，還是要它把正式環境的源碼覆寫掉？前者它做得到。後者需要 API、範圍、版本，以及一個願意按貼上的人。拒辦成立
