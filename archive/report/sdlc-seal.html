批號 PATTERN-02前站 《同事換了職業》旁線 《分層融化》日期 2026-09-11

下回分解 · 續《同事換了職業》

帽子可以借，
印章借不走

上回結尾問：AGENTS.md 和 Skills 會不會是 2026 年版的《A Pattern Language》？這篇拿 Anthropic 八月發表的〈The AI-native SDLC playbook〉一站一站走，但只用一個人的尺寸看：一個人帶著一群代理做產品，哪些麻煩早就有人解過、哪些還在長、哪些根本無解。先講結論：帽子可以借，員工可以請，章甚至可以事先蓋，但最後那顆章只能落在一個人身上。

業界層面怎麼分層、怎麼融化，在《分層融化》談過。這篇是個經，不是總經。

第一站 · 一張流程卡

程式碼不再是瓶頸，
蓋章才是

2026 年 8 月 21 日，Anthropic 在 Claude 部落格發表〈The AI-native SDLC playbook〉。它把軟體開發切成六站，每一站都 commit 一個檔案給下一站讀，最後一站發現的問題再寫回第一站：

“Build is no longer the constraint — the human-speed steps around it are.”

〈The AI-native SDLC playbook〉，2026-08-21

文章說，程式寫得比流程快之後，三件事會同時成立：瓶頸移到實作的前後，也就是規劃、審查與測試、部署這些還照人的速度走的步驟；原本的管控跟不上，逐行 review 在人寫程式時合理，代理寫大部分 diff 之後就追不上；治理變貴，因為例外還是要等每週或每月的會議。

換成一個人的尺寸，這三件事是：你一天讀得完多少，決定你出貨多少；你開始出現「看起來沒問題就合併」的時刻；你每天被問「要不要放行」的次數越來越多。文章也寫明，每個需要判斷的決定仍然由人負責。

第二站 · 六站走一遍

把公司的流程，
縮成一個人的尺寸

每一站先講 playbook 怎麼做，再講一個人時怎麼用。標籤是這一站遇到的問題屬於哪一堆：早有解方發展中無解，第三站會把它們攤開。

01規劃intent.md

以前需求靠委員會、工作坊一輪輪收斂；現在讓 Claude 直接從來源整理痛點，寫成一頁 intent.md：問題、想要的結果、影響誰、限制、還沒答案的問題。文章的範例只有一句話：客戶打電話只為了問理賠進度，客服大約三分之一的通話時間花在這種問題上。PO 核准，才往下走。

你就是 PO。intent.md 最大的用處不是給代理看，而是逼你把「為什麼要做」寫成一段話；寫不出來，就還不該開工。

格式：需求單早就有值不值得做

02設計spec.md

需求和設計在同一次對話裡寫完，受組織的 skills 約束，例如資安標準、API 慣例、品牌規則。文章給了一個檢查法：skill 抓出的問題數量如果一直不往零降，要嘛是 skill 沒被觸發，要嘛是它的內容已經跟正式政策脫節。

你的 skills 就是你過去做過的決定。把「我總是這樣做」寫成 skill，下次就不用再講一遍；但記得寫下當初為什麼這樣決定，不然三個月後的你只會照做、不敢改。

決策紀錄：ADRskill 有沒有觸發、有沒有過期

03實作plan.md → diff

先開唯讀的 plan mode 讓代理讀程式碼，寫出 plan.md：改哪些檔、先後順序、風險、怎樣算做完。人先質詢 plan，才讓它寫。每個任務開一個 worktree，也就是在自己分支上的另一份工作目錄，session 之間才不會互改同一個檔。文章建議從兩三個 session 開始，上限是一個人審得完的數量，審不過來就不要再加。

讀一頁 plan 比讀一千行 diff 快，錯誤在 plan 抓到最便宜。平行的 session 數，照你的審查速度來開，不是照機器的速度。

施工前先審計畫、git worktree跨 session 的記憶

04測試tests · evals

代理在交給人之前先自我驗證，而且檢查要能量化：「測試全過」、「截圖跟 mock 一致」、「API 回 200 而且帶新欄位」。修 bug 時，用 hook 擋住代理修改測試檔，免得它把考卷改簡單。CLAUDE.md 或 skill 一改，就要先跑一組評測（eval），每一次正式環境的事故都變成一題永久的考題。

擋住測試檔的 hook，是「寫程式的人不能改考卷」的機器版。一個人沒有同事幫你看，這種擋法比自律可靠。

職責分離、回歸測試對 prompt 與 skill 做回歸測試規格永遠寫不完

05部署PR · REVIEW.md

Claude 依 REVIEW.md 審 PR，把發現分成 Important（行為、資料、政策）和 Nit（風格、命名）；在 PR 留言標 @claude，它會自己修到綠燈，最後由 code owner 核准。上線前，hook 檢查有沒有具名的發佈授權，沒有就擋。文章特別提醒：要人核准的 hook 放在部署站就好，放在實作站會把人重新拉回關鍵路徑。

你是 code owner，也是發佈授權的人。Nit 交給代理修，Important 才佔你的章；要你按「同意」的關卡集中在上線前，不要散在寫程式的途中。

code review、核決權限AI 審 AI 的共同盲點一個人沒有第二雙眼睛

06維運事件紀錄

確定性的監控盯著 CI 失敗率、上線後錯誤率、PR 週期。偏離一個標準差只記錄，兩個標準差讓 Claude 唯讀診斷，三個標準差才讓它提修正或觸發回滾。發現寫成新的 intent.md，回到第一站；被人駁回的警報拿來調整門檻，降低雜訊。

這就是產線上的管制圖：Shewhart 1924 年在 Bell Labs 提出的東西，現在拿來看你自己的服務。一個人最怕半夜被叫，所以門檻寧可先寬，再用駁回紀錄慢慢收緊。

統計製程管制、事後檢討

第三站 · 問題分三堆

早有解方、還在長、
根本無解

把六站遇到的問題攤開，會發現大部分不是新問題，只是主詞從「一個部門」換成「你和你的代理」：

看點

早有解方的那一堆，其實是把公司裡幾十年的管理制度搬進 repo：核決權限變成 hook，稽核軌跡變成 commit，管制圖變成監控門檻。發展中的那一堆，多半卡在同一件事：代理的輸出不確定，舊的「測一次就能信」不再成立。無解的那一堆有個共同點：都需要一個會承擔後果的人。一人公司的麻煩在於，那個人和寫規則的人、按同意的人，全都是同一個。

第四站 · 半本《A Pattern Language》

有詞彙、有順序，
還缺「為什麼」

回到上回的問題。《A Pattern Language》的 253 個模式依尺度由大排到小，彼此註明誰完成誰，Alexander 相信一般人拿著它也能設計自己的房子。playbook 像它的地方有三個：有尺度順序（intent、spec、plan、diff）、非專家也能用、會跟著錯誤長大。不像的地方，並排欄位就看得出來：

看點

所以是半本：skills 是詞彙，交接鏈是文法，缺的是「力」。Alexander 晚年寫《The Nature of Order》四卷（2002—2004），也承認光有 pattern 生不出有生命的建築，要靠一步一步、每步都保留原有結構的過程。2026 年版的《A Pattern Language》如果存在，大概是 skills 加上一條每站都有人蓋章的交接鏈。至於缺的那個「力」，第六站會看到，2011 年就有現成的格式可以補。

第五站 · 你在流程卡上的位置

老闆、分身、外套，
各對一半

老闆：請數位員工

對在你真的在做老闆的事：寫職務說明（skills）、訂核決權限（hooks 的 allow／ask／block）、記考績筆記（CLAUDE.md 裡「Claude 常犯的錯」）。BMAD Method 乾脆把 PM、Architect、Dev、QA 等角色都做成代理。

漏在員工能負責、會累積經驗，數位員工兩樣都沒有。責任回到你身上，經驗只存在你寫下來的檔案裡。

分身：一個人當好幾個人用

對在一個人在多個 worktree 裡同時駕馭好幾個 session，產出確實是好幾個人的量。

漏在分身應該有你的記憶和判斷，但每個 session 都從空白開始，只讀得到你交接出去的檔案。它們不是分身，是拿著你派工單的臨時工。

外套：穿上就有超能力

對在Karpathy 2025 年說，該做的是 Iron Man 的戰甲而不是機器人。戴上資安 skill，你就帶著資安團隊的檢查表。

漏在外套給的是能力和檢查表，不是品味和判斷。戴上 PO 的帽子，不會讓你更認識你的客戶。

Anthropic 2026 年 3 月的 Economic Index 發現，用超過半年的老手比新手更少整件交辦、更常來回迭代，成功率高約一成。相關，不代表因果 老手比較像穿著戰甲、每一步都自己看過的人。

對一人公司來說，PO、PM、Designer、UI、Programmer、DevOps 不再是六份要親手做的工作，而是流程卡上六個要蓋章的格子：

看點

你不是老闆，因為員工不能替你負責；也不只是多工手，因為分身沒有你的記憶；外套只說對了能力那一層。比較準確的說法是：你是流程卡上每一站的簽核人。帽子讓你看得懂每一站的檢查表，數位員工替你把每一站的活做完，章只有你一顆。

第六站 · 章能不能事先蓋

章可以事先蓋，
責任會往上游走

如果章只有一顆，最直覺的解法是事先蓋好。playbook 部署站的示範 hook 就是這麼做的：只要指令同時含有 deploy 和 production，就檢查有沒有設定發佈授權，沒有就回傳錯誤碼 2，擋下這個動作，錯誤訊息會回給 Claude。

if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "Production deploys need a release authorization." >&2
    exit 2
  fi
fi

這等於把「放行上線」那顆章，事先蓋在一個環境變數上。問題也跟著來：出事的時候，責任算在蓋章的人，還是寫 hook 的人？這題人類其實回答過好幾次：

駕駛艙

美國聯邦航空法規 14 CFR 91.3：機長直接對航空器的運作負責，也是最終決定者。這條沒有「自動駕駛開著時例外」的但書。

自動化本身不轉移責任。

自駕車

SAE 分級裡，L2 的駕駛要一直監督；L3 由系統開車，系統要求時人才接手。據 2022 年 3 月的報導，賓士表示 L3 系統開啟期間，因技術故障造成的事故由它負責，但駕駛沒盡注意義務的不算。

真的交出控制權，責任才移給做系統的人，而且只限系統自己的錯。

財報稽核

PCAOB 的審計準則 AS 2201 允許自動化控制測過一次後繼續信任，前提是程式變更、存取與電腦作業的一般控制有效，而且那個控制從建立基準後沒有被改過。

信任從每一次動作，移到「誰能改規則」。

IT 變更管理

ITIL 的「標準變更」是事先核准、低風險、常見、照程序執行的一類變更，例如重設密碼。核准的是這一類，不是每一次。

章蓋在範本上，不蓋在個案上。

四個前例合起來，可以畫出事先蓋的章出事時，責任會落在哪：

在一人公司裡，寫 hook 的、核准的、半夜接到警報的都是你，所以「算誰」沒有懸念。真正的問題變成過去的你和現在的你：三個月前寫下這條規則的你，當時知道什麼、假設了什麼、打算多久重新看一次，現在的你還記得嗎？

這個問題早就有現成的格式。Michael Nygard 2011 年提出架構決策紀錄（ADR），每一份固定寫五欄：標題、情境、決定、狀態、後果。它剛好補上第四站說 SKILL.md 缺的「力」與「後果」。接回第四站

看點

章可以事先蓋，但蓋的對象從「這一次」變成「這條規則」，責任也跟著往上游走到規則。往上游走到底，一定停在一個人身上。這是無解那一堆裡最硬的一顆：程式可以執行授權，不能承擔責任。一個人實際能做的，是讓每一顆事先蓋的章都像一份授權書：寫明範圍、理由和期限，到期就重蓋。

末站 · 蓋章的速度

新的瓶頸，
是一天能蓋幾個章

playbook 建議追蹤的領先指標裡有一項：每位工程師同時跑幾個 session，而 review 品質不下降。這句話的後半段就是天花板：session 可以一直加，人判斷的速度不會跟著加。所以一人公司要練的不是戴更多頂帽子，而是替自己訂一張核決權限表。

看點

從 playbook 和前例借來、給一人公司用的五條規則：

  • 能寫成測試的判斷，交給 hook 和 eval，不佔你的章。
  • intent 和上線這兩格留給自己：前者決定值不值得做，後者決定出事誰扛。
  • 事先蓋的章要寫範圍、理由、期限，理由用 ADR 的格式，到期重蓋。
  • 沒有第二雙眼睛時，用時間當第二雙眼睛：重要的放行，隔一段時間再看一次。
  • 同一種錯出現第二次，就寫進 CLAUDE.md；出現在正式環境，就變成永久的 eval。

且聽下回分解：當兩個一人公司各自帶著代理合作，交接單要寫給對方本人，還是對方的代理？而那顆章，要蓋在誰的流程卡上？

playbook 每站的「以前 → 現在」與範本
  • 規劃：以前需求由委員會收集、經工作坊與簽核收斂、手寫成文件 → 現在 Claude 直接從來源整理痛點，寫進 intent.md。
  • 設計：以前分析師寫 spec、設計師解讀 → 現在需求與設計壓進一次與代理的工作階段，以 skills 編碼的標準引導。
  • 實作：以前手寫測試與程式、文件事後補 → 現在由 AI 產生，組織知識以版本控制、機器可讀的 CLAUDE.md 維護。
  • 測試：以前在各階段交界設 QA 關卡 → 現在評測持續穿插在實作過程中。
  • 部署：以前人逐行 review、治理隨審查週期而定且常不一致 → 現在多層代理審查，人只審受法規管制與關鍵的程式碼，治理在代理動作當下執行。
  • 維運：以前人盯正式環境找 bug → 現在代理監看部署，任何超出管制帶的狀況都被診斷並寫回迴圈。
  • intent.md 欄位：作者與狀態、問題、提議的結果、受影響的使用者與系統、限制、未決問題。
  • plan.md 欄位：會變動的檔案、工作順序、風險、證明（測試與驗證方式）。範例寫到「claims-core API 限速每秒 50 次，面板必須快取」。
  • 平行 session：建議從兩三個開始，實際上限是一個人能好好審查的串流數，審查跟得上才加；每個任務用獨立 worktree，所有 session 共讀 CLAUDE.md；重複性工作交給 .claude/agents/ 裡定義的 subagent。
  • 文章提醒的坑：CLAUDE.md 過期內容白佔 context；skill 發現數不降代表沒觸發或與政策脫節；實作站的 hook 要快、只看改動的檔案，完整測試放到 commit 或 PR；要人核准的 hook 放部署站；被駁回的警報用來調整管制帶。
  • 導入順序：規劃站沒有前置條件，只需要非工程人員能用 Claude、一份大家同意的 intent.md 範本、一個版本控制的共用位置；舊系統與 markdown 優先的流程可以並存，只要互相連結或指定其中一個為真相來源。
章能不能事先蓋：前例的原文與限制
  • 14 CFR 91.3(a)：“The pilot in command of an aircraft is directly responsible for, and is the final authority as to, the operation of that aircraft.” 條文本身沒有自動駕駛的例外；FAA AC 120-71B 另寫到操縱飛行的駕駛員即使在自動駕駛控制下也始終在飛這架飛機。
  • SAE J3016：2014 年 1 月首次發佈。官方說明圖寫 L0—L2「你必須持續監督這些輔助功能」，L3「功能要求時，你必須駕駛」；系統明顯故障時，L3 的人也要接手。
  • 賓士 Drive Pilot：2022 年 3 月多家媒體報導。賓士的說法是事故若因其技術故障造成由它負責，駕駛未盡注意義務則不在此列；並非承擔所有事故責任。
  • PCAOB AS 2201 .B28—.B33：自動化控制的「基準化」。.B29 大意是：若程式變更、程式存取、電腦作業的一般控制有效且持續測試，並確認該自動化控制自建立基準後未變更，可不重做前一年的特定測試。
  • ITIL 標準變更：ITIL 2011 詞彙表定義為事先核准、低風險、相對常見、依程序或作業指示執行的變更，例如重設密碼；ITIL 4（2019）改寫為低風險、事先核准、充分理解且完整文件化、不需額外授權即可實施的變更。
  • ADR：Michael Nygard〈Documenting Architecture Decisions〉，2011-11-15，欄位為 Title、Context、Decision、Status、Consequences。
  • 職責分離：常被說成沙賓法案的要求，但法條本身（第 404 條）要求的是管理階層評估內部控制；職責分離來自 COSO 等控制框架。
早有解方與發展中的補充
  • 管制圖：Walter Shewhart 在 Bell Labs 的備忘錄日期是 1924-05-16，約一頁、附一張示意管制圖；±3σ 管制界限也是 Shewhart 的做法。Western Electric《Statistical Quality Control Handbook》1956 年出版。
  • git worktree：2015 年 7 月 Git 2.5 加入，當時標為實驗性功能。
  • CODEOWNERS：GitHub 2017-07-06 推出，讓維護者指定哪些人或團隊必須審查哪些路徑。
  • 事後檢討：Google《Site Reliability Engineering》（2016）第 15 章談不究責的事後檢討文化。
  • MCP 授權：2025-03-26 版規格加入以 OAuth 2.1 為基礎的授權框架；2025-06-18 版把 MCP 伺服器定為 OAuth 資源伺服器。OAuth 2.1 本身仍是 IETF 草案。
  • 法律：歐盟產品責任指令 (EU) 2024/2853 把軟體（含 AI 系統）納入「產品」，適用於 2026-12-09 後上市的產品；歐盟 AI 責任指令提案則在 2025 年撤回。業界與法規的全貌見《分層融化》。
  • Rice 定理：Henry Gordon Rice，1953 年發表於《Transactions of the AMS》（1951 年底於學會報告），原文以遞迴可列舉集合的類別表述，今天常說成「程式行為的非平凡性質不可判定」。
playbook 的治理與指標
  • Hooks 三種層級：Allow（直接放行）、Ask（停下來等人核准，例如上線）、Block（拒絕並說明，例如受保護路徑、機密）。
  • Managed settings：管理者設定、工程師改不了，包括權限規則、沙箱隔離、憑證限制、核可的 plugin 與 MCP 伺服器清單、最低版本。
  • CLAUDE.md：放在 repo 根目錄、控制在一頁內，寫建置與測試指令、慣例、架構概覽，以及「Claude 常犯的錯」。
  • Skills：放在 .claude/skills/，寫資安標準、API 設計慣例、品牌規則、法遵要求；文章明說 skills 是建議性的，確定性的執行靠 hooks。
  • 領先指標：從第一次討論到 commit intent.md 的時間、intent 到 spec 的間隔、第一次 PR review 的等待時間、每位工程師平行 session 數（在 review 品質不降的前提下）、CI 首次通過率。
  • 落後指標：intent.md 進入設計站的比例、開工後的需求返工、第一版實作就合併的比例、合併前與上線後抓到的缺陷比、同類事故的重複次數。
Anthropic Economic Index 的兩個發現
  • 2026 年 3 月〈Learning curves〉：使用六個月以上的使用者，明顯較少用「整件交辦」的模式，較常來回迭代，對話成功率高約 10%；控制任務類型、國家等因素後關聯仍在。報告解讀為「做中學」。
  • 2026 年 6 月〈Cadences〉：自動化比例（整件交辦加回饋迴圈）越高的人，對 AI 對自己明年工作的影響越樂觀；Claude Code 與對話介面的自主度差異，約三分之二來自「同一種任務在 Claude Code 上被交辦得更多」。
  • 兩者都是相關性分析，不能直接推論因果。

  • 產品設計師與資料科學家在不熟 TypeScript 的情況下，做出完整的 React 應用來視覺化模型表現。

Agent Skills、BMAD、《A Pattern Language》
  • Agent Skills：Anthropic 2025 年 10 月推出，12 月 18 日以開放標準發佈於 agentskills.io。SKILL.md 的 frontmatter 有 name 與 description，啟動時只載入這兩欄，任務符合時才載入內文，另可附 scripts、references、assets。
  • BMAD Method：開源框架，代理角色包括 Analyst、PM、Architect、PO、Scrum Master、Dev、QA、UX Expert；規劃階段產出 brief、PRD、UX 規格、架構文件，再由 Scrum Master 切成一張張自帶脈絡的 story 交給 Dev。
  • 《A Pattern Language》（1977）：253 個模式，依尺度由大到小排列，從 Independent Regions 到 Things from Your Life；模式之間的連結構成語言，沒有連結的只是目錄。
  • 《The Nature of Order》（2002—2004，四卷）：Alexander 認為光有 pattern 不足以讓建築有生命，轉而強調保留結構的逐步轉化。
  • Karpathy〈Software Is Changing (Again)〉：2025 年 6 月 17 日 YC AI Startup School 演講，主張做會增強人的「戰甲」而非全自動的「機器人」，產品要有自主度滑桿，並讓產生與驗證的迴圈越快越好。
