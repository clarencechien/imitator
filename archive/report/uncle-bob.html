00 / Executive answer

先說結論：他移動了「人該讀什麼」

Uncle Bob 所謂「不讀程式碼」，精確地說，是不再逐行審查 AI 代理產生的實作碼與單元測試。原因不是他看不懂、懶得看，或突然否定 《Clean Code》；而是當代理能以遠高於人類閱讀速度產生程式碼時，逐行 review 會立刻成為整個開發系統的新瓶頸。

一句話判讀

他不是取消驗證，而是把人類判斷上移到「行為規格、架構邊界與風險」，把低階實作交給代理，再用不可討價還價的自動化關卡驗證。

不是

丟一句 prompt、看畫面能跑就上線的 vibe coding。

而是

用 Gherkin 驗收規格、單元測試、mutation testing、coverage、複雜度與依賴分析，建立一條代理必須通過的「測試刑場」。

仍由人負責

需求是否正確、架構是否合理、哪些風險不可接受、驗收規格有沒有漏掉，以及最後產品是否真的解決使用者問題。

01 / Source reconstruction

他究竟說了什麼？

2026 年 7 月，Robert C. Martin 在 X 的討論中表示，他目前的策略是不讀代理寫出的程式碼，因為那是取得代理生產力的唯一方式；替代方案是用「極端限制」包圍代理。該段討論目前可由專文的逐句整理交叉核對，而他在訪談、課程與公開 repository 中留下的實作又與這套說法一致。1

“My current strategy is to not read any of the code written by my agents.”

Robert C. Martin，2026 年 7 月 X 討論；引文依來源整理節錄，未延伸其字面範圍。

他對工作分配的描述更重要：

產物 主要作者 Uncle Bob 如何處理 人類判斷在哪裡
實作程式碼 AI 代理 不逐行閱讀 由規格與品質閘門間接約束
單元測試 AI 代理 通常不 review coverage、mutation 與另一條驗收測試流
Gherkin 驗收測試 AI 起草 依關鍵程度詳讀或抽查 確認業務行為是否被正確描述
QA 程序 AI 起草 依關鍵程度詳讀或抽查 確認驗證範圍與風險情境
最終產品行為 系統執行 定期人工測試 確認產品真的可用，而非只有測試變綠

重要修正：「不讀」不等於「永遠不看」。當測試怪異失敗、代理陷入自己製造的混亂、架構或安全出現異味時，人工仍要下探到程式碼。差別在於：讀碼從每次變更的固定流程，變成風險觸發的例外流程。

02 / Root causes

他不讀程式碼的四個真正原因

01

吞吐量經濟學改變

代理每小時能產生的變更量，遠高於人類可嚴謹閱讀的量。若每一行仍需人工批准，AI 只是把瓶頸從「寫」移到「讀」。

02

抽象層再往上爬

工程師早已不逐行審查 compiler 產生的 assembly；他的賭注是：規格與驗證管線會成為下一層可依賴的輸入，實作碼則逐漸像生成物。

03

逐行 review 不是最強證據

人眼擅長看可讀性與局部異味，卻不擅長窮舉狀態空間。能執行的驗收測試、mutation testing、型別與靜態分析，可提供可重跑、可阻擋 merge 的證據。

04

人的價值移到意圖與取捨

代理能遵守規則，卻未必在建構過程中自然展現「品味」與對未來後果的在意。需求、模組邊界、依賴方向與風險接受度仍需要資深判斷。

2026 年 6 月的訪談摘要把他的立場說得很清楚：離開程式碼這個「主要 review 表面」，不代表離開結構。持久的工程問題仍是模組、邊界、依賴、資料流與系統行為；代理能在被要求時批評設計，卻不一定會在實作時主動運用同等判斷，因此他用複雜度、coverage、函式與模組結構工具把回饋迴路關起來。2

03 / The gauntlet

真正取代逐行 review 的，是一條驗證管線

最容易誤解之處，是把「不 review 實作碼」看成少做了一件事。實際上，這種方法通常是把一個模糊的人工作業，拆成多個更嚴格、可重跑、可失敗關閉（fail closed）的關卡。

Uncle Bob-style control loop Human → Agent → Evidence
Human-owned 意圖與邊界 需求、驗收條件、架構、風險等級
→
Agent-owned 測試與實作 Gherkin、單元測試、程式碼、修復迴圈
→
Machine-enforced 證據與阻擋 Acceptance、mutation、coverage、architecture、security

一、可執行的驗收規格是「人類主要閱讀面」

Uncle Bob 的 Acceptance Pipeline Specification 把流程具體定義為： Gherkin feature → parser → JSON intermediate representation（IR）→ 產生測試入口 → 專案測試 runner。另有 acceptance mutation：修改規格裡的重要 example value， 再確認測試真的會失敗，而不是規格寫了卻沒有接到實際系統。3

二、單元測試與驗收測試必須是兩條不同證據流

單元測試容易貼著實作長，甚至把同一個錯誤假設複製兩次；驗收測試則從外部可觀察行為出發。兩者同時通過，仍不能證明絕對正確，但比「代理寫 implementation，再讓同一代理寫一組只驗證自己想法的 unit tests」更有獨立性。

三、品質規則必須是工具，不是 prompt 願望

函式大小、認知複雜度、重複碼、coverage、依賴循環、禁止跨層呼叫、檔案大小與命名規則，都應由 CI 中的 deterministic tools 判定。提示詞會隨長對話弱化；失敗就擋住的工具不會被代理說服。公開的 empire-2025 專案也可看到 acceptance pipeline、dependency checker、 acceptance boundary 與 AI map access audit 等實際關卡。4

四、管線深度依 criticality 調整

Uncle Bob 也公開反省「把所有測試都疊上去」可能過度。他提到 Gherkin、unit、QA、 mutation 與 Gherkin mutation 很容易叫 AI 做，但「做得到」不代表每次都值得；很多時候他也只用 unit tests 與 CRAP 分析。5 因此這不是單一教條，而是一個風險加權的驗證架構。

04 / The apparent paradox

《Clean Code》作者不讀 code，矛盾嗎？

表面上非常矛盾，實際上只矛盾了一半：程式碼的主要讀者可能從人類變成代理，但結構品質仍直接影響代理工作的成本與穩定性。

仍然成立

小函式、低複雜度、清楚命名、邊界分明、低耦合與無循環依賴，讓代理更容易定位、修改、測試與自我修復。

改變的是目的

過去主要為人類 maintainability；現在也同時是 AI 的 context efficiency、導航效率與修復可收斂性。

沒有自動成立

「測試全綠」不等於架構乾淨。若沒有 architecture fitness functions，代理仍可能在每次局部成功中累積整體腐化。

人仍需偶爾下探

遇到安全、效能、資料一致性、奇怪失敗或代理反覆修改同一區域時，乾淨結構讓人可以快速接手，而不是面對不可讀生成物。

Clean Code 沒有消失；它從「請人仔細遵守的美德」，變成「代理無法繞過的機械性預算」。

05 / Evidence

實證支持到哪裡？不要把立場當定論

一項 2026 年 5 月的受控 minimal-pair 研究，建立六組外部行為相同、但結構與靜態分析品質不同的 repository，設計 33 個任務，以 Claude Code / Claude Sonnet 4.6 各跑十次，共 660 次 trial。結果是：乾淨程式碼沒有改善通過率，卻明顯縮小代理的操作足跡。6

乾淨版本相對髒亂版本

圖條以最大變化 33.8% 正規化，只用來比較幅度；不是 0–100% 的成功率刻度。Pass rate 差異為 −0.9 個百分點，研究者判定整體任務成功率未因 cleanliness 改變。

這支持了什麼？

它支持 Uncle Bob 的一個較窄主張：髒亂程式碼會讓代理花更多 token、產生更多往返與重讀；乾淨程式碼是代理效率問題，不只是人類審美。但該研究沒有證明「不需要 human review」，也沒有證明 Gherkin + mutation 管線足以取代所有人工查核。

另一篇「code review 終結」論文又代表什麼？

2026 年 6 月的 The End of Code Review 主張 agent-driven verification 可取代傳統 mandatory human review；但作者明確說這是綜合既有資料的立場論文，不是新的實證研究。它也承認模型可能有 false negative、生成與審查盲點高度相關、程式碼內 prompt injection，以及架構一致性仍需人類判斷。7

研究結論的正確強度：目前資料足以支持「逐行人工 review 不應再是唯一品質關卡」，還不足以支持「所有團隊、所有系統都能安全停止讀碼」。

06 / Failure modes

六個不能被漂亮管線掩蓋的盲點

01

同源錯誤

同一代理寫規格、程式與測試，可能把同一個誤解複製三次。綠燈只證明三者一致，不證明它符合真實需求。

02

規格未寫出的世界

資料遷移、時序競態、資源耗盡、網路分割、觀測性、復原與人因錯誤，往往不在 happy-path Gherkin 裡。

03

架構緩慢腐化

每個 feature 都通過外部行為測試，系統仍可能多一層不必要抽象、重複能力或錯誤依賴方向。

04

安全與 adversarial code

產生與審查模型可能共享盲點；程式碼中的自然語言甚至可能對 reviewer agent 形成 prompt injection。

05

知識傳承斷層

若人不讀 code，又沒有架構地圖、決策紀錄與可追溯規格，團隊可能只知道系統「有通過」，不知道為何如此設計。

06

責任不能外包

醫療、金融、工控、安全連鎖與法規稽核要求的是可歸責決策。代理通過測試，不等於組織完成專業簽核。

最大的陷阱，是新手只複製「我不看 code」這句話，卻沒有複製 Uncle Bob 數十年累積的架構判斷，也沒有建立同等嚴格的 deterministic guardrails。 這兩者看起來都叫 no-look coding，風險卻完全不同。

07 / Applicability

什麼情境能採用？用風險分級，而非信仰表態

一次性 prototype、內部展示 可大幅 no-look 需求、demo 行為、明顯安全風險 build、unit、lint、手動 smoke test
內部 CRUD、一般報表與 dashboard 風險抽樣 驗收規格、權限、資料查詢、migration acceptance + unit、RBAC 測試、SAST、schema 檢查
OEE／良率計算、事件處理、MES 整合 保留熱點 review 公式、時序、idempotency、錯誤恢復、資料契約 property tests、replay、contract、load、故障注入

最務實的中間路線不是「全讀」或「全不讀」，而是： 規格與架構必讀、低風險實作不讀、關鍵路徑與異常訊號觸發閱讀。 這既保留代理吞吐量，也不把高風險責任藏進綠色 CI。

08 / Adoption blueprint

企業落地：先建證據，再降低 review

不要先宣布「從今天起不看程式碼」。安全順序剛好相反：先測量現有品質、補齊規格與關卡，再逐級縮小人工作業。

建立風險分類與不可 no-look 路徑

把 security、billing、migration、production control、PII、deployment 與 shared libraries 標成 protected paths，預設要求人工簽核。

把需求轉成可執行行為契約

先寫 acceptance criteria，再由代理轉成 Gherkin；人要審查 happy path、edge cases、錯誤、安全與跨系統條件，而不是只看語法漂亮。

讓證據彼此獨立

實作代理不應是唯一 reviewer。可用不同 agent/model 產生反例、獨立 QA scenarios，並將隱藏測試或 production replay 與實作者隔離。

建立 fail-closed 的 deterministic gates

build、type、lint、unit、acceptance、coverage、mutation、dependency、duplicate、SAST/SCA、secret scan；失敗就阻擋，代理不能以文字解釋略過。

保留 architecture 與 hotspot review

人工審查 plan、模組圖、依賴差異、資料流與風險熱點；觸發條件包括高複雜度、異常 churn、測試反覆修改、跨邊界變更或未知 failure。

用 shadow mode 證明可行

先讓新管線與既有人工作業並行 4–8 週，記錄 escaped defects、rollback、review latency、agent retry、token cost 與人工工時，再決定哪些類別能降級。

一個可操作的 policy 骨架

change_policy:
  default_mode: risk_sampled_review

  protected_paths:
    - "auth/**"
    - "billing/**"
    - "migrations/**"
    - "control/**"
    - "infra/**"

  human_owned_artifacts:
    - acceptance_criteria
    - architecture_plan
    - threat_model
    - rollback_plan

  mandatory_gates:
    - build
    - typecheck
    - unit_tests
    - acceptance_tests
    - coverage_budget
    - complexity_budget
    - dependency_rules
    - sast_and_sca

  escalate_to_code_review_when:
    - protected_path_changed
    - architecture_boundary_changed
    - complexity_budget_exceeded
    - tests_modified_repeatedly
    - migration_or_data_loss_risk
    - security_agent_disagrees
    - rollback_or_manual_test_fails

上線前最低檢核表

  • 行為規格由懂 domain 的人確認
  • 驗收與單元測試不是同一證據
  • coverage 門檻搭配 mutation，不只看百分比
  • 模組依賴、循環與複雜度有硬性預算
  • 權限、secret、供應鏈與輸入安全已掃描
  • migration、rollback、backup 已演練
  • 效能、容量、併發與故障模式有驗證
  • 變更、代理、模型與測試結果可稽核
  • 異常時能快速定位並由人接手
  • production 指標能證明產品行為正常
09 / Final judgment

最終判讀：這是高紀律的「不看」，不是低責任的「不管」

Uncle Bob 的核心洞察是對的：當 AI 代理的產出速度持續增加，人類逐行 review 不可能無限擴張；工程控制必須上移到意圖、結構與可執行證據。

但「不讀程式碼」本身不是方法，只是成熟方法可能產生的結果。真正的方法是： 可審查的規格、明確架構、兩條以上的驗證流、mutation、靜態與依賴分析、 criticality-based review、人工最終行為測試，以及失敗時願意下探程式碼的資深判斷。

因此，團隊不應問「我們要不要學 Uncle Bob 不看 code？」；應問： 「我們是否已建立足夠獨立、可重跑、會阻擋錯誤的證據，讓某一類低風險變更不再需要逐行閱讀？」 如果答案還是否定的，跳過 review 只是少了一層防線，不是升上新的抽象層。

可帶走的決策原則

先把品質寫進系統，再把人從低價值的逐行檢查中解放；高風險處仍由人負責，且責任永不交給綠燈。
