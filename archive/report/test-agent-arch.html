還是一條有界的流程?

同一個需求,兩種蓋法。差別不在「用不用 LLM」,而在控制流由誰決定——以及判斷錯的時候,錯誤會擴散多遠。

六個會咬人的地方

Anti-patterns

前三個是架構問題,後三個是 test agent 特有的。AP-03 比架構選型更值得先想清楚——它會讓你以為系統在運作。

AP-01 · CONTROL_FLOW_GIVEN_AWAY

把已知的順序交給模型決定

「拉工單 → 產 case → 跑 → 寫回」這個順序,你在寫 code 之前就知道了。交給模型 runtime 決定,只是多付一次 token、多一個出錯機會。

判準畫得出流程圖的,就寫流程圖。
AP-02 · UNBOUNDED_LOOP

沒有 step 上限

單步 95% 正確,20 步下來是 36%。Agent 的可靠度隨軌跡長度衰減,不會自己收斂到對的地方——只會收斂到「能停下來」的地方。

做法每個迴圈都要有 max attempts,超過就走失敗出口,不是繼續試。
AP-03 · TAUTOLOGICAL_TEST

一定會過的測試

模型很擅長讀完程式碼,然後 assert 現在的行為。這種測試通過率 100%、鑑別力 0,抓不到任何 bug,還給你虛假的安全感。這是 test agent 最大的陷阱。

防守拿一個已知有 bug 的版本當基準,生成的測試必須在那個版本上失敗;或用 mutation testing 量鑑別力。
AP-04 · NO_SANDBOX

生成的程式碼直連正式環境

不是理論風險。模型寫的測試很容易照著 config 連到真的資料庫、真的產線 API,然後做出寫入動作。

做法跑在容器裡,不給正式憑證,網路白名單。
AP-05 · WRITE_BACK_TOO_EARLY

一上線就讓它改工單狀態

準確率還沒量出來之前就給寫入權,錯誤會直接進到別人的工作流,而且很難回溯是哪一次跑壞的。

做法初期只發 comment 或開 sub-task,不動 status。累積夠多樣本再放開。
AP-06 · FRAMEWORK_HIDES_CONTEXT

框架把 context 組裝藏起來

調 agent 最主要就是調進 context 的東西。框架包掉這層之後,你會變成隔著兩層抽象在猜——而它給你的持久化、重試、tracing,自己寫大概一天的工。

判準你已經有自己的 state 管理習慣的話,框架帶來的多半是抽象稅。
B 的實作

確定性骨架,節點內包一個有界迴圈

保留探索能力,但把不確定性關在盒子裡。整段大概 30 行,每一行你都懂,出事時 stack trace 直接指到問題點。

def process(issue_key):
    issue = jira.get(issue_key)              # code
    cases = llm_gen_cases(issue)             # model → schema
    code  = llm_gen_code(cases)              # model → schema

    # ── 有界迴圈:上限 3,失敗有出口 ──
    for attempt in range(3):
        result = run_in_sandbox(code)        # 容器,無正式憑證
        if result.ok:
            break
        code = llm_fix(code, result.stderr)
    else:
        return mark_needs_human(issue_key, result)

    if not discriminates(code, known_buggy_rev):  # AP-03 防守
        return mark_needs_human(issue_key, "測試無鑑別力")

    jira.comment(issue_key, render_report(cases, result))
UPPER BOUND最多跑幾次?沒有這個數字,就不叫有界。
EXIT CONDITION什麼情況算成功?要能用程式判斷,不是模型自評。
FAILURE PATH用完次數之後往哪走?預設不能是「繼續試」或「當作成功」。

畫得出流程圖的,就寫流程圖。

需要 agent 的條件是「分支事先枚舉不完」。這條流程裡唯一符合的,是測試失敗後的修復判斷——語法錯、缺套件、fixture 沒建好,還是真的抓到 bug。那一段值得放迴圈,其餘的不值得。

另外,框架解決的是 workflow 那一側的問題:狀態機、持久化、重試。它不會讓 agent 變可靠。
