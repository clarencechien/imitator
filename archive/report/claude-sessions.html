哪條線
接得通

Claude Code 有兩種「接線」：一種把整段對話搬到別處，一種只遞一段文字給另一個 session。先看圖和結論，細節放在後面。

依據標籤：文件＝官方文件寫的；實測＝有人實際試過；回報＝GitHub issue；推測＝我的判斷，未證實

TLDR 1 · 搬 session

整段對話搬家：拉回來可以，推上去不行

  • 通本機 → 網頁／手機：/rc。還是同一個 session，程式仍在本機跑。
  • 通雲端 → 本機：claude --teleport。拉回的是一份複本，之後兩邊各走各的。
  • 不通本機 → 雲端（終端機）：做不到。claude --cloud 只會另開一個新的雲端 session。
  • 通本機 → 雲端（桌面版）：session 選單裡的「Continue in」。

TLDR 2 · 遞紙條

跨 session 傳訊：同機穩、跨機要開 /rc、往雲端不可靠

  • 通同一台機器的 session 互傳，不經伺服器。
  • 通兩台機器之間：兩邊都開 /rc 就能互傳。文件
  • 通雲端 → 本機開著 /rc 的 session。實測
  • 不穩本機 → 雲端：文件說通，實測不通。要從本機塞話給雲端，改用 claude -p "訊息" --cloud <id>。文件 實測
  • 不通沒開 /rc 的 session 碰不到任何跨機器對象；容器 ↔ host、WSL ↔ Windows 也不通。

紙條只帶一段文字，不帶對話紀錄、不帶檔案，也不能替你按「允許」。

追查 · 往雲端的那條線

為什麼雲端傳得過來，本機傳不過去

先說結論：官方文件寫這條線是通的，但我找不到有人實測成功；而你實測不通。目前沒有找到「開啟本機 → 雲端」這種開關。能影響它的只有下面幾件事，照順序排除：

  1. 本機看得到那個雲端 session 嗎？在本機 session 打 /list-agents（或 /peers），雲端 session 應該帶著 cloud 標籤出現。沒出現的話，有兩個常見原因：本機這個 session 其實沒連上 /rc；或者雲端 session 比較舊，被清單截掉了，因為清單只從最新的往回讀幾頁。文件
  2. 看得到但沒收到：可能被「擱置」了。沒有另外設定時，收件方會看兩邊的權限模式：一邊是 bypass、一邊不是，訊息就先擱著等你核准。核准框出現在收件方，也就是雲端那頁；五分鐘沒人按就直接丟掉。雲端 → 本機會成功，可能是因為核准框出現在你眼前的終端機，或是那個方向剛好沒被擱置。文件 推測
  3. 雲端 session 還活著嗎？雲端 session 閒置太久，VM 會被回收；已封存的 session 則一律拒收新訊息。文件
  4. 送出前有沒有跳提示？如果設了 isolatePeerMachines: true，每張要離開本機的紙條都要先經過你同意；拒絕或沒回應就不會送出。文件
  5. 版本或 bug。跨 session 傳訊還很新，GitHub 上有不少可靠度的 issue，包括「回報已送達、實際被默默丟掉」的回歸 bug。也有人回報雲端 session 之間沒有 SendMessage 可用，雲端這一側的支援看起來還不完整。回報

本機 → 雲端，先用這條

claude -p "訊息" --cloud <session-id> 是另一套機制：它把一則訊息排進那個雲端 session 就結束，不需要本機 session 開 /rc，任何登入同一帳號的機器都能跑，也能寫在排程腳本裡。成功時會印出 Sent to cloud session.；session 不存在或已封存會直接報錯，不會默默失敗。缺點是單向：雲端的回覆不會自動傳回來，要自己去網頁看。文件

補充 1 · 三個地方

執行只在兩處，第三處只是窗戶

程式只會在「你的機器」或「雲端 VM」上跑。claude.ai/code、手機 app、桌面版都只是看進某個 session 的窗戶。要判斷一條線通不通，先問那個 session 跑在哪裡。

地方誰在跑用得到什麼關掉會怎樣
本機 sessionCLI · VS Code你的機器本機檔案、本機 MCP、內網process 一停，遠端就看到離線
雲端 sessioncloudAnthropic 的 VMclone 下來的 GitHub repo、雲端環境設定關瀏覽器照跑；閒置太久 VM 回收，重開會還原對話，但背景工作不會還原
窗戶web · mobile · desktop不跑只負責顯示和送指令什麼都不影響

補充 3 · 遞紙條逐條

跨 session 傳訊的每一條線

需要 Claude Code v2.1.224 以上（原生 Windows 要 v2.1.234）。不用自己呼叫工具，用一般的話說就好，例如「跟 @api-worker 說 migration 跑完了」。打 @ 會跳出 session 名稱讓你選；不過雲端和其他機器的 session，要先讓 Claude 列過一次才會出現在選單裡。

從 → 到狀態細節
同機 ↔ 同機M1通 文件走每個 session 自己的本機 socket（Windows 是 named pipe），不經伺服器。用 API key 或 Bedrock 也可以。背景 session、claude -p 也收得到；bare mode 收不到。
雲端 → 本機 /rc sessionM2a通 實測你實際成功過。本機要開著 /rc。
本機 → 雲端M2b不穩 文件 實測文件寫本機連著 /rc 就能送，你實測不通。排查順序見上面的「追查」。替代做法：claude -p "訊息" --cloud <id>。
本機 A ↔ 本機 BM3通 文件兩邊都開 /rc；要主動開啟對話需 v2.1.225 以上。對方離線也送得出去，等它重新連線才會收到。
沒開 /rc → 跨機器M4不通 文件清單裡根本不會出現雲端和他機 session；就算硬送出去，也沒有回覆地址，對方回不了你。
雲端 ↔ 雲端M5不明 回報有 feature request 指出雲端 session 之間沒有 SendMessage 可用。
容器 ↔ hostM6不通 文件容器有自己的檔案系統，找不到彼此；同一個容器裡的兩個 session 則可以互傳。
WSL 2 ↔ 原生 WindowsM7不通 文件註冊在不同的 home 目錄，socket 型別也不同。
閒置時通知我M8限同機 文件請另一個 session 下次閒置或結束時回報一次，不耗對方 token；12 小時沒回報就自動取消。

收件的 session 會知道紙條來自另一個 session，不是你本人。所以它不能替你批准權限提示，不能叫對方改權限設定或 CLAUDE.md；紙條裡的 /compact 之類指令也只會被當成純文字。

補充 4 · 用法

這些線能接出哪些情境

每張卡片上方標的是它用到的線路；只靠「不穩」那條線的用法已經換掉了。

L1

長任務丟著跑，手機批准

桌機上 claude --rc 開一個重構任務，出門後用手機看進度；遇到權限提示時手機會推播，直接在手機上核准。程式從頭到尾都在桌機跑。

L2 → L3

路上先開工，回座位收尾

在手機上開雲端 session 修 bug。回到座位後 /tp 拉回本機，接著跑只有本機碰得到的部分：內網、實體裝置、地端 GPU。雲端那份從此不會再同步。

M1

平行 worktree 互報變更

後端 session 改了 API 的回傳結構，Claude 發現前端 session 會受影響，就自己遞一張紙條過去提醒。你不用在兩個終端機之間複製貼上。

M8

等 migration 跑完再動

跟目前的 session 說「migration 那個 session 做完時通知我」。對方閒置時會回報一行狀態，你這邊如果也閒著，就會自動接著做下一步。

M2a

雲端做完，回報給本機

本機主 session 開著 /rc，雲端 session 跑完任務後主動把摘要傳回本機，由本機這邊接手收尾。這是你實測走得通的方向，所以讓雲端當發話的一方。

L4 + --cloud -p

本機派工，腳本追加指令

claude --cloud 一次丟幾件獨立任務上雲端，之後用 claude -p "追加說明" --cloud <id> 補充指令。排程腳本也能這樣投遞，不必依賴本機 → 雲端的紙條。

兩個常見的誤用

想把整段討論交給另一個 session：紙條只帶一段文字，這時該用 resume 或 teleport。想讓 A session 幫 B session 按「允許」：刻意設計成做不到，權限只認你本人。

補充 5 · 相關設定

會影響紙條的設定

設定效果
crossSessionInboundaccept：直接送達；hold：擱著等你核准；refuse：直接丟掉。也可以在 /config 的「Messages from your other sessions」設定。
沒設定時的預設收件方看兩邊的權限模式：兩邊都是 bypass，或兩邊都不是，就直接送達；一邊是、一邊不是，就擱著等核准，五分鐘（dialogExpiry）沒人按就丟掉。
isolatePeerMachines設成 true，每張要離開本機的紙條都要你先同意，連 bypass 模式也一樣。
deny SendMessage、ListAgents這個 session 不能發、也不能列；會一起關掉對 subagent 和 agent team 的傳訊。
disableRemoteControl關掉 Remote Control，跨機器那半邊的線路也就全斷了。
