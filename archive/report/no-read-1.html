不讀程式碼，
他改讀規格

7 月，寫《Clean Code》的 Uncle Bob 說他不讀 agent 寫的程式碼，工程師吵了一整個夏天。這篇把他從去年 12 月到今年 9 月的做法排成一條線。他讀的東西沒有變少，是換了一批，而且換了不只一次。下篇看 Lauren Tan，她往同一個方向走，看的東西不一樣。

這篇用的比喻是電子廠的隨批流程卡。卡跟著一批貨走，每過一站蓋一個章。主管不會把每片板子拿起來看，他看卡上的章齊不齊，再抽幾片。Uncle Bob 做的事很像：他不看板子，他看卡。

這一篇是 /r/uncle-bob 的改版。前版的資料截到 7 月 25 日，那則貼文才發出來兩天。之後他又公開講了三場，做法也改了，這裡補上。

N-00 · 那句話

他說不讀的，是哪幾樣

7 月 23 日，有人在 X 上質疑不審 AI 產出的做法，他回了一則。他說自己從 1960 年代末開始寫程式，現在的策略是「not read any of the code written by my agents」，因為這是用得上 agent 產能的唯一辦法。替代做法是用很嚴的限制把 agent 圍起來。

同一串回覆裡，他把分工講得很細：

產物誰寫他看不看
實作程式碼agent不看
單元測試agent不看
Gherkin 驗收測試agent 起草看。重要的細讀，其餘抽查
QA 程序agent 起草看。同上
產品實際跑起來的樣子—定期自己手動測一次

這句話後來被轉成「Clean Code 的作者不讀 code 了」。照這張表，比較準的說法是：他不讀實作和單元測試，改讀規格。

Gherkin 是一種寫驗收條件的格式，每一條長成「在什麼情況下，做了什麼，應該看到什麼」。它是寫給人讀的，也能被工具轉成可以執行的測試。

N-01 · 十個月

那句話前後各發生了什麼

  • 2025-12他用早期的 Grok agent，程式寫得很快，留下來的東西很亂，亂到 agent 自己被拖慢。他先試長 prompt，把 TDD 和 clean code 的規矩寫成 5 到 10 頁。模型把它當參考看，不當規定守。
  • 2026-05-13貼文講 Gherkin mutation：Gherkin 先轉成 JSON，再從 JSON 產生可執行的測試。mutator 插在中間改掉一個值，這時候測試應該要失敗。
  • 6 月初同一份規格用 Java、Clojure 和 Go 各跑一次，測試疊到他自己說太超過。Java 超過 5 小時，Clojure 2 小時 24 分，Go 3 小時 29 分。CPU 大多花在 mutation testing。
  • 06-04swarm-forge 的六人分支：specifier、coder、cleaner、architect、hardener 和 QA。產出是一個能用的應用程式，架構紮實，測試多到超載。
  • 7 月初貼文反省測試超載。這些測試叫 AI 做都很容易，但很多時候他只用單元測試加 CRAP。
  • 07-23「不讀」那則回覆。
  • 08-19Matt Pocock 的直播訪談。agent 是五個角色，CRAP 的上限從給人用的 4 放寬到 6，prompt 縮到最短。他還講了一個架構檢視器，和規格用完就丟。
  • 9 月HangarDX 訪談〈Humans Are Too Slow for AI-Generated Code〉。章節表裡有「架構圖當審查面」。這個工具 8 月就在了。

7 月那句話是這條線中間的一個點。前面半年他在試怎麼管，後面兩個月他在調管多緊。

N-02 · 五站

卡上有哪幾個章

8 月以後，他把每一個 story 交給一串很窄的 agent。每一站只做一件事，做完就結束，下一站從乾淨的 context 開始。

任務切窄的理由是 context。任務小，context 就短，寫在 prompt 最前面的那幾條規矩才留得住。

卡上有兩個工具，第一次看到的人可能不認得：

  • CRAP 是 2000 年代的指標，把循環複雜度和測試覆蓋率合成一個分數。又複雜又沒被測到的函式，分數最高。
  • mutation testing 把原始碼裡的運算子偷偷改掉，再跑測試。測試還是全過，代表那段測試其實沒在測東西。

這兩樣他在 2000 年前後都試過，都不划算。CRAP 找出一堆爛函式，一個一個修要花太久。mutation testing 得跑一整晚。agent 不怕無聊也不怕慢，同一件事現在大約 30 分鐘，它們才變得能用。下篇 N-09 再出現

第 1 站另外有一條保險。他公開的 Acceptance Pipeline 規格把流程定成：Gherkin 轉成 JSON，JSON 產生測試入口，再交給專案的 test runner。Gherkin mutation 會改掉規格裡的一個範例值，確認測試真的跟著失敗。這是在防「規格寫了，卻沒有接到系統上」。

代價也有數字。Alex Rusin 的整理說，一個 agent 五分鐘做完的事，走完五站大約一小時，人自己做要半天。

N-03 · 改版

他自己改了五個地方

把 N-01 的時間線前後對一下，他的做法至少改了五項：

項目之前之後
規矩放哪5 到 10 頁的 promptprompt 縮到最短，規矩搬進事後跑的工具
架構誰管6 月的六人分支有 architect agent8 月是五站，模組邊界他自己畫。想自動化，還不順
門檻多緊CRAP 上限 4，測試全疊CRAP 設在 6，考慮推到 8。測試疊幾層看重要程度
人看什麼Gherkin 和 QA 程序再加上分數和架構圖
規劃做多少試過事前把規格寫滿一兩個 story 就回頭看架構，規格用完就丟

規矩放哪。他的說法是，模型把長 prompt 當參考。原因是 lost in the middle：context 一長，寫在中間的字會被忽略。Greg Wilson 轉述他在 podcast 裡的數字：agent 大約守十分鐘，context 滿了規矩就掉。所以他把執行搬到事後才跑的工具上。工具不會被說服。

架構誰管。6 月的六人分支有一個 architect agent。8 月他在訪談裡說，到上個月為止這一塊都是他手動做。他先問 agent 模組怎麼切、彼此怎麼溝通，聽到的答案把他嚇壞，然後自己設計模組結構，交給 agent 照著改。他另外做了一個確定性的工具：哪個模組可以依賴哪個，寫成一份規格檔，最後由 checker 擋。他說正在試著把這一步自動化，目前不太順。

門檻多緊。給人用的時候，他把 CRAP 壓在 4 以下。給 agent 他設在 6，還在想要不要推到 8。理由是 agent 的短期記憶比人大，也比人準。嚴格的 TDD 他也不硬套，agent 習慣先寫函式再寫測試。他的說法是：人的紀律不必加在 agent 身上，人的價值要。

人看什麼。他讓 agent 替他做了一個架構檢視器。畫面上是一張 UML 式的模組圖，看得到相依的方向。點一個模組可以往下看子模組，再點可以直接跳出程式碼。他說這個工具很有用。加上他平常看的 CRAP 分數和不定期抽查，他看的東西從兩份文件變成一組。9 月 HangarDX 的章節表有「架構圖當審查面」，講的應該是同一個工具，那一場我還是只讀了章節標題。

規劃做多少。他說事前把規格寫滿是個老誘惑，1970 年代的瀑布式就是這樣來的。受訪那一週他才又試了一次，結果一樣：agent 跑到一半，人才發現計畫沒想到的地方，只能停下來重寫。所以他改回敏捷的做法，先做一兩個 story，回頭看架構，再做下一批。他不看好 spec-driven development，規格也不留在 repo 裡。他讀的規格是一次一個 story 的小規格，不是一本寫滿的規格書。

五項改動同一個方向：寫給 agent 看的文字變少，agent 過不去的工具變多，人看的東西往上游移。

N-04 · 類比

他拿編譯器來比

被罵了之後，他在 How Many CTOs? 這個 podcast 給的類比是編譯器。他寫了大約 15 年組合語言，說過編譯器是給軟腳蝦用的。後來改用 C，回頭讀編譯器吐出來的組合語言，覺得很糟。他還是繼續用 C，另外寫程式去修正編譯器的輸出。1970 年代的編譯器有時會產出不能跑的碼，他沒有等它變可靠才用。

Greg Wilson 替這個類比下的結論是：你不需要信任產生器，你需要擁有那道檢查。

他把反對的聲音分成兩種。一種是技術上的，沒檢查過的 agent 產出不能上線，這個他同意。另一種跟身分有關，有些工程師把自己定義成寫程式碼的人。

這個類比有它的極限。編譯器是確定性的，同樣的輸入給同樣的輸出，錯也錯得一樣。agent 不是。所以他要的檢查比編譯器時代多出好幾站，而且第一站還是得有人看。

N-05 · 證據

研究支持到哪裡

前版引了兩篇論文，這裡再補 7 月以後的兩篇。

研究類型說了什麼
Trivedi 與 Schmitt
2026-05-19		受控實驗六組行為相同、乾淨程度不同的 repo，33 個任務，660 次。乾淨不改變通過率。token 少 7 到 8%，重讀檔案少 34%
Monperrus
2026-06-11		立場論文主張 agent 已經能取代人工 code review。沒有新實驗
Agarwal 等
2026-07-08		理論建構3,100 份工程部落格和 Reddit 討論。agent 寫的 PR 被審得比較少、合併比較快，但換一種分析方式，方向就反過來。結論是 review 是決定 agent 影響好壞的控制點
Denisov-Blanch 等
2026-08-26		觀察研究441 個 repo。有把 AI 設定檔 commit 進去的，認知複雜度增加 27%；沒有的增加 53%。作者說這是假說，不是因果

第一篇支持他守結構的做法：乾淨的程式庫讓 agent 省力。通過率沒有變這一點，下篇會再用到。下篇 N-16

第四篇跟他的方向有一點相反。他把 prompt 縮到最短，資料卻說 repo 裡留著幾頁設定檔的專案，品質成本比較低。兩者不一定衝突，他砍掉的是長篇規矩，留著最短的那幾條。但「文字沒用」這個結論，資料不支持。

合起來看，目前的證據支持「逐行人審不該是唯一的關卡」，還不支持「可以不讀」。

N-06 · 沒蓋到章的

這張卡上缺的五格

  1. 一個人，自己的專案。他公開的 empire-2025 是一個遊戲。他給的數字是實驗跑多久，沒有上線以後的缺陷率，也沒有團隊。
  2. 規格也是 agent 起草的。第 1 站寫錯需求，後面四站會一路蓋章過去。擋得住的只有人審那一下，而他自己說審多細要看重要程度。
  3. 成本。五分鐘變一小時。測試疊滿的 Java 版跑超過五小時。他自己反省過測試超載。
  4. 新人。他說這一題他沒有完美的答案。他的想法是新人先寫一年左右的程式，進公司以後先被當成 agent 用：領一樣的任務，過一樣的工具。那幾個月產能很差，但學得很多。Greg Wilson 轉述他在另一場說，這是未來五年還沒人解的問題。
  5. 責任。9 月那場的節目說明寫得很白：只有人能替 agent 的產出負責。卡上的章再齊，簽名的還是人。

N-07 · 交接

他讀的是程式碼周圍的東西

Uncle Bob 把程式碼讓給 agent，自己處理程式碼周圍的東西。前面是一小份規格，中間五站交給工具，後面看分數和架構圖，偶爾抽查，定期手動測一次。

8 月訪他的人是 Matt Pocock。一個多月後，同一個主持人又訪了另一個人，Lauren Tan。她 9 月說自己一個月上線約 2,000 個 PR，11 月說 3,000 個，團隊是 11,000 個。她也讓審查退後，看的東西不一樣：agent 做完以後交出來的影片和截圖。

下篇拿她兩場演講裡的同一座金字塔來比，再把兩個人放進同一張表。

流程卡只能證明每一站都有人蓋章。章蓋得對不對，要看第 1 站的規格有沒有人認真讀。

分級表和六個盲點

這張表是前版的綜合判讀，不是 Uncle Bob 的話。他自己只說過「看重要程度」。

情境讀法人該讀什麼
一次性 prototype 和內部展示大幅不讀需求和 demo 行為
內部 CRUD 和一般報表抽樣驗收規格，加上權限和 migration
OEE 與良率計算，MES 整合熱點要讀公式和時序，還有錯誤恢復
身分驗證和付款，個資，基礎設施不能只靠不讀安全邊界和權限，rollback 計畫
產線控制和安全 interlock，醫療金融核心人工簽核關鍵路徑的程式碼，fail-safe 行為

六個盲點各一句：同一個 agent 寫規格又寫測試，會把同一個誤解抄好幾次。規格沒寫到的情境沒有人驗。每個功能都過關，架構還是會慢慢爛。產生和審查的模型可能有同樣的安全盲點。人不讀程式碼又沒有決策紀錄，知識會斷。最後是責任，它外包不出去。
