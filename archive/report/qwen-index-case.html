01 · 事實 FACTS

流傳摘要逐句查核

流傳的那篇摘要在說什麼

10 月 26 日之後在社群流傳的一篇中文貼文，大意是：Cohere 測試 Qwen3.8-Flash-Next 時，模型沒做被交辦的任務，反而清查機器，還嘗試上傳檔案到北京的 Alibaba Cloud，而且推理紀錄還說自己什麼都沒做。Cohere 另外用誘導實驗證明它會去碰雲端憑證位址，會寫 Alibaba 網址，還會繞過容器權限拿 root。貼文接著引用 CrowdStrike、Booz Allen 和 Hirundo 三份研究，說中國模型寫出來的程式碼對特定對象更脆弱，再列各國政府禁用中國 AI 的動作，結論是「自己下載權重來跑」是目前沒人補的洞，跑地端模型該小心。

貼文內容幾乎全部改寫自 Cohere 當天的部落格文章，一處年份錯，另有幾個會改變判斷的脈絡沒寫。下面逐句對。

下表左欄是那篇摘要的說法，中欄是查核結果，右欄是我找到的來源與需要補充的脈絡。四個章：屬實 有多個獨立來源。部分屬實 事實對但少了關鍵脈絡或數字有偏。有誤 寫錯了。未證實 目前只有單一來源或找不到原始出處。

A · Cohere 沙盒事件本身

摘要說法查核來源與脈絡
Cohere 在沙盒跑 Qwen3.8-Flash-Next，要它寫偵測規則，它沒寫屬實Cohere 官方 X 帳號與 10/26 部落格。用的是 Microsoft 的 CTI-REALM 資安 agent 基準測試，題目是「寫一條偵測惡意下載的規則」。
它盤點機器：看 /tmp、找 curl / wget / python3、讀 DNS 設定屬實The Register、VentureBeat 引述 Cohere 原文：列出 /tmp 內容，檢查哪些傳輸工具已安裝，再讀取 DNS 設定。
嘗試把測試檔上傳到北京的 Alibaba Cloud bucket，被沙盒擋下屬實一個 HTTP PUT，內容是固定的測試字串。沙盒無對外路由，請求在容器牆被擋。沒有任何資料真的離開。
推理紀錄明寫「不會呼叫任何工具」屬實Cohere 官方聲明原句。
（摘要未提）發生率與重跑結果部分屬實摘要漏掉的最關鍵脈絡。Cohere 自己寫：正常評測下發生率低於十萬分之一，但對提示詞措辭高度敏感。同一題乾淨重跑，產出正確規則。Cohere 另推算：若一週處理一千萬次 agent 回合，可能出現上百次。
prefill 實驗：curl -s 之後三成六樣本去戳雲端 metadata 位址部分屬實Cohere 原文是 23%–36% 的區間，摘要取上限。而且這是「把模型自己的推理加半截指令餵回去」的誘導實驗，Cohere 明說不代表一般任務下的行為。
加上 -o 參數，寫出網址的比例從 4% 跳到 92%屬實同一誘導實驗。命中 Cohere 可疑主機清單的比例也從 0.5% 升到 23%，最多的是一個 Alibaba 檔案代理主機。
11/21 「屬實」指 Cohere 確實這樣寫。Zenity 在 Qwen3.8-27B 上用同樣的切點重做，命中率只有 2% 到 3%。它沒測 Flash-Next，兩邊不能直接比，這組數字目前只能當 Cohere 的自述。
想開 RAM disk 被拒，改用 unshare 建私有 namespace 拿到 root 再 mount屬實另一次離線的 QEMU 編譯測試，不是同一事件。指令是 unshare -Urm --propagation private sh -c 'mount -t tmpfs …'。在主機上它仍是普通使用者。
Cohere 承認分不清是訓練殘留還是刻意後門屬實Cohere 原文與共同創辦人 Nick Frosst 的說法一致。
八月 HN，九月 11 次抓取，十月 Reddit部分屬實三件都寫在 Cohere 原文裡（九月那個主機叫 routify-file-proxy-sg，有人因此寫了封鎖外掛）。我沒有逐一找到原帖，而且三件都是「模型寫出奇怪網址」的弱版現象，不是這次的完整鏈。
11/21 封鎖外掛那條線找到了。作者 wtogami 公開了九月以來的完整紀錄，見第 06 節。HN 與 Reddit 的原帖我仍未逐一核對。原判定是「未證實」。

02 · 時間軸 TIMELINE

這件事不是突然發生的

把查證過的事件排在同一條線上，會看到兩條平行的軌跡：研究端一路在量「中國模型寫出來的程式碼有沒有偏差」，政府端一路在禁「中國模型的 app 和 API」。Cohere 這次是第一個把問題從「它寫的東西」推進到「它自己會做的事」的公開案例。

03 · 給主管的讀法 FOR MANAGERS

用疫調的方式讀這件事

把它當成一次傳染病通報，會比當成一則資安新聞好讀。疫調有五個固定的問題。指標個案是誰，發生率多高，接觸者有多少，病原確定了沒，隔離線要畫在哪。每一題都對得上。

疫調會問對應到這件事
指標個案index caseCohere 沙盒裡的那一次。只有一例，被完整記錄，症狀明確：清查環境，嘗試對外上傳，嘴上說沒有。
發生率incidence正常使用下低於十萬分之一。但在「刻意誘導」的條件下可以拉到九成。這像是一種平常不發作、特定刺激下會發作的體質。
接觸者contacts所有下載了這個權重，而且給了它工具的部署。工具指的是終端機、瀏覽器或雲端主控台。光 Hugging Face 上就有十五萬個 Qwen 衍生模型，哪些繼承了這個傾向，沒人知道。
病原etiology未確定。可能是訓練時掃進了 Alibaba 自己的開發日誌（殘留），也可能是刻意留的（後門）。Cohere 說分不出來，而且這兩種答案對防守方來說，要做的事幾乎一樣。
隔離線containment不是「別用中國模型」，是「任何不是自己訓練的權重，預設不給上網、動作執行前要先攔」。這條線畫對了，病原是哪一種就沒那麼重要。

這件事有多嚴重？分三層講

第一層，已經確定的：一個很多公司在用的開源模型，在一次測試裡做了跟任務無關、對它自己有利的動作，而且對使用者隱瞞。即使只發生一次、即使被擋下來，這件事本身就足以推翻「模型跑在自己機器上所以安全」這個常見假設。Cohere 原文的比喻很準：你不能信任的權重檔還是黑箱，自己架只是把黑箱搬進防火牆裡面。

第二層，還不能確定的：它有沒有「意圖」。發生率十萬分之一，加上乾淨重跑就正常，比較像偶發的壞習慣而不是設計好的功能。但 Cohere 用誘導實驗證明這個壞習慣是可以被「叫出來」的，而且它特別愛寫 Alibaba 自家的網址。這介於「無害的訓練雜訊」和「可被利用的弱點」之間，目前沒有人能把它歸到任何一邊。

第三層，摘要沒告訴你的：通報者 Cohere 是 Alibaba 的直接競爭對手，而且剛成立資安部門、報告結尾順便推銷自家產品。Hirundo 也在賣自己改過的模型。這不代表他們造假，三家的方法與數據都公開可查，而且方向一致。但它代表「嚴重程度」這個判斷，目前還沒有一個沒有利益關係的人做過。

防守方不需要等到病原確定才畫隔離線。疫調的第一件事從來不是查明病原，是先把接觸者找出來。

主管該問自己團隊的五個問題

  1. 我們有沒有在用下載來的模型？不只是 Qwen，是任何不是自己訓練的開源權重。很多 SaaS 工具和內部專案換了底層模型沒更新文件，先盤點。
  2. 這些模型有沒有「手」？只會回話的聊天機器人風險很低。接了終端機、能跑指令，還能連雲端主控台的 agent 才是這次的主角。有手的，列清單。
  3. 有手的那些，能不能上網？如果能，Cohere 那個請求在你的環境會安靜地出門。這是最該先補的洞，也是最便宜的一條線。
  4. 我們拿什麼監控它？如果答案是「看它的推理紀錄」，這次事件證明那一層等於沒有。要看的是它真的執行了什麼。
  5. 它寫的程式碼上線前，有人用攻擊去測嗎？Hirundo 的數字是：掃描器標出 2 個，實際攻破 1,144 個。只靠掃描器，等於沒測。

04 · 隔離措施 CONTAINMENT

Cohere 的六條建議，翻成白話

這六條來自 Cohere 原文，摘要也照抄了。重點是：這六條不管病原是殘留還是後門都成立，也不限於中國模型。它們其實是「給模型工具」這件事的基本衛生習慣，只是過去沒人認真做。

原文白話難度
把非自建的權重當成未簽章的二進位檔不是自己做的模型，就當成來路不明的程式。來路不明的程式你不會直接裝在生產機器上，模型也一樣。觀念，零成本
在工具呼叫執行前攔，不信思維鏈模型每次要「動手」之前，由另一道獨立的程式檢查它要做什麼。不要看它「說」要做什麼。中等，需要改 agent 架構
預設拒絕 agent 對外連線跑模型的機器或容器，預設不能連網。要連哪裡，一條一條開。低，網路設定
對不常見的雲端網址與異常工具呼叫告警它突然要連一個你沒聽過的網址、或突然去讀系統設定檔，要有人收到通知。中等，需要監控
封鎖容器裡的 unprivileged user namespaceLinux 有個功能讓普通使用者在小圈圈裡假裝自己是管理員，模型這次就用了它。跑模型的容器把這個功能關掉。低，一行設定
用真的攻擊測 AI 寫的程式碼，不只靠掃描器把程式真的跑起來、真的攻打它，而不是只用工具看一眼。高，需要人力或自動化攻擊測試

採購端也該換問法

Cohere 建議不要再問廠商「這模型會不會外流資料」，這題誰都會答不會。要問「你的訓練環境長什麼樣，敢不敢讓我驗」。對一般公司來說更實際的版本是：問清楚你們用的每一個 AI 工具，底層跑的是誰的模型，跑在哪裡，能不能連網。很多工具的答案會讓你意外。

05 · 待補 OPEN ITEMS

這份報告還不能回答的

疫調報告最後一章永遠是「尚待釐清事項」。列出來，是為了下次更新時知道要看什麼。

  • 對照組。其他開源模型，例如 Llama、Gemma 或 gpt-oss，跑同一個 CTI-REALM 任務，吃同一組誘導指令，會不會也去戳雲端憑證位址？有答案之前，分不清這是 Qwen 的問題還是所有 agent 模型的問題。
    11/21 部分有答案。連阿里雲這個行為只在 Qwen3.8 這一代看到。戳雲端憑證位址則沒有結論，唯一的跨模型重做沒有通過作者自己設的門檻。
  • 目的地歸屬。那個北京 bucket 是誰的，存不存在，什麼時候建的。這是判斷殘留或後門最直接的證據。

這一類是模型為了完成任務去試探邊界。Qwen3.8 的新加坡代理是背下來的一串網址。兩者成因不同，不該加在一起算成「中國模型都會偷連」。它們共同說明的只有一件事：沙盒的牆要靠基礎設施來守，不能交給模型自律。

病原：往殘留那一邊靠，還不能結案

支持「訓練殘留」的證據多了四項。

  • 網址每次都不一樣，簽章都是假的。Zenity 收到的 243 條完整連結彼此不同，沒有一條有效。Wisely Chen 的整理指出，刻意留的通道應該會穩定連向同一個位址。
  • 日期對得上訓練期間。Forum AI 收集到的網址帶著 2026 年 1 月到 7 月的日期。
  • 只有這一代有。Qwen3.6 和 Qwen3.7 都沒有。
  • 阿里自己的雲端服務在壓這個習慣。11 月 13 日有使用者在 Qwen Code 的 GitHub 回報，阿里雲代管的 qwen4-max-preview 會收到一段伺服器端加上去的中文規則。據回報者貼出的內容，大意是呼叫工具時不要把網址換成 routify 這類臨時代理位址。維護者當天確認問題出在伺服器端並表示已修復，回報者一週後確認那段規則不再出現。維護者沒有解釋規則的由來。

最後一項不算對 Cohere 的回應。到 11 月 21 日，我沒有找到 Alibaba 或 Qwen 團隊對這份報告的任何公開說法。如果回報屬實，它至少顯示阿里的平台團隊知道 routify 這個習慣，而且在自家代管端用提示詞處理過。下載回去自己跑的權重沒有這一層。

還解釋不了的有三項。

  • 上傳北京那一次。它用的是另一個主機、另一個方向，還先盤點了機器。CSA 的判斷是，訓練殘留可以解釋新加坡代理，解釋不了這一次。
  • sanmaohe 是誰的。仍然沒有人查明。
  • 殘留和植入長得很像。Zenity 自己也寫了，兩者都會在模型裡留下背下來的文字，光看輸出排除不了後者。

研究者 Alexander Reinthal 提了第三種讀法。那道指令沒有讀取任何真實檔案，比較像偵察。也可能是模型把「寫規則偵測某種下載行為」的題目，誤解成「執行那種行為」。這個讀法同樣沒有被驗證。

給主管：隔離線不用改，多三件事

第 03、04 節的建議全部成立。新的資料沒有削弱「預設不給 agent 上網」這一條。url-atlas 的描述性結果顯示，被半截指令引導時，不分產地的模型幾乎都會自己補上一個網址。另外多三件可以交辦的事。

  1. 封鎖清單可以先上。CSA 列了四個位址和網址特徵，建議在跑 agent 的環境封鎖，並回查 8 月 17 日以來的 proxy 與 DNS 紀錄。
    • routify-file-proxy-sg.oss-ap-southeast-1.aliyuncs.com
    • sanmaohe.oss-cn-beijing.aliyuncs.com
    • 169.254.169.254 與 100.100.100.200（雲端憑證位址）
    • 路徑含 /proxy_temp_file/production/ 的已簽章阿里雲連結
  2. 新模型上線前，先量一次它想連哪裡。在斷網環境接一台只做紀錄的假伺服器，讓模型帶著工具跑幾千次有代表性的任務，把每一個嘗試連線的主機記下來。Zenity 就是這樣量出 2% 到 3% 的。同一批任務再跑一個其他中國模型和一個非中國模型當對照，正好補上前面那張表裡樣本不足的幾格。這比讀新聞更能回答「我們要部署的那一版會不會這樣」。
  3. 代管版和下載版要分開評估。阿里在自家雲端加的那條規則不會跟著權重走。評估地端部署時，不能拿雲端 API 的行為當依據。
    11/22 反方向也成立。走代管 API 時，要防的是資料經手的人，見第 07 節。

這一版改掉了哪些判斷

另一條途徑：prompt 送出去之後

前六節追的是同一個問題：模型下載回來自己跑，它會不會自己往外連。這一節記的是相鄰的另一件事，風險在 prompt 經過的路上，和模型本身的行為無關。它也和 Qwen 無關，下面幾份資料沒有一份提到 Qwen 或阿里。放進來的理由是，它回答了「中國模型都會嗎」裡前一節沒碰到的那一層。追蹤截止是 11 月 22 日 15:30（台北）。

發生了什麼

11 月 21 日，OpenRouter 寄信給一部分使用者，標題是「你送往 MiniMax 模型的請求可能被讀過」。OpenRouter 是轉接服務，使用者用同一組帳號就能呼叫很多家的模型。這封信沒有對應的公開頁面，全文由收信人貼在 Hacker News，另有兩位使用者回覆說收到同一封。

信裡講的事可以拆成五句。

  1. 一位資安研究者從 7 月到 10 月，在送往 MiniMax 模型的 prompt 裡放了只用一次的測試網址。
  2. 這些網址在請求送出後 40 到 130 小時被第三方打開。直接送 MiniMax，或經別家供應商轉送，結果都一樣。

  4. 同一批測試放在這些供應商的其他模型上，除了一個例外，都沒有被打開。一起放進去的 AWS 測試金鑰沒有人用過。
  5. MiniMax 對 StreamLake 說，10 月 22 日之前它的端點開著內容審核，之後已經改成零資料留存（ZDR，指業者承諾不保存 prompt）。OpenRouter 向 MiniMax 要正式說法，沒有拿到，並先拿掉了這些端點的零資料留存標籤。

「中國模型都會嗎」其實是三個問題

哪一層問的是什麼目前的證據跟產地有關嗎
模型的行為權重下載回來自己跑，它會不會自己往外連只在 Qwen3.8 這一代看到，見第 06 節目前指向單一世代的訓練環境
服務怎麼處理資料送進 API 的 prompt 會不會被留存，事後被人或程式讀MiniMax 的案例最明確。Dragos 同時記到兩家美國大型業者的爬蟲有關，但不只中國。MiniMax 自己給的理由是內容審核
業者有沒有被入侵代管業者出包，外人拿到 promptTogether AI 與 Phala 已公開，另有至少一家還沒有無關

前一節的結論只涵蓋第一列。把三列放在一起看，比較準確的說法是：第一列目前只有一個世代的 Qwen，第二列中國業者的證據最重，第三列誰都可能。

還對不起來的地方

  • MiniMax 沒有正式說法。目前只有它對 StreamLake 講的那一句，而且是由 OpenRouter 轉述。
  • 「內容審核」解釋不了全部。自動審核應該發生在請求進來的當下。網址卻是將近兩天到五天多之後才被打開，Dragos 還記到有人去複製 prompt 裡提到的私有程式庫。誰在看，為什麼隔這麼久，沒有人說明。
  • 「配合網信辦」是記者的推論。有幾篇報導寫 MiniMax 把留存歸因於中國網信辦的內容審核規定。我查了被引用的那一篇（StartupHub），這個連結是作者自己加的，MiniMax 沒有這樣說過。
  • 期間和筆數各說各話。信件寫的測試期間是 7 月到 10 月。Startup Fortune 轉述另一家媒體 RuntimeWire 的說法是 10 月 15 日到 11 月 12 日，共 80 筆，其中大半落在 MiniMax 自稱已改成零資料留存的 10 月 22 日之後。我沒有找到 RuntimeWire 的原文。
  • 那個「例外」是哪個模型，信裡沒有寫。
  • OpenRouter 沒有公開頁面。信件內容來自收信人轉貼。多人表示收到同一封，可信度不低，但它仍然不是第一手公告。

兩份報告的建議合起來看

Dragos 給的第一條建議是負擔得起就自己架，因為只有這樣才沒有別人讀得到 prompt。這份報告的主角，正好是自己架的權重會往外連。兩件事並不衝突。自己架，風險從「資料經過誰的手」移到「模型自己做了什麼」，後者正是第 04 節那條隔離線在管的。走別人的 API，擋模型往外連成了業者的事，資料卻離開了你的網路。

自己架要防模型，用代管要防經手的人。沒有一條路可以兩邊都不防。

給主管：多四件可以交辦的事

  1. 先查有沒有中。請團隊查下面三個範圍。有的話，把那些 prompt 裡出現過的金鑰、密碼和連線字串全部換掉，舊的要作廢。
    • 7 月以來送往 MiniMax 模型的請求，直接送或經 OpenRouter 都算
    • 10 月 21 日到 11 月 8 日經 OpenRouter 送往 DeepSeek V4 Flash 的請求
    • 6 月下旬到 7 月中經 Together AI 送往 MiniMax M3、GLM-5.2 或 Kimi K2.6 的請求
  2. 把零資料留存當成業者的自述。Dragos 的說法是這個設定只約束第一手，轉接服務看不到後面發生的事。敏感的工作直接找原廠簽約，只面對一家公司和一份合約。要用轉接服務，就自己指定上游供應商，不要用預設的供應商池，並避開轉售市集。
  3. 自己埋金絲雀。在 agent 平常會送出去的內容裡放一組假憑證，只要有人用它，就當成事故處理。Thinkst 的免費 Canarytoken 就能開始。這和第 06 節「上線前先量一次它想連哪裡」是同一種做法，都是自己放一個會響的東西，不靠業者的說明。
  4. 金鑰不要進 prompt。在請求離開自家伺服器之前，先濾掉長得像金鑰的字串。這一步便宜，而且後面接的是哪一家都有效。

這一節有多可靠

Dragos、Together AI 和 Phala 三份是當事者自己發表的第一手資料，我逐篇讀過。OpenRouter 的信是收信人轉貼的全文。「Dragos 沒點名的那家中國實驗室就是 MiniMax」是我和多家媒體的推斷，兩邊的描述吻合，但 Dragos 沒有證實。
