00 · THREE AXES

三件事不在同一層，所以才能疊在同一專案

學員進場時最常見的誤解是把 TDD、DDD、Event-Driven 當成三個互相替代的架構選項。它們回答的問題不同，失敗的樣子也不同。

名稱它是什麼它回答放進本專案的位置
企業流程再造BPR 方法論 · 先問「這步該不該存在」 誰為顧客創造價值？哪段交接只是部門牆？ 場站值班、計費對帳、故障通報、總部派工
領域驅動設計DDD 設計方法論 · 戰略 + 戰術 這個詞誰擁有？邊界在哪？不變條件是什麼？ 停車會話、充電會話、帳單、工單、派工
事件驅動EDA 架構風格 · 實作範式 事實如何跨邊界流動，而不把兩個系統鎖死？ 場站 ↔ 帳務 ↔ 總部維運
測試驅動TDD 開發實踐 · 過程 這條不變條件現在就能跑紅、轉綠、再重構嗎？ 每個 Aggregate 與每個 Event Handler

流程再造決定什麼不該被自動化；DDD 決定什麼值得被模型化；事件決定邊界怎麼呼吸；TDD 決定模型明天還能不能改。

本教案的強迫順序不是口味，是因果：沒有被再造過的流程，寫進 DDD 只會得到一個很精緻的舊組織圖。沒有領域語言的事件，只會得到一個會飛的 Excel。

01 · THE SITE

先把現場講清楚，再准許畫方塊

系統有兩層地理、三種錢、一條故障生命週期。任何後續模型若對不上這三句，就是在發明另一家公司。

現地 · SITE

停車場 + 樁

閘門、車位、OCPP、值班室

總部 · HQ

維運派工

資產、工單、技術員、備品

錢的種類

三種

停車費 · 電費 · 維修成本

允許的中斷

總部可掛

場站必須能獨自收車、充電、出帳草稿

角色（進工作坊要坐在桌上的人）

  • 場站值班長：管閘門、車位占用、客人糾紛、樁顯示異常。
  • 充電營運：管費率時段、啟動授權、度數、異常中止。
  • 帳務：管停車單與充電單要不要合併、發票、對帳、爭議。
  • 總部調度：管哪一座樁掛了、誰去修、SLA、備品是否在車上。
  • 技術員：只認工單上的樁編號、故障碼、是否可遠端重啟。

本教案的產品假設

連鎖場站。每站既有既有停車場系統（LPR / 月票 / 臨停），又新上充電樁（OCPP 1.6/2.0.1）。總部要看全國樁健康度並派工。顧客可能是臨停車主，也可能是合約車隊。場站在專線中斷時仍要能放行與充電，對帳可事後補。

02 · BPR

企業流程再造：先刪交接，再談系統

Hammer 的原意不是「把紙本搬上雲」。再造問的是：這一步是為顧客創造結果，還是為了部門之間互相證明自己做過？充電場站最貴的不是電，是人在兩套系統之間當 API。

現況（As-Is）——值班長用身體串起來的流程

  1. 車子進閘，停車場系統開一張停車單。充電系統一無所知。
  2. 車主自行找有槍的車位。油車占充電位，靠巡邏與罰單。
  3. 插槍後，車主再開一個 App 或刷第二張卡。失敗就按對講機。
  4. 充電結束，充電系統出一張單；離場時停車場再出一張單。兩張對不上。
  5. 樁故障：值班長拍照、打電話、總部助理開 Excel。技術員到場才發現備品不對。
  6. 月底三個單位對帳，爭議單在 Line 群流轉。
演練 1 切換 As-Is / To-Be 同一條顧客旅程，看哪些角色從鏈上消失

    再造原則（本專案只留四條）

    1. 以結果為單位，不以部門為單位。顧客要的是「車能走、帳能清」，不是「兩個系統都有紀錄」。
    2. 現場擁有完整的現場交易。進場、占位、充電、離場的進行中狀態，總部讀得到，但批不准卡住閘門。
    3. 故障是一等公民流程，不是客服例外。樁說自己壞了，工單就該存在；電話只是備份通道。
    4. 對帳是事後對齊，不是同步鎖。允許短暫的兩邊數字不一致，但每筆都要有因果事件可追溯。

    BPR 課後必做

    用紅筆在 As-Is 上圈出「這一步只因為兩個系統不說話才存在」的活動。圈得到的，不准直接做成 microservice。先決定它該消失，還是該變成一個事件。

    03 · EVENT STORMING

    用事件風暴，把再造結果變成領域語言

    Event Storming 是 BPR 走到 DDD 的橋。牆上先只准貼「已經發生的事實」，不准先貼服務名稱。橘色是命令、黃色是事件、紫色是政策、粉紅色是聚合、藍色是角色。本單元不寫程式。

    一句話檢驗：這張黃貼能不能被現場的人唸出來，而不需要解釋系統名詞？

    04 · STRATEGIC DDD

    戰略設計：邊界比類別重要

    連鎖場站最容易畫成一個「超級充電平台」Bounded Context。那是大泥球的學名。本專案預設五個上下文——不是因為微服務流行，是因為它們換語言、換生命週期、換一致性邊界。

    上下文它說的話一致性獨立存活
    場站停車Parking 進場、車位、停車會話、放行 一輛車同一時間一個進行中停車會話 總部掛掉仍能開關閘
    充電會話Charging 連接器、授權、計量、中止原因 一個連接器同一時間一個進行中會話 OCPP 在場站；總部只訂閱結果
    計費帳務Billing 費率套用、帳單、發票、爭議 一張帳單的金額一旦開立就不可默默改 可延遲出帳，不可丟失事件
    資產維運AssetOps 樁、槍、韌體、健康、工單 一座樁同一時間一個進行中根因工單 總部主系統；場站只上報
    調度派工Dispatch 技術員、路線、SLA、備品預留 一張工單同一時間一個主責技術員 可離線執行，回報後再對齊

    Context Map 上只准出現的關係

    • OCPP 對充電上下文是防腐層（ACL），不是領域模型。ChargePointStatus 不是 Ubiquitous Language。
    • 停車與充電是伙伴 + 事件下游：停車知道「這格是充電格」，但不管電。
    • 帳務對停車 / 充電是顧客—供應者：上游事件是契約，帳務不得回呼凍結會話。
    • 資產維運對充電是遵奉者：接受 ChargerFaulted 的語意，不要求場站懂工單狀態機。
    • 派工在維運內部，對外不發「技術員已出發」給顧客帳務。
    演練 3 這個概念該住在哪個上下文？

    05 · REQUIREMENTS FROM DDD

    DDD 如何「成為」需求，而不是補一章詞彙表

    許多團隊在規格書末頁貼上 Entity / Value Object 清單，以為那就是 DDD。本教案把需求寫成三種可驗收的句子：領域規則、跨上下文契約、例子。沒有例子的規則不准進 Sprint。

    Ubiquitous Language（節錄，進場第一天就要釘死）

    用語是不是
    停車會話從進場到放行的一次占用契約閘門硬體日誌
    充電會話從插槍授權到結束計量的一次能量交付OCPP Transaction
    連接器一把槍的業務身份Modbus 位址
    帳單對顧客的求償文件MeterValue 陣列
    工單總部對一根故障的承諾一通值班電話
    故障申告設備已聲明自己無法按契約供電App 連不上的客訴

    領域規則寫成可驗收需求（範例）

    情境：進行中的充電會話不可被第二次 Start 覆寫
既有：連接器 CP-A12-2 已有會話 S-991，狀態為 Charging
當：同一連接器收到 StartCharging（任何 idTag）
則：拒絕；原會話不變；發布 ChargingStartRejected(reason=ConnectorOccupied)

情境：樁故障必須產生且只產生一張根因工單
既有：樁 CP-A12 健康
當：收到 ChargerFaulted(code=GroundFailure) 兩次，間隔 8 秒
則：只開啟工單 WO-… 一張；第二次只附加「重複申告」紀錄

情境：離場放行不依賴總部
既有：總部連線中斷；停車費已預估
當：值班長執行人工放行並留下原因
則：閘門開啟；發布 ParkingManuallyReleased；帳務稍後對齊

    需求的完成定義

    一條規則進 Backlog 時必須同時帶：擁有它的 Bounded Context、觸發命令、成功時的領域事件、拒絕時的事件或錯誤、一個數字例子（度數、金額、時間）。缺一項就還是願望。

    06 · EVENT-DRIVEN DESIGN

    事件怎麼設計：場站能離線，總部能追因果

    Event-Driven 在本專案不是「全部丟進 Kafka」。它解決的是 BPR 留下的那條原則：跨部門的事實用事件走，跨部門的鎖用原則禁止。

    兩種事件，不准混名

    Domain Event

    上下文內部的事實。用領域語言。可以同步、可以在同一交易裡收集。例如 ChargingCompleted 被同一個 Charging 應用服務拿去通知讀模型。

    Integration Event

    跨上下文的契約。穩定、版本化、經過 Outbox、永遠非同步。例如 charging.session.completed.v1 給帳務與維運。

    本專案的最小事件契約

    事件發布者訂閱者備註
    parking.vehicle_entered.v1Parking占位政策、可選充電預約含 plate、siteId、lane
    charging.session.started.v1ChargingBilling 草稿、Parking 占用確認含 connectorId、idTag
    charging.session.completed.v1ChargingBilling含 Wh、起迄、中止原因
    parking.session.closed.v1ParkingBilling含時長、放行方式
    charging.charger.faulted.v1ChargingAssetOps含 faultCode、是否仍帶電
    ops.work_order.opened.v1AssetOpsDispatch、場站看板場站只讀，不回寫狀態機
    ops.work_order.closed.v1AssetOpsCharging 健康、SLA關閉後才允許自動恢復「可售」

    必須一起教的配套，否則 EDA 會爛

    • Transactional Outbox：先寫聚合與 outbox 同一筆交易，再由 relay 發佈。禁止在領域物件裡直接打 broker。
    • 至少一次 + 冪等處理：帳務用 sessionId 當去重鍵；維運用 chargerId + faultFingerprint 去重。
    • Saga / Process Manager 只放跨上下文政策：「故障 → 開單 → 派工 → 修復驗證 → 恢復可售」是政策，不是 Charging 聚合的私務。
    • 命令與事件分開：總部不能對場站發 ForceStopSession 當日常手段；緊急停權走明確的安全命令，並留下審計事件。

    反模式

    把 OCPP 的 StatusNotification 原封不動當 Integration Event 廣播到全公司。下游會被協定細節綁死，換樁商就全炸。防腐層要先翻譯成「充電器已申告故障」。

    07 · TDD

    TDD：先讓規則紅掉，再准許寫產品程式
