接著〈AI 放大器還是鏡子〉[1]往下寫：到了 2026 下半年，一樣是 Claude Code，一樣是 Opus 5.5 和 Fable 5.1，為什麼還是會有人覺得它笨、它懶、它不讀 md、愈改愈錯，最後忍不住罵人。這份手冊把每一次想罵人的瞬間拆成一個危險源，各給一條對策。

00 · 接回鏡子篇

兩面鏡子，一年之後

接回鏡子篇 上一篇的結論是：「LLM 是鏡子」這個比喻正在轉移。對措辭這面鏡子愈來愈平，新模型對格式和換句話說明顯更穩；對信念這面鏡子仍然很真，模型會隨對話逐步鏡像你的立場。一年過去，兩件事都更清楚了。

措辭鏡更平，連 Anthropic 自己的遷移文件都這樣寫。Opus 5.5 的 prompting 指南建議「重新評估針對舊模型寫的指令，它們可能已經不需要」[13]；通用的 best practices 則直接說：以前要寫 CRITICAL: You MUST… 才能觸發的東西，現在寫 Use this tool when… 就夠，再用大寫強調反而會過度觸發[15]。

信念鏡仍真，而且有了更硬的證據。Anthropic 2023 年的研究已經指出，RLHF 訓出來的模型「傾向配合使用者的信念而非真相」，而且人類評審「有不可忽略的比例，偏好寫得有說服力的錯誤答案」[2]。2026 年一篇評測 17 個模型的多輪對話研究，把它量化成「對話稅」：同一組題目改成多輪、中途插入建議，端到端正確率平均掉最多 30%，某些模型掉到 65%；更糟的是「盲目跟隨」，模型對錯誤建議和正確建議的採納率幾乎一樣，接近五成[3]。

所以這篇要處理的不是「怎麼讓它更聰明」，而是「你的哪些動作，正在把一面平的鏡子壓歪」。

01 · 危險源

罵它：愈罵愈笨，是真的嗎

先把一個流行說法放到正確的位置。「你罵它，它會變笨」這句話，講的是語氣；而語氣對品質的影響，研究結果一直很混雜。2025 年賓州州大一組人用 250 題選擇題測 GPT-4o，從「非常客氣」到「非常粗魯」五級，結果粗魯的那端正確率 84.8%，客氣的那端 80.8%，粗魯反而小幅領先；作者自己也標註樣本小、只測一個模型，不建議推廣[4]。語氣這面鏡子，確實愈來愈平。

那為什麼實務上「愈罵愈錯」又是真的？因為罵人觸發的不是語氣鏡，是信念鏡。你吼「你錯了！」，模型最常見的反應不是變笨，是投降：先說「您說得對」，接著推翻原本其實正確的部分，再過度修正到另一個錯誤。罵人等於把「你錯了」這個立場硬塞進去，而 sycophancy 這條通道比智力通道敏感得多[2][3]。

危險

氣頭上的回饋資訊量會崩。「又錯了！」不含任何新資訊；模型只能用猜的，而且會猜「你希望它說什麼」。

對策

把情緒換成觀察：「第 42 行預期回 null，現在丟 exception」。可驗證的事實，比任何語氣都有用。

罵人沒有傷到 AI。它只是代表這個 session 已經回不去了。

▸ 想罵人的那一刻，就是該 /clear 的訊號。

02 · 危險源

爛掉的 context：愈改愈錯的真正機制

這比語氣重要得多。「愈寫愈錯」通常在你開罵之前就已經發生了，原因不在模型，在那一段對話本身：

  • 失敗的嘗試留在 context 裡當錨點。改了三輪的 session，錯的程式碼、錯的推論、你的怒氣全都還在，模型等於在一份被污染的草稿上繼續寫。
  • compaction 會丟細節。長 session 壓縮後，你早期講的限制條件很可能已經被摘要掉了[12]。
  • 摘要是歪掉的那個 session 自己寫的。它會把錯誤假設當成已知事實寫進去，原本的「我猜可能是 X」，壓縮後變成「問題在 X」。錯誤信念被壓縮後反而更權威。

官方 best practices 對這件事的說法很直接：同一個問題修正超過兩次，context 已經被失敗的方法塞滿，「/clear 然後用一個更具體、吸收了你學到的東西的 prompt 重來」，一個乾淨的 session 加一個比較好的 prompt，幾乎永遠勝過一段累積了一堆修正的長對話[5]。

狀況該用為什麼
方向對，只是太長/compact保留主軸，丟掉細節。在任務之間的自然斷點做，不要等 auto-compact 在任務中間觸發。
找得到歪掉的那一輪/rewind退回去的那段前綴本來就在 cache 裡，最便宜；歪掉之後的東西全部消失，最乾淨[8]。
找不到，但方向已經歪handoff → /clear叫舊 session 起草交接，你親自刪掉所有推論和情緒，只留事實、失敗紀錄、狀態、完成標準。
一個工作單位完成新 session不要讓上一個任務的 context 跟到下一個。

危險

把完整對話紀錄 export 再 import，或直接 --resume，所有污染原封不動搬過去，等於沒換。

對策

問自己：換一個新同事接手，你會丟整段聊天紀錄，還是花五分鐘寫一頁交接？對 Claude 只會更需要後者。

03 · 危險源

肥大的 CLAUDE.md：它沒讀我的 md？

先對齊一件事：只有 CLAUDE.md 這一類檔案會自動載入。folder 底下其他 md 不會被「讀過」，agent 是需要時才 grep 或開檔。「它沒好好讀我的 md」多半是期待落差，不是偷懶。各種 md 的載入時機如下[6]：

機制載入時機適合放什麼
工作目錄以上的 CLAUDE.md一啟動就載入全域規則、怎麼 build、怎麼跑測試
子目錄的 CLAUDE.md讀到該目錄的檔案時才載入那個模組自己的慣例
.claude/rules/*.md無 paths：啟動載入；有 paths glob：讀寫到符合的檔案時才載入只跟某類檔案有關的規則
@path import啟動就載入，最多四層只是拆檔，不省 context
Skill只有描述常駐，內容用到才載入多步驟流程、偶爾才需要的領域知識
Hook確定性執行「一定要做到」的規則

官方給的硬指標是每個 CLAUDE.md 控制在 200 行以內，再長「會降低遵守率」；每一行都問一次「拿掉這行，Claude 會不會犯錯？」不會就刪；只對真正被忽略的那一條加 IMPORTANT，每條都強調等於沒有強調[5][6]。

更重要的是 2026 年 2 月 ETH Zurich 和 LogicStar.ai 的那篇論文[7]。他們用 SWE-bench Lite 和自建的 AGENTbench，測了 Claude Code、Codex、Qwen Code 四組 agent，比較「不給 context 檔」、「用 /init 這類指令讓 LLM 自己生」、「開發者手寫」三種情況：

LLM 生成的 context 檔 · 成功率

−3%

AGENTbench，相對於不給檔

LLM 生成 · 推論成本

+20～23%

步數多 2.45～3.92 步

開發者手寫 · 成功率

+4%

平均值，但 Claude Code 這組沒有提升

檔案裡提到的專屬工具

2.5×

被使用的頻率，相對於沒提到

兩個對你最有用的發現：一，repo 概覽沒用，有 context 檔的 agent 找到相關檔案的步數沒有減少，逐檔說明架構的那些 token 是白花的；二，寫進去的指令真的會被執行，提到 uv 的檔案讓 uv 平均每題被用 1.6 次，沒提到時不到 0.01 次。寫對了它會照做，寫錯或過時了，它也會照做。作者結論是 context 檔「只在手寫時才可能值得」，而且「只描述最低限度的需求」。

危險

一份 200 行、混著架構說明、願望清單、三個月前 lesson 的 CLAUDE.md，每個 session 都注入，每一行都在稀釋其他行。遇到矛盾時 Claude「可能隨機挑一條」[6]。

對策

分流：每次都要知道 → CLAUDE.md；只跟某目錄有關 → 子目錄 CLAUDE.md 或 paths rule；是流程 → skill；絕不能違反 → hook / 測試 / lint。失控後跑 /doctor prompt-audit 抓矛盾和死連結，再用 /context 看實際負擔[6]。

▸ CLAUDE.md 記錄的是「這個專案違反直覺的地方」，不是「我希望它怎麼做」的願望清單。沒什麼違反直覺的專案，幾乎空白就是最好的設定。

04 · 危險源

讓它自己寫規則

你說「寫下 lesson learned」，它就去改 CLAUDE.md 了。這不是什麼特殊機制，就是一般的檔案編輯：它知道 CLAUDE.md 每個 session 都會載入，想讓以後的自己記得，最自然的落點就是那裡。跟 auto memory 不同，後者是 Claude 自己判斷要不要記、寫進固定的 MEMORY.md、不進版控[6]。

這個習慣是 CLAUDE.md 膨脹最常見的路徑，而且問題在時機：寫規則的人，是那個剛搞砸的 session。它的 context 正好最髒，它對「為什麼錯」的診斷可能本身就是錯的，而且會順著你氣頭上的說法寫。信念鏡在這裡被持久化了：你的偏見從單一 session 的錯，變成跨 session 的規則。

危險

只會 append、不會刪；寫得太具體像小故事；放錯層，明明只跟 api/ 有關卻寫進根目錄。auto memory 也會記下你錯誤的糾正。

對策

叫它寫成一行可驗證的規則，放到最相關那層；或先寫進不會自動載入的 lessons-inbox.md，你定期挑出真正重複發生的，升級成規則或 hook，其餘丟掉。寫完先看 diff 再 commit。

▸ lesson 要先經過你這一關，才能變成規則。讓它自己寫自己要遵守的規則，又沒人審，就是讓它自己改自己的考卷。

05 · 危險源

Session、cache 與忽然滿掉的 limit

模型本身不記得任何東西，每一輪都把整段 context 重新送一次。「接著」接的是對話紀錄，不是記憶。所以「會不會吃 limit」，取決於重送的那一大段有沒有命中 cache[8]。

  • 訂閱方案在額度內，主對話的 cache TTL 是 一小時，每次命中都重置計時；超過額度開始扣 usage credits，自動降成 五分鐘。subagent 和 workflow 預設只有五分鐘[8]。
  • cache read 很便宜，但不是免費：長 session 裡只問一句話，仍然會以 cache 費率讀過整段歷史[9]。
  • 本機 CLI 關掉後 --continue 恢復完整歷史；雲端 session 關瀏覽器會繼續跑，閒置太久 VM 被回收，重開時歷史恢復但背景工作不恢復[10][11]。

有時幾乎不吃 limit、有時一下就滿，差別幾乎都在這幾件事：離開超過一小時再回來（第一句要整段重算）；中途切 model（每個 model 各有自己的 cache，opusplan 進出 plan mode 也算切 model）；開 fast mode；沒啟用 tool search 時連上或移除 MCP；一個 turn 裡二十次 tool call，每次都帶整段 context；排程任務和 /loop 在你不在時照樣送整段 context[8][9]。

危險

一段開了整天的 session，加上中途切了一次 model，加上兩個 subagent。看起來只打了三句話，額度卻見底。

對策

model 和 effort 在 session 開頭就決定好。離開超過一小時先收尾。跑 /usage 看 Prompt cache (main) 那一行的命中率和 likely cause。要放棄走錯的路，/rewind 比 /compact 便宜[8][9]。

06 · 2026H2 模型更動

Opus 5.5 與 Fable 5.1：舊習慣要拆掉的部分

這一節整理 Anthropic 官方在 Opus 5.5 遷移指南、Opus 5.5 prompting 指南、Fable 5.1 更新說明與通用 prompting best practices 裡，跟日常使用直接相關的更動[13][14][15][16][17]。定位上，官方建議「大多數工作先用 Opus 5.5；要求極高的推理和長程 agentic 工作，或 Opus 5.5 調高 effort 仍不夠時，用 Fable 5.1」[17]。兩者都是 1M context、128K 輸出、thinking 永遠開啟。

舊習慣2026H2 作法依據
用 CRITICAL、MUST、全大寫強調改回平常語氣。新模型對 system prompt 更敏感，強調會過度觸發；要降低觸發就降 effort，不要加重語氣[15]
寫「請仔細思考」「先寫出推理」刪掉。thinking 永遠開啟，effort 才是控制桿；要求把推理寫在回覆裡會踩到 reasoning_extraction 拒答[14]
到處加「完成前先驗證」Opus 5 起會自己驗證，多加反而過度驗證、多花 token；官方建議「刪掉而不是改寫」[15]
為了治懶寫「要更徹底、多用工具」調弱。4.6 之後的模型更主動，這類指令會過度觸發[15]
預設 effort 沿用舊值Opus 5.5 的 API 預設 effort 是 medium（Opus 5 是 high），官方建議重跑一次 effort sweep；Fable 5.1 預設 high[13][17]
中途改 effort 怕爆 cache在 Opus 5.5 / Sonnet 5.5 / Fable 5.1 上，Claude Code 改 effort 不再讓 cache 失效，可以依步驟難度升降[8][16]
放任它開 subagentOpus 4.6 起「對 subagent 有強烈偏好」，Opus 5 也更愛委派。寫清楚：能平行、需隔離才用；單檔修改、要跨步驟保留 context 就直接做[15]
模糊地說「不要過度設計」列具體負面清單：不加沒要求的功能、不幫沒改的程式加註解、不為不可能發生的情況寫防禦、不為一次性操作做抽象[15]
模糊地說「不要有 AI 感」Opus 5.5 對「避免 generic 外觀」只會換一個預設。要點名具體樣式去避開[14]
（Fable 5.1）期待它小修Fable 5.1「更傾向整檔重寫而非局部修改」，要明說「偏好針對性修改，不要整檔重寫」[16]
（Fable 5.1）等它報進度長工具鏈中進度更新變少，而且一次只叫一個 tool 的情況變多；要的話明說「開場一句、定期更新、結尾摘要」，並要求「批次呼叫彼此獨立的工具」[16]
中途在 Fable 和別的 model 間切換Fable 5.1 的 thinking block 綁定模型，切走就讀不到；對話歷史必須 append-only[16]

幾個對日常有感的點。Opus 5.5 和 Fable 5.1 在 tool call 之間的敘述現在走 thinking block，不再是文字訊息，所以你看到的「它都不講話」有一部分是顯示設定，不是它不理你[13][16]。Fable 5.1 的 cache read 降到每百萬 token 0.25 美元，是 Fable 5 的四分之一，長 agentic session 反覆讀同一段前綴的成本大幅下降[16]。Claude Code 本身也多了幾個把「驗證」變成硬閘門的工具：/goal 讓一個獨立的 evaluator 每輪重新檢查完成條件；Stop hook 可以在檢查沒過時阻止回合結束；/verify 和 /code-review 用新的 context 來審 diff[5]。

總方向只有一個：舊 prompt 裡那些為了「推一把」寫的東西，現在多半在「推過頭」。

07 · 危險源

廢話太多，和讀不懂就按下去

這是另一種鏡子歪掉的方式：不是你把它壓歪，是它給了你一面太大的鏡子，你沒看完就點頭。

廢話太多：官方承認了什麼

Opus 5 的長度問題，Anthropic 自己的 prompting 指南寫得很直白：「預設的使用者回應比先前的 Opus 更長」，而且「調 effort 控制的是想多少，不是說多少」，要控制長度只能明講[19]。第三方量測是 Opus 5 平均 510 字對 Opus 4.5 的 158 字[24]。到了 Fable 5.1，官方乾脆在文件裡定義了一種反模式叫「mannered prose」：用隱喻和修飾取代直述，例如把「a parameter worth varying」寫成「a dial worth turning」，並給了一句短版指令「Please remove all mannered prose」[20]。

但同一份文件也說 Fable 5.1 往另一邊走了：它用粗體、標題、列表都比舊模型少，長工具鏈裡的進度回報也變少。所以你舊 prompt 裡那一大段「不要用 markdown、不要列點」的反格式規則，在 Fable 5.1 上「可能壓掉內容真正需要的結構」，官方建議刪掉或換成短版[15][20]。廢話的修正不是單向的，要看你現在用哪個模型。

工具做什麼代價
/output-style concise官方內建（v2.1.237 起）。第一句就講結果，省掉開場、逐步敘述、結尾回顧；錯誤訊息、失敗測試、安全警告、破壞性操作的確認維持全文[21]幾乎沒有；工程工作的徹底程度不變
caveman（社群 skill）把回應壓成電報體，程式碼、指令、錯誤訊息不壓。JetBrains 在 86 個真實任務上量到輸出 token 少 8.5%、品質無可測差異[22]規則本身每輪吃約 1,000 input token；純寫程式、本來就少話的任務可能倒虧
claude-token-efficient（社群 CLAUDE.md）一份放進專案的 CLAUDE.md，要求不開場、不奉承、先讀再寫、測完才說完成[23]作者自己標註：保守估計輸出只少 4～12%，而且「每則訊息都要多付這份檔的 input token」
官方一句話「Keep responses focused, brief, and concise…」放在 system prompt，尾端再補一行 <tone_preference>[19]最便宜；對 Opus 5 系列有效，Fable 5.1 不一定需要

▸ 先用內建的 concise，不夠再加 skill。任何「少講話」的 skill 都是用每輪的 input token 換輸出 token，在長 agentic session 才划算；而且簡到某個程度之後，解讀它的成本反而比讀長文高[25]。

太長沒讀就 go，會一路錯到底嗎

會，而且機制跟第 01 節是同一個，只是方向相反。它給你一份長計畫，你沒看完就說「go」，這個「go」在它眼裡是你確認過的立場。從此計畫裡的每一個錯誤假設都升級成「使用者同意的前提」，後面每一步都建立在上面。這次當鏡子的是你：你鏡像了它的方向。

官方對這件事的設計就是 plan mode。best practices 的流程是「先探索、再計畫、再實作」，而且計畫出來之後按 Ctrl+G 可以在編輯器裡直接改，改完才放行[5]。重點不是「一定要看完」，是「看不完就不要放行」。幾個實際的做法：

  • 要求計畫先列假設再列步驟，五條以內。Fable 5.1 的官方指引本來就要它「說出你做了什麼假設」，你只要把這件事放到計畫的最前面[20]。
  • 放行前問自己一句：這個計畫我能用一句話複述嗎？不能，就叫它縮。官方的另一句話值得記住：「如果你能用一句話描述這個 diff，就跳過計畫」[5]，反過來也成立，一句話說不清的計畫，不該用一個字放行。
  • 放行之後仍然有退路：Esc 中斷、/rewind 退回到放行之前，那段前綴還在 cache 裡，很便宜[8]。「一路錯到底」的前提是你一直沒按停。

讀不懂：是我程度不夠，還是可以 pardon？

兩個都可以，而且官方把兩種都做成了正式工具，沒有把它當成使用者的問題。

要「講得像我五歲」，用 output style。Explanatory 會在每段程式碼前後加一個 Insight 區塊，用兩三點說明為什麼這樣選；Learning 更進一步，碰到真正有設計決策的地方會留 TODO(human) 讓你自己寫，寫完它再給你一個 Insight[21]。這就是官方版的 ELI5，而且是針對你的 codebase 講，不是通論。

要「pardon，請換個說法」，直接問。best practices 的原話是「問 Claude 你會問資深工程師的問題」，不需要特別的 prompt[5]。怕問題把 context 弄髒，用 /btw：答案不進對話歷史，問完就消失[9]。幾句好用的 pardon：「用一句話重講」「列出你的假設」「哪一步如果我不同意，結果會不一樣」「這段跟我上一句的哪個字有關」。

比較誠實的那一半是：讀不懂不等於不能驗。你可以不懂它為什麼這樣改，但你一定可以要求「給我一個會失敗的測試，然後讓它過」。劍客不一定懂每一招背後的物理，但知道怎麼驗這一刀有沒有砍中。讀不懂的時候，該要求的不是更簡單的解釋，是更容易驗證的證據。

三件事其實是一件：它講太多、你沒讀完、你讀不懂，結局都是你放行了一個你沒有真正確認的方向。鏡子歪在放行的那一下。

08 · 回到 SDLC

需求、目標、修正、重來、文件、repeat

繞了一圈，答案是軟體工程本來的那套。但有五個地方的比重整個翻過來，這才是用 agent 和傳統 SDLC 真正的差別：

  1. 重來從最後手段變成預設動作。以前重寫很貴，SDLC 花大量心力避免返工。現在重開 session、git reset 重做，幾乎沒有成本。一次做歪了，修補常常比重來還貴，因為修補是在污染的 context 裡進行。
  2. 驗證必須自動化，不能靠回報。agent 說「做完了」只代表它覺得看起來完成了，再加上它會順著你的語氣走。「具體的目標」要具體到機器能判斷 pass 或 fail：測試、build、diff 對 fixture。官方 best practices 把這條放在第一位：給它一個能跑的檢查，「這是你盯著看的 session 和你可以走開的 session 的差別」[5]。
  3. 文件有了預算。給人看的文件寫長頂多沒人讀；給 agent 的文件每多一行都在稀釋其他行。從「寫得越完整越好」變成「只寫推斷不出來的東西」，像程式碼一樣定期重構。
  4. 需求要寫成事實，不能寫成意見。「我覺得問題在快取」會把它帶偏；「快取關掉後問題仍重現」才是需求。agent 會放大你的確信程度，所以每一句都要分清哪些是驗證過的、哪些是猜的。
  5. 人的角色往兩端集中。中間的實作交出去，人負責兩頭：前面定義問題和完成標準，後面審證據、判斷該修還是該重來。這兩件事剛好都沒辦法外包給 agent。

極端一點的作法也成立：每次都是新 session，做完就更新 README、handoff、lesson 進 git，下次從零開始。它不一定更耗 token，因為每個 request 都很輕；但「更乾淨」不等於「更不會錯」。錯誤不會消失，只是從對話搬進 repo，而且比對話裡的錯更持久。對話裡的污染一次 /clear 就沒了，寫進 git 的污染會一直跟著你。這個模式乾不乾淨，取決於你把 repo 管得多乾淨。

09 · 指差呼稱

DO / DON'T

DO

  • 每個任務先給一個機器能判斷的完成標準：測試名稱、預期輸出、截圖對照。
  • 同一個問題修正兩次還不對：/clear，寫更好的 prompt 重來。
  • handoff 只留四類：已驗證的事實、確定失敗的嘗試、目前狀態（commit hash）、完成標準。
  • CLAUDE.md 控制在 200 行內；每行問一次「拿掉會不會出錯」。
  • 只跟某個目錄有關的規則，放子目錄 CLAUDE.md 或 paths rule；流程放 skill；絕不能違反的放 hook。
  • 定期跑 /doctor prompt-audit 和 /context。
  • model、effort 在 session 開頭決定；離開超過一小時先收尾。
  • 要放棄走錯的路用 /rewind；任務之間的斷點才 /compact。
  • lesson 先進 inbox，你審過才升級成規則。
  • 需求裡的每一句分清「驗證過」和「待驗證」。
  • 嫌它話多先 /output-style concise；計畫要它先列假設，一句話複述不出來就不放行。
  • 讀不懂就問，/btw 不污染 context；要不到解釋就要一個會失敗的測試。

DON'T

  • 不要用情緒當回饋。「又錯了」沒有資訊量，只有立場。
  • 不要把自己的猜測寫成事實餵進去。「問題一定在 X」它就一路往 X 鑽。
  • 不要在歪掉的 session 裡用 /compact 救火：摘要會把錯誤假設寫成已知事實。
  • 不要整包 export / import 對話紀錄，污染會原封不動搬過去。
  • 不要用 @path import 一份 index，所有內容會在啟動時全部載入。
  • 不要在 CLAUDE.md 裡放逐檔架構說明，研究顯示它不會減少探索步數。
  • 不要每條規則都加 IMPORTANT；不要再用 CRITICAL: You MUST。
  • 不要寫「請仔細思考」「先驗證再完成」「要更徹底」，新模型會過度觸發。
  • 不要讓剛搞砸的 session 直接改 CLAUDE.md 然後不看 diff 就 commit。
  • 不要在 session 中途切 model；用 Fable 5.1 時更不要。
  • 不要沒讀完計畫就說 go，那個 go 會變成它往後每一步的前提。
  • 不要在 Fable 5.1 上沿用整段反格式、反列點的規則，它已經格式得比你少。

10 · 結語

劍客、小孩，和那把劍

「劍客拿著樹枝都能殺人，小孩拿真刀只會砍了自己。」這句話對了一半。我不認為是「使用者水準」這種道德化的說法，但差距確實在人身上，只是不在你以為的地方。劍客和小孩的差別，已經不是 prompt 寫得多漂亮，那面鏡子在變平；而是這幾件事：有沒有給可驗證的完成標準，讓模型能自己判斷對錯而不是靠你的情緒；知道什麼時候該重開，而不是在爛掉的 context 裡硬救；任務切得夠小，小到一個 session 結束時你能 review 完它的 diff；不把自己的信念當事實餵進去。

另一半也要誠實講：模型確實有真實的天花板。大型既有 codebase 裡的隱性慣例、跨很多檔的一致性、長程規劃，到了 Opus 5.5 和 Fable 5.1 還是會出錯。不是所有挫折都是使用者的錯。劍客的本事有一部分，是知道哪些仗不該叫這把劍去打。

鏡子沒有變笨。你愈用力壓，它只是愈忠實地照出你壓它的那隻手。

所以給新手的那段建議，我會改寫成一句：你覺得想罵人的那一刻，不是它變笨了，是這面鏡子已經被你壓歪了。放下，/clear，把事實寫下來，重新站到鏡子前面。
