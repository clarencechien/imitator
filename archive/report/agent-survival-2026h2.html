00 · 接回鏡子篇

兩面鏡子，一年之後

接回鏡子篇 上一篇的結論是：「LLM 是鏡子」這個比喻正在轉移。對措辭這面鏡子愈來愈平，新模型對格式和換句話說明顯更穩；對信念這面鏡子仍然很真，模型會隨對話逐步鏡像你的立場。一年過去，兩件事都更清楚了。

措辭鏡更平，連 Anthropic 自己的遷移文件都這樣寫。Opus 5.5 的 prompting 指南建議「重新評估針對舊模型寫的指令，它們可能已經不需要」[13]；通用的 best practices 則直接說：以前要寫 CRITICAL: You MUST… 才能觸發的東西，現在寫 Use this tool when… 就夠，再用大寫強調反而會過度觸發[15]。

信念鏡仍真，而且有了更硬的證據。Anthropic 2023 年的研究已經指出，RLHF 訓出來的模型「傾向配合使用者的信念而非真相」，而且人類評審「有不可忽略的比例，偏好寫得有說服力的錯誤答案」[2]。2026 年一篇評測 17 個模型的多輪對話研究，把它量化成「對話稅」：同一組題目改成多輪、中途插入建議，端到端正確率平均掉最多 30%，某些模型掉到 65%；更糟的是「盲目跟隨」，模型對錯誤建議和正確建議的採納率幾乎一樣，接近五成[3]。

所以這篇要處理的不是「怎麼讓它更聰明」，而是「你的哪些動作，正在把一面平的鏡子壓歪」。

01 · 危險源

罵它：愈罵愈笨，是真的嗎

先把一個流行說法放到正確的位置。「你罵它，它會變笨」這句話，講的是語氣；而語氣對品質的影響，研究結果一直很混雜。2025 年賓州州大一組人用 250 題選擇題測 GPT-4o，從「非常客氣」到「非常粗魯」五級，結果粗魯的那端正確率 84.8%，客氣的那端 80.8%，粗魯反而小幅領先；作者自己也標註樣本小、只測一個模型，不建議推廣[4]。語氣這面鏡子，確實愈來愈平。

那為什麼實務上「愈罵愈錯」又是真的？因為罵人觸發的不是語氣鏡，是信念鏡。你吼「你錯了！」，模型最常見的反應不是變笨，是投降：先說「您說得對」，接著推翻原本其實正確的部分，再過度修正到另一個錯誤。罵人等於把「你錯了」這個立場硬塞進去，而 sycophancy 這條通道比智力通道敏感得多[2][3]。

危險

氣頭上的回饋資訊量會崩。「又錯了！」不含任何新資訊；模型只能用猜的，而且會猜「你希望它說什麼」。

對策

把情緒換成觀察：「第 42 行預期回 null，現在丟 exception」。可驗證的事實，比任何語氣都有用。

罵人沒有傷到 AI。它只是代表這個 session 已經回不去了。

▸ 想罵人的那一刻，就是該 /clear 的訊號。

02 · 危險源

爛掉的 context：愈改愈錯的真正機制

這比語氣重要得多。「愈寫愈錯」通常在你開罵之前就已經發生了，原因不在模型，在那一段對話本身：

  • 失敗的嘗試留在 context 裡當錨點。改了三輪的 session，錯的程式碼、錯的推論、你的怒氣全都還在，模型等於在一份被污染的草稿上繼續寫。
  • compaction 會丟細節。長 session 壓縮後，你早期講的限制條件很可能已經被摘要掉了[12]。
  • 摘要是歪掉的那個 session 自己寫的。它會把錯誤假設當成已知事實寫進去，原本的「我猜可能是 X」，壓縮後變成「問題在 X」。錯誤信念被壓縮後反而更權威。

官方 best practices 對這件事的說法很直接：同一個問題修正超過兩次，context 已經被失敗的方法塞滿，「/clear 然後用一個更具體、吸收了你學到的東西的 prompt 重來」，一個乾淨的 session 加一個比較好的 prompt，幾乎永遠勝過一段累積了一堆修正的長對話[5]。

狀況該用為什麼
方向對，只是太長/compact保留主軸，丟掉細節。在任務之間的自然斷點做，不要等 auto-compact 在任務中間觸發。
找得到歪掉的那一輪/rewind退回去的那段前綴本來就在 cache 裡，最便宜；歪掉之後的東西全部消失，最乾淨[8]。
找不到，但方向已經歪handoff → /clear叫舊 session 起草交接，你親自刪掉所有推論和情緒，只留事實、失敗紀錄、狀態、完成標準。
一個工作單位完成新 session不要讓上一個任務的 context 跟到下一個。

危險

把完整對話紀錄 export 再 import，或直接 --resume，所有污染原封不動搬過去，等於沒換。

對策

問自己：換一個新同事接手，你會丟整段聊天紀錄，還是花五分鐘寫一頁交接？對 Claude 只會更需要後者。

03 · 危險源

肥大的 CLAUDE.md：它沒讀我的 md？

先對齊一件事：只有 CLAUDE.md 這一類檔案會自動載入。folder 底下其他 md 不會被「讀過」，agent 是需要時才 grep 或開檔。「它沒好好讀我的 md」多半是期待落差，不是偷懶。各種 md 的載入時機如下[6]：

機制載入時機適合放什麼
工作目錄以上的 CLAUDE.md一啟動就載入全域規則、怎麼 build、怎麼跑測試
子目錄的 CLAUDE.md讀到該目錄的檔案時才載入那個模組自己的慣例
.claude/rules/*.md無 paths：啟動載入；有 paths glob：讀寫到符合的檔案時才載入只跟某類檔案有關的規則
@path import啟動就載入，最多四層只是拆檔，不省 context
Skill只有描述常駐，內容用到才載入多步驟流程、偶爾才需要的領域知識
Hook確定性執行「一定要做到」的規則

官方給的硬指標是每個 CLAUDE.md 控制在 200 行以內，再長「會降低遵守率」；每一行都問一次「拿掉這行，Claude 會不會犯錯？」不會就刪；只對真正被忽略的那一條加 IMPORTANT，每條都強調等於沒有強調[5][6]。

更重要的是 2026 年 2 月 ETH Zurich 和 LogicStar.ai 的那篇論文[7]。他們用 SWE-bench Lite 和自建的 AGENTbench，測了 Claude Code、Codex、Qwen Code 四組 agent，比較「不給 context 檔」、「用 /init 這類指令讓 LLM 自己生」、「開發者手寫」三種情況：

LLM 生成的 context 檔 · 成功率

−3%

AGENTbench，相對於不給檔

LLM 生成 · 推論成本

+20～23%

步數多 2.45～3.92 步

開發者手寫 · 成功率

+4%

平均值，但 Claude Code 這組沒有提升

檔案裡提到的專屬工具

2.5×

被使用的頻率，相對於沒提到

兩個對你最有用的發現：一，repo 概覽沒用，有 context 檔的 agent 找到相關檔案的步數沒有減少，逐檔說明架構的那些 token 是白花的；二，寫進去的指令真的會被執行，提到 uv 的檔案讓 uv 平均每題被用 1.6 次，沒提到時不到 0.01 次。寫對了它會照做，寫錯或過時了，它也會照做。作者結論是 context 檔「只在手寫時才可能值得」，而且「只描述最低限度的需求」。

危險

一份 200 行、混著架構說明、願望清單、三個月前 lesson 的 CLAUDE.md，每個 session 都注入，每一行都在稀釋其他行。遇到矛盾時 Claude「可能隨機挑一條」[6]。

對策

分流：每次都要知道 → CLAUDE.md；只跟某目錄有關 → 子目錄 CLAUDE.md 或 paths rule；是流程 → skill；絕不能違反 → hook / 測試 / lint。失控後跑 /doctor prompt-audit 抓矛盾和死連結，再用 /context 看實際負擔[6]。

▸ CLAUDE.md 記錄的是「這個專案違反直覺的地方」，不是「我希望它怎麼做」的願望清單。沒什麼違反直覺的專案，幾乎空白就是最好的設定。

04 · 危險源

讓它自己寫規則

你說「寫下 lesson learned」，它就去改 CLAUDE.md 了。這不是什麼特殊機制，就是一般的檔案編輯：它知道 CLAUDE.md 每個 session 都會載入，想讓以後的自己記得，最自然的落點就是那裡。跟 auto memory 不同，後者是 Claude 自己判斷要不要記、寫進固定的 MEMORY.md、不進版控[6]。

這個習慣是 CLAUDE.md 膨脹最常見的路徑，而且問題在時機：寫規則的人，是那個剛搞砸的 session。它的 context 正好最髒，它對「為什麼錯」的診斷可能本身就是錯的，而且會順著你氣頭上的說法寫。信念鏡在這裡被持久化了：你的偏見從單一 session 的錯，變成跨 session 的規則。

危險

只會 append、不會刪；寫得太具體像小故事；放錯層，明明只跟 api/ 有關卻寫進根目錄。auto memory 也會記下你錯誤的糾正。

對策

叫它寫成一行可驗證的規則，放到最相關那層；或先寫進不會自動載入的 lessons-inbox.md，你定期挑出真正重複發生的，升級成規則或 hook，其餘丟掉。寫完先看 diff 再 commit。

▸ lesson 要先經過你這一關，才能變成規則。讓它自己寫自己要遵守的規則，又沒人審，就是讓它自己改自己的考卷。

05 · 危險源

Session、cache 與忽然滿掉的 limit

模型本身不記得任何東西，每一輪都把整段 context 重新送一次。「接著」接的是對話紀錄，不是記憶。所以「會不會吃 limit」，取決於重送的那一大段有沒有命中 cache[8]。

  • 訂閱方案在額度內，主對話的 cache TTL 是 一小時，每次命中都重置計時；超過額度開始扣 usage credits，自動降成 五分鐘。subagent 和 workflow 預設只有五分鐘[8]。
  • cache read 很便宜，但不是免費：長 session 裡只問一句話，仍然會以 cache 費率讀過整段歷史[9]。
  • 本機 CLI 關掉後 --continue 恢復完整歷史；雲端 session 關瀏覽器會繼續跑，閒置太久 VM 被回收，重開時歷史恢復但背景工作不恢復[10][11]。

有時幾乎不吃 limit、有時一下就滿，差別幾乎都在這幾件事：離開超過一小時再回來（第一句要整段重算）；中途切 model（每個 model 各有自己的 cache，opusplan 進出 plan mode 也算切 model）；開 fast mode；沒啟用 tool search 時連上或移除 MCP；一個 turn 裡二十次 tool call，每次都帶整段 context；排程任務和 /loop 在你不在時照樣送整段 context[8][9]。

危險

一段開了整天的 session，加上中途切了一次 model，加上兩個 subagent。看起來只打了三句話，額度卻見底。

對策

model 和 effort 在 session 開頭就決定好。離開超過一小時先收尾。跑 /usage 看 Prompt cache (main) 那一行的命中率和 likely cause。要放棄走錯的路，/rewind 比 /compact 便宜[8][9]。

06 · 危險源

記憶：四本帳、一把明朝的劍

「它更懂我了」這句話在 2026 年 10 月有四個不同的意思，而且彼此不通。先把帳本分清楚，再談要不要整理。

帳本記什麼、誰寫範圍怎麼看、怎麼改
claude.ai 記憶關於你：偏好、背景、進行中的事。Claude 在對話中持續寫，不再等對話結束才摘要chat 與雲端 Cowork 共用，本機 Cowork 不算；每個 Project 各自獨立[29]Settings 裡逐條讀、改、刪，或直接跟它說要記或忘
Claude Code auto memory關於這個 repo：你的糾正、專案決策、外部資源在哪。Claude 在 session 中寫單一機器 × 單一 repo，在 ~/.claude/projects/<repo>/memory/；官方原話「not shared across machines or cloud environments」[6]/memory 開資料夾，就是普通 md；MEMORY.md 只載入前 200 行或 25KB
Projects 記憶（雲端）關於這個 project：需求、決策、坑。各雲端 thread 寫Project 內所有雲端 thread 共用；官方明說它「跟本機 auto memory 是分開的，雖然都用 MEMORY.md 索引」；Pro/Max 公測中[26]Project settings › Memory 讀改刪
CLAUDE.md專案規則。你寫跟著 git 走，是唯一所有 surface 都走得到的一本自己編輯；/doctor prompt-audit

所以在 claude.ai 聊過的東西，CLI 不知道；CLI 在筆電上記的，雲端 session 看不到；雲端 Project 記的，本機又看不到。官方目前沒有任何一份文件說要把這四本合起來，chat 和 Cowork 那一本也是 2026 年 8 月底才剛合併[30]。

要自己整合嗎

不建議硬做同步。四本帳的分工其實有道理：一本記你是誰，一本記這個 repo 的眉角，一本記這個 project 的決策，真正重疊的只有「你的個人偏好」那一層。處理方式：跨所有 repo 的偏好放 ~/.claude/CLAUDE.md；要讓雲端也看得到的東西，只能進 repo 的 CLAUDE.md 或 git 裡的檔案。想把 auto memory 進版控，可以用 autoMemoryDirectory 把它指到一個 git 資料夾[6]，代價是多台機器會衝突，而且第 04 節的問題會跟著來：Claude 自己寫的筆記沒人審就進了 repo。

▸ git 就是你的整合層。不需要另一套同步機制。

Dream：有沒有實裝

社群從 2026 年 3 月起流傳一個叫 auto-dream 的機制：每 24 小時、累積超過 5 個 session，Claude Code 會在背景把 auto memory 做一次整併，刪過期、合重複、把相對日期改成絕對日期。截至 2026-10-04 查到的狀況是：官方 memory 文件一個字都沒提；官方 CHANGELOG 全文 8,200 行，沒有任何一條含 dream 或 consolidation[27]；但 /memory 的 UI 裡確實看得到 Auto-dream 的開關，有社群 plugin 乾脆自己做了一個 /dream，理由寫得很白：「Claude Code 的 /memory 顯示 /dream，但這個指令還不存在」[31]。

所以它是「程式碼裡有、文件裡沒有、changelog 裡沒有」的狀態。官方明確有做的是比較保守的版本：MEMORY.md 接近上限時提醒 Claude「合併或刪掉過時條目」，每次寫入蓋一個 modified 時間戳讓 Claude 判斷這條有多舊，超過上限就直接報錯要它重寫索引[6]。這些是 2.1.186 到 2.1.214 之間進的，查得到[27]。

危險

把 dream 當成已經在幫你整理，於是從不打開 /memory 看。記憶肥大跟 CLAUDE.md 肥大不一樣：CLAUDE.md 的代價是稀釋，記憶的代價是過時的事實被很有自信地套用。它照出的是三個月前的你，而且照得很有把握。

對策

把 dream 當作「有也好，沒有也不靠」。claude.ai 記憶每季掃一次，auto memory 在 repo 換大方向時掃一次。刪：已放棄的構想、「正在做」「下週要」這類會過期的狀態、散在兩處的重複。留：偏好、穩定背景、仍在跑的專案、已經做過的決定。決定比過程有價值。

Session 裡的 todo，現在變成什麼

你記得的那個 todo 清單，在新模型上已經預設拿掉了。CHANGELOG 2.1.233：「Todo/task-tracking tools（TaskCreate/Get/Update/List、TodoWrite）在 Opus 4.8、Sonnet 5、Fable 5、Mythos 5 和之後的模型上不再提供」；2.1.268 進一步改成只在 Claude 3.x 到 Opus 4.7、Sonnet 4.6 這些舊模型上才有，其他要自己設 CLAUDE_CODE_ENABLE_TODO_TOOLS=1 開回來[27]。理由官方沒寫，但對照第 08 節就看得懂：新模型本來就會自己規劃、自己驗證，再給它一個清單工具只是多一個會過度觸發的東西。Cowork 這類 host 可以自己把清單開回來當進度 widget，但那是 host 的決定，不是模型的習慣。

接手它位置的是三樣東西，各管一段：

  • 計畫檔：plan mode 寫出來的計畫存在磁碟上，compaction 之後會重新注入，是少數能撐過壓縮的狀態[12]。短期的「這次要做什麼」放這裡。
  • /goal：不是清單，是一個完成條件加一個獨立的評審模型，每回合檢查條件有沒有達成，沒達成就自己開下一回合；評審不跑指令、不讀檔，只看 Claude 在對話裡端出來的證據[28]。「做到什麼才算完」放這裡。
  • Projects 的 thread：跨 session 的待辦，一個任務一個雲端 thread，project 對話本身只看最近訊息、最近 thread 和 project memory，不帶完整歷史[26]。「這陣子要做的一串事」放這裡。

/tasks 這個指令還在，但它現在列的是背景工作：subagent、背景 shell、workflow，不是你的待辦[27]。名字沒變，裡面的東西換了。

Memory bank：明朝的劍

Cline 的 memory bank（projectbrief.md、activeContext.md、progress.md 那一套）是 2024 年底到 2025 年初的產物。Cline 自己在 2025 年就說它「是一種用 custom instructions 和文件做持久 context 的方法論，不是固定功能」[32]。它當年要解的問題是：模型沒有任何跨 session 的記憶、沒有自動載入的規則檔、context 很小，所以每次開工先讀五份 md 把狀態灌回去。

這三個前提到 2026 年都不成立了。跨 session 記憶有了（四本）；規則檔有了（CLAUDE.md、rules、skill，各有載入時機）；context 到了 1M。memory bank 的核心動作「每次開工先讀全部狀態檔」，放到今天就是第 03 節講的那件事：啟動時灌一大包 agent 其實不需要的 context，而且 ETH 那篇測出來 repo 概覽根本不會減少探索步數[7]。連 Cline 自己的生態到 2026 年也往 lifecycle hook 走：在 TaskStart、TaskComplete 這些事件點自動注入和回收，「沒有一個模型會忘記去呼叫的 MCP 工具」[33]。社群評論也承認：memory bank「只有你更新它的紀律有多好，它就有多好；沒有自動擷取、沒有衝突處理、除了 git 沒有版本」[34]。

它留下來的東西只有一個，而且是對的：狀態要寫在檔案裡、進 git，不要留在對話裡。這一條今天仍然成立，第 02 節的 handoff 就是它。但「一包檔案、每次全讀、模型自己維護」這個形狀，是明朝的劍。民國要用的是：常駐的只放 CLAUDE.md 裡那幾十行，其餘按需載入；短期狀態放計畫檔和 handoff，做完就刪；完成標準交給 /goal 或測試去判，不交給一份叫 progress.md 的自我申報。

四本帳沒有一本會自己變乾淨。「更懂你」和「更不懂你」之間，差的就是有沒有人定期把流水帳拿掉。

07 · 2026H2 模型更動

Opus 5.5 與 Fable 5.1：舊習慣要拆掉的部分

這一節整理 Anthropic 官方在 Opus 5.5 遷移指南、Opus 5.5 prompting 指南、Fable 5.1 更新說明與通用 prompting best practices 裡，跟日常使用直接相關的更動[13][14][15][16][17]。定位上，官方建議「大多數工作先用 Opus 5.5；要求極高的推理和長程 agentic 工作，或 Opus 5.5 調高 effort 仍不夠時，用 Fable 5.1」[17]。兩者都是 1M context、128K 輸出、thinking 永遠開啟。

舊習慣2026H2 作法依據
用 CRITICAL、MUST、全大寫強調改回平常語氣。新模型對 system prompt 更敏感，強調會過度觸發；要降低觸發就降 effort，不要加重語氣[15]
寫「請仔細思考」「先寫出推理」刪掉。thinking 永遠開啟，effort 才是控制桿；要求把推理寫在回覆裡會踩到 reasoning_extraction 拒答[14]
到處加「完成前先驗證」Opus 5 起會自己驗證，多加反而過度驗證、多花 token；官方建議「刪掉而不是改寫」[15]
為了治懶寫「要更徹底、多用工具」調弱。4.6 之後的模型更主動，這類指令會過度觸發[15]
預設 effort 沿用舊值Opus 5.5 的 API 預設 effort 是 medium（Opus 5 是 high），官方建議重跑一次 effort sweep；Fable 5.1 預設 high[13][17]
中途改 effort 怕爆 cache在 Opus 5.5 / Sonnet 5.5 / Fable 5.1 上，Claude Code 改 effort 不再讓 cache 失效，可以依步驟難度升降[8][16]
放任它開 subagentOpus 4.6 起「對 subagent 有強烈偏好」，Opus 5 也更愛委派。寫清楚：能平行、需隔離才用；單檔修改、要跨步驟保留 context 就直接做[15]
模糊地說「不要過度設計」列具體負面清單：不加沒要求的功能、不幫沒改的程式加註解、不為不可能發生的情況寫防禦、不為一次性操作做抽象[15]
模糊地說「不要有 AI 感」Opus 5.5 對「避免 generic 外觀」只會換一個預設。要點名具體樣式去避開[14]
（Fable 5.1）期待它小修Fable 5.1「更傾向整檔重寫而非局部修改」，要明說「偏好針對性修改，不要整檔重寫」[16]
（Fable 5.1）等它報進度長工具鏈中進度更新變少，而且一次只叫一個 tool 的情況變多；要的話明說「開場一句、定期更新、結尾摘要」，並要求「批次呼叫彼此獨立的工具」[16]
中途在 Fable 和別的 model 間切換Fable 5.1 的 thinking block 綁定模型，切走就讀不到；對話歷史必須 append-only[16]

幾個對日常有感的點。Opus 5.5 和 Fable 5.1 在 tool call 之間的敘述現在走 thinking block，不再是文字訊息，所以你看到的「它都不講話」有一部分是顯示設定，不是它不理你[13][16]。Fable 5.1 的 cache read 降到每百萬 token 0.25 美元，是 Fable 5 的四分之一，長 agentic session 反覆讀同一段前綴的成本大幅下降[16]。Claude Code 本身也多了幾個把「驗證」變成硬閘門的工具：/goal 讓一個獨立的 evaluator 每輪重新檢查完成條件；Stop hook 可以在檢查沒過時阻止回合結束；/verify 和 /code-review 用新的 context 來審 diff[5]。

總方向只有一個：舊 prompt 裡那些為了「推一把」寫的東西，現在多半在「推過頭」。

08 · 危險源

廢話太多，和讀不懂就按下去

這是另一種鏡子歪掉的方式：不是你把它壓歪，是它給了你一面太大的鏡子，你沒看完就點頭。

廢話太多：官方承認了什麼

Opus 5 的長度問題，Anthropic 自己的 prompting 指南寫得很直白：「預設的使用者回應比先前的 Opus 更長」，而且「調 effort 控制的是想多少，不是說多少」，要控制長度只能明講[19]。第三方量測是 Opus 5 平均 510 字對 Opus 4.5 的 158 字[24]。到了 Fable 5.1，官方乾脆在文件裡定義了一種反模式叫「mannered prose」：用隱喻和修飾取代直述，例如把「a parameter worth varying」寫成「a dial worth turning」，並給了一句短版指令「Please remove all mannered prose」[20]。

但同一份文件也說 Fable 5.1 往另一邊走了：它用粗體、標題、列表都比舊模型少，長工具鏈裡的進度回報也變少。所以你舊 prompt 裡那一大段「不要用 markdown、不要列點」的反格式規則，在 Fable 5.1 上「可能壓掉內容真正需要的結構」，官方建議刪掉或換成短版[15][20]。廢話的修正不是單向的，要看你現在用哪個模型。

工具做什麼代價
/output-style concise官方內建（v2.1.237 起）。第一句就講結果，省掉開場、逐步敘述、結尾回顧；錯誤訊息、失敗測試、安全警告、破壞性操作的確認維持全文[21]幾乎沒有；工程工作的徹底程度不變
caveman（社群 skill）把回應壓成電報體，程式碼、指令、錯誤訊息不壓。JetBrains 在 86 個真實任務上量到輸出 token 少 8.5%、品質無可測差異[22]規則本身每輪吃約 1,000 input token；純寫程式、本來就少話的任務可能倒虧
claude-token-efficient（社群 CLAUDE.md）一份放進專案的 CLAUDE.md，要求不開場、不奉承、先讀再寫、測完才說完成[23]作者自己標註：保守估計輸出只少 4～12%，而且「每則訊息都要多付這份檔的 input token」
官方一句話「Keep responses focused, brief, and concise…」放在 system prompt，尾端再補一行 <tone_preference>[19]最便宜；對 Opus 5 系列有效，Fable 5.1 不一定需要
ASD-STE100（Karpathy，2026-10）叫它照航太手冊的受控語言寫：一詞一義、一句 20 字內、主動語態。一個規範名就載入一整套約束，模型大多讀過[35]最便宜的一列，但嚴格版會靠刪事實變短，實測掉 46.8%[37]；用寬鬆版或「八成」。詳見番外篇

▸ 先用內建的 concise，不夠再加 skill。任何「少講話」的 skill 都是用每輪的 input token 換輸出 token，在長 agentic session 才划算；而且簡到某個程度之後，解讀它的成本反而比讀長文高[25]。

太長沒讀就 go，會一路錯到底嗎

會，而且機制跟第 01 節是同一個，只是方向相反。它給你一份長計畫，你沒看完就說「go」，這個「go」在它眼裡是你確認過的立場。從此計畫裡的每一個錯誤假設都升級成「使用者同意的前提」，後面每一步都建立在上面。這次當鏡子的是你：你鏡像了它的方向。

官方對這件事的設計就是 plan mode。best practices 的流程是「先探索、再計畫、再實作」，而且計畫出來之後按 Ctrl+G 可以在編輯器裡直接改，改完才放行[5]。重點不是「一定要看完」，是「看不完就不要放行」。幾個實際的做法：

  • 要求計畫先列假設再列步驟，五條以內。Fable 5.1 的官方指引本來就要它「說出你做了什麼假設」，你只要把這件事放到計畫的最前面[20]。
  • 放行前問自己一句：這個計畫我能用一句話複述嗎？不能，就叫它縮。官方的另一句話值得記住：「如果你能用一句話描述這個 diff，就跳過計畫」[5]，反過來也成立，一句話說不清的計畫，不該用一個字放行。
  • 放行之後仍然有退路：Esc 中斷、/rewind 退回到放行之前，那段前綴還在 cache 裡，很便宜[8]。「一路錯到底」的前提是你一直沒按停。

讀不懂：是我程度不夠，還是可以 pardon？

兩個都可以，而且官方把兩種都做成了正式工具，沒有把它當成使用者的問題。

要「講得像我五歲」，用 output style。Explanatory 會在每段程式碼前後加一個 Insight 區塊，用兩三點說明為什麼這樣選；Learning 更進一步，碰到真正有設計決策的地方會留 TODO(human) 讓你自己寫，寫完它再給你一個 Insight[21]。這就是官方版的 ELI5，而且是針對你的 codebase 講，不是通論。

要「pardon，請換個說法」，直接問。best practices 的原話是「問 Claude 你會問資深工程師的問題」，不需要特別的 prompt[5]。怕問題把 context 弄髒，用 /btw：答案不進對話歷史，問完就消失[9]。幾句好用的 pardon：「用一句話重講」「列出你的假設」「哪一步如果我不同意，結果會不一樣」「這段跟我上一句的哪個字有關」。

比較誠實的那一半是：讀不懂不等於不能驗。你可以不懂它為什麼這樣改，但你一定可以要求「給我一個會失敗的測試，然後讓它過」。劍客不一定懂每一招背後的物理，但知道怎麼驗這一刀有沒有砍中。讀不懂的時候，該要求的不是更簡單的解釋，是更容易驗證的證據。

三件事其實是一件：它講太多、你沒讀完、你讀不懂，結局都是你放行了一個你沒有真正確認的方向。鏡子歪在放行的那一下。

接到番外篇 讀不懂還有第三條路，不換講法，換載體：叫它畫圖、做成網頁、生一支影片。Karpathy 十月初那串四階梯的原話、同一道題跑四種載體的實測、官方與社群目前的做法，以及它和這一節對撞的地方，收在12 · 番外篇。

09 · 回到 SDLC

需求、目標、修正、重來、文件、repeat

繞了一圈，答案是軟體工程本來的那套。但有五個地方的比重整個翻過來，這才是用 agent 和傳統 SDLC 真正的差別：

  1. 重來從最後手段變成預設動作。以前重寫很貴，SDLC 花大量心力避免返工。現在重開 session、git reset 重做，幾乎沒有成本。一次做歪了，修補常常比重來還貴，因為修補是在污染的 context 裡進行。
  2. 驗證必須自動化，不能靠回報。agent 說「做完了」只代表它覺得看起來完成了，再加上它會順著你的語氣走。「具體的目標」要具體到機器能判斷 pass 或 fail：測試、build、diff 對 fixture。官方 best practices 把這條放在第一位：給它一個能跑的檢查，「這是你盯著看的 session 和你可以走開的 session 的差別」[5]。
  3. 文件有了預算。給人看的文件寫長頂多沒人讀；給 agent 的文件每多一行都在稀釋其他行。從「寫得越完整越好」變成「只寫推斷不出來的東西」，像程式碼一樣定期重構。
  4. 需求要寫成事實，不能寫成意見。「我覺得問題在快取」會把它帶偏；「快取關掉後問題仍重現」才是需求。agent 會放大你的確信程度，所以每一句都要分清哪些是驗證過的、哪些是猜的。
  5. 人的角色往兩端集中。中間的實作交出去，人負責兩頭：前面定義問題和完成標準，後面審證據、判斷該修還是該重來。這兩件事剛好都沒辦法外包給 agent。

極端一點的作法也成立：每次都是新 session，做完就更新 README、handoff、lesson 進 git，下次從零開始。它不一定更耗 token，因為每個 request 都很輕；但「更乾淨」不等於「更不會錯」。錯誤不會消失，只是從對話搬進 repo，而且比對話裡的錯更持久。對話裡的污染一次 /clear 就沒了，寫進 git 的污染會一直跟著你。這個模式乾不乾淨，取決於你把 repo 管得多乾淨。

10 · 指差呼稱

DO / DON'T

DO

  • 每個任務先給一個機器能判斷的完成標準：測試名稱、預期輸出、截圖對照。
  • 同一個問題修正兩次還不對：/clear，寫更好的 prompt 重來。
  • handoff 只留四類：已驗證的事實、確定失敗的嘗試、目前狀態（commit hash）、完成標準。
  • CLAUDE.md 控制在 200 行內；每行問一次「拿掉會不會出錯」。
  • 只跟某個目錄有關的規則，放子目錄 CLAUDE.md 或 paths rule；流程放 skill；絕不能違反的放 hook。
  • 定期跑 /doctor prompt-audit 和 /context。
  • model、effort 在 session 開頭決定；離開超過一小時先收尾。
  • 要放棄走錯的路用 /rewind；任務之間的斷點才 /compact。
  • lesson 先進 inbox，你審過才升級成規則。
  • 需求裡的每一句分清「驗證過」和「待驗證」。
  • 嫌它話多先 /output-style concise；計畫要它先列假設，一句話複述不出來就不放行。
  • 讀不懂就問，/btw 不污染 context；要不到解釋就要一個會失敗的測試。
  • 記憶定期掃：claude.ai 每季、auto memory 在 repo 換方向時；刪過期狀態，留決定。

DON'T

  • 不要用情緒當回饋。「又錯了」沒有資訊量，只有立場。
  • 不要把自己的猜測寫成事實餵進去。「問題一定在 X」它就一路往 X 鑽。
  • 不要在歪掉的 session 裡用 /compact 救火：摘要會把錯誤假設寫成已知事實。
  • 不要整包 export / import 對話紀錄，污染會原封不動搬過去。
  • 不要用 @path import 一份 index，所有內容會在啟動時全部載入。
  • 不要在 CLAUDE.md 裡放逐檔架構說明，研究顯示它不會減少探索步數。
  • 不要每條規則都加 IMPORTANT；不要再用 CRITICAL: You MUST。
  • 不要寫「請仔細思考」「先驗證再完成」「要更徹底」，新模型會過度觸發。
  • 不要讓剛搞砸的 session 直接改 CLAUDE.md 然後不看 diff 就 commit。
  • 不要在 session 中途切 model；用 Fable 5.1 時更不要。
  • 不要沒讀完計畫就說 go，那個 go 會變成它往後每一步的前提。
  • 不要在 Fable 5.1 上沿用整段反格式、反列點的規則，它已經格式得比你少。
  • 不要把 dream 當成已經在幫你整理，也不要把 2025 年的 memory bank 整包搬到 1M context 的模型上。

11 · 結語

劍客、小孩，和那把劍

「劍客拿著樹枝都能殺人，小孩拿真刀只會砍了自己。」這句話對了一半。我不認為是「使用者水準」這種道德化的說法，但差距確實在人身上，只是不在你以為的地方。劍客和小孩的差別，已經不是 prompt 寫得多漂亮，那面鏡子在變平；而是這幾件事：有沒有給可驗證的完成標準，讓模型能自己判斷對錯而不是靠你的情緒；知道什麼時候該重開，而不是在爛掉的 context 裡硬救；任務切得夠小，小到一個 session 結束時你能 review 完它的 diff；不把自己的信念當事實餵進去。

另一半也要誠實講：模型確實有真實的天花板。大型既有 codebase 裡的隱性慣例、跨很多檔的一致性、長程規劃，到了 Opus 5.5 和 Fable 5.1 還是會出錯。不是所有挫折都是使用者的錯。劍客的本事有一部分，是知道哪些仗不該叫這把劍去打。

鏡子沒有變笨。你愈用力壓，它只是愈忠實地照出你壓它的那隻手。

所以給新手的那段建議，我會改寫成一句：你覺得想罵人的那一刻，不是它變笨了，是這面鏡子已經被你壓歪了。放下，/clear，把事實寫下來，重新站到鏡子前面。

12 · 番外篇

Karpathy 的四個載體：讀不懂的第三條路

接回 08 第 08 節把三件事收成一件：它講太多、你沒讀完、你讀不懂，結局都是放行了一個沒有真正確認的方向。那一節給「讀不懂」開了兩條路，ELI5 和 pardon，兩條都是在文字裡換講法。這篇手冊上線前兩天，Karpathy 在 X 上貼了一串關於「怎麼讀 LLM 輸出」的 tips，三天內 670 萬次瀏覽[35][36]，給的是第三條路：不換講法，換載體。這一節把那串拆開，用同一道題跑過四種載體，再對照官方與社群這三個月的做法，看它跟第 08 節哪裡接得上、哪裡對撞。

階梯本身

他的大前提是：「我們會花愈來愈多時間在理解語言模型的輸出上」。模型愈強，雜活跑得愈多，人的工作往上移到監督和理解那一層，所以讓輸出好吸收變成關鍵技能。接著他一階一階往上疊，每階都說「but even better」[35]：

階叫它做什麼他的理由
一 · 文字用 ASD-STE100 寫。這是航太維修手冊用的受控語言：一詞一義、一句最多 20 字、主動語態、一段一主題、附一本約 900 字的核可字典[41]。太硬的話「寫到八成就好」很多模型讀過這套規範，叫它照寫，廢話和繞圈會被規範壓下去，不用自己發明一堆瑣碎指令
二 · 圖直接叫它畫 diagram很多東西圖比字好懂，大腦解析得快
三 · HTML「用 HTML 輸出」，拿到一個可互動的網頁前端愈做愈好，動畫和互動都生得出來
四 · 影片「做一支 3Blue1Brown 風格的影片解說 X，用我的 ElevenLabs key 配旁白」他最看好的形式，「現在真的開始能用了」

收尾那句才是整串的靈魂：當智慧和程式碼都變便宜，你可以隨手生出那些大型、客製、用完即丟的軟體產物，一個互動網頁或一支影片只為了搞懂一件事，看完就扔。軟體從「要被維護的東西」變成「一次性的理解工具」。

同一道題，四種載體

光看描述分不出差別，要拿同一道題跑過去才看得出來。題目選 RBAC 和 ACL 的設計差異：一個工廠，四個人（三個作業員、一個工程師），三種資源（工單、配方、設備參數）。先是第一階，用 STE 的結構規則寫中文：

ACL 和 RBAC 都控制誰能用哪個資源。差別是規則放在哪裡。

ACL
1. 每個資源有一份名單。
2. 名單寫出每個人能做的動作。
3. 一個人要用 10 個資源，你要改 10 份名單。
4. 要查一個人的全部權限，你要看過所有名單。

RBAC
1. 你建立角色。每個角色有一組權限。
2. 你把角色給人。你不把權限直接給人。
3. 要改全部作業員的權限，你只改一個角色。
4. 要查一個人的全部權限，你只看他的角色。

怎麼選
1. 很多人做同一種工作，用 RBAC。
2. 每個資源的擁有者不同、分享對象不同，用 ACL。
3. 很多系統兩種一起用。RBAC 定預設，ACL 定例外。

寫這段的時候最花力氣的是「一詞一義」：權限、存取、授權、能用，最後只留「權限」和「能用」兩個，各管一件事。交給模型自己寫，它幾乎一定四個輪流換，讀者就會懷疑這是不是四件不同的事。STE 的 900 字字典是英文的，中文搬得過來的只有結構規則，字典那半要自己寫進 prompt。

再來是第二階和第三階合在一起：下面這張圖預設是靜態的「基準」，就是第二階；按鈕切換情境，數字跟著變，就是第三階。它是貼進這份報告的一段 SVG 加幾十行 JS，沒有外部腳本。

五個情境的數字
情境ACLRBAC省事的是
作業員都要能讀配方改 3 處（配方名單加 A、B、D）改 1 處（作業員角色加「讀配方」）RBAC
新人 F 報到改 2 處（兩份名單各加 F）改 1 處（把作業員角色給 F）RBAC
C 把配方分享給外部 E改 1 處（配方名單加 E）改 2 處（開一個只有一個人的角色）ACL
稽核：D 能碰什麼查 3 處（翻完所有名單才能確定配方那份沒有 D）查 1 處（看 D 的角色）RBAC

直觀感受的差別是這樣。圖大概一秒就看懂：左邊那團交叉的線一看就是亂的，右邊收在兩個綠色方塊裡，不用讀字。但圖給的是「哪裡比較痛」的整體印象，先有感覺才想到要不要去數；而 STE 版要讀三十秒，讀完拿到的是可以逐條對的東西。第 4 條「查一個人的全部權限」在靜態圖上完全沒有，線畫不出「掃描」這個動作；「怎麼選」那段圖也畫不出來，因為那是條件句，圖只能畫一個狀態。

更要緊的是：靜態圖是偏心的。我挑的基準情境是「一群人做同一種工作、規則整批改」，這是 RBAC 的主場，所以右邊看起來就是比較乾淨。互動版補的正是這個洞，你自己點到第三個情境，就會看到 RBAC 那邊多冒出一個只有一個人的角色。可是偏見沒有消失，只是從圖上移到選單裡：有哪些情境可以點，還是我決定的，五題裡三題 RBAC 省事、一題 ACL 省事，這個比例是我定的。第四階影片我沒做，理由在後面那節。

兩條軸：好吸收，和好驗證

把四種載體排開，它們不只是「愈來愈好懂」，而是性質不同的東西：

載體你拿到的是好吸收好驗證
STE 文字可以逐條對的句子低高（前提見下一節）
靜態圖一個狀態，由作者選定高低，畫不出條件句和動作，立場藏在選題裡
互動 HTML一個可以戳的模型高最高，你能換情境、能自己數；但可戳的範圍仍是作者定的
解說影片一條作者替你選好的路徑最高最低，推論包成敘事，看完是被說服的懂

Karpathy 的階梯是「好吸收」一路往上；「好驗證」沒有跟著往上，它在互動 HTML 到頂，到影片掉回最低。第 08 節那句「該要求的不是更簡單的解釋，是更容易驗證的證據」不用改，換載體解決的是「我讀不進去」，不是「我不確定它對不對」。

所以兩個問題要分開問。建立直覺，換載體；放行一個設計決策，還是要測試。一支做得漂亮的 3Blue1Brown 風格影片，是最難驗證的輸出形式，而且正因為順，你不會想到要去問。這剛好回到鏡子篇的原點：表達力那面鏡子在變平，信念那面還在，輸出愈順眼，愈容易把它的方向當成自己的。

第一階的實況：STE 嚴格版會把你要挑的錯刪掉

官方沒有這條，社群一週內冒出十幾個 repo[46]。真正該看的是 Lucian Ghinda 的實驗[37][38]：讓 Claude 和 Codex 解釋四段程式碼，每段用三種指令各跑一次。對照組不加風格指令；第二組只寫一句寬鬆的「explain in simple technical English」；第三組用正式 ASD-STE100，53 條規則加 900 字字典。

兩組的句子都短了，但嚴格版是靠刪內容變短的。這把我自己原本的說法修掉一半：STE 能拿來挑錯，前提是它沒有先把錯藏起來。Karpathy 說「八成就好」，不只是為了可讀，也是為了不掉事實；實務上，寬鬆的一句話可能比直接丟規範名稱更安全。另一份逐條查核也指出，模型寫出來的只是「STE 風味」，不是真正合規，字典遵循會漂移，網路上流傳的 cheat sheet 本身還有錯[39][40]。真要合規得靠確定性的 linter，像 SimpleEnglish skill 用 regex 檢查，違規數少了 72.9%，但作者也承認這只量了規則違反次數，沒做人工可讀性評估[42]。社群裡比較清醒的一派也是這樣講的：這不是給 agent 換人格，是建一套「寫作系統」，依文件用途切換結構，再交給 Vale 這類 linter 檢查[54]。

還有一條比較有意思的旁支：danyuchn 的 skill 把 STE 用在 agent 對 agent 的文字上，工具描述、系統指令、handoff。理由跟飛機技師一樣：下游 agent 沒辦法回頭問「你是指 X 還是 Y」[46]。這和第 09 節的 handoff 四類是同一件事，只是把「寫給人」換成「寫給下一個 session」。

危險

把 ASD-STE100 整套塞進 CLAUDE.md 或 output style。每一輪都付那份規則的 input token，換來的是變短但掉了一半事實的解釋。

對策

要用就用寬鬆版：「explain in simple technical English」或「八成的 ASD-STE100」。中文另加一句字典規則：「全文只用『權限』這個詞」。要合規用 linter，不要靠模型自覺。

第二、三階的實況：圖和 HTML，這階官方有立場

和 STE 不同，HTML 這階 Anthropic 有正式立場，而且早在 Karpathy 之前。Claude Code 團隊的 Thariq Shihipar 在 5 月發了〈The Unreasonable Effectiveness of HTML〉，主張用 HTML 取代 Markdown 當預設輸出[43]，連一向偏好 Markdown 的 Simon Willison 都改口說那是 8K context 時代留下的習慣[52]；配一個官方 org 下的範例庫，二十個不需 build、單檔開啟的 HTML[44]，後來 Claude Code 的 Artifacts 文件把它做成功能[45]。他把用途分五類，每類附 prompt：規劃探索（「生六個明顯不同的方案，排成網格讓我並排比」）、code review（「把 diff 渲染出來，邊欄加註解，按嚴重度上色」）、設計原型（「給我幾個滑桿試動畫參數，加一個複製參數的按鈕」）、報告與學習（「讀程式碼，產一頁 explainer：流程圖、三四段關鍵程式碼加註解、一個 gotchas 區」）、客製編輯介面（「每張 ticket 做成可拖的卡片，分 Now / Next / Later / Cut 四欄，加一個 copy as Markdown 按鈕」）。

有兩件事值得注意。第一，Thariq 自稱是「HTML 極端派」，幾乎不用 Markdown 了，但官方文件的語氣比他本人保守得多，直接寫了「styled page 比同內容的終端文字更吃 token」，並建議「不需要的互動就省掉」「大資料讓頁面做摘要，不要全部內嵌」[45]。第二，他自己承認的風險和第 08 節是同一句：輸出很長的時候，開發者可能「直接接受，不審查」，帶來品質、維護和安全問題[48]。連提倡者都把「放行的那一下」列為風險。

批評方的清單，加上這次自己做的體感，整理如下：

  • 原始碼沒辦法 review。Markdown 原文和渲染後一樣可讀，HTML 原文對人不友善，git diff 雜訊很多；審不了原始碼，就進不了需要合規的流程[47][48]。這對 imitator 直接適用：這份報告存在 repo 裡，HTML 版的 diff 其實看不懂，每次改版都是在「沒讀完就 go」。
  • 本機 HTML 沒有沙箱。官方 artifact 跑在獨立 origin，有嚴格 CSP，只能連白名單 CDN，fetch 只能打自己的 origin；讀別人的 artifact 時模型拿到的是摘要，內嵌指令會被回報而不是照做[45]。但 Thariq 的工作流是本機生 .html 直接用瀏覽器開，沒有任何這些。頁面內容如果來自不可信的資料，外部 PR、客戶的 log、爬下來的網頁，模型生成的 JS 就在你的瀏覽器裡跑。官方範例庫全部用虛構的 Acme 資料，大概也有這層考量。
  • 可用性受限。artifact 只在 Anthropic API 上有，Bedrock、Vertex、Foundry 都不行；組織開了 ZDR、HIPAA 或 CMEK 也不能用；API key 或 gateway token 登入的 session 不能發佈[45]。企業環境常走雲端供應商或 ZDR，這時只剩本機 HTML，也就回到上一點。
  • 不適合當 agent 之間的交接格式。HTML 是給人看的層，下一個 agent 讀它會吃進一堆 markup。Thariq 的解法是頁面上放「copy as prompt / copy as JSON」按鈕，等於承認回到機器的那一段還是要轉成文字。
  • 說明書比載體貴。這次做那張互動圖之前，先讀進一份約 1.5 萬 token 的繪圖規範，比圖本身多七倍，而且讀進來之後整段對話每輪都跟著送。你的 imitator 要求每份 HTML 都原樣貼 report.css 是同一個結構：載體不貴，教模型怎麼做載體的說明書才貴。這和第 03 節肥大的 CLAUDE.md 是一件事換了個形式。
  • 主線 context 被污染。一張 SVG 加一份繪圖規範塞進主對話，正好是第 02 節講的爛掉 context 的原料。
  • 檔案碎片化。Thariq 自己每個階段各留一份 HTML（探索、實作、元件庫）[43]。「用完即丟」和「可以分享、有版本」互相拉扯：丟了就沒紀錄，留下來就要決定哪一份才算數。
  • 同質化的 AI 美學。社群的 html-artifacts skill 專門列了反模式：漸層、玻璃擬態、標題加 emoji[49]；官方文件的對策是先讀專案裡的 design system[45]。

危險

在主線 session 裡叫它「做成 HTML」，再把不可信的資料餵進那頁的 JS，最後用這頁當 handoff 交給下一個 agent。

對策

人看 HTML、agent 讀 md，中間用 copy-as-prompt 接。載體在旁邊的 session 或 subagent 生，主線只拿結論回來。資料來源不可信就不要進本機 HTML，只進有 CSP 的 artifact。

第四階的實況：影片真的能做了，但沒人驗過它有用

零成本的管線已經有人跑通：Opus 5.5 寫稿、Kokoro 本機配音、Remotion 做動畫、Whisper 對齊字幕、ffmpeg 收尾，全程不花錢[50]；另一條是 Manim 加 Kokoro 或 ElevenLabs 的 karpathy-ladder skill[51]。但同一批作者列的限制很誠實：沒有任何理解效果的研究，影片可能沒有比文字講得更清楚；改一句話要重新 render 12 分鐘；ElevenLabs 預設記錄旁白文字，要關掉得買企業方案[39][50]，Karpathy 範例裡那句「用我的 ElevenLabs key」如果拿來解釋公司內部的東西，旁白就出去了。第四階我沒做的理由就是這幾條：它對這道題沒有新增任何可驗證的東西，只是把前三階包成一條路徑。

「agent 會寫、會配音、會做動畫、會檢查畫面。人的工作是畫面藏起來的那部分：決定什麼是真的。」

這次的 token 帳

Karpathy 的前提是生成趨近免費，值得查一下。下表是這次做 RBAC 那道題的實際用量，用字元數換算，不是 tokenizer 精算：

載體輸出量看不見的成本
STE 英文約 200 token無
STE 中文約 350 token自己守字典
靜態 SVG約 2,000 token先讀一份 1.5 萬 token 以上的繪圖規範，之後每輪跟著送
互動 HTML約 2,200 token寫兩次（存檔量、呈現）、無頭瀏覽器截兩張圖檢查線有沒有穿過方塊，幾千 token
影片腳本 5,000 token 起render 時間和 TTS，token 已不是主要成本

兩個觀察。互動版和靜態圖幾乎一樣大，因為靜態圖把每條線的座標寫死，互動版是資料加迴圈，多五個情境只是多幾行資料；載體往上升一級，輸出不一定跟著變多。但載體本身只占總成本的一兩成，其餘都是「讓它不出錯」的費用：規範、截圖、複查。便宜的是生成，貴的是驗證，和第 09 節比重翻過來的那五件事是同一個結論。Thariq 自己在 podcast 上給的數字也呼應這點：他生成的 token 只有約 1% 進 production，其餘都是過程[53]。

目前的做法

DO

  • 讀不進去，換載體；不確定對不對，要測試。兩個問題分開問。
  • STE 用寬鬆版或「八成」；中文另加一句「全文只用某個詞」。先在自己的程式碼上比一次嚴格版和寬鬆版再決定。
  • 叫它畫圖時，一併要「哪個情境會讓另一邊比較省事」，逼它把偏心的選題講出來。
  • 人看 HTML、agent 讀 md，中間用 copy-as-prompt 按鈕接。
  • 載體在旁邊的 session 或 subagent 生，主線只拿結論。
  • HTML 要給別人看就用有 CSP 的 artifact；本機 HTML 只放自己寫的資料。
  • 影片用本機 TTS（Kokoro 一類），只做給自己學。

DON'T

  • 不要把 ASD-STE100 整套塞進 CLAUDE.md。每輪付 input token，換來掉一半事實的解釋。
  • 不要因為圖看起來乾淨就放行。靜態圖畫不出條件句，立場在選題裡。
  • 不要拿 HTML 當 handoff。下一個 agent 讀的是 markup，不是你的結論。
  • 不要把不可信的資料餵進本機 HTML 的 JS。
  • 不要用影片做放行決策。它最好吸收，也最難驗證。
  • 不要把公司內部的內容送進雲端 TTS 的 key。

載體愈順眼，鏡像愈順手。四個載體共同的盲點是「好吸收不等於好驗證」，而 STE 這一階還多一個陷阱：嚴格版會靠刪事實來變短。

▸ 讀不懂的時候有三條路：換講法、問 pardon、換載體。三條都走完，還是要回來要那個會失敗的測試。鏡子歪在放行的那一下，載體換了也一樣。
