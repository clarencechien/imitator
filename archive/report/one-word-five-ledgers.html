說書 · workflow 的帳本 · 2026-11

同一個字，
五本帳

「workflow」這個字，業務和工程師各說各話，資料人又是另一套。這篇從 1990 年代的簽核系統一路講到 2026 年的 agent，把它拆成五本帳加一本底帳：每一種工具都在替你記一本帳，差別在記的是什麼，出事時從哪裡翻帳重來。

楔子 · 一則留言

「這不就是 Airflow 嗎？」

2026 年 11 月，Medium 上有一篇〈6 Open-Source Projects for Serious AI Infrastructure〉，介紹 Temporal、NATS 等六個開源專案，說它們各管一種故障。文章底下只有一則留言，問的就是這句：這不就等於 Apache Airflow？

這個問題問得不算離譜。Temporal 和 Airflow 都叫自己 workflow，都會重試、都能排程，畫出來都是一張方塊加箭頭的圖。真正的差別藏在看不見的地方：它們各自替你記了一本帳，帳上記的東西完全不同。

說書人先亮底牌。分辨任何一個 workflow 工具，只要問兩個問題：

問題一

狀態記在哪

它替你記住了什麼

問題二

失敗怎麼重來

出事之後，翻哪一本帳、從哪裡接著做

帳上記的東西大致分三類。流程帳記「這件事走到哪一步」。資料帳記「哪一批資料處理過了、讀到哪一筆」。第三類其實不算 workflow，它記的是「某個東西現在長什麼樣子」，例如一台機器的狀態、一個帳戶有沒有被凍結。這第三類會在第三回出來攪局。

接下來六回，每介紹一本帳，就在存摺上印一行。

第一回 · 1990s 起

畫給業務看的流程，記一本簽核帳

最早把「流程」當成一種軟體來做的，是 1990 年代的 workflow management system。公文要誰簽、簽完往哪送，畫成一張圖，再由引擎照著圖執行。

這一派很早就有人認真整理。荷蘭學者 van der Aalst 與同事在 2000 年調查當時的工具，歸納出 20 種控制流模式，像循序和平行分支，再拿 15 套商用系統逐一比對，沒有一套支援全部。後來的 BPMN 標準把這類圖的畫法統一下來，讓業務和 IT 看同一張圖。

這本帳的長處，是讓不寫程式的人看得懂、改得動。圖本身就是業務與 IT 之間的合約。

第一本 · 簽核帳
摘要
業務流程與簽核
記什麼
流程走到圖上哪一格、誰核准過
失敗怎麼重來
退回、重新送簽
代表
Camunda、Flowable 與公司簽核系統

這本帳到今天還在，只是換了引擎。開源 BPMN 引擎裡最普及的 Camunda 7，社群版在 2025 年 10 月發出最後一版。接班的 Camunda 8 改用 Zeebe 引擎，把流程狀態寫成分散式的事件紀錄，授權也從開源改成 source-available。

第二回 · 2010s 起

畫給一般人看的流程，記一本執行快照帳

第二批畫流程的人不在 IT 部門。Zapier 和 n8n 這類工具，讓業務和行銷人員自己用拖拉的節點，把表單和通訊軟體串起來：來了新訂單，就寫進試算表，再發一則通知。

以 n8n 為例，它在 2019 年 10 月公開上線，2022 年起改用自訂的 Sustainable Use License，可以自架。它的帳很直白：每跑一次，就把進來的資料和每個節點的輸出整份存下來，連停在哪一個節點也記著。流程中途要等一天也行。等待超過 65 秒時，n8n 會把這份執行資料寫進資料庫，條件成立再載回來接著跑。

第二本 · 執行快照帳
摘要
串接各種 app 的自動化
記什麼
每次執行、每個節點的輸入輸出
失敗怎麼重來
從失敗的節點重跑
代表
n8n、Zapier 與 Make

這本帳有個值得停下來的細節。在 n8n 按下重試，已經成功的節點保留原本的結果，失敗的那個節點則把整批資料再處理一次。假設它負責發十則訊息，發到第三則失敗，重試時前兩則會再發一遍。

帳記得「哪個節點失敗了」，沒記住「這個節點做到第幾筆」。後面每一本帳，都會以不同的形式再碰到這個缺口。

第三回 · 2010–2025

同一批人把圖改成程式，記一本執行歷史帳

第三本帳的故事有兩個主角。Maxim Fateev 是 Amazon Simple Workflow Service（SWF）公開版的技術負責人，Samar Abbas 是同一個團隊的成員，SWF 在 2012 年初對外推出。之後 Abbas 回到微軟 Azure，主導 Durable Task Framework，這套框架後來成了 Azure Durable Functions 的底層。兩人在 Uber 重逢，2017 年開源 Cadence。2019 年 10 月，他們離開 Uber 創立 Temporal。

這一派的轉折，是把流程從圖改成程式碼。流程就是一段普通的函式：先做 A，等審核，再做 B。引擎在背後把每一步的結果記成事件歷史。機器當掉之後，新的 worker 從頭重新執行這段函式，碰到歷史裡已經有結果的步驟，就直接拿結果、不再真的執行，一路快轉回中斷點。

第三本 · 執行歷史帳
摘要
工程師寫成程式的流程
記什麼
程式每一步的結果
失敗怎麼重來
重播回中斷點
代表
Temporal、Step Functions 與 Cloudflare Workflows

代價寫在規則裡：流程程式碼必須是確定性的。重播時要走出同一條路，所以不能在流程裡直接讀時間或打 API，這類動作都要包成一個「步驟」。AWS 在 2025 年 12 月推出的 Lambda durable functions 用的也是這套規則，重播時會檢查每一步的名稱與型別是否對得上紀錄。

這本帳後來在雲端各長出一份。AWS Step Functions 用 JSON 寫狀態機，記的是同一種帳，而且讓你自己選耐久程度：Standard 版保證每一步恰好執行一次、最長跑一年。Express 版只保證至少執行一次、最長五分鐘，計價方式也跟著不同。Cloudflare 在 2024 年 10 月推出 Workflows 公測，技術文章寫明每個 workflow instance 都對應一個以 SQLite 儲存的 Durable Object。

接回〈演員登台〉 講到 Durable Objects，順手把第三類東西請出場。Durable Object 是一個 Actor：每個 ID 一個實體，自己保管一份狀態，一次處理一則訊息。它記的是「這個東西現在的樣子」，所以它本身不是 workflow。Cloudflare 把 Actor 當成地基，在上面蓋出記執行歷史帳的 Workflows。Actor 從 1973 年走到 Durable Objects 的那段路，在〈演員登台〉講過。

這本帳記得每一步的結果，管不到帳外面的世界。一個步驟逾時重跑，外面的付款 API 可能已經扣過一次款。Medium 那篇文章講得很直接：耐久執行不會讓外部 API 只執行一次。

第四回 · 2014–2026

資料人另起爐灶，記時段帳與游標帳

前三本帳的主角是「一件事」，像一張公文或一筆訂單。資料工程師面對的是另一種東西，每天都會來一批的資料。他們發展出另外兩本帳。

Airflow 2014 年誕生於 Airbnb，用 Python 寫 DAG。它的帳按時間切：每個任務在每個日期區間，成功或失敗。某一天的資料有問題，就把那一天清掉重跑。新管線上線，就把過去一整段日期補跑一次，這叫 backfill。

第四本 · 時段帳
摘要
按時間切的資料批次
記什麼
任務 × 日期區間的成敗
失敗怎麼重來
清掉那段時間重跑、回補
代表
Airflow、Dagster 與 Prefect

2018 年出現的 Dagster 換了一個問法：與其記「哪個任務跑過了」，它記「哪一張表是最新的」，以資料資產為中心來編排。Airflow 3.0 在 2025 年 4 月正式推出，把 dataset 改名為 asset、加上事件驅動排程，也讓每一次執行綁定開跑當下的 DAG 版本，兩派開始靠攏。

第五本帳屬於專門搬資料的產品。Airbyte、Fivetran 的工作是把資料從 A 搬到 B，單位是一條連線。它們的帳記「讀到哪一筆」：Airbyte 的 connector 讀完一段資料，就發出一則 state message 當作 checkpoint，下次從這個 cursor 接著讀。就算 API 不支援增量讀取，Airbyte 也會拿分頁數當成「合成 cursor」，讓失敗的同步從上一頁接續。

第五本 · 游標帳
摘要
一條資料連線
記什麼
每條資料流讀到哪一筆
失敗怎麼重來
從 cursor 續讀
代表
Airbyte、Fivetran

這一行在 2026 年 6 月有了大變動：Fivetran 與 dbt Labs 完成合併，把搬資料和轉換資料收進同一家公司。

最底下還有一本底帳

Kafka、Flink、NATS JetStream 這類串流系統，資料一直流進來，沒有終點，所以嚴格說不算 workflow。它們只記「讀到哪個位置」。Flink 的 checkpoint 存的，就是各個運算子的狀態，加上每個 Kafka 分區讀到的位置。

摘要

記什麼
offset 與運算子狀態
失敗怎麼重來
從 checkpoint 還原

Kafka、Flink 與 NATS JetStream

回到那則留言

現在可以回答 Medium 底下那個問題了。Airflow 記的是第四本帳，Temporal 記的是第三本帳，兩者都叫 workflow，記的東西不一樣。更有意思的是 Airbyte：它是記第五本帳的產品，可是每一次同步怎麼排、怎麼取消，都交給 Temporal 管，連「同一條連線同時只能跑一個」也是它守著。

一次同步走下來會經過三本帳，每一本只知道自己那一段。真正把資料寫進倉儲的那一層，沒有人替你記帳。

第五回 · 三個產業

工廠、銀行、電商，翻開都是同一套帳

把這把尺放到三個產業，每一格都找得到大家熟悉的事。

帳本傳統工廠（MES）銀行金融電商
第一本簽核帳工單與工程變更簽核放款核貸、KYC 定期複審退貨與客訴審核
第二本執行快照帳設備告警轉發到通訊軟體內部報表定時寄送新訂單寫進試算表並通知
第三本執行歷史帳批次配方執行：做到第幾步，可暫停或中止付款與轉帳：每一筆都要確定成功，或知道卡在哪下單流程：扣庫存與扣款後出貨，失敗就補償
第四本時段帳每班、每日的產量與良率報表日終批次：計息與產生會計分錄每日銷售報表與推薦模型重算
第五本游標帳MES 資料同步到 ERP 或資料倉儲核心系統資料抄到倉儲做報表訂單、廣告資料匯入倉儲
底帳位置帳設備事件、SPC 告警即時交易監控訂單事件推給搜尋索引與通知
不是帳實體狀態機台狀態、lot 的 Hold帳戶正常或凍結庫存、購物車

表裡有三個故事值得細講。

房貸核貸，兩種記法

同樣是核貸，BNP Paribas 旗下的烏克蘭 UKRSIBBANK 用 Camunda 畫成 BPMN，中小企業放款從最長 28 天縮到最短 12 天。澳洲的 ANZ 用 Temporal 寫成程式碼，新的房貸核貸系統六週就上線。兩家都對，差別在流程要給誰看懂。業務要自己看流程、改流程，帳就記在第一本。交給工程團隊維護，帳就記在第三本。

退款是一筆新帳

電商下單，系統先扣庫存和款項，再建立出貨單。出貨單建立失敗，就要釋放庫存、退款，這種做到一半要補償的流程叫 saga。補償沒辦法倒帶：款已經扣了，退款是一筆新的業務動作，有自己的稽核紀錄。也因為扣款可能被重試，付款 API 都要帶 idempotency key。Stripe 收到同一把 key 的第二個請求，會直接回傳第一次的結果，不會再扣一次。key 至少保留 24 小時。

工廠的 Hold

傳統 MES 裡，一個 lot 被 Hold 住，後面的動作就做不了。業界的說法很直接：Hold 必須是一個有後果的狀態，會擋下後續動作，不能只是紀錄上的一個旗標。這是實體狀態。另一邊，ISA-88 的批次配方本身就是一個集中編排的 workflow，指揮下層設備依序動作，內建暫停與中止這類狀態控制。雲端還沒開始談 durable execution，工廠早就同時用著這兩種東西。

還有一個跨產業的共同需求：同一件事不能同時跑兩次。核心銀行的日初、日終批次開跑前，會先確認沒有另一個在跑。Airbyte 也保證同一條連線同時只有一個同步。帳記得越清楚，這種互斥就越好做。

第六回 · 2025–2026

大家都說自己是 agent 的編排層

2025 年起，這幾本帳的主人幾乎同時改了口。

誰現在怎麼說實際記的是
Camundaagentic orchestration：agent、人、系統放進同一張 BPMN第一本：誰核准過、流程走到哪
n8n原生 AI 能力，拖拉就能做出 agent 流程第二本：每次執行的快照
TemporalOpenAI Agents SDK 跑在 workflow 裡，每次模型呼叫都是一個步驟第三本：agent loop 跑到第幾輪
Lambda durable functions明講適用於 agentic AI 應用第三本
Cloudflare Workflows用 waitForEvent 讓 agent 動手前先等人核准第三本
Airflow 3為 AI 時代重新設計資料編排第四本
Fivetran + dbt Labs給 AI agent 的資料基礎設施第五本

名字都掛上了 agent，帳本一本也沒換。所以挑 agent 的編排工具，先問一句：你的 agent 最怕丟哪一本帳？怕丟稽核軌跡，看第一本。怕 loop 跑到一半要整個重來，看第三本。怕餵給 agent 的資料過期，那其實是第四、五本的問題，換一個 agent 框架也解決不了。

這股熱潮的溫度也要一併記下。Camunda 自己的 2026 年調查說，71% 的組織表示有在用 AI agent，但過去一年只有 11% 的 agentic 用例真正進到正式環境。這是廠商做的調查，數字照廠商說法。

收尾 · 一把尺、一個坑

五本帳加一本底帳，和一個躲不掉的坑

帳本記什麼失敗怎麼重來代表
第一本簽核帳流程走到圖上哪一格、誰核准過退回、重新送簽Camunda、Flowable
第二本執行快照帳每次執行、每個節點的輸入輸出從失敗的節點重跑n8n、Zapier 與 Make
第三本執行歷史帳程式每一步的結果重播回中斷點Temporal、Step Functions 與 Cloudflare Workflows
第四本時段帳任務 × 日期區間的成敗清掉重跑、回補Airflow、Dagster
第五本游標帳每條資料流讀到哪一筆從 cursor 續讀Airbyte、Fivetran
底帳位置帳offset 與運算子狀態從 checkpoint 還原Kafka、Flink
不是帳實體狀態某個東西現在的樣子狀態一直都在，做到一半的事要自己推回來Durable Objects、機台狀態

每一本帳都只對帳內的事負責。n8n 重試會重發訊息。Temporal 的步驟逾時會重跑，它接 MCP server 時也明說，耐久保證管不到 MCP 那一端。Flink 的恰好一次，到了外部系統也要靠交易或冪等寫入才成立。

挑哪一本帳，買到的都是「有人替你記帳」。事情只發生一次這件事，沒有人替你保證，帳本邊界上一律要自己帶 idempotency key。

什麼時候該換一本帳

大部分專案不需要一開始就上第三本帳。最省的做法是自己記：每做完一步，就在一張表或 git 裡寫一筆，重跑時跳過做過的步驟。等這張表開始長出新欄位，就是換帳的訊號。

表上出現 wait_until，代表流程開始要等。再出現 cancel_requested、compensate_from，代表要能從外面喊停、要能補償。走到這一步，你其實已經在手刻第三本帳，換成現成的引擎通常比較划算。反過來說，如果你的流程是「每天把資料搬一次」，該找的是第四、五本帳。

下次有人問「這不就是 Airflow 嗎」，可以反問他一句：你要記的是哪一本帳？
