OKF 知識庫 · 情境一 · 使用說明

不是叫它記得，
是讓它被提醒

一份 30 分鐘就能跑起來的跨專案知識庫：Claude Code 在你的任何一個 repo 工作時，會在正要踩坑的那一刻收到以前的教訓。這一頁是說明書；零件和程式都在 okf-dev-multirepo.md。

適用 Claude Code · 需要 python3 / git / rg · 2026-09

§0 · 使用前

它是什麼、不是什麼

你會建一個叫 ~/knowledge 的 git repo，裡面放幾種 markdown 檔。每個檔案開頭有一小段像表格的資料（作者、標籤、觸發字），後面是正文。這種寫法叫 OKF（Open Knowledge Format），Google 在 2026 年 6 月公開的約定，它就只是「markdown 加檔頭」，沒有軟體要裝。

接著你會讓 Claude Code 在四個時刻自動跑幾支小程式，這些程式叫 hook：開工時、你打字時、它要動手前、它收工前。程式做的事只有一件：拿當下的文字去比對你寫過的教訓，比對到就塞給它看。

重點在「塞給它看」。它不用自己想起來要查，是環境把教訓推到它眼前。

它是

一個你自己維護、放在 git 裡的教訓庫，用最普通的 markdown 寫，任何編輯器都能開。

它不是

不是向量資料庫，不是 wiki，也不是 Claude Code 內建的記憶。它不需要伺服器；壞了 git log 就能查回來。

注意

這套只有在你願意每週花 15 分鐘審草稿時才會活。不審，三週後它就是一堆沒人看的檔案。安裝之前先決定這 15 分鐘排在哪一天。

§1 · 原理

為什麼寫下來了還是會重踩

「明明記錄過，它卻沒去看」其實是四個不同的故障，每一個都對應到手冊裡的一個零件。先看懂這張表，後面每一步在做什麼就都說得通。

故障發生在哪用哪個零件修
沒去查它覺得自己會，直接做了。這段靠提醒它「先查」幾乎沒用。hook 主動推送（§3）
查了對不上教訓是照「原因」寫的，但踩坑當下看到的是「症狀」，字不一樣。triggers 只寫字面（§5）
看到但沒理推給它了，但那是一段筆記不是一條規則，它讀完照樣做自己的。升格成 rules/ 或直接擋（§7）
寫得不能用教訓是事後敘述，沒有「當 X 時不要 Y 改 Z」這一句。lesson 模板 + 每週 compact（§5、§6）

§2 · 零件表

資料夾裡每一個東西是做什麼的

把 markdown 的 Part B 依下面的位置放好。「誰改」那一欄是重點：標「你」的檔案只有你能改，標「Claude」的檔案它會自己寫，標「腳本」的檔案永遠不要手改。

~/knowledge/
├── CLAUDE.md            工作規範
├── index.md             自動產生
├── log.md               變更史
├── rules/               硬規則
├── lessons/
│   ├── _inbox/          草稿
│   └── *.md             審過的教訓
├── projects/<repo>/     專案現況 + ADR
├── references/          外部材料鏡像
├── templates/           模板
├── hooks/               四支 hook
├── scripts/             腳本
└── .okf/                暫存記號（gitignore）
檔案作用誰改對應 md 章節
CLAUDE.mdClaude Code 進這個 repo 時的工作規範：什麼不准做、lesson 要長什麼樣你B1
rules/*.md硬規則。每次開工都會被整段塞給它，所以要少，十條以內你B6 rule.md
lessons/*.md審過的教訓。有 triggers，命中才會被推送你 + ClaudeB6 lesson.md
lessons/_inbox/它收工時丟的草稿。你每週審完才會移出去ClaudeB7
projects/<repo>/每個專案一頁現況 + 決策記錄（ADR）你B6 overview / adr
hooks/*.sh四支小程式，Claude Code 在四個時刻呼叫腳本B4
scripts/*.py比對 triggers、檢查格式、產 index腳本B5
index.md目錄，build_index.py 自動產生。手改會被覆蓋腳本B5
log.md給人看的變更史，每週 compact 加一行你A5
.okf/hook 的暫存記號，加進 .gitignore腳本B4 stop.sh

§3 · 運作

四個時刻、一個迴圈

讀取有三層，寫入只有一條路。虛線以上是每次 session 自動發生的，虛線以下是每週你動手的。

四支 hook 各做一件事，記住它們的名字，後面排錯會用到：

時刻hook 檔做什麼
開工session-start.sh把 rules/ 每條的那句祈使句印出來，Claude Code 會把它當成 context 的一部分
你打字prompt-submit.sh拿你這句話去比對 lessons 的 triggers，命中的塞進去
它要動手pre-tool.sh拿它要跑的指令或要改的檔名去比對；命中 enforce: block 的規則就直接擋下
收工stop.sh每個 session 擋一次，問它「有沒有踩坑」，有就寫草稿到 _inbox/，沒有回 NO-LESSON

§4 · 安裝

30 分鐘，六步

每一步都有「確認」行，沒過就不要往下。步驟裡提到的檔案內容全部在 markdown 的 Part B，這裡只講順序和怎麼驗。

  1. 建 repo，放零件

    開終端機：git init ~/knowledge。照 §2 的位置建資料夾，把 Part B 的 B1、B4、B5、B6 各節內容存成對應檔案，然後 chmod +x ~/knowledge/hooks/*.sh。在 .gitignore 加一行 .okf/。

    python3 ~/knowledge/scripts/validate.py 印出 0 個 ERR（WARN 可以有）

  2. 把專案接上

    挑一個你常用的專案。在它的 CLAUDE.md 末尾貼上 B2 那一段；把 B3 的 settings.json 合併進該專案的 .claude/settings.json。裡面的 OKF_HOME 改成你的絕對路徑，不要留 ~。

    cat .claude/settings.json 能看到四個 hook 事件，路徑都是絕對路徑

  3. 手寫三條教訓

    用 templates/lesson.md 寫三條你最近真的踩過的坑，存到 lessons/。只寫三條。寫法見 §5，關鍵是 triggers 要有你當時真的看到的那串字。

    validate 對這三份沒有 ERR；build_index.py 跑完 lessons/index.md 列出三條

  4. 看它有沒有被提醒

    在那個專案開 Claude Code。第一句話之前，你應該看到 hook 印出的「[OKF] 硬規則」（如果 rules/ 是空的，這行不會出現，正常）。接著故意打一句話，裡面含有某條 lesson 的 trigger 原文。

    回覆前出現「[OKF] 命中 1 條相關規則/教訓」和那條的第一段

  5. 看它有沒有被問

    隨便請它做一件小事，然後讓它結束。Stop hook 會擋一次，它會回你「有踩坑就寫草稿、沒有就 NO-LESSON」。

    它回了 NO-LESSON，或 lessons/_inbox/ 多了一個檔

  6. commit，排定每週那 15 分鐘

    git add -A && git commit -m "okf: day 1"。然後在行事曆上放一個每週的提醒，內容就寫「審 _inbox」。

    git log 有第一筆；行事曆有下週的提醒

如果 hook 沒有反應

先別改程式。九成是三件事之一：檔案沒有執行權限、settings.json 裡的路徑寫了 ~、或你的 Claude Code 版本還不支援 additionalContext。對照表在 §8。

§5 · 寫法

一條能被用到的教訓長什麼樣

同一件事，兩種寫法。左邊是人習慣的寫法，右邊是 hook 抓得到、Claude Code 照得了的寫法。差別不在文筆，在兩個地方：triggers 是不是它當下真的會看到的字，第一段是不是一句可以照做的話。

寫成這樣不會被用到

---
type: Lesson
title: Modal 效能問題
tags: [modal]
triggers:
  - "效能"
---
# 經過
上次 deploy 到 Modal 之後
第一次呼叫很慢，等很久
才回，後來發現是冷啟動，
之後就先預熱了。

寫成這樣才會

---
type: Lesson
title: Modal L4 冷啟動導致首次呼叫逾時
description: deploy 前先預熱
tags: [modal, gpu, deploy, jevlike]
triggers:
  - "modal deploy"
  - "container did not start"
  - "infra/modal_*.py"
status: draft
sources:
  - id: handoff
    resource: /references/jevlike/handoff-v3.md
---
# 當你要 deploy Modal L4 任務時
不要直接呼叫，先跑一次 warmup。[^handoff]

# 經過
（不超過十行）

三條規矩，validate 會幫你抓：

  • triggers 至少兩條，只准四種東西：指令片段、錯誤訊息原文、檔案路徑（可以用 *）、library 名。「效能」「設定錯誤」這類詞永遠不會命中，因為踩坑當下螢幕上不會出現這兩個字。
  • 正文第一個標題以「# 當」開頭，第一段是「不要 …，改 …」。這是 hook 真正推送出去的那幾行；經過寫在後面，推送時不帶。
  • sources 至少一條，指向 repo 裡的檔案或一個網址。沒有來源的教訓一年後你自己也不會信。

踩坑當下它看到的是症狀，不是原因。triggers 要寫症狀。

§6 · 保養

每週 15 分鐘做什麼

  1. 看 inbox

    ls ~/knowledge/lessons/_inbox/。每一份三選一：跟既有的是同一件事就合併、新坑就留、廢話就刪。

  2. 讓它 compact

    在 ~/knowledge 目錄開 Claude Code，貼 B7 那段指令。它會補 triggers、去重、把敘述改寫成祈使句，然後把 validate 的結果貼給你。它不會 commit，也不准加 verified。

  3. 你審

    只看兩件事：triggers 是不是字面？第一段能不能照做？不行就退回。通過的加一行 verified: { by: human:你的名字, at: 時間 }，從 inbox 移到 lessons/。

  4. 收尾

    validate、build_index、在 log.md 今天的日期下加一行、commit。

一個好的訊號

inbox 裡大部分草稿是 NO-LESSON 或被你刪掉。這代表 Stop hook 在問、它有在答、而且你沒有把垃圾放進去。教訓少而準，比多而雜有用得多。

§7 · 升格

什麼時候一條教訓該變成規則

唯一要記的判準是「重踩幾次」。

1
重踩一次 → 改 triggers，通常是漏了症狀原文
2
重踩兩次 → 搬進 rules/，或加 enforce: block 讓 hook 直接擋
10
rules/ 超過十條 → 有東西該變成 test 或 lint，不該是規則

每個月看一次四個數字：本月踩的坑裡有幾個是 lessons 已經有的（重踩率）；被推送的教訓裡有幾條真的改變了它的行為（翻 transcript 抽幾份就好）；inbox 最舊的草稿幾天了；validate 有幾條 stale 和 draft。任何一個在變差，先修你的紀律，再修格式。

§8 · 故障對照

沒動作？先查這裡

症狀最可能的原因怎麼修
開工時沒有「[OKF] 硬規則」rules/ 是空的（正常）；或 hook 沒執行權限chmod +x hooks/*.sh；在終端機直接跑 hooks/session-start.sh 看有沒有輸出
打了 trigger 原文也沒有命中triggers 跟你打的字大小寫或空白不同；或 lesson 是 deprecated在終端機跑 python3 scripts/okf_match.py --text "你那句話"，直接看比對結果
PreToolUse 有印東西但它沒理你的 Claude Code 版本不支援 additionalContext，輸出只給你看把注入交給 UserPromptSubmit（已經有），PreToolUse 只留 block；行為退化但仍成立
Stop hook 每次都擋、擋不完.okf/ 目錄寫不進去，記號沒存到確認 OKF_HOME 是絕對路徑、目錄可寫；看 .okf/ 裡有沒有 lesson-checked-* 檔
settings.json 裡 $OKF_HOME 沒展開該版本的 command 欄位不做變數展開四個 command 全部改成絕對路徑
validate 說「body 第一段不是 # 當」檔案開頭有空行或用了別的標題正文第一行就是 # 當 …時，前面不留任何東西
index.md 被改回去了你手改了它，build_index 每次會重產不要改 index.md；要加描述改該檔案的 description 欄位
它不停地讀 lessons 全文，很慢OKF_INJECT_MODE=full 給了路徑，它每條都去開改 OKF_INJECT_MODE=rule、OKF_TOPK=3；弱模型一律這樣設

§9 · 換機型

不是 Claude Code、不是大模型的時候

骨架不變，只調三個旋鈕。弱模型（OpenCode 接 Qwen、Gemma 之類）：OKF_TOPK=3、OKF_INJECT_MODE=rule、並且當作第三層 grep 不存在，它逛不動。每週 compact 仍然用強模型做，那是離線的事，跟線上用什麼模型無關。沒有 pre-tool 事件的 harness：注入全部交給打字那一刻，pre-tool 只留 block；再沒有就寫一支 wrapper 在組 prompt 時呼叫 okf_match.py。Codex：CLAUDE.md 換成 AGENTS.md，其餘一樣。

§10 · 接下來

拿 markdown 往下走

這一頁到此為止。打開 okf-dev-multirepo.md，你需要的順序是：

  1. B1 → B6：先把檔案放齊（§4 第一步）。B5 的 okf_fm.py 是其他腳本共用的，要先放。
  2. B2、B3：接上第一個專案（§4 第二步）。
  3. B6 lesson.md：寫三條（§5）。
  4. B7：下週日才用得到，先不用看。
  5. A5 到 A8：跑一個月之後再回來讀，那時候你才會有問題要問它。

情境二（Line Manager 的每日 snapshot 與 RCA）用的是同一套骨架，多了「數字只能來自受檢計算」這一條紀律，在 okf-line-manager-rca.md。等這一套在你自己的專案上跑順了再看它。
