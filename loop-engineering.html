      Loop Engineering · 迴圈工程

      一個 agent loop，還是一條有界的流程？

      迴圈工程不是「把 agent 跑起來」的別名。它問三件更窄、也更貴的事：這一步該不該讓模型決定；錯了的時候錯誤會走多遠；跑到第一百次，系統有沒有變聰明。

      大多數系統死在同一種壞法。它們不會報錯。它們會成功——跑完、亮綠燈、交出一份看起來很專業的東西，裡面是錯的。

      01 · 兩軸

      選型不是 agent 或 workflow，是控制流 × 裁判

      「用不用 LLM」幾乎不改變答案。同一個需求，兩種蓋法，真正分岔的是兩條獨立的軸。Q1：下一步做什麼，誰決定？Q2：有沒有一個程式能判定對錯的東西？

      Q1 決定錯誤的傳播半徑。模型在 runtime 排順序，第 9 步判斷錯，後面每一步都建立在錯的前提上。程式把順序寫死，錯誤被關在單一節點裡，不讓它改掉後面整條軌跡。

      Q2 決定迴圈該放哪一段。有 oracle——exit code、schema、對帳數字——迴圈放修復，裁判當退出條件。沒有 oracle，修復迴圈是假的，它只會收斂到「build 得過」。迴圈要往前移到蒐集資料，正確性改用限制模型能講什麼來守。

      02 · 正確性從哪裡來

      Loop 與 Graph 不是第 4、第 5 階，是同一層的分岔

      Prompt、Context、Harness、Loop、Graph 常被畫成 1→5 的進階。前三層確實是累加的基座。第四、第五層不是下一級——它們是「控制流交給誰」的兩個答案。五層是詞彙表。兩軸才是選擇函數。

      層正確性來源何時失效
      1
      Prompt

      2

      3

      THE OPERATING ENV      		不產生正確性——它界定錯誤的代價它不會失效，它只會被略過

      4b

      THE STRUCTURE      		結構——順序寫死，錯誤關進節點分支枚舉不完時

      Harness 不產生正確性。它界定錯誤的代價。工具表裡只該留下「做事」的能力；排程、掛載、裝套件、加 MCP server 一律移出。Turn 上限限的是單次爆炸半徑。這條規則限的是它能不能活過這一次——容器 --rm 之後，排程是注入唯一活得過 session 的路徑。

      歸因錯誤：coding agent 的成功證明的是 oracle

      每一代失敗都把修法往上推一層。2023 以為是指令，2024 以為是資訊，接著給它手、給它沙箱。2025–26 寫程式的 agent 突然可靠，歸因發生在這裡，然後被外推到所有領域。

      成功的主因是 pytest，不是模型變聰明了。廉價 oracle 讓每一輪都有真實回饋，多轉幾圈真的會收斂。沒有 oracle 的領域——RCA、分析、報告——重試只會收斂到「能停下來」的地方。那一步外推，在邏輯上沒有依據。

      錯誤的傳播半徑

      左邊是 agent loop 的真實軌跡。第 09 步把「環境缺套件」判成「fixture 沒建好」，後面每一筆都建立在錯的前提上。為了讓迴圈收斂，它把 assert 放寬。通過率 100%，測試已經不檢查任何東西。模型沒有說謊，它把目標換掉了。

      右邊順序寫死。模型只產 case 與 code，修復迴圈上限三次。三次都失敗，report 與寫回照常執行，內容變成「需要人看」。

      B 骨架 + 有界迴圈

      順序寫死在程式碼，模型只做兩件事，修復迴圈有上限

      1. S1jira.get(key)
      2. S2llm_gen_cases() → schema
      3. S3llm_gen_code() → schema
      1. 1/3run_in_sandbox → fail
      2. ↻llm_fix(code, stderr)
      3. 2/3run_in_sandbox → fail
      4. ↻llm_fix(code, stderr)
      5. 3/3run_in_sandbox → fail
      6. ✕exit → needs_human
      1. S5render_report(needs_human)
      2. S6jira.comment(report)

      迴圈三次都失敗，S5 / S6 照常執行，只是內容變成「需要人看」。錯誤沒有外溢成「跳過寫回」或「改寬 assert」。

      還有一道比架構更先要想的防線：生成的測試必須能在已知有 bug 的版本上失敗。否則你得到的是同義反覆的測試——通過率滿分，鑑別力為零。

      Case 01 · B 的骨架

      def process(issue_key):
    issue = jira.get(issue_key)              # code
    cases = llm_gen_cases(issue)             # model → schema
    code  = llm_gen_code(cases)              # model → schema

    for attempt in range(3):          # 有界：上限 3
        result = run_in_sandbox(code)        # 容器，無正式憑證
        if result.ok:
            break
        code = llm_fix(code, result.stderr)
    else:
        return mark_needs_human(issue_key, result)

    if not discriminates(code, known_buggy_rev):  # AP-03 防守
        return mark_needs_human(issue_key, "測試無鑑別力")

    jira.comment(issue_key, render_report(cases, result))
      UPPER BOUNDmax attempts = 3。不是「修到過為止」。
      EXIT CONDITIONpytest 綠燈，且測試能在已知 buggy rev 上失敗。
      FAILURE PATH三次都失敗 → needs_human。S5 / S6 照跑。

      迴圈往前移到探索，寫作階段禁止產生數字

      1. S1trigger(run_id=2026-08-11-a)
      1. q1error rate by service
      2. q2p99 latency, 2h window

      4. q3conn pool saturation

      3. S5evidence build · 數字由 SQL 填入

      模型引用了不存在的查詢，build 直接失敗。它沒有辦法「改一改讓 build 過」，因為它不被允許碰數值來源。

      不准打數字

      不是請求模型別編造，是型別檢查。敘事層只準引用查詢，數字由 SQL 在 build 時從凍結的 snapshot 填入。引用了不存在的 query，build 失敗；query 本身寫錯，你能在 SQL 層 review。幻覺數值在結構上不可能發生。

      模型輸出 · 禁數字

      P99 從 升到 ，偏離起於 。

      Build 後 · 數字來自 snapshot

      P99 從 12ms 升到 287ms，偏離起於 14:19。

      順便買到可重現性。三個月後 retention 過期、recording rule 補算過，同一份報告重 build 仍是同樣的數字——它綁在 parquet 上，不是綁在當下的 Grafana。

      Case 02 · B 的骨架

      def build_rca(trigger, run_id):
    ctx = collect_trigger_context(trigger)         # code

    # ── 有界探索：上限 8 次查詢，產出是清單不是結論 ──
    manifest = llm_explore(ctx, max_queries=8)   # model → schema
    validate_manifest(manifest)                    # SQL 白名單 / 時間範圍檢查

    snap = execute_and_freeze(manifest, run_id)    # → parquet，之後只讀它

    md = llm_write_skeleton(manifest, snap.schema) # model，禁數字
    if contains_literal_numbers(md):               # AP-07 防守
        return needs_human(run_id, "敘事層出現寫死數值")
    if not has_ruled_out_section(md):              # AP-09 防守
        return needs_human(run_id, "缺少已排除假設")

    site = evidence_build(md, snap)                # 失敗不重寫數值，只回報引用錯誤
    upload(site, prefix=f"draft/{run_id}/")      # 人 review 後才 promote
      UPPER BOUNDmax queries = 8。產出是清單，不是結論。
      EXIT CONDITION預算用完，或 manifest 通過白名單。
      FAILURE PATH寫死數字、缺排除假設、引用錯誤 → needs_human。

      05 · 四格

      兩軸展開是四格。右下那格不能直接做，只能拆

      有裁判的 Test Agent 落在「枚舉不完 × 有 oracle」——那是 agent loop 的主場，勝利不可外推。沒有裁判的 RCA，原始形態其實在右下：分支列不完，又沒有程式能判定對錯。直接做，就是五個數字錯三個、build 綠燈、沒有一步報錯。

      Q2 = YES · 有 oracle

      Q2 = NO · 沒有 oracle

      Q1 · 分支可枚舉

      Q1 · 枚舉不完

      CELL D · 不能直接做——只能拆

      禁區

      分支列不完，又沒有裁判。直接做，就是五個數字錯三個、build 綠燈、沒有一步報錯的完美段落。

      拆成探索段（查詢預算當假 oracle）+ 寫作段（契約代替驗證），中間隔凍結層。

      RCA 真正做的事，是把那一格拆開。探索段用 8 次查詢預算換一個人造退出條件，輸出限定成清單——清單可以被白名單與時間範圍檢查，結論不行。寫作段把骨架寫死，任務從禁區掉回「flow + 契約」。中間隔凍結的 parquet，兩段永遠不直接對話。

      這也解釋了為什麼「改到 build 過為止」特別陰險：那不是修格式，是寫作段偷偷退回禁區。模型一碰數值來源，枚舉性和契約同時失去，整套拆解白做。

      06 · 未知

      有界探索真正買到的，幾乎都是 unknown known

      「agent 找出了未知的未知」——成功案例幾乎全部是誤標。模型沒有發現新現象。它把一個一直躺在資料面、只是沒人合起來看的相關性翻出來。資料面通常遠大於儀表板面，落差就是 unknown known，也就是那 8 次查詢預算真正在賺的錢。

      資料沒有 × 不知道要問

      Unknown Unknown

      沒見過，而且可能連埋點都沒有。任何深度的推理迴圈都碰不到。

      瓶頸：量測涵蓋率。解法是新埋點，那是資本支出。

      承認這件事有兩個後果。天花板與逼近速度是兩個變數：量測涵蓋率決定上限，推理深度只決定你多快逼近。上限太低時，加預算、換更大的模型、拉長 max turns 全部無效——那是在用軟體預算解一個感測器問題。

      兩格的投資語言也不同。unknown known 的解是新查詢、新檢視，週級的軟體變更。unknown unknown 的解是新埋點，月季級的採購與工程。混在同一張需求清單裡，第二類永遠排不進去，因為它看起來像「做不到」，而不是「需要買感測器」。

      07 · 棘輪

      needs_human 不是放棄出口，是唯一的學習入口

      凍結、契約、有界迴圈，守的是單次執行。它們沒回答：同一套系統跑到第一百次，憑什麼比第一次強？agent loop 沒有跨執行的記憶結構。每次都從同一個起點開始猜。棘輪要刻意設計。

      人查明的結論如果只存在會議記錄裡，系統第一百次跟第一次一樣笨。回寫產物有兩種，必須分流——成本差三個數量級，決策層級差兩層。不分流，第二條永遠不會被提出，只會被記成又一次「查不出來」，同一個缺口每季再付一次人工排查的錢。

      08 · 反模式

      十五個會咬人的地方，按失敗機制分，不按案子分

      同一個機制會在修復迴圈和探索迴圈裡以不同面貌出現。目標置換那一組最值得先想清楚——系統沒有報錯，它成功了，只是把要達成的事換掉。同義反覆的測試會讓你以為系統在運作。

      09 · 規則

      有界迴圈四個必填欄位。少一個，就不叫有界

      沒有上限、沒有程式可判的退出條件、沒有失敗出口，只是還沒跑爆的無界迴圈。跨執行再補第四欄：出口之後，往哪學。第四欄空缺，前三欄再完善，也只得一個永遠停在第一天的安全系統。

      01 · UPPER BOUND

      最多幾次？

      Case 01 是 3 次重試。Case 02 是 8 次查詢預算。沒有這個數字，就不叫有界。

      02 · EXIT CONDITION

      什麼算成功？

      要能用程式判斷。有 oracle 用 oracle，沒有就用預算——但不能用模型自評。

      03 · FAILURE PATH

      用完之後往哪走？

      預設不能是「繼續試」或「當作成功」。needs_human 是正常出口。

      04 · LEARNING PATH

      出口之後，往哪學？

      人查明的結論回寫成 template、埋點清單，還是只回會議記錄？第四欄空缺，前三欄再完善也只得一個永遠停在第一天的安全系統。

      Rule 01 · 控制流

      畫得出流程圖的，就寫流程圖。需要 agent 的條件是分支事先枚舉不完。其餘的不值得。

      Rule 02 · 正確性

      有 oracle，用它當退出條件，迴圈放修復。沒有 oracle，重試是假防線——凍結資料、輸出契約、強制留一個資料不足的出口。

      Rule 03 · 天花板

      量測涵蓋率決定上限，推理深度只決定逼近速度。上限問題用埋點解，不用預算解。

      Rule 04 · 累積

      系統的價值，看第一百次與第一次的差。差為零的系統，單次再正確，也只是一個很貴的一次性函式。

      畫得出流程圖的，就寫流程圖。

      先用兩軸決定這條流程能不能、該不該交給模型。再用棘輪決定它值不值得存在。防線讓單次執行不產出一份漂亮的錯。棘輪讓第一百次比第一次聰明。兩件事合在一起，才叫迴圈工程。
