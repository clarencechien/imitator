document → working interface

差別不在 HTML 還是 Markdown，
而在這份東西是要你讀完的文件，還是你可以動手的介面。

Anthropic 那篇文章沒有主張「所有輸出都該改成 HTML」。它抓到的是：當 agent 產生一次性 UI 的邊際成本被打到趨近於零，很多原本只能靠長篇文字描述的決策，可以直接改成「為這個問題做的介面 ＋ 結構化匯出」。HTML 只是成本最低、可攜性最高的容器。

你在對話裡拿到的read-only

要改一個決定，你得把整段重看一次，再用文字把新的偏好描述回去。

同一件事，做成介面live

左邊那段字是右邊按鈕生出來的。你按一下，畫面下方那條軌就記了一筆——這頁從現在開始有「可以交回給 agent 的狀態」，而不只是被你讀過。

主張 / 01

文章實際說了什麼

先把來源攤開。這頁後面所有判斷都會標記出處，因為「聽起來很有道理但其實是我編的」是這類文件最貴的錯誤。

文章原文明確寫過的內容
我們我們自己的判斷，文章沒這樣說，甚至相反

文章 作者 Thariq Shihipar 給了五個理由，說明為什麼他改用 HTML 當輸出格式：

Information density資訊密度

表格、CSS、SVG、canvas、絕對定位、互動元件都能用。他說幾乎沒有什麼 Claude 讀得懂的資訊，是 HTML 表達不出來的；在 Markdown 裡模型只好退而求其次去畫 ASCII 圖，甚至用 unicode 字元去逼近顏色。

Visual clarity可讀性

他坦承自己不會真的讀超過一百行的 Markdown，更不可能讓公司其他人讀。HTML 可以用分頁、插圖、連結安排結構，還能做 RWD。

Ease of sharing可分享

瀏覽器多半不會好好渲染 .md，你得夾附件。HTML 傳個連結就好——「別人真的會讀」的機率高很多。

Two-way interactions雙向互動

可以請 Claude 加滑桿、旋鈕來調設計或演算法參數，然後把調完的結果複製成 prompt 貼回去。他稱之為為當下這個問題做的專屬編輯環境。

Data ingestion脈絡攝取

這是他認為要用 Claude Code 而不是 claude.ai 或 Claude Design 產 HTML 的最大理由：它讀得到你的檔案系統、MCP、瀏覽器、git 歷史。文章裡那些圖，就是叫它掃過整個 code 資料夾之後生出來的。

文章 他列了五種用途，其中最後一種最值得注意——

用途做法
規格、計畫、方案探索不是一份 Markdown 計畫，而是一疊 HTML：先發散六種方向並排比較，挑一種展開成 mockup，最後才寫實作計畫，然後開新 session 把整疊丟進去實作。
Code review渲染真正的 diff、行內註記、依嚴重度上色、模組圖。
設計與原型Claude Design 本身就建立在 HTML 上。就算最終產物是 Swift 或 React，先用 HTML 調也划算；動畫參數尤其適合做成滑桿。
報告、研究、學習跨 Slack／codebase／git／網路的資訊綜合，輸出成解說頁、互動說明或投影片。
專屬編輯介面為「這一份資料」做一個用完即丟的編輯器：不是產品，不是可重用工具，就是一個檔案。
整篇最可操作的一句 文章 專屬編輯介面的訣竅永遠是以匯出收尾：一顆 copy as JSON 或 copy as prompt，把你在 UI 裡做的事變回可以貼進 Claude Code、或 commit 進檔案的東西。人還在迴圈裡，但迴圈變短很多。
沒有這一步，做出來的東西就只是比較好看的文件。

文章 幾個容易被忽略的事實：他說自己「大概站在 HTML 極端派那一側」，已經幾乎完全不用 Markdown 了；token 雖然比較多，但在 Opus 4.7 的百萬 context 下他覺得不明顯，而且他真的會讀，整體產出反而更好；他也不再寫單一份計畫，而是同一件事散成好幾份 HTML 並長期留著當參考。文章結尾把所有理由收斂成一句：這讓他覺得自己重新回到迴圈裡了。

主張 / 02

我們加的限制

下面這些原文沒有講，甚至和作者的立場相反。這是我們自己的判準，出錯要算在我們頭上。

該做成 HTML 的訊號

「看懂」還不夠，你希望人能動到問題本身。

  • 要比較好幾個方案，而不是接受一個答案
  • 資訊本身有空間關係，攤平成文字會失真
  • 人要調參、排序、標註、勾選
  • 操作結果需要變成 JSON／prompt／diff 回到 agent
  • 要給不會讀 .md 的人看

不要硬做的訊號

內容本質是機器的權威來源，或吃 Git diff。

  • Compose、GitLab CI、Terraform：HTML 可以當 viewer/editor，但 source of truth 留在 YAML／HCL
  • README、ADR、changelog：短、要 diff、人還會手改
  • 已經要登入、要 state、要 backend、要測試的東西：那已經是 app，單檔 HTML 只適合原型
我們和作者分歧的點 我們 作者已經幾乎不用 Markdown。我們保守一點：HTML 是審閱與操作的表面，不一定要當權威來源。最終決議該不該回寫成一份短的 Markdown ADR，看你們團隊的規範，不看這篇文章。

這就是純文字做不到的部分：你調整問題的性質，結論當場重算，而且算式攤開給你看。

    上一版體檢

    對照先前那份 internal-gitops-blueprint.html：逐項打分，不是憑印象。細線是目標值。

    項目狀態說明
    章節導覽與卡片達成十六節可以掃讀
    架構版面達成沒有退回 ASCII，空間關係留住了
    註記與 JSON 匯出達成人的意見可攜，最貼近文章心法的一項
    即時取捨探索缺Portainer／GitLab／VM 的選項只能讀，不能動
    決策狀態缺註解不等於「已接受／已否決／待議」，交不出去
    實作 prompt部分有 code 複製，沒有整份決策匯出
    所以問題從來不是 CSS 它已經是一份可註解的高密度技術文件，但還不是工作台。缺的是「改決定 → 架構跟著變 → 匯出交付」這條線。上面第 04 節就是把那個缺口補起來的樣子。
    交付 / 06

    出手前檢查

    我們 用來擋掉「只是比 Markdown 好看」的那一類產出。

    問題好的答案答不出來代表
    有用到空間、圖、表去減輕讀者的工作記憶嗎資訊的形狀本身有意義Markdown 就夠了
    有漸進揭露嗎第一眼看到結論，要細節才展開只是換皮的長文
    人能不能直接動到問題比較、切換、調參、標註還是被動閱讀
    動完之後能匯出嗎JSON／prompt／diff／Markdown互動回不到 agent，等於白做
    權威來源有沒有放錯地方YAML／HCL／JSON 還在原位HTML 變成新的設定陷阱
    是為這個問題做的，還是在造平台剛好夠用，用完可以丟開始過度工程
    單檔、離線、無 CDN 嗎寄出去對方直接開得起來分享成本又長回來
    下一個 agent 讀得進去嗎有決策狀態、來源、註記可匯出資訊被鎖回視覺層
