Claude Code 連線地圖

三個常被當成同一件事的東西 —— 本機 CLI、網頁版、Remote Control —— 各自在哪裡跑、怎麼串起來、彼此能做到什麼程度。

文件 官方文件明載 實測 2026-09-01 在 dev-vm 與雲端 session 之間實際跑出來的結果
先修正一個常見誤解

Remote Control 不是第三個地方,是一扇窗

Claude Code 和 Claude Code on the web 是兩個執行環境:一個在你的機器上,一個在 Anthropic 的雲端容器裡。Remote Control 不是第三個 —— 它是讓瀏覽器或手機去操作那個已經在你機器上跑著的 session 的通道。

文件的原話:

Unlike Claude Code on the web, which runs on cloud infrastructure, Remote Control sessions run directly on your machine and interact with your local filesystem. The web and mobile interfaces are a window into that local session.

這決定了後面所有事情:程式在哪執行、檔案在哪、誰找得到誰,答案全都從「這個 session 的行程實際上跑在哪台機器」推導出來。

核心問題

誰能訊息誰

從 →到 →可以嗎條件與實際錯誤
本機 session同機器的另一個 session 可以 兩者要看得到同一組檔案。容器與宿主機互相看不到 文件
本機 session
(連著 Remote Control)		另一台機器的 session 可以 雙方都要連著 Remote Control;對方要出現在列表裡 文件
本機 session
(連著 Remote Control)		雲端 web session 可以 本頁就是這樣收到 dev-vm 回報的 實測
雲端 web session任何其他 session 不行 憑證不允許對外投遞,連「回覆」都不行 實測
沒連 Remote Control 的本機 session機器以外的 session 找不到 列不出來就沒有名字可以定址 文件

雲端 session 送不出去的兩種失敗長得不一樣,原因也不同:

主動送給對方 → No agent named 'azure-dev' is reachable. (列不到機器外的 session,沒有名字可用) 用對方給的回覆地址 → auth: this cloud session cannot message other sessions yet — its credential is accepted for its own work but not for delivering to another session

第二個才是真正的天花板:就算對方先開口、就算訊息帶著回覆地址,雲端 session 還是回不了話。所以雲端這一端是唯讀的收件匣。

那雲端這端能不能設定開起來?

收 —— 已經能了

不用設定。雲端 session 現在就收得到,session 記錄裡是 cross_session_inbound: available。管收訊的 crossSessionInbound 預設就是通的。

送 —— 沒有設定可以開

錯誤訊息寫的是 cannot message other sessions yet —— 平台端還沒開放的能力,不是你少設了什麼。

  • 文件裡跟跨 session 訊息有關的設定只有 crossSessionInbound、isolatePeerMachines、permissions.deny、disableRemoteControl 四個。全部都只能「限制」,沒有一個能「授予」。
  • 也不能靠「讓雲端 session 連上 Remote Control」繞過 —— Remote Control 的定義是把本機行程開放給遠端操作,雲端 session 不是本機行程,這個前提本身不成立。
  • 收訊端(VM 那側)也沒有東西可以開。那則錯誤是發送端的憑證檢查,訊息根本沒離開雲端 session,VM 從頭到尾沒被問過。分辨方法:收訊端若設 refuse 或 hold,發送端會收到不一樣的通知(「對方不接受」或「被擋下等批准」)。都不是這些,就表示卡在更上游。
  • 所以要把資訊送進雲端 session,只有兩條路:叫本機那端主動送,或你自己貼過去。

怎麼自己確認 文件

  • 在任一 session 打 /list-agents(別名 /peers)—— 列得出誰就能訊息誰。第一行是這個 session 自己的名字,也就是別人要用的地址。
  • /status 的 Peer address 那列顯示自己的收件位址。
  • 指令不存在 = 版本太舊。需要 v2.1.224 以上(原生 Windows 需 v2.1.234)。
  • 名字會變。同一個雲端 session 在四次檢查裡分別叫 azurevm-fb、-32、-a9、-7c,所以要傳訊息前先查一次,別用記憶中的。實測
只能傳訊息嗎

能做到什麼程度

「只能傳訊息」這句話同時高估和低估了它。管道本身只送純文字 —— 不帶對話歷史、不帶檔案。但收訊的那一端是個完整的 agent,它會用自己的工具去做事,所以一則訊息可以引發真正的工作。

訊息做得到

  • 讓對方跑指令、讀寫檔案、改程式 —— 在它自己的權限範圍內
  • 把發現、狀態、決定傳過去,取代你手動複製貼上
  • 對方可以回覆(雲端 session 除外)

訊息做不到

  • 不算你的同意 —— 回答不了對方待批准的權限提示
  • 不能改設定 —— 收訊端被明確指示不得因為別的 session 要求而改權限、CLAUDE.md 或設定
  • 斜線指令不會執行,只當純文字
  • 不搬 context。要延續整段對話得用 --resume,不是訊息
限制 文件值
內容型別純文字。結構化的 agent team 協定訊息不跨 session
同機器訊息大小序列化後約 100 萬字元,超過在發送端就被擋
連發短時間大量送同一個 session 會在發送端被拒,要你合併成一則
迴圈防護收訊端限流、丟棄短時間內的重複訊息、佇列上限 50 則 —— 兩個 session 互相回話會自己停下來
閒置通知 notify_when_idle只限同一台機器,且只有主對話能訂閱。12 小時沒等到就放棄
另一條軸線

Remote Control 本身能做什麼

跨 session 訊息是 session 之間互相講話;Remote Control 是你操作一個 session。後者能做的多得多 —— 它就是那個 session 的完整介面。

可以 文件

  • 用完整的本機環境:檔案系統、MCP、工具、專案設定,打 @ 會自動補本機路徑
  • 終端機、瀏覽器、手機同時開著,對話與 subagent／workflow 進度全部同步
  • 從手機或瀏覽器傳圖片和檔案進去
  • 網路斷掉會自動重連,期間的訊息與權限提示會排隊等連線回來

不行 文件

  • /resume 與 /plugin 只能在本機終端機用,不管有沒有帶參數
  • 本機行程必須活著。關掉終端機 session 就離線 —— 所以遠端機器上要跑在 tmux 或 screen 裡
  • 不支援 API key、Bedrock／Vertex／Foundry,或指向非 api.anthropic.com 的 ANTHROPIC_BASE_URL
  • DISABLE_TELEMETRY 等環境變數會關掉它依賴的功能旗標評估

/resume 這條會反覆咬人。每次那台機器重開、或 session 行程結束,你都會得到一個全新的 session,接不回昨天的脈絡。對話記錄本身沒丟(在 ~/.claude/projects/ 底下),但只能從本機終端機 claude --resume 接回去,而那會是一般 session、不是 Remote Control。

結論很實際:要跨天延續的東西放檔案 —— 專案的 CLAUDE.md、筆記、repo —— 不要指望 session 記得。

開關

要收緊的話

設定作用
crossSessionInboundaccept 全收／hold 先擋下等你批准／refuse 直接丟棄。也可在 /config 的「Messages from your other sessions」選
isolatePeerMachinestrue = 任何往機器外送的訊息都要你先批准,連 bypassPermissions 模式也擋
permissions.deny列入 SendMessage、ListAgents 就完全關掉送訊息與列出對象
disableRemoteControl整個關掉 Remote Control

沒設定的話,預設會依兩邊的權限模式決定:收訊端會跳權限提示的,就直接送達(除非發送端宣告自己是 bypass);收訊端本身是 bypass 的,則每則都先擋下來等你批准。

這份地圖的實測來源

標 實測 的部分來自 2026-09-01 這組實際配置:一台 Azure 上的 dev VM(dev-vm,japaneast)跑 claude --remote-control=azure-dev,由 systemd user service 包在 tmux 裡開機自啟;另一端是 claude.ai/code 開的雲端 web session。

試了什麼結果
雲端 session 跑 /list-agents完全空的 —— 容器隔離所以沒有同機器的對象,又沒連 Remote Control 所以看不到機器外的
雲端 → VM,用名字失敗 找不到該名稱
VM → 雲端成功 訊息直接出現在雲端 session 裡
雲端 → VM,用對方訊息附的回覆地址失敗 憑證不允許對外投遞
VM 重開機後Remote Control session 自己回來(開機 +14 秒),但是新的 session id,舊對話接不回去
