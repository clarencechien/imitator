01 · Vocabulary

五層詞彙,與一個常見的誤讀

市面上把 AI 工程拆成五個詞:Prompt、Context、Harness、Loop、Graph,常畫成 1→5 的遞進階梯。前三層確實是累加的基座,但第 4、5 層不是第 4、5 階——Loop 與 Graph 是同一層的分岔,是「控制流交給誰」這個問題的兩個答案。

比較有用的讀法:五層各自回答「正確性從哪裡來」。

Harness 該獨立成一族

上一篇把「無沙箱」(AP-04)與「太早給寫入權」(AP-05)散在兩個 family 裡,回頭看,它們是同一層的東西:Harness 不決定系統對不對,它決定錯了會多貴。這層有一條可以直接抄的設計規則,來自 NanoClaw 一整季的 breaking changes:

agent 能呼叫的工具只能「做事」,不能改變自己的能力邊界。排程、掛載、裝套件、加 MCP server——一律移出工具表,改走 host-only CLI 或人類審批。

理由不是整潔,是持久化:容器 --rm 之後,排程是注入唯一活得過 session 的路徑。一次成功的注入,能種一個每天自己重新注入的後門。turn 上限限的是單次爆炸半徑,這條規則限的是它能不能活過這一次。

02 · The Attribution Error

每一代的失敗,把修法往上推一層

這條歷史線不是懷舊,它導出一個 2026 年被普遍搞錯的因果。

2023 · PROMPT 時代

ReAct、AutoGPT

讓模型自己想、自己做。失敗形態:無界迴圈、目標漂移、在第 40 步忘記自己要幹嘛。

→ 修法上推:問題不在指令,在它看得到什麼
2024 · CONTEXT 時代

RAG 與檢索管線

把對的資訊塞進視野。失敗形態:資訊夠了,但只能「說」,不能「做」。

→ 修法上推:得給它手
2024–25 · HARNESS 時代

Function calling、MCP、沙箱

能動作了。失敗形態:能動作但不安全、不可稽核。這條線一路長成 2026 年的權限模型競賽——審批卡、egress 封鎖、憑證不落地。

→ 修法上推:界定代價之後,還缺收斂機制
2025–26 · LOOP 時代

Coding agent 大勝

寫程式、SQL、資料轉換、爬蟲修復——agent 突然可靠了。歸因錯誤發生在這裡。

→ 被外推到所有領域
2026 · GRAPH 時代

回頭發現結構

沒有 oracle 的領域(RCA、分析、報告)接連翻車,大家重新發現:那裡的正確性要靠結構守,不是靠重試。

→ 也就是 VOL.1 的全部內容
Coding agent 成功的主因是 pytest,不是模型變聰明了。

模型確實變強,但成功案例高度集中在有廉價 oracle 的領域:exit code、schema 驗證、對帳數字——每一輪迴圈都有真實回饋,多轉幾圈真的會收斂。整個 2026 的 agent platform 熱潮,建立在把這個成功外推到沒有 oracle 的領域,而那一步在邏輯上沒有依據。

這也解釋了為什麼平台商真正在蓋的是審批、隔離、稽核,而不是更聰明的 orchestrator:在沒有 oracle 的地方,人就是 oracle——只是變得很貴。所謂 human-in-the-loop,本質上是租一個裁判。租金要花在刀口上,這是第 05 節的主題。

Case 02 真正做的事:把一格 D 拆成兩格 B

CELL DRCA 原始形態 拆成 → 探索段查詢預算當假 oracle

探索段用 8 次查詢預算換一個人造的退出條件,且輸出被限定成「清單」——清單可以被白名單與時間範圍檢查,結論不行。寫作段把骨架寫死,任務就從 D 掉回 B。中間隔一層凍結的 parquet,兩段永遠不直接對話。

這也給了 AP-10(改到 build 過為止)更深的解釋:那不只是繞過防線,是寫作段偷偷退回 CELL D——模型一碰數值來源,就同時失去枚舉性和契約,整套拆解白做。

假設空間可列舉——三十種故障模式,不知道是哪一種。候選生成 + 證據排序 + 人確認,Case 02 中段的形狀。

Unknown Known

資料早就在了,但沒有任何一張儀表板顯示它——埋了點沒人看的 metric、線長腦裡沒寫下的手感、跨兩個系統才看得出的相關性。

瓶頸:查詢涵蓋率與表達力 → 迴圈深度真的有用
資料沒有 × 不知道要問

Unknown Unknown

沒見過,而且可能連埋點都沒有。任何深度的推理迴圈都碰不到,因為要的資料不存在。

瓶頸:量測涵蓋率 → 解法是新埋點,那是資本支出,不是軟體
「agent 找出了未知的未知」——成功案例幾乎全部是 unknown known 被誤標的結果。模型沒有發現新現象,它把一個一直躺在那裡、只是沒人合起來看的相關性翻了出來。

這格之所以存在,是因為資料面通常遠大於儀表板面。落差就是 unknown known,而它正是有界探索那 8 次查詢預算真正在賺的錢。承認這件事有兩個實際後果:

一,天花板與逼近速度是兩個變數。量測涵蓋率決定系統的能力上限;推理迴圈的深度只決定你多快逼近那個上限。上限太低時,加預算、換更大的模型、拉長 max turns,全部無效——那是在用軟體預算解一個感測器問題。

二,兩格的投資語言不同。unknown known 的解是新查詢、新檢視,是週級的軟體變更;unknown unknown 的解是新埋點,是月季級的採購與工程。混在同一張需求清單裡,第二類永遠排不進去——因為它在軟體專案裡看起來像「做不到」,而不是「需要買感測器」。

05 · The Ratchet

needs_human 不是放棄出口,
是唯一的學習入口

VOL.1 把 needs_human 設成正常出口,擋掉了「一定會有的根因」。但出口之後呢?人查明的結論如果只存在會議記錄裡,系統第一百次執行,跟第一次一樣笨——agent loop 沒有跨執行的記憶結構,它每次都從同一個起點開始猜。

會隨時間變強的系統,靠的是一條刻意設計的回寫迴路,而且產物有兩種,必須分流:

OUTFLOW 1 · 軟體側

「資料本來就有,只是沒人看」

人查明後發現答案一直在資料面裡——unknown known。結論收斂成新查詢、新檢視、新規則,併進 template 庫,下一次同型 alert 直接落在 CELL A。

「這需要新的埋點」

人查明後發現資料面根本沒有——unknown unknown。結論是一張 instrumentation 需求單:加感測器、開 log 等級、接新資料源。下一輪之後,它才進得了資料面。

兩條分流的成本差三個數量級,決策層級差兩層。不分流,第二條永遠不會被提出——它會被當成一次「查不出來」而不是一次「量測缺口被定位」記錄下來,然後同一個缺口每季讓你再付一次人工排查的錢。

棘輪:同一套系統,第 1 次到第 N 次

每一次 needs_human 被回寫,未知帶就被咬掉一塊,而且不會彈回來

template 帶(CELL A · 決定性) 候選排序帶(CELL B · 契約) needs_human(學習入口)

綠帶單調成長是棘輪性質:被 template 化的案型不會退回未知。對照組是純 agent loop——它的三帶比例永遠不變,因為沒有任何東西被寫回結構。系統的價值不是看第 1 次跑多好,是看第 100 次和第 1 次差多少。

先量比例,再決定投資順序

三帶的初始比例決定該先蓋哪一段。如果九成 alert 落在 template 帶,那整套探索 + 凍結 + 契約其實只服務一成的流量——先把報告產製與回寫迴路做完,比先做探索划算。反過來,如果未知帶佔三成,探索段就是主戰場。這個比例是一個要先量的數字,不是一個可以假設的數字;而多數導入失敗的樣子完全相同:自動化做完了,回寫沒人做,系統停在第一天。

06 · Anti-Patterns, Continued

四個會咬人的地方,補遺

編號接續 VOL.1 的十一個。前兩個屬於新的一族——Family E · 不會變強:系統單次執行全對,卻在時間軸上原地踏步。後兩個分別回填 Family B 與 Harness。

AP-12 · LOOP_DEPTH_FOR_COVERAGEFamily E · 天花板

用迴圈深度補量測缺口

探索查不出根因,直覺反應是加預算:8 次查詢變 16 次、換更大的模型、拉長 max turns。但如果根因在沒埋點的地方,任何深度都碰不到——你在付軟體的錢,解感測器的問題。更糟的是它會「成功」:預算加大後,模型更有餘裕組出一個漂亮的 unknown known 敘事,把真正的量測缺口蓋掉。

防守探索段結束時強制輸出「查過但資料不足以區分」的假設清單。這份清單連續出現同一項,就是埋點需求,不是預算需求。
AP-13 · AUTOMATION_WITHOUT_WRITEBACKFamily E · 累積

只做自動化,不做回寫

needs_human 之後,人查明了,結論進了會議記錄,系統本身什麼都沒學到。下一次同型案例,同樣的探索、同樣的排序、同樣的 needs_human——你自動化了排查的前半段,卻讓後半段的知識持續蒸發。這是最常見的失敗,因為它不會報錯:系統每一次都「正常運作」。

防守把「回寫」設成 needs_human 工單的關閉條件:沒有產出新 template 或新埋點需求,案子不能結。回寫率是這類系統唯一值得放在儀表板上的北極星指標。
AP-14 · CONFLATED_OUTFLOWSFamily E · 分流

兩種學習產物混在一條流裡

「加一條查詢」和「加一顆感測器」被寫進同一張 backlog。前者三天能上,後者要立案採購——混流的結果是後者被前者淹沒,永遠停在 backlog 深處,而同一個量測缺口每季讓你重付一次人工排查。

防守needs_human 的結案表單就分兩欄:軟體側(查詢/template)走工程 backlog,資本側(埋點)走另一條有預算主的清單,各自追蹤各自的週期。
AP-15 · ORACLE_EXTRAPOLATIONFamily B · 目標置換的宏觀版

把有裁判領域的勝利,外推到沒裁判的領域

「coding agent 都能自己修 bug 了,RCA 當然也行」——這句話 2026 年在每一間會議室出現過。它是 Family B 的宏觀版本:個體層次的目標置換是模型為了收斂偷換目標,組織層次的目標置換是團隊拿「demo 跑完了」代替「答案是對的」。CELL C 的勝利證明的是 oracle 的價值,不是模型的普遍能力。

防守立案前先回答一句話:這個領域的 oracle 是什麼、單價多少?答不出 oracle,就從 CELL D 的拆解做起,不從 agent loop 做起。
07 · The Fourth Field

有界迴圈,第四個必填欄位

VOL.1 說有界迴圈有三個必填欄位,少一個就只是還沒跑爆的無界迴圈。跨執行的視角補上第四個:

01 · UPPER BOUND
最多幾次?

3 次重試、8 次查詢預算。

02 · EXIT CONDITION
什麼算成功?

有 oracle 用 oracle,沒有就用預算。不能用模型自評。

03 · FAILURE PATH
用完往哪走?

needs_human 是正常出口,不是「繼續試」。

04 · LEARNING PATH
出口之後,往哪學?

人查明的結論回寫到哪個結構——template、埋點清單,還是只回寫到會議記錄?

第四欄空著,前三欄做得再好,你得到的也只是一個永遠停在第一天的安全系統。

RULE 01 · 控制流

畫得出流程圖的,就寫流程圖。需要 agent 的條件是「分支事先枚舉不完」。(VOL.1)

RULE 02 · 正確性

有 oracle 用 oracle 當退出條件;沒有,就限制模型能講什麼——凍結、契約、資料不足出口。(VOL.1)

RULE 03 · 天花板

量測涵蓋率決定上限,推理深度只決定逼近速度。上限問題用埋點解,不用預算解。

RULE 04 · 累積

系統的價值,看第 100 次與第 1 次的差。差是零的系統,不管單次多正確,都只是一個很貴的一次性函式。

VOL.1 是防禦指南:單次執行,怎麼不產出一份漂亮的錯誤。這一篇是演進指南:跨執行,系統憑什麼一次比一次強。兩份合起來才是完整的選型——先用兩軸決定架構,再用棘輪決定它值不值得存在。
